# Example: shop

A small shop database managed with super-deploy. Its five migrations were made
with the real tool (`draft`, `rehearse`, `finalize`, `recovery`), so their
hashes, metadata and generated schema changes are genuine. Read them in order
to see the workflow, including what to do when a deployment fails on real
data.

## Running it

From the repository root, run `pnpm install` (it also builds the library). Then,
in this folder:

```sh
pnpm precommit                                # what the Git hook and CI run
pnpm exec super-deploy deploy --target dev    # deploy the history to the local dev target
pnpm exec super-deploy status --target dev
```

`super-deploy.config.ts` runs a private PostgreSQL 18 server in
`.super-deploy/postgres` (gitignored). It provides the throwaway databases that
rehearsals use and the local `dev` target.

## Where things are

- `data-model/desired-schema/`: the schema as it is now, edited by hand.
- `data-model/migrations/NNNNN-name/`: one folder per migration, read-only
  once finalized:
  - `pre-migration.sql` and `post-migration.sql`: hand-written scripts that
    run before and after the schema change (both optional).
  - `schema-change.sql`: generated by `draft`, never edited.
  - `seed-data.sql`: data that reproduced a problem during the draft's
    rehearsals (optional). It is kept as a record and never loaded again.
  - `metadata.json`: tool versions, any acknowledged destructive statements,
    and any overrides.
  - `desired-schema/`: a snapshot of the desired schema when the migration
    was finalized.
  - `recoveries/recovery-K/`: replacement scripts and seed data for targets
    that haven't run the migration yet.
- `data-model/migrations/index.json`: every migration's and Recovery's content
  hash, chained to the one before. `super-deploy validate` checks the hashes,
  so any edit to history is caught.

## The history

| Migration | What it shows |
| --- | --- |
| `00001-add-customers` | The simplest case: a desired-schema edit, `draft`, `finalize`. |
| `00002-add-orders` | Named constraints, a foreign key and an index. |
| `00003-rename-customer-name-to-full-name` | A rename done in a pre-migration script. |
| `00004-unique-customer-emails` | A data fix in a pre-migration script that failed on real data, and Recovery 1, which fixed it with seed data reproducing the problem. |
| `00005-add-loyalty-accounts` | A new table backfilled by a post-migration script, rehearsed with seed data. |

### 00001: add customers

`desired-schema/customers.sql` got a `customers` table. `draft --name "add
customers"` generated `schema-change.sql`, and `finalize` rehearsed it on a
throwaway database and froze it as migration 1.

### 00002: add orders

An `orders` table that references `customers`. `draft` refused the first
version of `desired-schema/orders.sql` before any database work:

```
Error: data-model/desired-schema/orders.sql:1: The foreign key constraint on orders.customer_id has no name; name it (CONSTRAINT <name> ...), because generated names can depend on load order [unnamed-constraint] (and 1 more)
```

So the foreign key and the check constraint are named explicitly.

### 00003: rename `customers.name` to `full_name`

The differ only compares structures, so it can't tell a rename from a drop
plus an add. After changing `name` to `full_name` in the desired schema,
`draft` generated a `DROP COLUMN "name"` and an `ADD COLUMN "full_name" text
NOT NULL`, and warned:

```
warning: Column customers.name is dropped with its data (...): rename it, or copy what you need, in the pre-migration script
warning: Column customers.full_name is added NOT NULL without a default (...): add and backfill it in the pre-migration script
```

So `draft/pre-migration.sql` renames the column, keeping its values. Run
`draft` again, and the schema change is empty: after the pre-migration
script, nothing is left to generate.

**PostgreSQL 18 gotcha.** PostgreSQL 18 gives every NOT NULL constraint a name
(`customers_name_not_null`), and renaming the column keeps that name. A fresh
`full_name text not null` would be named `customers_full_name_not_null`, so
`rehearse` refused the draft:

```
The rehearsal does not match the desired schema (...). First difference: catalog: - constraint: customers customers_name_not_null n NOT NULL full_name ...
```

So the script renames the constraint as well. Do the same whenever you rename
a NOT NULL column.

### 00004: unique, lower-case customer emails

The desired schema made `customers.email` unique and lower case (a unique
constraint and a check constraint). The pre-migration script lower-cases the
existing addresses so they pass the check. `finalize` warned that both
constraints lock `customers` for the length of the deployment while they check
every row, which was fine for a table this size.

Migration 4 deployed to dev and QA without trouble. In production it failed,
and the whole deployment rolled back, leaving production untouched:

```
Error: data-model/migrations/00004-unique-customer-emails/schema-change.sql: PostgreSQL refused it: could not create unique index "customers_email_key"
```

Some customers had signed up twice, typing the same address in different case
(`ada@example.com` and `Ada@Example.com`). Lower-casing made them duplicates.

A finalized migration never changes, and other targets had already recorded
it. So the fix is a **Recovery**: replacement scripts for targets that haven't
run migration 4 yet. `recovery --migration 4` started a Recovery draft with
migration 4's schema change and scripts. Then:

1. `draft/seed-data.sql` reproduces the problem with synthetic rows. Seed data
   loads only in the draft's own rehearsals, just before the pre-migration
   script. With it, `rehearse` failed exactly as production had.
2. The new `pre-migration.sql` merges the duplicates first. It keeps the
   oldest account for each address, moves the other accounts' orders to it,
   deletes the other accounts, then lower-cases what's left. `rehearse` then
   passed, and proved the Recovery ends in the same structure as the original.
3. The `DELETE` is destructive, so `finalize` refused it without a terminal to
   confirm on. `finalize --acknowledge-destructive` froze it as
   `recoveries/recovery-1/`, with the acknowledged statement in its
   `metadata.json`.

The next deployment to production ran Recovery 1 in place of migration 4's
original scripts, and recorded which variant it ran. Dev and QA keep their
record of the original. Migration 4's own hashes didn't change, because
Recoveries are hashed separately.

### 00005: loyalty accounts, backfilled

A `loyalty_accounts` table with one account per customer. The schema change
creates the empty table. `post-migration.sql` then backfills it, opening an
account for every existing customer with points for their past orders. That
work needs the new table to exist, so it runs after the schema change. The
draft's `seed-data.sql` (customers with and without orders) let its
rehearsals run the backfill over real rows.

## How the history is checked

`pnpm precommit` runs from the repository's Git hook and in CI. It runs:

1. Biome and the type checker.
2. `super-deploy validate --strict`: every migration's and Recovery's hashes
   and the chain, with no unfinished draft and no desired-schema edit that a
   draft doesn't cover.
3. `node scripts/rehearse-history.ts`: rehearses the whole history against
   PostgreSQL 18. It deploys every migration (Recovery 1 for migration 4) to
   an empty throwaway database, the way `deploy` does for a new target.
   `deploy` first rehearses on a second throwaway database, and the result
   must match migration 5's desired-schema snapshot. Then `status` must find
   nothing pending and no drift. This catches a history that no longer
   replays, for example after upgrading super-deploy or PostgreSQL.
