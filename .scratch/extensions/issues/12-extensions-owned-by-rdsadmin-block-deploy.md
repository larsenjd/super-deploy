# 12: On Aurora, extensions a deploy creates are owned by rdsadmin, and every later deploy is refused

**Status:** resolved
**Category:** bug

## What happened

Aurora PostgreSQL target `DO_NOT_TOUCH__WORKFLOW_TARGET_ONLY`, deploy role `command_center_app`.

1. A deployment created `pg_trgm` and `unaccent` in the managed schema `managed`. It succeeded.
2. The next deployment had no new migrations, and its pre-flight refused it:

```
Target DO_NOT_TOUCH__WORKFLOW_TARGET_ONLY failed the deploy pre-flight checks: extension pg_trgm is owned by rdsadmin, whose privileges the deploy role doesn't have (fix: DROP EXTENSION pg_trgm; SET ROLE command_center_app; CREATE EXTENSION pg_trgm SCHEMA managed VERSION '1.6'; RESET ROLE); extension unaccent is owned by rdsadmin, whose privileges the deploy role doesn't have (fix: DROP EXTENSION unaccent; SET ROLE command_center_app; CREATE EXTENSION unaccent SCHEMA managed VERSION '1.1'; RESET ROLE)
```

From then on, every deploy to this target is refused.

## Established facts (from the target, as `command_center_app`)

- `pg_extension`: `plpgsql`, `pg_trgm` 1.6 and `unaccent` 1.1 are all owned by `rdsadmin`.
- `command_center_app` is a member of `rds_superuser`, among others including `pg_database_owner`, so it owns the database.

## Analysis

- The refusal comes from the ownership check (`packages/super-deploy/src/deploy/ownership.ts`, run in the deploy pre-flight). An extension in the managed schema must be owned by a role whose privileges the deploy role has (`pg_has_role(current_user, owner, 'USAGE')`), because only an extension's owner may `ALTER EXTENSION ... UPDATE` or `DROP` it.
- On community PostgreSQL, a non-superuser creating a trusted extension owns it (research file §4, confirmed on embedded 18.4). On RDS/Aurora, a `CREATE EXTENSION` run by an `rds_superuser` member ends up owned by `rdsadmin`. The likely cause is that RDS runs it with `rdsadmin`'s privileges. GLOSSARY "Deploy role" ("it owns the extension") and ADR-0009 assume the community behavior.
- Ticket 11's Aurora install test ran as an `rds_superuser` member and didn't check who owned the result.
- The suggested fix goes in a circle. `SET ROLE command_center_app; CREATE EXTENSION ...` produces another extension owned by `rdsadmin`. The fix script also says to run it "as a superuser", and RDS has none.
- Pre-flight can't see this coming. The first deploy's checks passed because the extensions didn't exist yet.

- **The refusal is a false positive.** As `command_center_app`, in a transaction that was rolled back:
  - `alter extension pg_trgm update to '1.6'` raised no error.
  - `drop extension unaccent` failed only on dependents: `function managed.employee_search_text(text)` uses the text search dictionary `managed.unaccent`. PostgreSQL checks ownership before dependencies in `DROP`, so the role passed the ownership check.

  So the deploy role can update and drop the extensions `rdsadmin` owns, which is everything the ownership check is there to protect.

## Still unknown

- Whether a deploy role without `rds_superuser`, with only `CREATE` on the database, would own what it creates on Aurora, as community PostgreSQL does.

### 2026-11-17: agent brief

## Agent Brief

**Category:** bug
**Summary:** Check that the deploy role can update each extension in the managed schema, not that it owns it, so that extensions owned by `rdsadmin` on Aurora stop blocking every deploy.

**Current behavior:**
The ownership check treats an extension like any other object in the managed schema. The deploy role must have the privileges of the extension's owner (`pg_has_role(current_user, owner, 'USAGE')`). On Aurora and RDS, an extension created by a deploy role in `rds_superuser` is owned by `rdsadmin`. So after the first deploy that creates an extension, every `deploy`, `deploy-draft`, `status` and `mark` refuses the target with "extension x is owned by rdsadmin, whose privileges the deploy role doesn't have". `rebuild`'s wipe refuses it as undroppable, and `adopt` lists it as not owned. That role can in fact update and drop those extensions (confirmed on the reporter's Aurora target). The suggested fix (drop it, `SET ROLE` to the deploy role, create it again) only produces another extension owned by `rdsadmin`.

**Desired behavior:**
- An extension in the managed schema passes the ownership check when the deploy role can update it, whoever owns it. The test is a no-op `ALTER EXTENSION <name> UPDATE TO '<installed version>'`, rolled back. PostgreSQL makes its ownership check first. For an extension the role may update, it then only emits a NOTICE, "version … is already installed", and changes nothing. Confirmed on PostgreSQL 18.4.
- An extension fails only when the test raises `insufficient_privilege` (SQLSTATE `42501`, "must be owner of extension …"). Any other error propagates as it does today. The update test stands in for `DROP` as well: there is no safe way to test `DROP`.
- The test never leaves anything behind and never aborts a transaction the caller has open. Outside a transaction it runs in its own short transaction, rolled back. Inside one it runs in a savepoint, rolled back to. It can't run in a `READ ONLY` transaction, because PostgreSQL refuses `ALTER EXTENSION` there, so don't put it in the drift check's.
- Every object other than an extension keeps today's owner test unchanged. Extension members stay excluded as today.
- The same test decides everywhere the tool currently judges extension ownership: the deploy pre-flight (`deploy`, `deploy-draft`, `status`), `mark` both before YES and under the lock, `adopt`'s refusal, and `rebuild`'s wipe (which extensions in the managed schema `objectsNotDroppable` reports).
- An extension that does fail the test is reported as today (`NotOwnedObject`, `NotOwnedError`, the fix script), with its owner and the existing drop-and-recreate fix.
- No host's roles (`rdsadmin`, `rds_superuser`) are named in code.
- Update the header comments of the ownership module and the pre-flight to match. The pre-flight is no longer "read-only queries, no transaction": the extension test runs a statement in a transaction that is always rolled back. `GLOSSARY.md` "Deploy role" and ADR-0009's "Ownership" consequence are already updated.

**Key interfaces:**
- `objectsNotOwned` / `objectsNotOwnedAt`: no longer return an extension the deploy role can update. Their return types are unchanged.
- `objectsNotDroppable`: no longer returns an extension in the managed schema that the deploy role can update. Members of extensions elsewhere are still reported as today.
- One shared function answers "can the deploy role update extension X?" on a `Session`. All of the above use it.
- `requireOwnership`, `NotOwnedError`, `PreflightFindings.notOwned`: unchanged shapes.

**Acceptance criteria:**
- [x] A target whose deploy role owns an extension in the managed schema passes the ownership check (deploy, status, mark, adopt, rebuild).
- [x] A target whose extension is owned by a role the deploy role is a member of, with inherited privileges, passes.
- [x] A target whose extension is owned by a role the deploy role can't act as (e.g. the embedded superuser) is still refused by deploy, status, mark, adopt and rebuild, with the existing message and fix.
- [x] After the check runs, the extension's version, owner and the catalogs are unchanged, and no transaction the caller had open is aborted or left open.
- [x] A check that runs while the caller has a transaction open (e.g. `mark` under the lock) still records normally afterwards.
- [x] A target with no extensions behaves exactly as before.
- [x] No source file names `rdsadmin` or `rds_superuser`.
- [x] The ownership module's and the pre-flight's header comments describe the extension test.
- [x] `pnpm precommit` passes.
- [ ] **Maintainer, on Aurora (not for the agent):** on `DO_NOT_TOUCH__WORKFLOW_TARGET_ONLY` (deploy role `command_center_app`, extensions `pg_trgm` and `unaccent` owned by `rdsadmin`), `deploy` with no pending migrations succeeds, and `status` shows no ownership finding.

**Out of scope:**
- The "To fix, run as a superuser:" heading of fix scripts on hosts without a true superuser (see round 2).
- Changing the fix text for an extension that genuinely fails the test.
- Checking ownership of extensions a pending unit is about to create: they don't exist yet, and the next command checks them.
- Supporting or refusing particular cloud roles. The test is the only judge.

### 2026-11-17: implemented

> *This was generated by AI.*

- **The check.** An extension in the managed schema whose owner fails the owner test (`pg_has_role`) passes when a no-op `ALTER EXTENSION x UPDATE TO '<installed version>'`, rolled back, raises no `42501`. One function (`canUpdateExtension` in `deploy/ownership.ts`) decides for the pre-flight, `mark` (before YES and under the lock), `adopt` and `rebuild`'s wipe. An extension the deploy role already has the owner's privileges of isn't tried: it passes PostgreSQL's own check, so such targets send no extra statement.
- **Transactions.** `rolledBack` (`adapters/transaction.ts`) runs the test in a savepoint when the caller has a transaction open, else in a transaction of its own. It tells which by comparing `transaction_timestamp()` with `statement_timestamp()`, not by trying `SAVEPOINT`, so the target's server log gets no `ERROR`.
- **The "transaction open" box is ticked with a caveat.** The brief's example doesn't hold: `mark` checks ownership under the lock before `recordMarked` sends its `BEGIN`, and the target lock is a session-level advisory lock, so no caller has a transaction open today. `mark` under the lock records normally, which is tested. The savepoint branch, including a `READ ONLY` caller's transaction surviving the refusal, was checked with a throwaway test that imported the module directly. No committed test covers it: test code can't import `src/`.
- **Tests.** Community PostgreSQL can't reproduce Aurora, so the new tests use `extensionsManagedAs` (`test/support/deploy.ts`), an adapter that runs `ALTER`/`DROP EXTENSION` as the role owning the extension, as Aurora does. Each has a target through it and one without, on the same database: `status` and `deploy` (`preflight.test.ts`), `adopt` (`adopt.test.ts`), `mark` (`cli-mark.test.ts`) and `rebuild` (`cli-deploy-draft-rebuild.test.ts`). All four failed against the old `ownership.ts`.
- **Left unticked: the Aurora check**, which is the maintainer's.
