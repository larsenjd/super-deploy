# 47: A deploy that fails on real data doesn't say the target was rolled back, or point to `recovery`

**Status:** wontfix
**Category:** enhancement
**Severity:** medium
**Duplicate of:** 46
**Area:** fail

## What I did
Target `script` at migration 3, with real rows including one with `email` NULL. Migration 4 adds `customers.country text not null`, with a pre-migration backfill that misses rows:

```sql
-- data-model/draft/pre-migration.sql
alter table customers add column country text;
update customers set country = 'US' where email like '%.com';
update customers set country = 'UK' where email like '%.org';
```
`draft` warned (`fill in the nulls in the pre-migration script`), `finalize` passed (the rehearsal has no rows), and then:
```sh
pnpm exec super-deploy deploy --target script
```

## Expected
The failure says the deployment was rolled back and the target is unchanged at migration 3. Because a finalized migration can't be edited, it also says what to do next, e.g. "reproduce the problem rows in seed data and fix the scripts in a Recovery: `super-deploy recovery --migration 4`".

## Actual
```
Error: data-model/migrations/00004-add-country/schema-change.sql: PostgreSQL refused it: column "country" of relation "customers" contains null values
```
That's all (exit 1). I only found `recovery` in `--help`. The README has no mention of Recovery at all, so I had to work out:
- that `recovery --migration 4` creates `data-model/draft/` with `recoveryOf: 4` and copies of the scripts;
- that `seed-data.sql` is how to reproduce the problem in the rehearsal;
- that `schema-change.sql` must not change (the refusal says so clearly);
- that `finalize` writes `recoveries/recovery-1` and the next `deploy` uses it.

`recovery`'s own output doesn't say what to do next either:
```
Created a Recovery draft of migration 00004-add-country in data-model/draft (it becomes Recovery 1 when finalized)
```

## Notes
- Once I'd worked it out, the flow worked well: seed data reproduced the failure in `rehearse`, the fixed script rehearsed to `ends in the same structure as the original`, and the deploy succeeded. The same went for a failing post-migration script (migration 5).
- Issue 15 (README missing failed-deploy workflow) may already cover the README part. This issue is mainly about the CLI's failure and `recovery` messages.
