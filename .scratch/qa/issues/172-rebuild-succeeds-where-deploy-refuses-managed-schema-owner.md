# 172: rebuild doesn't check who owns the managed schema, so it succeeds on a target deploy refuses

**Status:** ready-for-agent
**Category:** bug
**Severity:** low
**Area:** disp
**Round:** 2

## What I did
Disposable target `qa` (`managedSchema: "app"`), deploy role `qa2_disp_deployer`. As the superuser:
```sql
alter schema app owner to postgres;
grant usage, create on schema app to qa2_disp_deployer;
```
Then:
```sh
pnpm exec super-deploy rebuild --target qa --to 5     # YES
pnpm exec super-deploy status --target qa
```

## Expected
rebuild refuses before YES, as `deploy`, `deploy-draft` and `mark` do for this target ("the deploy role must own the managed schema and everything in it", README "Permissions"). Or the confirmation at least warns that `deploy` will refuse the result.

## Actual
```
Rebuilt qa with 5 migrations: 00001-add-customers, ..., 00005-add-tags
```
and right after:
```
Target qa (disposable): 5 migrations recorded, 0 pending
Deploy would refuse:
  schema app is owned by postgres, whose privileges the deploy role doesn't have (fix: ALTER SCHEMA app OWNER TO qa2_disp_deployer)
```
`deploy-draft` on a target in the same state refuses before asking with `Target qa failed the deploy pre-flight checks: schema ... is owned by ...`.

## Notes
With a superuser-owned table also in the schema, rebuild does refuse before asking ("the deploy role can't drop table app.su_owned (owned by postgres)"). It just doesn't name the schema's owner as the cause. The README's rebuild bullet says it "runs migrations 1 to N as a deployment does", which suggests the same pre-flight checks.

### Triage, 2026-10-21

**Verification:** CONFIRMED in a pseudo-terminal.
- Setup: `alter schema app owner to postgres; grant usage, create on schema app to qa2t_disp_deployer`.
- `rebuild --to 5` asked nothing about ownership, and after YES printed `Rebuilt qa with 5 migrations`.
- `status` then listed `schema app is owned by postgres ...` under "Deploy would refuse", and `deploy-draft` refused before asking with `Target qa failed the deploy pre-flight checks: schema app is owned by postgres ...`.
- Root cause: before asking, `rebuild` checks only what its wipe can drop (`requireWipeable`, `commands/rebuild.ts:137`). That test is deliberately weaker than ownership (`deploy/ownership.ts` header: "the schema's owner may drop anything in it but an extension"). Nothing checks who owns the managed schema itself.
- After a rebuild, every object in the schema belongs to the deploy role, so the schema's owner is the only ownership problem that can remain. A rebuild over such a schema always leaves a target that `deploy` refuses.
- ADR-0006's list of commands that refuse such a target (`deploy`, `status`, `deploy-draft`, `adopt`, `mark`) leaves `rebuild` out, as does the README's "What each target needs". Nothing says the omission is deliberate, and the README says `rebuild` "runs migrations 1 to N as a deployment does".

## Agent Brief

**Category:** bug
**Summary:** `rebuild` refuses before asking when the deploy role doesn't own the managed schema, since the target it would leave fails the deploy pre-flight.

**Current behavior:**
`rebuild` wipes and replays a target whose managed schema belongs to a role the deploy role doesn't have the privileges of (as long as it can drop what's inside). It reports success, and `deploy`, `deploy-draft` and `mark` then refuse the target.

**Desired behavior:**
- Before asking, `rebuild` runs the ownership check on the managed schema itself. If the schema fails it, `rebuild` refuses with the same wording the pre-flight uses (`schema app is owned by postgres, whose privileges the deploy role doesn't have (fix: ALTER SCHEMA app OWNER TO <deploy role>)`), says nothing changed, and records no attempt.
- Objects inside the schema keep today's test (what the wipe can drop): they are dropped anyway and come back owned by the deploy role.
- A target without the managed schema passes, as in the pre-flight.
- ADR-0006's consequence and the README's "The deploy role" bullet add `rebuild` to the commands that refuse.

**Key interfaces:**
- `rebuild`'s guarded `check()`, next to `requireWipeable`.
- `objectsNotOwned` / `NotOwnedError` from the ownership module (the schema is its first entry), or a typed error with the same `not-owned` code.

**Acceptance criteria:**
- [ ] Pseudo-terminal: with the managed schema owned by the superuser and the deploy role granted `USAGE, CREATE` on it, `rebuild` refuses before any YES prompt, naming the schema, its owner and the `ALTER SCHEMA ... OWNER TO` fix. The target is unchanged.
- [ ] A superuser-owned table in a schema the deploy role owns still doesn't stop `rebuild` (it can drop it), as today.
- [ ] ADR-0006 and the README list `rebuild` among the commands that refuse.

**Out of scope:**
- Running the rest of the deploy pre-flight in `rebuild` (history mismatches are what `rebuild` resets).
- The advice for extensions (163).
- For `public`, the `ALTER SCHEMA public OWNER TO` fix contradicting the README (126).
