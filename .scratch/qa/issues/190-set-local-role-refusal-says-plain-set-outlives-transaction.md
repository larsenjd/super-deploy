# 190: `SET LOCAL ROLE` in a script is refused with a reason that doesn't apply ("a plain SET outlives the transaction")

**Status:** resolved
**Category:** bug
**Severity:** low
**Area:** privs
**Round:** 2

## What I did
In a project with finalized migrations, `pnpm exec super-deploy draft --name
scripts` with no schema change, then `data-model/draft/pre-migration.sql`:

```sql
set local role qa2_privs_reader;
```

`pnpm exec super-deploy rehearse`

## Expected
A refusal that names the real reason: switching role (or session authorization) in a
deployment is refused because the deploy role runs everything / privileges are set
up outside super-deploy.

## Actual
```
data-model/draft/pre-migration.sql:1: SET is not allowed: super-deploy pins the session settings, and a plain SET outlives the transaction [escapes-transaction]
```

`SET LOCAL` doesn't outlive the transaction, so the stated reason is wrong for it, and
a user may conclude `SET LOCAL` would be fine elsewhere. `set role` and `set session
authorization` get the same message.

## Notes
Refusing it is right (it would let a script act as another role); only the message
is off. Suggest a role-specific reason for `SET [LOCAL] ROLE` / `SESSION
AUTHORIZATION` / `set_config('role', ...)`, and for other `SET LOCAL` a reason that
fits ("super-deploy pins the session settings").

**Intended?** Refusing all of them is (spec "Other statements: `SET`, `RESET` ... refused"; the denylist header says `set_config` with `is_local` is refused because it overrides the pinned settings for the rest of the deployment). Only the message is wrong.

## Agent Brief

**Category:** bug
**Summary:** The deploy-time `SET` refusal gives a reason that fits the statement: role switches, `SET LOCAL`, and plain `SET`/`RESET` each get their own.

**Current behavior:**
Every `SET`/`RESET` in a deploy-time file is refused as `[escapes-transaction]` with "a plain SET outlives the transaction", including `SET LOCAL ...`, which doesn't outlive it, and `SET [LOCAL] ROLE` / `SET SESSION AUTHORIZATION`, whose real problem is running the deployment as another role.

**Desired behavior:**
- `SET [LOCAL] ROLE`, `SET [LOCAL] SESSION AUTHORIZATION` and their `RESET`s: refused because a deployment runs everything as the deploy role, and roles and privileges are set up on targets outside super-deploy.
- Any other `SET LOCAL`: refused because super-deploy pins the session settings for every migration in the deployment's one transaction, and `SET LOCAL` would change them for the rest of it.
- Plain `SET` / `RESET`: today's message.
- Rule ids stay as they are, unless the role case belongs under `unsupported-object` with the other privilege refusals (either is acceptable; keep it unoverridable).

**Key interfaces:**
- The deploy-time rule for `VariableSetStmt` (its `kind`, `is_local` and `name`).

**Acceptance criteria:**
- [ ] `set local role x`, `set role x` and `set session authorization x` in a pre-migration script are refused with the role reason (unit seam).
- [ ] `set local statement_timeout = 0` is refused with the `SET LOCAL` reason, which doesn't say it outlives the transaction.
- [ ] `set statement_timeout = 0` and `reset all` keep today's message.
- [ ] `SET TRANSACTION ...` keeps its `transaction-control` refusal.

**Out of scope:**
- `SET` inside routine bodies, which isn't checked at all (noted in 185).
- The desired schema's own `SET` refusal (`[desired-schema-statement]`), which is accurate.
- Wording of the other privilege refusals (189).
