## What I did
Database `qa2_adopt_typo` created by `postgres` (so owned by `postgres`); deploy role `qa2_adopt_deployer`, with `CREATE` on the database; `managedSchema` left at its default, `public`.

```sh
pnpm exec super-deploy init --adopt qa
```

## Expected
The README, "What each target needs set up outside super-deploy": "For `public`, which `pg_database_owner` owns, deploy as the database's owner." So the fix offered would be `ALTER DATABASE qa2_adopt_typo OWNER TO qa2_adopt_deployer` (which is what I did, and adoption then worked).

## Actual
```
Error: The deploy role on target qa doesn't own everything in the managed schema: schema public is owned by pg_database_owner, whose privileges the deploy role doesn't have (fix: ALTER SCHEMA public OWNER TO qa2_adopt_deployer)
```

## Notes
Both fixes work, but they differ: re-owning `public` breaks the PostgreSQL 15+ convention (and anything that relies on `pg_database_owner`), while changing the database owner is what the README recommends. The message and the README should agree, or the message could offer both.

## Agent Brief

**Category:** bug
**Summary:** When `pg_database_owner` owns the managed schema, the ownership refusal's fix is the one the README gives: make the deploy role the database's owner.

**Current behavior:**
For a managed schema owned by `pg_database_owner` (`public` on PostgreSQL 15+), every ownership refusal suggests `ALTER SCHEMA public OWNER TO <deploy role>`. That takes `public` away from `pg_database_owner`. The README says to deploy as the database's owner instead.

**Desired behavior:**
- A managed schema owned by `pg_database_owner` is reported as owned by the database's owner, naming that owner, e.g. `schema public is owned by pg_database_owner (the owner of database shopdb, postgres)`.
- Its fix is `ALTER DATABASE <database> OWNER TO <deploy role>`, with identifiers quoted as the other fixes quote theirs.
- `init --adopt`, `mark`, `deploy`, `deploy-draft` and `status` all show this, since they share the check.
- Objects inside such a schema that another role owns keep their own `ALTER ... OWNER TO` fix.

**Key interfaces:**
- `objectsNotOwned` and `NotOwnedObject` (`fix`, `owner`) in the ownership module.

**Acceptance criteria:**
- [ ] API seam: with `managedSchema` `public`, and a database owned by another role in which the deploy role has CREATE, `adopt` refuses with a `NotOwnedObject` whose fix is `ALTER DATABASE ... OWNER TO <deploy role>`.
- [ ] Running that fix makes the same adoption succeed.
- [ ] `status` shows the same fix under "Deploy would refuse".
- [ ] A managed schema owned by an ordinary role still gets `ALTER SCHEMA ... OWNER TO`.

**Out of scope:**
- Saying who must run the fixes (188's other point): that goes in the heading of the fix block in 121.
- Formatting the list (121).
