# 19: Widening a column type warns that the cast "could fail or lose data" and generates a needless `DROP DEFAULT`

**Status:** resolved
**Category:** enhancement
**Severity:** low
**Area:** newproj

## What I did
Desired schema change in `orders` (the column has no default):
```sql
  total_cents bigint not null constraint orders_total_cents_check check (total_cents >= 0),   -- was integer
```
```sh
pnpm exec super-deploy draft --name "rename display name"
pnpm exec super-deploy rehearse
```

## Expected
`integer` to `bigint` can't fail or lose data, so no "convert it in the
pre-migration script" warning (the lock warning is fair). And no statements
for defaults that don't exist.

## Actual
Every `draft` repeats:
```
warning: Column orders.total_cents changes type by a plain cast (2 non-null values in the rehearsal data): convert it in the pre-migration script if the cast could fail or lose data
```
There's no way to say "I checked, it's fine", so the warning stays for the
life of the draft and trains people to ignore it. In issue 09 (text to
varchar(5)) the same wording appears where the cast really does lose data.

The generated change also drops a default that was never there:
```sql
ALTER TABLE "public"."orders" ALTER COLUMN "total_cents" DROP DEFAULT;
ALTER TABLE "public"."orders" ALTER COLUMN "total_cents" TYPE bigint USING "total_cents"::bigint;
```
(Same for `customers.display_name` text to varchar(5).) Harmless, but it's
in an immutable migration that reviewers have to read and wonder about.

## Notes
Guess: classify casts (widening int2→int4→int8, varchar(n)→text, etc. are
safe) and only warn for the rest. Ideally the warning for lossy casts says
exactly what happens: truncation, rounding, or error.

### Triage, 2026-10-20

**Verification:** CONFIRMED. An `integer` to `bigint` draft gave the coverage warning "changes type by a plain cast ... could fail or lose data". It also emitted `ALTER COLUMN "total" DROP DEFAULT;` for a column with no default.

Causes:
- The warning comes from the draft's script-coverage check, which flags every `ALTER COLUMN ... TYPE` without asking whether it widens. The destructive-change analysis used by `finalize` already classifies widening type changes (its `widens` check).
- The `DROP DEFAULT` comes from pg-delta, whose source calls it a "harmless no-op". Removing it means post-processing or patching pg-delta's output, which is the same decision as issue 09, so it is out of scope here.

## Agent Brief

**Category:** enhancement
**Summary:** Don't warn "could fail or lose data" for column type changes that only widen.

**Current behavior:**
Every `draft` whose schema change alters a column's type by a plain cast warns "Column X changes type by a plain cast (N non-null values in the rehearsal data): convert it in the pre-migration script if the cast could fail or lose data". That includes casts that can't fail or lose data, such as `integer` to `bigint` or `varchar(n)` to `text`. The warning stays for the life of the draft, and nothing can silence it.

**Desired behavior:**
The draft's script-coverage warning for plain-cast type changes is skipped when the change widens, judged by the same classification `finalize` uses to decide that a type change is not destructive. Narrowing or converting casts keep the warning. Lock and rewrite warnings for the same statement are unchanged.

**Key interfaces:**
- The draft's script-coverage check: the plain-cast case of its "to cover" findings.
- The destructive-change analysis's widening classification. Reuse it rather than duplicate it, exporting or moving it if needed.

**Acceptance criteria:**
- [ ] At the API seam, a draft changing `integer` to `bigint` (with rehearsal rows) has no plain-cast coverage warning.
- [ ] A draft changing `varchar(10)` to `text` has none.
- [ ] A draft changing `text` to `varchar(5)`, or `text` to `integer`, still warns.
- [ ] Destructive classification at `finalize` is unchanged (existing tests pass).

**Out of scope:**
- The needless `DROP DEFAULT` pg-delta emits (goes with issue 09's differ-output decision).
- The truncation itself and the warning's wording for lossy casts (issue 09).
