# 34: Pre-flight checks that an external schema exists, but not that the deploy role can use it

**Status:** wontfix
**Category:** enhancement
**Severity:** low
**Area:** adopt

## What I did
Adopted `qa_adopt_ext2`: `app.posts` with a `SECURITY DEFINER` trigger function reading `auth.users`, exactly as in the README. Config has `externalSchemas: ["auth"]`. Then I removed the grants the README says every target needs:

```sql
revoke usage on schema auth from adopt_deployer;
revoke select on auth.users from adopt_deployer;
```
```sh
# add a column to app.posts, then:
pnpm exec super-deploy draft --name title
pnpm exec super-deploy finalize
pnpm exec super-deploy status --target ext2
pnpm exec super-deploy deploy --target ext2
```
Then, as the app's writer role: `insert into app.posts(author_id) values (1)`.

## Expected
The pre-flight checks already refuse when an external schema is missing (`external schema "auth" does not exist`). They could also refuse, or at least warn, when the deploy role lacks `USAGE` on it, since every `SECURITY DEFINER` body that reads it will fail.

## Actual
`status` and `deploy` both pass (`Deployed 1 migration to ext2`). The app then fails at run time:

```
permission denied for schema auth
```

## Notes
README, "Grants on external schemas and their objects", documents the requirement, so this is only a safety net. Object-level `SELECT` can't be checked without parsing PL/pgSQL bodies, but schema `USAGE` is cheap to check.

## Agent Brief

**Category:** enhancement
**Summary:** `status` and `deploy` warn when the deploy role lacks USAGE on a declared external schema.

**Current behavior:**
The pre-flight checks refuse when a schema listed in `externalSchemas` doesn't exist on the target. They don't check that the deploy role can use it. A deploy then succeeds, and any `SECURITY DEFINER` function that reads the external schema fails at run time with `permission denied for schema <name>`.

**Desired behavior:**
- The pre-flight checks add a warning for each declared external schema on which the deploy role lacks `USAGE` (checked through `has_schema_privilege`, so membership-inherited privileges count).
- The warning names the schema, the deploy role and the fix, e.g. `The deploy role "fail_deployer" on target ext2 has no USAGE on external schema "auth": grant usage on schema auth to fail_deployer, or functions that read it will fail at run time`.
- `status` lists it with the other pre-flight warnings, and `deploy` prints it like the existing deploy-role warnings (stderr in the CLI). It is a warning, not a refusal, because the deploy itself succeeds.
- A missing external schema keeps refusing as today, with no extra USAGE warning.

**Key interfaces:**
- The pre-flight findings and warnings that `status` and `deploy` share (the same mechanism as the existing deploy-role warnings, such as the superuser warning).

**Acceptance criteria:**
- [ ] With `externalSchemas: ["auth"]` and the deploy role's USAGE on `auth` revoked, `status` reports the warning and `deploy` succeeds while emitting it (API seam: the warning appears in the command results).
- [ ] With USAGE granted directly or through a role the deploy role belongs to, there is no warning.
- [ ] A missing external schema still refuses with the existing message and no USAGE warning.

**Out of scope:**
- Checking object-level privileges (e.g. `SELECT` on `auth.users`); that would need parsing PL/pgSQL bodies.
- Making this a refusal.

### Note, 2026-10-20

ADR-0006 puts privileges, ownership and row-level security outside the system in V1 (`.scratch/super-deploy/issues/28-privileges-out-of-scope.md`). `SECURITY DEFINER` is refused, so routines run as their caller and the application's roles, not the deploy role, need the external schema's grants. That removes this issue's motivating case. Re-triage before implementing: it may now be wontfix.

### Decided, 2026-10-21

The maintainer closed it: routines run as their caller (`SECURITY DEFINER` is refused, ADR-0006), so the deploy role's access to external schemas doesn't matter, and per 06 external schemas are the DBA's job and no longer checked at all.
