# 68: The disposable and rebuild confirmations don't show what's on the target

**Status:** ready-for-human
**Category:** enhancement
**Severity:** low
**Area:** disp

## What I did
`qa` is a non-disposable target with real data (1000 rows in `customers`) and
seven migrations. I ran `disposable --target qa --set yes` at a terminal.
Later, on a disposable target with hand-made tables in `public`, I ran
`rebuild --to 5`.

## Expected
Before typing YES on "this may now be wiped", something that helps me notice
I picked the wrong database: e.g. the number of tables and approximate rows in
the managed schema, or objects that aren't from any migration. Similarly for
rebuild, a list (or count) of objects that aren't from migrations and will be
dropped (`public.handmade`, a view, an extension).

## Actual
`disposable` on the 1000-row `qa`:

```
◇  disposable: Mark target qa as disposable
│  Target:    qa
│  Host:      [::1]:54818
│  Database:  qa_disp_qa
│  Last recorded migration: 00005-tag-color
│  deploy-draft and rebuild will then be allowed to wipe it and load seed data
```

This looks the same as for an empty database. The `rebuild` box says
"Drops everything in schema public" and lists the migrations it will replay,
but not what extra it will drop.

## Notes
The guard otherwise worked well: refusing on a non-disposable target before
prompting, strict `YES` (rejects `yes`, ` YES`, `YES `, empty), refusing without
a TTY on stdin or stdout, refusing under `CI=true`, and detecting the target
changing while the prompt waited (another `deploy`, `disposable --set no`, or
the database dropped and recreated). Also "deploy-draft ... will be allowed to
wipe it" is slightly off: deploy-draft doesn't wipe.

## Brief (ready-for-human)

**Category:** enhancement
**Summary:** The `disposable` and `rebuild` confirmations should help the user notice they picked the wrong database.

**Current behavior:**
Marking a 1000-row production-like target disposable shows the same box as for an empty database. `rebuild` says "Drops everything in schema public" without saying what's there that no migration created.

**Desired behavior (once decided):**
- `disposable --set yes` shows a short summary of what's in the managed schema (for example, table count and approximate rows).
- `rebuild` lists, or counts, the objects in the managed schema that no recorded migration created, which it will drop.
- In scope regardless: the disposable box's wording says deploy-draft may *deploy a draft* and rebuild may *wipe*, instead of both wiping.

**Key interfaces:**
- The guarded commands' confirmation details (`runGuarded`'s question).
- The `disposable` and `rebuild` checks that run before asking.
- The catalog comparison, if "objects not from any migration" reuses drift.

**Acceptance criteria (once decided):**
- [ ] The disposable confirmation shows the agreed summary for a target with data.
- [ ] The rebuild confirmation names (or counts) extra objects in the managed schema.
- [ ] The deploy-draft wording no longer says it wipes.
- [ ] Pseudo-terminal tests cover both boxes.

**Out of scope:**
- Objects in other schemas that depend on the managed schema (61).
- Objects rebuild can't drop (63, merged into 61).

**Why not delegated:** what to show, and how much catalog querying a confirmation may do, are UX choices.
**Decision needed:**
- Disposable: table count and estimated rows (`reltuples`). Rebuild: the drift-style list of objects not from migrations, capped with "and N more" (recommended).
- Counts only, for both.
- Fix the wording only.
