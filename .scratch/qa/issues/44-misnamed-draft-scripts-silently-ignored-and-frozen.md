# 44: A misnamed script in the draft (e.g. `post-migrate.sql`) never runs, yet is frozen into the migration

**Status:** ready-for-agent
**Category:** bug
**Severity:** medium
**Area:** fail

## What I did
In a project with finalized migrations (customers table), added a `slug` column to the desired schema and wrote the backfill. The README names `pre-migration.sql` but never the post-migration script, so I guessed:

```sh
pnpm exec super-deploy draft --name "add slug"
echo "update customers set slug = lower(name);" > data-model/draft/post-migration.sql
echo "update customers set slug = lower(name);" > data-model/draft/post-migrate.sql
pnpm exec super-deploy draft
pnpm exec super-deploy validate
pnpm exec super-deploy finalize
ls data-model/migrations/00005-add-slug
```

Then, to check whether misnamed files run at all, in another draft:
```sh
echo "select 1/0;" > data-model/draft/pre-migrate.sql
echo "select 1/0;" > data-model/draft/premigration.sql
pnpm exec super-deploy rehearse
pnpm exec super-deploy validate --strict
```

## Expected
An unknown file in `data-model/draft/` makes `draft`, `rehearse`, `validate` and `finalize` fail, or at least warn, naming the files the draft may hold (`pre-migration.sql`, `post-migration.sql`, `seed-data.sql`, ...).

## Actual
- No command mentions the stray files. `rehearse` passes (`Rehearsed draft notes after 5 migrations: matches the desired schema`), so `select 1/0;` never ran.
- `finalize` copies the stray file into the immutable migration, where it stays forever looking like a real script:
  ```
  data-model/migrations/00005-add-slug:
  desired-schema  metadata.json  post-migrate.sql  post-migration.sql  schema-change.sql
  ```

If the only backfill is in a misnamed file, the backfill silently never runs, the rehearsal (with no rows) passes, and the migration is frozen with a script that looks as if it ran.

## Notes
- README gap: it never names `post-migration.sql` or says which files a draft may contain or in what order they run (seed data, then pre-migration, schema change, post-migration?). I only found the name by guessing.
- `recovery --migration 5` later created a Recovery draft without `post-migrate.sql`, so the tool apparently knows the stray file isn't part of the migration.

## Brief (ready-for-human)

**Category:** bug
**Summary:** Unknown files in the draft folder must not be silently ignored by replay and then frozen into the migration.

**Current behavior:**
A misnamed script (`post-migrate.sql`, `premigration.sql`) in `data-model/draft/` is never run by rehearsals or deploys. No command mentions it, and `finalize` copies it into the immutable migration, where it looks like a script that ran.

**Desired behavior (once decided):**
`draft`, `rehearse`, `validate` and `finalize` notice files in the draft folder that aren't part of a draft. They refuse, or warn, naming each file and the file names a draft may hold. `finalize` never copies a file that replay doesn't read, unless the decision allows notes.

**Key interfaces:**
- The deploy-time file list (`deployTimeFileNames`) and the draft's own files (`draft.json`, `schema-change.sql`, `desired-schema/`).
- `finalize`'s copy step, and `validate`'s draft checks.

**Acceptance criteria (once decided):**
- [ ] A draft holding `post-migrate.sql` makes `rehearse`, `validate` and `finalize` refuse (or warn), naming the file and the allowed names.
- [ ] `finalize` doesn't freeze an unknown `.sql` file.
- [ ] A draft with only known files behaves as today.

**Out of scope:**
- README text naming the scripts and their order (15).
- Stray files in finalized migrations, which hashing already protects.

**Why not delegated:** refuse or warn, and whether non-SQL notes (e.g. `NOTES.md`) may live in a draft.
**Decision needed:**
- Refuse any unknown `.sql` file; allow non-`.sql` files and keep copying them (recommended).
- Refuse any unknown file at all.
- Warn only.

### Decided, 2026-10-21

The maintainer chose: **warn only.** Unknown files are still copied into the migration when it is finalized.

- `draft`, `rehearse`, `validate` and `finalize` warn about each file in the draft folder that isn't part of a draft, naming it and listing the names a draft may hold (`pre-migration.sql`, `post-migration.sql`, `seed-data.sql`, ...). An unknown `.sql` file's warning adds that it will not run.
- `finalize` still freezes it (the warning is shown before the acknowledgement-free finalize completes); `validate --strict` treats it as a warning, so it fails CI.
- A draft with only known files behaves as today.

**Acceptance criteria** (replacing the "once decided" ones):
- [ ] A draft holding `post-migrate.sql`: `rehearse`, `validate` and `finalize` warn, naming the file and the allowed names; `finalize` still succeeds and copies it.
- [ ] `validate --strict` exits 1 on it.
- [ ] A draft with only known files prints no such warning.
