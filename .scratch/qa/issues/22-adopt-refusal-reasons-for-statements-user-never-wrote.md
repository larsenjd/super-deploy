# 22: Adoption refusals list internal ALTER statements with reasons that don't fit the actual problem

**Status:** wontfix
**Category:** enhancement
**Severity:** low
**Duplicate of:** 20
**Area:** adopt

## What I did
Adopted targets holding objects that V1 doesn't support (non-terminal, `pnpm exec super-deploy init --adopt <target> </dev/null`):

```sql
-- qa_adopt_shop, schema app
create type app.order_status as enum ('new','paid','shipped');
create table app.orders (..., status app.order_status not null default 'new', ...);

-- qa_adopt_unsup, schema legacy
create table legacy.base (id int);
create table legacy.child (extra text) inherits (legacy.base);
create table legacy.tmp_like (x int) with (fillfactor = 70);
```

## Expected
One entry per object, with the real reason: "Enums are not supported", "Table inheritance is not supported", "Table storage parameters are not supported in V1" (that's what `draft` says for a hand-written `with (fillfactor = 70)`).

## Actual
Besides the real reason, there are entries for statements the user never wrote, all with the generic desired-schema rule and its advice "declare everything else in CREATE TABLE". That advice means nothing during adoption, where the user hasn't written any desired schema:

```
  ALTER TABLE "app"."orders" ADD COLUMN "status" app.order_status NOT NULL DEFAULT 'new'::app.order_status
    desired-schema-statement: Only ALTER TABLE ... ENABLE ROW LEVEL SECURITY, FORCE ROW LEVEL SECURITY or ADD CONSTRAINT is allowed in the desired schema; declare everything else in CREATE TABLE
  CREATE TYPE "app"."order_status" AS ENUM ('new', 'paid', 'shipped')
    unsupported-object: Enums are not supported in V1: use a lookup table with a foreign key, or a CHECK constraint

  ALTER TABLE "legacy"."child" ADD COLUMN "extra" text
    desired-schema-statement: Only ALTER TABLE ... (same text)
  ALTER TABLE "legacy"."tmp_like" SET (fillfactor=70)
    desired-schema-statement: Only ALTER TABLE ... (same text)
```

For `tmp_like`, the refusal never says storage parameters are the problem.

## Notes
- Related to issue 20 (same cause, guessed: rules run on the differ's split statements).
- Rules that are about how a hand-written desired schema is laid out shouldn't fire on adoption's own output. When they do, the entry should name the object and the real unsupported feature.

### Triage, 2026-10-20

Closed as a duplicate of 20: its findings are folded into 20's brief, which adds the fold of `ADD COLUMN` and `SET (...)` statements into `CREATE TABLE`.

**Verification:** CONFIRMED at the API seam. Same cause as 20: adoption files pg-delta's split `ALTER TABLE` statements unchanged, so enum columns, `INHERITS` children and `SET (fillfactor=70)` each add a `desired-schema-statement` entry beside (or instead of) the real reason. Refusing enums, inheritance and storage parameters is by design.
