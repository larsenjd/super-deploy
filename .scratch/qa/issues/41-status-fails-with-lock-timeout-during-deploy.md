# 41: `status` fails with a bare "canceling statement due to lock timeout" while a deploy is running

**Status:** resolved
**Category:** bug
**Severity:** medium
**Area:** fail

## What I did
Target `kill` (`postgresTarget({ env: "FAIL_KILL_URL" })`, `postgres://fail_deployer:dep@localhost:54818/qa_fail_kill`) at migration 6, with 4M rows in `notes`. Pending migration 8 adds `notes.body_len` with post-migration `update notes set body_len = length(body);` (~10 s).

```sh
pnpm exec super-deploy deploy --target kill &   # long-running deploy
sleep 3
pnpm exec super-deploy status --target kill; echo "exit=$?"
```

Also reproduced after SIGKILLing a deploy mid-UPDATE: its orphaned backend kept running the UPDATE, and `status` failed the same way until it finished.

## Expected
`status` is what I'd run to find out what a running deploy is doing. It should say the target is being deployed by attempt #N (who, when started) and skip or postpone the drift check, rather than fail.

## Actual
After waiting 5 s:
```
Error: canceling statement due to lock timeout
exit=1
```
With `--debug`, it comes from the drift check reading the catalog:
```
error: canceling statement due to lock timeout
    at .../verification/catalog.js:237:28
    at async catalogFacts (...verification/catalog.js:235:5)
    at async driftBetween (...verification/drift.js:15:27)
    at async status (...commands/status.js:40:15)
```
No file, target, attempt or hint. The deploy itself succeeded.

## Notes
- A concurrent `deploy` handles the same situation well: `Target kill is locked by attempt #4 (deploy by jonathanl, started ...); try again when it has finished`. `status` could use the same check before checking drift.
- Exit 1 also reads as "drift" to anything using `status` as a drift gate (its help says "exit 1 on drift").

### Triage, 2026-10-20

**Verification:** CONFIRMED, both for a live deploy and for an orphaned backend after SIGKILL. A `status` started while a deploy's post-migration `UPDATE` (8M rows) was running took 5.2 s, then printed `Error: canceling statement due to lock timeout` (exit 1). The deploy went on to succeed. `--debug` shows the error comes from the catalog read (`verification/catalog.ts`) in the drift check. Root cause: `status` (`commands/status.ts`) takes no lock and runs `driftBetween` under the target's lock timeout. The deploy transaction's ACCESS EXCLUSIVE lock blocks the catalog read. `deploy` already handles this case through `lockHolder()` (`deploy/lock.ts`). Related: issue 51 (telling a live deploy from an orphaned one) is separate and ready-for-human.

## Agent Brief

**Category:** bug
**Summary:** While another attempt holds the target, `status` reports who holds it and skips the drift check instead of failing with a lock timeout.

**Current behavior:**
If a deploy (or an orphaned backend from a killed deploy) holds the target, `status` waits for the lock timeout during its drift check, then fails with a bare `canceling statement due to lock timeout` and exit 1. Exit 1 also means "drift" to anything using `status` as a drift gate.

**Desired behavior:**
- Before checking drift, `status` checks the target lock the same way `deploy` does.
- If the lock is held, `status` still prints what it can without the blocked catalog read: recorded migrations, pending migrations, recent attempts. It reports that the target is being deployed by attempt #N (command, who, when started, and the holding backend's pid). Drift is reported as not checked, with that reason (e.g. `Drift: not checked (target is locked by attempt #4)`).
- In that case `status` exits 0, unless something it did check gives a non-zero exit.
- If the lock is free, behaviour is unchanged.

**Key interfaces:**
- `lockHolder()` and the information `TargetLockedError` carries (attempt number, command, user, start time); add the pid if it isn't already exposed.
- The `status` result type: drift becomes "not checked" with a reason that can say the target is locked, and the result carries the lock holder.
- The CLI's rendering of `status`.

**Acceptance criteria:**
- [ ] With a test session holding the target's deployment lock (or a paused deploy, as in the existing fault-injection helpers), `status` returns promptly (well under the lock timeout), reports the holder and leaves drift unchecked (API seam).
- [ ] The CLI prints the holder line and exits 0 in that case (CLI seam).
- [ ] With no lock held, `status` output and exit codes are unchanged.

**Out of scope:**
- Telling whether the holding attempt's CLI is still alive, or suggesting `pg_cancel_backend`; that is issue 51.
- Changing `deploy`'s own locked-target refusal.
