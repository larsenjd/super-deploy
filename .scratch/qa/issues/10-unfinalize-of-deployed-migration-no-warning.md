# 10: `unfinalize` moves an already-deployed, committed migration back into the draft without a warning, and the resulting refusal says nothing about how to recover

**Status:** ready-for-agent
**Category:** enhancement
**Severity:** medium
**Area:** newproj

## What I did
Migration `00003-drop-notes` was finalized, committed to git and deployed
to `dev` and `qa`. Then:
```sh
pnpm exec super-deploy unfinalize < /dev/null      # no terminal, no flag
# change the desired schema (add a column), then
pnpm exec super-deploy draft
pnpm exec super-deploy finalize --acknowledge-destructive
pnpm exec super-deploy status --target qa; echo "exit=$?"
pnpm exec super-deploy deploy --target qa
```

## Expected
`unfinalize` warns (or asks, like `discard-draft` and `restore-schema` do)
that the newest migration may already be deployed or committed, and that
changing it will make those targets refuse. The deploy refusal says what to do
next (restore the original migration from git, or start a Recovery).

## Actual
`unfinalize` runs without asking, even with no terminal:
```
Moved migration 00003-drop-notes back into draft drop-notes in data-model/draft
```
Later:
```
Target qa: 3 migrations recorded, 0 pending
Deploy would refuse:
  the target records migration 00003-drop-notes with content hash 6dcb0009..., but the repo's is 9cf80a38...
Drift: not checked (the recorded history doesn't match the project's migrations)
exit=0
```
```
Error: Target qa failed the deploy pre-flight checks: the target records migration 00003-drop-notes with content hash 6dcb0009..., but the repo's is 9cf80a38...
```
I recovered by unfinalizing again, reverting the desired schema by hand and
re-finalizing (finalize is deterministic, so the hash matched again). Nothing
told me that would work.

## Notes
- `discard-draft` and `restore-schema` refuse without a terminal unless given
  `--acknowledge-overwrite`. `unfinalize` has the same flag in `--help`, but
  it didn't ask here, where it rewrites history that's already deployed. It
  could at least check whether the migration folder is committed in git.
- The README doesn't mention `unfinalize`, `restore-schema` or
  `discard-draft` at all. `--help` is the only description.
- Right after `unfinalize` (before re-finalizing), `validate --strict` only
  warns "Draft drop-notes is not finalized yet". It doesn't notice that a
  committed migration folder has disappeared.

## Brief (ready-for-human)

**Category:** enhancement
**Summary:** Warn before unfinalizing a migration that may already be shared or deployed.

**Current behavior:**
`unfinalize` moves the newest migration back into the draft silently, even when it's committed to git and recorded on targets. Once it's changed and re-finalized, every target that recorded it refuses deploys with a content-hash mismatch.

**Desired behavior (once decided):**
Before or while moving the migration back, `unfinalize` tells the user that a migration already deployed anywhere must not change. Depending on the decision, it may also check whether the migration folder is committed in git.

**Key interfaces:**
- The `unfinalize` command, its result and the CLI output line.
- The `Question` union, if it becomes a confirmation.

**Acceptance criteria (once decided):**
- [ ] `unfinalize` prints (or asks) as decided, and a CLI test pins the wording.
- [ ] Unfinalizing an uncommitted migration in a scratch project is no harder than today.

**Out of scope:**
- The deploy refusal's next-step text (50).
- README sections for draft housekeeping (15).

**Why not delegated:** it's a UX decision about friction versus safety, and `unfinalize` can't know where a migration was deployed.
**Decision needed:**
- Print a warning line after moving it ("if this migration was deployed anywhere, restore it instead of changing it"), with no new question (recommended).
- Ask for confirmation when the migration folder is committed in git (needs a git dependency).
- Leave as is.

### Decided, 2026-10-21

The maintainer chose: **a warning line after moving it, with no new question.**

- After `unfinalize` moves migration N back into the draft, it prints: `If migration N was deployed anywhere, don't change it: run restore-schema to put it back, then make the change in a new migration (or a Recovery if it failed on a target)`. Wording may be tightened; it must name the migration, `restore-schema`, and Recovery.
- The API result carries the same note so the menu prints it too.

**Acceptance criteria** (replacing the "once decided" ones):
- [ ] CLI test pins the warning line after a successful `unfinalize`.
- [ ] `unfinalize` asks nothing new and works as today otherwise.
