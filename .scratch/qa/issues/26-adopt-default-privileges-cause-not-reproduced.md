# 26: Adoption refuses a database that has ALTER DEFAULT PRIVILEGES, with a puzzling "not-reproduced" ACL diff

**Status:** wontfix
**Category:** bug
**Severity:** medium
**Area:** adopt

## What I did
A grown database where the deploy role had set default privileges (common practice before super-deploy):

```sql
-- as postgres
create database qa_adopt_defpriv;
grant connect, create on database qa_adopt_defpriv to adopt_deployer;
-- in qa_adopt_defpriv:
set role adopt_deployer;
create schema app;
alter default privileges in schema app grant select on tables to adopt_app_reader;
alter default privileges revoke execute on functions from public;
grant usage on schema app to adopt_app_reader;
create table app.notes (id bigint generated always as identity primary key, body text not null);
create function app.note_count() returns bigint language sql stable as $$ select count(*) from app.notes $$;
```

Config: `managedSchema: "app"`, target `defpriv` from `DEFPRIV_DATABASE_URL=postgres://adopt_deployer:deploy@localhost:54818/qa_adopt_defpriv`.

```sh
pnpm exec super-deploy init --adopt defpriv </dev/null
```

## Expected
Either:
- adoption succeeds, recording the objects' *actual* ACLs as `GRANT SELECT ON app.notes TO adopt_app_reader` and `REVOKE EXECUTE ON FUNCTION app.note_count() FROM PUBLIC`, and warns that the default privileges must be removed (the README's Permissions section says not to use them); or
- adoption refuses, naming the default privileges as the cause and saying to remove them.

## Actual
```
Target defpriv has 2 things V1 doesn't support:
  function note_count()
    not-reproduced: The desired schema generated from the target creates it differently: - acl: note_count() {<owner>:EXECUTE/<owner>}; + acl: note_count() {<owner>:EXECUTE/<owner>,adopt_deployer:EXECUTE/<owner>}
  table notes
    not-reproduced: The desired schema generated from the target creates it differently: - acl: notes {<owner>:DELETE/<owner>,...,adopt_app_reader:SELECT/<owner>}; + acl: notes {<owner>:DELETE/<owner>,...,adopt_app_reader:SELECT/<owner>,adopt_deployer:DELETE/<owner>,adopt_deployer:INSERT/<owner>,...,adopt_deployer:UPDATE/<owner>}
Error: Cannot adopt target defpriv: its managed schema has 2 things V1 doesn't support: function note_count(); table notes. Nothing was written; change the target first, then adopt again
```

The message doesn't mention default privileges. The generated side has a phantom grantee `adopt_deployer`, the owner itself, as if the owner's privileges had been turned into an explicit `GRANT ... TO adopt_deployer`. Removing both default privileges, without touching the objects or their ACLs, makes the same adoption succeed with the expected grants:

```sql
alter default privileges in schema app revoke select on tables from adopt_app_reader;
alter default privileges grant execute on functions to public;
```

Each default privilege on its own triggers the refusal (I removed them one at a time).

## Notes
- Guess: when `pg_default_acl` has an entry for the owner, the owner's privileges stop looking like the default `acldefault()` and get emitted as an explicit grant to the deploy role, which then differs in the rehearsal.
- README, "Permissions": the warning about `ALTER DEFAULT PRIVILEGES` covers deploys after adoption. It could add "remove any default privileges before `init --adopt`".

### Triage, 2026-10-20

**Verification:** CONFIRMED, root cause found. The reporter's setup gives the same `not-reproduced` refusal with a phantom `adopt_deployer` grant. Removing only the default privileges makes adoption succeed. When the target has a `pg_default_acl` entry for the deploy role, pg-delta emits an owner self-grant for each object:
```
REVOKE ALL ON TABLE "app"."notes" FROM "deployer";
GRANT DELETE, INSERT, MAINTAIN, REFERENCES, SELECT, TRIGGER, TRUNCATE, UPDATE ON TABLE "app"."notes" TO "deployer";
ALTER DEFAULT PRIVILEGES FOR ROLE "deployer" IN SCHEMA "app" GRANT SELECT ON TABLES TO "reader";
```
`adoptedDesiredSchema` (`sql-analysis/adoption.ts`) drops grants to the owner or deploy role only for schema grants, so the object-level self-grant survives. In the rehearsal the deploy role isn't the owner, so it shows up as a named grantee and adoption reports "not-reproduced". The `ALTER DEFAULT PRIVILEGES` statement is dropped silently. Related: issue 27 (with 33 and 62 merged in) covers default privileges causing drift on deploy and rebuild after adoption. A preflight check for the deploy role's `pg_default_acl` entries is likely shared work between the two.

## Agent Brief

**Category:** bug
**Summary:** Adoption ignores owner self-grants and refuses up front, naming the deploy role's default privileges, instead of giving a puzzling "not-reproduced" ACL diff.

**Current behavior:**
If the deploy role has default privileges (`ALTER DEFAULT PRIVILEGES`, in the managed schema or global), the differ emits explicit `REVOKE ALL ... FROM <owner>` and `GRANT <all> ... TO <owner>` statements for the affected objects. Adoption keeps them in the generated desired schema. The rehearsal then grants to a role that isn't the owner there, so adoption refuses each object as "not-reproduced" with two long ACL strings, and never mentions default privileges.

**Desired behavior:**
- When building the adopted desired schema, object-level `GRANT` and `REVOKE` statements whose grantee is the object's owner or the deploy role are left out, as is already done for schema grants.
- Before anything else, adoption refuses if `pg_default_acl` has entries for the deploy role, in the managed schema or global (namespace 0). The refusal names each entry (role, schema or "all schemas", object type, privileges, grantee). It says to remove them (with the matching `ALTER DEFAULT PRIVILEGES ... REVOKE` / `GRANT` statement) and adopt again. The README's Permissions section already says not to use default privileges for the deploy role.
- With the default privileges removed, adoption records the objects' actual grants, as it does today.

**Key interfaces:**
- `adoptedDesiredSchema` (SQL analysis): the owner/deploy-role grant filter extends from schema grants to object grants.
- `AdoptConflictError` or `AdoptUnsupportedError`: a reason naming default privileges. Pick whichever matches how other target-setup refusals are reported.
- If issue 27 adds a preflight check for the deploy role's default privileges first, reuse that query rather than writing a second one.

**Acceptance criteria:**
- [ ] Adopting the reporter's database (default privileges for the deploy role in `app` and globally) refuses with a message naming both default-privilege entries and how to remove them, without any "not-reproduced" entries (API seam).
- [ ] After removing the default privileges, the same adoption succeeds and the desired schema grants `SELECT ON app.notes TO adopt_app_reader` with no grant to the deploy role.
- [ ] A generated desired schema never contains a `GRANT` or `REVOKE` to the object's owner or the deploy role (unit test on the adoption step with a self-grant statement).
- [ ] Default privileges set by other roles (not the deploy role) don't cause a refusal.

**Out of scope:**
- Managing default privileges (REFINEMENTS.md "Roles, grants and ownership").
- Default privileges causing drift on deploy or rebuild; that is issue 27.

### Closed, 2026-10-20

Out of scope. ADR-0006 puts privileges, ownership and row-level security outside the system in V1 (`.scratch/super-deploy/issues/28-privileges-out-of-scope.md`). Adoption no longer writes grants or compares ACLs, so default privileges can't cause a "not-reproduced" refusal.
