# 101: Columns of a domain or composite type end up last in the table, not where the desired schema puts them

**Status:** ready-for-human
**Category:** bug
**Severity:** medium
**Merged:** 120
**Area:** newproj
**Round:** 2

## What I did
In a new project (`node <cli> init`, `git init`, `pnpm install`):

`data-model/desired-schema/schema.sql`:
```sql
create domain email_address as text;

create table people (
  id bigint generated always as identity primary key,
  email email_address not null,
  name text not null
);
```
```sh
pnpm exec super-deploy draft --name one
grep -i "people\|email" data-model/draft/schema-change.sql
```

Same thing in a bigger project: `customers (id, email email_address, full_name, created_at, updated_at)` and
`orders (..., price money_amount, ...)` where `money_amount` is a composite type. After `finalize` and
`deploy --target dev` / `deploy --target qa`:
```sql
select attname from pg_attribute where attrelid='customers'::regclass and attnum>0 order by attnum
```

## Expected
`CREATE TABLE people (id, email, name)`: the columns in the order the desired schema declares them, on every target.

## Actual
```
CREATE TABLE "public"."people" ("id" bigint GENERATED ALWAYS AS IDENTITY NOT NULL, "name" text NOT NULL, CONSTRAINT "people_pkey" PRIMARY KEY (id));
CREATE DOMAIN "public"."email_address" AS text;
ALTER TABLE "public"."people" ADD COLUMN "email" public.email_address NOT NULL;
```
On dev and on the real target, `customers` is `id, full_name, created_at, updated_at, email`: the domain column is last.
It happens even when the domain is created before the table, in the same file. Every column whose type is a
domain or composite type in the desired schema is moved to the end.

## Notes
- Nothing warns about it, and the rehearsal passes because (I guess) the comparison ignores column order (the README says
  `mark` does).
- Column order matters to `select *`, `insert ... values (...)` without a column list, `COPY` without a column list, and
  tools that show tables. The user wrote one order and every target gets another.
- Guess: the differ creates tables before domains/types and adds the dependent columns afterwards; creating
  the domain or type first would keep the order.

### Triage, 2026-10-21

Merged here: 120 (adoption: `00001-adopt` builds every other target with the adopted target's columns in a different order).

**Verification:** CONFIRMED with the built CLI. A desired schema with `people (id, email email_address, price money_amount, ref text default new_ref(), name)`, where the domain, the composite type and the function are created in the same migration, drafts as `CREATE TABLE people (id, name)`, then `CREATE DOMAIN`, `ADD COLUMN email`, `CREATE TYPE`, `ADD COLUMN price`, `CREATE FUNCTION`, `ADD COLUMN ref`. So every target gets `id, name, email, price, ref`. Columns whose default calls a managed-schema function move too, as 120 found.

**Root cause:** pg-delta's tie-break, not our wrapper.
- pg-delta means a new table to keep its declared column order. Its `column-order.test.ts` calls a reorder "a silent column reorder that changes `SELECT *`, positional INSERTs". Its compaction pass (`compactColumnFolds` in `plan/internal.ts`) folds each `ADD COLUMN` into the `CREATE TABLE`, in declared order, but only when no dependency edge crosses the fold.
- Actions with no edge between them are ordered by kind weight: tables 4, domains and types 7, routines 8 (`plan/rules/*.ts`). So `CREATE TABLE` comes before the type or function a column needs, the column's fold crosses that edge, and the column stays a trailing `ADD COLUMN`.
- Creating the type or function first in the desired schema changes nothing: the differ reads the desired schema from the catalogs (ADR-0003), so statement order doesn't reach it.

**By design, and not:**
- Physical column order is never a difference (spec "Differ"; pg-delta research §1), and scripts refuse column-order-dependent SQL (spec story 37). So rehearsals, drift and `mark` are right to pass. Round 1 (01) put "create domain columns in place" out of scope for that reason.
- But a *new* table not getting its declared order is a generator defect: the user's `select *` and `COPY` without a column list differ from what they wrote, and for an adopted database (120) they differ between the adopted target and every target built from `00001-adopt`. Nothing tells the user. The README mentions column order only under `mark`.

## Brief (ready-for-human)

**Category:** bug
**Summary:** A table created by a migration gets its columns in the order the desired schema declares them, even when a column's type or default is created in the same migration.

**Current behavior:**
A column typed with a domain or composite type, or defaulting to a managed-schema function, created in the same migration is added after the `CREATE TABLE` with `ALTER TABLE … ADD COLUMN`, so it ends up last. This holds for `draft` and for `init --adopt`'s `00001-adopt`. The adopted target keeps its original order, so it differs from `dev`, rehearsal databases and every other target. Nothing warns.

**Desired behavior (once decided):**
- `CREATE TABLE` in a generated schema change lists the columns in declared order. For adoption, that is the target's order. This holds when a column's type (domain, composite) or its default's function is created in the same migration. The type or function is created before the table.
- A function whose body depends on the table itself still can't come first. That column may stay a trailing `ADD COLUMN`, which is valid SQL and order-insensitive by design.
- Adding a column to an existing table still appends it (unchanged, by design).
- The README says that physical column order is not compared and may differ between targets for columns added later. It points to spec story 37's refusals.

**Key interfaces:**
- The `Differ` seam and its pg-delta implementation: the order of create actions for tables versus the types and routines their columns use.
- The pg-delta research §8 "Known behaviours", which gains a row for this.
- `init --adopt`: its generated `00001-adopt` and desired schema.

**Acceptance criteria (once decided):**
- [ ] API seam: the report's `people` schema (domain, composite and function-default columns, all new) drafts one `CREATE TABLE` with `id, email, price, ref, name` in that order. After deploy, `pg_attribute` order on `dev` matches.
- [ ] API seam: adopting a target with a domain column, a composite column and a function-default column in the middle of a table (120's `customers` and `orders`) gives `00001-adopt`. Deploying `00001-adopt` to a fresh target reproduces the adopted target's column order.
- [ ] The round-trip fixtures and the prototype scenarios (required for any change to the pinned pg-delta) still pass.
- [ ] README states the column-order rule as above.

**Out of scope:**
- Reordering columns of existing tables (never: order is not a difference).
- Composite type attribute reordering (102).
- Collation and generated-expression changes moving a column to the end (103).

**Why not delegated:** the fix is in pg-delta's ordering. ADR-0003 wraps pg-delta without rewriting its output, and for 09 the maintainer chose to keep its output as is. Changing the pinned dependency, or reordering its plan, is an architecture call.

**Decision needed:**
1. **(recommended)** Patch the pinned pg-delta (`pnpm patch`) so that, among actions with no edge between them, domains, types and routines come before tables. Then the columns fold into `CREATE TABLE` as pg-delta intends. Report it upstream, drop the patch when a fixed version is pinned, and record it in research §8.
2. Report upstream only. Pin the fixed version when it ships, and document the behaviour in the README meanwhile.
3. Keep the behaviour and only document it: columns whose type or default is created in the same migration go last, and an adopted target's order can differ from other targets'.
