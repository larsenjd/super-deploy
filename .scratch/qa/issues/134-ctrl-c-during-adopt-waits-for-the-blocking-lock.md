# 134: Ctrl+C during an adoption that waits on a lock doesn't stop it until the lock clears or lockTimeout passes

**Status:** ready-for-agent
**Category:** bug
**Severity:** low
**Area:** adopt
**Round:** 2

## What I did
Target `qa` with `lockTimeout: "30s"` (managedSchema `app`, one table `app.t`). Another session holds a lock for 15 s:

```sh
node scripts/hold_lock.mjs qa2_adopt_sig "lock table app.t in access exclusive mode" 15 &
sleep 1.5
node node_modules/super-deploy/dist/cli.js init --adopt qa </dev/null &   # pid $CPID
sleep 3; kill -INT $CPID; wait $CPID
```

## Expected
Ctrl+C (SIGINT) cancels the blocked read on the target and exits promptly. Adoption hasn't written anything yet, so there is nothing to clean up but the connection.

## Actual
```
Interrupted by SIGINT: cleaning up before exiting (interrupt again to exit at once)
```
then nothing for 11 s: the command exited (130) only when the other session released its lock, 14 s after it started. With a longer-held lock it would wait the full `lockTimeout`. Nothing says what it is waiting for. The second Ctrl+C the message offers works around it.

Nothing was written to the project or the target afterwards (checked), so the result is safe; it is the wait that is surprising.

## Notes
Guess: the cleanup waits for the in-flight query; `pg_cancel_backend` on its own session (or closing the connection) would end it at once.

### Triage, 2026-10-21

**Verification:** CONFIRMED on `qa2t_adopt_lock`, with `lockTimeout: "30s"` and another session holding `ACCESS EXCLUSIVE` on `app.t` for 15 s. SIGINT reached adoption 3 s after it started. It printed `Interrupted by SIGINT: cleaning up ...`, then exited 130 about 10.7 s later, just after the lock was released. Nothing was written to the project or the target.

**Cause:** adoption reads the target on a plain `connectTarget` session (`readTarget` in `commands/adopt.ts`). Commands that hold the target use `interruptibleSession` (`deploy/interruptible-session.ts`), which terminates the server process on abort. Adoption's read session isn't wrapped that way or registered with `cleanupOnAbort`, so a statement waiting on a lock runs on until the lock clears or `lockTimeout` passes. Its throwaway databases are dropped at once, as `interruption.ts` provides, but the blocked query is on the target.

**Category:** bug
**Summary:** Interrupting `init --adopt` while it reads the target ends the read at once.

**Current behavior:**
Ctrl+C during adoption's read of the target waits for the blocked statement to finish (until the lock clears or `lockTimeout` passes) before exiting 130. Nothing says what it's waiting for.

- When the project's signal aborts during adoption's read, the statement running on the target is ended at once (by cancelling or terminating its server process), and the command exits 130 promptly.

- No server process of the deploy role is left waiting in the target's lock queue.

**Key interfaces:**
- The adoption command's read session.
- `cleanupOnAbort` (`interruption.ts`), and `interruptibleSession` or a lighter equivalent for a read-only session.
