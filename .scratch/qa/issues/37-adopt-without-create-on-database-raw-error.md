# 37: Adoption without CREATE on the database fails with a bare "permission denied for database"

**Status:** resolved
**Category:** enhancement
**Severity:** low
**Area:** adopt

## What I did
```sql
-- as postgres
create database qa_adopt_nocreate;
grant connect on database qa_adopt_nocreate to adopt_deployer;     -- no CREATE
create schema app authorization adopt_deployer;
set role adopt_deployer;
create table app.t (id bigint generated always as identity primary key);
```
Project with `managedSchema: "app"`, target `nc`:
```sh
NC_DATABASE_URL=postgres://adopt_deployer:deploy@localhost:54818/qa_adopt_nocreate pnpm exec super-deploy init --adopt nc
```

## Expected
A message that says what's missing and how to fix it. The README's Permissions section says the deploy role "needs `CREATE` on the database for the first deployment to create the history schema". For example: `The deploy role adopt_deployer needs CREATE on database qa_adopt_nocreate to create the history schema "deployment_history": grant create on database qa_adopt_nocreate to adopt_deployer`.

## Actual
```
Error: permission denied for database qa_adopt_nocreate
```

It also left an empty `data-model/migrations/` directory, despite "Nothing is written". Harmless, since git ignores empty directories, and the retry worked after `grant create on database ... to adopt_deployer`.

## Notes
The deploy pre-flight checks (which say things like `role "x" does not exist (the desired schema grants to it; create it on the target)`) seem like the natural place for this check, and adoption could reuse them.

### Triage, 2026-10-20

**Verification:** CONFIRMED. With the deploy role owning `app` but CREATE on the database revoked, adoption failed with a raw `DatabaseError: permission denied for database test_...`, and an empty `data-model/migrations/` was left behind. Root cause: the error comes from `ensureHistorySchema`'s `CREATE SCHEMA` (`deploy/history.ts`), called by `withLockedTarget`, after draft and finalize have already rehearsed twice. `undoAdoption` (`commands/adopt.ts`) removes the migration folders but not the `migrations/` directory that finalize created. Proved from code, not run: a first plain `deploy` to such a target goes through the same `withLockedTarget` path, so it very likely hits the same raw error.

## Agent Brief

**Category:** enhancement
**Summary:** Adoption and the first deploy refuse up front, naming the missing grant, when the deploy role can't create the history schema.

**Current behavior:**
When the history schema doesn't exist yet and the deploy role lacks `CREATE` on the database, `init --adopt` rehearses, writes the migration, then fails with a bare `permission denied for database <name>`. It leaves an empty `data-model/migrations/` behind, despite "Nothing is written". A first plain `deploy` to such a target takes the same path to the history schema and very likely fails the same way.

**Desired behavior:**
- When the history schema is missing and `has_database_privilege(current_user, current_database(), 'CREATE')` is false, adoption refuses before any rehearsal or writing. It names the deploy role, the database, the history schema and the fix, e.g. `The deploy role adopt_deployer needs CREATE on database qa_adopt_nocreate to create the history schema "deployment_history": grant create on database qa_adopt_nocreate to adopt_deployer`.
- The same check is a pre-flight finding for `deploy` (and so `status` reports it as "Deploy would refuse"). Implement it once in the pre-flight checks and have adoption reuse it, if that fits the existing pre-flight structure. If it doesn't fit naturally, do adoption and leave a note on the ticket.
- When adoption does fail after creating `data-model/migrations/`, its undo removes that directory if adoption created it.
- A target whose history schema already exists is unaffected (the role no longer needs CREATE on the database).

**Key interfaces:**
- The deploy pre-flight checks and their findings (the same mechanism as `role "x" does not exist (the desired schema grants to it; create it on the target)`).
- The adoption command's target-reading step and its undo (`undoAdoption`).

**Acceptance criteria:**
- [ ] Adopting a target where the deploy role lacks CREATE on the database refuses with the message naming the grant, before any rehearsal (API seam). No `data-model/migrations/` directory remains afterwards.
- [ ] `deploy` to a fresh target (no history schema) with the same missing privilege refuses with the same finding, and `status` lists it under "Deploy would refuse".
- [ ] With CREATE granted, both adoption and the first deploy succeed.
- [ ] A target that already has the history schema deploys without CREATE on the database.

**Out of scope:**
- Other missing privileges (e.g. on the managed schema), unless they already have pre-flight findings.
- README wording beyond what the Permissions section already says.

### Note, 2026-10-20

ADR-0006 puts privileges, ownership and row-level security outside the system in V1 (`.scratch/super-deploy/issues/28-privileges-out-of-scope.md`). The example finding `role "x" does not exist` goes with it. Model the message on the other pre-flight refusals, such as the new ownership one.
