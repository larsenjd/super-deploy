# 131: Adoption doesn't mention objects in other schemas that depend on the managed schema; later deploys fail on them

**Status:** ready-for-agent
**Category:** enhancement
**Severity:** low
**Area:** adopt
**Round:** 2

## What I did
```sql
-- database qa2_adopt_edge
create schema core authorization qa2_adopt_deployer;
create schema reporting authorization qa2_adopt_deployer;
create domain core.pos as int check (value > 0);
create domain core.small_pos as core.pos check (value < 100);
create table core.items (id int primary key, qty core.small_pos, price numeric);
create view reporting.item_view as select id, qty from core.items;
```
```sh
pnpm exec super-deploy init --adopt qa       # managedSchema "core", externalSchemas ["reporting"]
# change items.qty to bigint in data-model/desired-schema/tables.sql
pnpm exec super-deploy draft --name "widen qty"
pnpm exec super-deploy finalize --acknowledge-destructive
pnpm exec super-deploy deploy --target qa
```

## Expected
Adoption tells me that `reporting.item_view` depends on `core.items` (it is outside super-deploy, rehearsals won't have it, and migrations that change or drop what it uses will fail on this target), the way it counts grants and policies. Or the README warns about it, as it does for hand-made policies.

## Actual
Adoption says nothing about it. The deploy fails (rolled back cleanly, with a clear message):
```
Error: data-model/migrations/00002-widen-qty/schema-change.sql:6: PostgreSQL refused it: cannot alter type of a column used by a view or rule. Detail: rule _RETURN on view reporting.item_view depends on column "qty". The deployment rolled back: target qa is unchanged, still at migration 00001-adopt.
```

## Notes
- The README's "Two things to know about grants and policies made by hand" covers the policy version of this; views, foreign keys and columns of managed types in other schemas aren't mentioned outside `rebuild`. In adopted databases these are common (reporting schemas, other apps' views).
- Separately, `finalize` called the domain-to-`bigint` change destructive because "super-deploy cannot tell the column's current type", and the draft included a no-op `ALTER COLUMN "qty" DROP DEFAULT` for a column without a default.

## Agent Brief

**Category:** enhancement
**Summary:** Adoption names the objects in other schemas that depend on the managed schema, and the README warns that migrations touching what they use fail at deploy.

**Current behavior:**
Views, foreign keys and columns in other schemas that depend on managed objects are adopted silently. Rehearsals don't have them, so a later migration that changes or drops what they use is first refused on the real target, at deploy. The README says this only for hand-made policies.

**Desired behavior:**
- After a successful adoption, the result lists every object outside the managed and history schemas that depends on the managed schema, described as `rebuild` describes them (`view reporting.item_view`, `column reporting.snap.it`, `foreign key ... on ...`).
- The CLI prints them after the "Left ..." line, saying rehearsals don't have them and that a migration changing or dropping what they use will fail on that target.
- With none, the output is unchanged.
- The README's "What each target needs set up outside super-deploy" gains a third point beside the two about grants and policies. Objects in other schemas that depend on managed ones aren't in rehearsals. A migration that changes or drops what they use fails at deploy and rolls back. The fix is to drop them, deploy, and recreate them.

**Key interfaces:**
- `dependentsOutside(session, managedSchema, historySchema)`: reuse it.
- `AdoptResult` (a new field, e.g. `dependentsOutside: readonly string[]`) and the CLI's adoption output.

**Acceptance criteria:**
- [ ] API seam: adopting a target whose `reporting` schema holds a view on a managed table returns that view in the new field.
- [ ] A target with no such objects returns an empty list, and the CLI output is as today.
- [ ] README updated.

**Out of scope:**
- Detecting such dependents in rehearsals or the deploy pre-flight.
- The `DROP DEFAULT` noise (round-1 issue 19) and the destructive classification of a domain-to-base-type change.
- RLS and default-privilege counts (130).
