# 140: SIGTERM to `pnpm exec super-deploy deploy` exits 143, but the deployment keeps running and commits

**Status:** ready-for-agent
**Category:** enhancement
**Severity:** medium
**Area:** fail
**Round:** 2

## What I did
Project with migrations 1–3 on a shared-server target `qa` (`postgresTarget({ env: "QA_DATABASE_URL" })`, `lockTimeout: "60s"`), migration 4 pending (`ALTER TABLE customers ADD COLUMN phone text`).

In one session, hold a lock so the deploy has to wait (`hold.mjs` is a small `pg` script that runs `begin; <sql>`, sleeps, then rolls back):

```sh
node hold.mjs qa2_fail_main 15 "select * from app.customers" &
sleep 1.5
pnpm exec super-deploy deploy --target qa > t.out 2> t.err &
P=$!                      # the pid the shell (or a CI runner, systemd, docker) knows about
sleep 4
kill -TERM $P             # SIGTERM to that process only, not to its process group
wait $P; echo "exit=$?"
cat t.out t.err
# wait for the holder to release, then
pnpm exec super-deploy status --target qa
```

## Expected
The deploy is interrupted: it exits 143 and the deployment rolls back ("Interrupted deploys now exit with the interruption's code"). Or, if the signal can't reach it, it doesn't exit 143.

## Actual
```
exit=143
                       <- nothing on stdout or stderr
...
Target qa: 4 migrations recorded, 0 pending
Recent attempts:
  #11 deploy succeeded migration 4 by jonathanl at 2026-10-21T15:26:20.645Z
  #10 deploy abandoned migration 4 ...: Interrupted (SIGTERM)   <- from an earlier, group-signalled test
```
`ps` after the `kill` shows the deploy still running, reparented to init:
```
2505486  1  /home/jonathanl/.cache/node/corepack/v1/pnpm/12.14.0/pnpm-native exec super-deploy deploy --target qa
```
The command the user started reports "terminated" (143), prints nothing, and the deploy goes on to commit migration 4 once the lock is released. The same happens with `rehearse`: pnpm exits 143 and the orphaned CLI still prints `Rehearsed draft t3 after 19 migrations: matches the desired schema` into the redirected file.

Signalling the whole process group (Ctrl+C in a terminal, `kill -TERM -<pgid>`, `timeout`) works: it prints `Interrupted by SIGTERM: cleaning up before exiting` and exits 143 with the deploy rolled back. Running `./node_modules/.bin/super-deploy rehearse` directly and sending SIGTERM to its pid also works (exit 143, interrupted).

## Notes
- Guess: the pnpm wrapper (corepack's `pnpm` → `pnpm-native` → `node …/cli.js`, and the CLI runs in a process group of its own) exits on SIGTERM without forwarding it to the CLI.
- This matters because the README tells users to run every command as `pnpm exec super-deploy …`, and many supervisors send SIGTERM only to the process they started (systemd with `KillMode=process`, `docker stop` on PID 1, some CI runners on cancel). The user sees a cancelled deploy, and it commits anyway.
- Possible fixes: document running the bin directly in CI or under a supervisor, or have the CLI notice that its parent died.

### Triage, 2026-10-21

**Verification:** CONFIRMED, but the signal is lost in pnpm's launcher, not in super-deploy.
- Reproduced as reported: SIGTERM to the `pnpm exec super-deploy deploy --target qa` pid while the deploy waited on a lock gave exit 143 and no output, and the deploy then committed (`#2 deploy succeeded migration 21`).
- The process tree: `node …/bin/pnpm` (corepack's launcher, here through fnm) → `pnpm-native exec …` → `node …/dist/cli.js` (a process group of its own when there is no terminal).
- SIGTERM to the `pnpm-native` pid instead is forwarded: the CLI printed `Interrupted by SIGTERM`, and the attempt was recorded `abandoned … Interrupted (SIGTERM)` with the migration still pending.
- So corepack's `pnpm` launcher exits on SIGTERM without passing it on, and `pnpm-native` and the CLI keep running. Other ways of installing pnpm weren't tried.

**Root cause:** outside super-deploy. The CLI handles the signal correctly when it gets it (`cli/process.ts`). "Notice that the parent died" can't help: the CLI's parent, `pnpm-native`, stays alive. What super-deploy can do is document how to run it under something that stops it with a signal.

**Related:** 141 (in a terminal, `pnpm-native` forwards SIGTERM and SIGHUP, so the CLI gets them twice) and 110 (an interrupted deploy doesn't say what happened).

## Agent Brief

**Category:** enhancement
**Summary:** The README says how to run super-deploy in CI or under a supervisor so that stopping the job really interrupts a deployment.

**Current behavior:**
The README runs every command as `pnpm exec super-deploy …` and says nothing about signals. When pnpm comes from corepack, SIGTERM to that process (systemd with `KillMode=process`, `docker stop` on a container whose PID 1 is pnpm, a CI runner cancelling a step) ends only the launcher with exit 143. The CLI keeps running unseen and the deployment commits.

**Desired behavior:**
A short README passage, near the real-target or CI advice:
- Ctrl+C or SIGTERM during a deployment rolls it back, records the attempt as abandoned and exits 130 or 143.
- In CI or under a supervisor, run the binary directly (`./node_modules/.bin/super-deploy deploy --target prod`), or make sure the stop signal reaches the whole process group. With corepack, `pnpm exec` exits on SIGTERM without passing it on, and the deployment carries on.
- After a cancelled job, `status --target X` shows whether the attempt was abandoned or succeeded.

**Key interfaces:**
- The template README only. No code change.

**Acceptance criteria:**

**Out of scope:**
- Changing how the CLI handles signals (141 for repeated signals, 144 for a signal after success).
