# 09: Narrowing a column type silently truncates data on the target (generated `USING col::varchar(n)`)

**Status:** ready-for-human
**Category:** bug
**Severity:** high
**Area:** newproj

## What I did
Target `qa` had `customers.display_name text not null` with rows
`'Real One'` and `'Real Two'` (8 characters each).

Desired schema change:
```sql
-- data-model/desired-schema/tables/customers.sql
  display_name varchar(5) not null,   -- was: text not null
```
```sh
pnpm exec super-deploy draft --name "shorten names"
pnpm exec super-deploy finalize --acknowledge-destructive
pnpm exec super-deploy deploy --target qa
node ~/.local/share/super-deploy-qa/sql.mjs qa_newproj_shop "select id, display_name from customers"
```

## Expected
The deploy fails and rolls back, as PostgreSQL does for a plain
`ALTER TABLE customers ALTER COLUMN display_name TYPE varchar(5)`:
```
ERROR: value too long for type character varying(5)
```
That's what the draft's warning leads you to expect: "convert it in the
pre-migration script if the cast could fail or lose data". The cast should
*fail*, so the problem shows up on the first real target.

## Actual
The generated schema change uses an explicit cast:
```sql
ALTER TABLE "public"."customers" ALTER COLUMN "display_name" TYPE character varying(5) USING "display_name"::character varying(5);
```
An explicit cast to `varchar(n)` truncates silently (SQL standard). The deploy
succeeds:
```
Deployed 1 migration to qa: 00005-shorten-names
```
and the data is gone:
```
[{"id":"1","display_name":"Real "},{"id":"2","display_name":"Real "}]
```
I checked on a scratch database: without `USING`, PostgreSQL refuses with
"value too long for type character varying(5)"; with the generated `USING`,
it truncates.

## Notes
- The finalize prompt ("can lose data: not every text value fits varchar(5)
  unchanged") reads like a warning that the deploy *might fail*, not that it
  will quietly truncate. Rehearsal seed data can't catch it either: a seed row
  with a long name is truncated just as silently.
- Probably affects any length-narrowing explicit cast (`varchar(n)`, `char(n)`,
  `bit(n)`, `numeric(p,s)` rounding).
- Guess: omit `USING` when the old type is assignment-castable to the new
  one, so PostgreSQL's own checks apply.

## Comments

> *This was generated by AI during triage.*

### Triage, 2026-10-20

**Verification:** CONFIRMED on PostgreSQL 18.4.

| Change | Plain `ALTER ... TYPE` | With `USING col::newtype` |
|---|---|---|
| `text` → `varchar(5)` | `value too long for type character varying(5)` | `'Real '` (truncated) |
| `varchar(10)` → `char(3)` | errors | truncated to `'abc'` |
| `bit(4)` → `bit(2)` | errors | truncated to `'10'` |
| `numeric(6,2)` → `numeric(4,1)` | rounds | rounds |

So `USING` makes no difference for numeric; the reporter's guess there is wrong. A rehearsal seed row `'Real One'` is truncated silently too, so seed data can't catch it.

**Root cause:**
- pg-delta always emits ``USING <col>::<newtype>`` for a column type change, except for foreign tables and generated columns (`@supabase/pg-delta` `plan/rules/tables.ts`).
- Our differ wrapper passes it through unchanged.

**Correction:** "silently" overstates it slightly. `finalize` does refuse without acknowledgement ("can lose data: not every text value fits varchar(5) unchanged"). What is wrong is that the acknowledged deploy *succeeds by truncating*, where PostgreSQL's own check would have failed it.

## Brief (ready-for-human)

**Category:** bug

**Summary:** A generated column type change must let PostgreSQL's own assignment checks apply, so a narrowing change that doesn't fit the data fails the deployment instead of truncating it.

**Current behavior:**
Every generated type change carries an explicit `USING col::newtype`. Explicit casts to `varchar(n)`, `char(n)` and `bit(n)` truncate by SQL rule. So a deploy of an acknowledged narrowing change succeeds, and the data is cut short on every target.

**Desired behavior:**
- When an assignment or implicit cast exists from the old type to the new one (`pg_cast.castcontext in ('a', 'i')`, or a binary-coercible pair), the generated statement omits `USING`. PostgreSQL then raises "value too long" and the deployment rolls back.
- Changes that need an explicit cast (e.g. `text` → `integer`) keep `USING`.
- The finalize warning wording says what happens: the deployment fails if a value doesn't fit. A pre-migration script is the place to shorten values on purpose.

**Key interfaces:**
- The `Differ` seam (ADR-0003) and its pg-delta implementation's output for `ALTER TABLE ... ALTER COLUMN ... TYPE`.
- The destructive-change warning text for narrowing casts.

**Acceptance criteria:**
- [ ] `text` → `varchar(5)` drafts without `USING`. Deploying it to a target holding an 8-character value fails and rolls back. API seam.
- [ ] `text` → `integer` still drafts with `USING` and round-trips.
- [ ] Round-trip fixtures for `varchar(n)`, `char(n)` and `bit(n)` narrowing pass.
- [ ] The migration records which differ and version generated it, unchanged.

**Out of scope:**
- The draft's "could fail or lose data" warning on widening casts (19's warning part, a separate ticket).
- Numeric rounding (unaffected by `USING`).

**Why not delegated:** ADR-0003 wraps pg-delta and doesn't rewrite its output. Choosing between post-processing its statements and changing it upstream is an architecture call.

**Decision needed:**
1. **(Recommended)** Post-process in our pg-delta differ: drop `USING <col>::<newtype>` when an assignment or implicit cast exists, checked against `pg_cast` on the rehearsal server. Record it in ADR-0003 and the pg-delta research §8 "Known behaviours". Rehearsal verification still guards the result.
2. Fix upstream in pg-delta and pin the new version. Cleaner, but blocked on an alpha project's release.
3. Refuse narrowing type changes in the generated schema change unless the pre-migration script converts the column first.

The needless `ALTER COLUMN ... DROP DEFAULT` that pg-delta emits before a type change on a column with no default (from 19) belongs to the same decision: post-process it away under option 1, or ask upstream under option 2.
