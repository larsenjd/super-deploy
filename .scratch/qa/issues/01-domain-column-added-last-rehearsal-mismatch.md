# 01: A column typed with a domain is added last, so a comment on it makes every rehearsal fail with "run draft again"

**Status:** resolved
**Category:** bug
**Severity:** high
**Area:** newproj

## What I did
Fresh project (`node .../dist/cli.js init`, `git init`, `pnpm install`), then:

`data-model/desired-schema/types.sql`:
```sql
create domain email_address as text
  constraint email_address_check check (value ~ '^[^@\s]+@[^@\s]+$');
```

`data-model/desired-schema/tables/customers.sql`:
```sql
create table customers (
  id bigint generated always as identity primary key,
  email email_address not null constraint customers_email_key unique,
  full_name text not null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
comment on column customers.email is 'Login e-mail';
```

```sh
pnpm exec super-deploy draft --name "initial schema"
pnpm exec super-deploy rehearse
pnpm exec super-deploy draft     # as the error says
pnpm exec super-deploy rehearse
```

## Expected
The generated schema change creates `customers` with `email` as its second
column (or at least produces something that rehearses), and `rehearse` passes.

## Actual
`schema-change.sql` creates the table without `email`, then the domain, then
adds the column at the end:
```
CREATE TABLE "public"."customers" ("id" bigint GENERATED ALWAYS AS IDENTITY NOT NULL, "full_name" text NOT NULL, "created_at" ..., "updated_at" ..., CONSTRAINT "customers_pkey" PRIMARY KEY (id));
CREATE DOMAIN "public"."email_address" AS text CONSTRAINT "email_address_check" ...;
ALTER TABLE "public"."customers" ADD COLUMN "email" public.email_address NOT NULL;
```
Rehearsal then fails, every time, however often `draft` is re-run:
```
Error: The rehearsal does not match the desired schema; run draft again. First difference: catalog: - comment: pg_class customers sub=5 Login e-mail (and 1 more)
```
- Renaming `types.sql` so it sorts first (`a-types.sql`) changes nothing.
- Removing the column comment makes `rehearse` pass, but the table is then
  deployed with `email` as column 5 instead of 2. The rehearsal doesn't notice
  the different column order, so `select *` / positional `insert` on a target
  disagree with the desired schema.

## Notes
- The advice "run draft again" can't help here: the draft is regenerated
  identically. The user is stuck, with nothing telling them why.
- "pg_class customers sub=5" is catalog jargon; a user would need "comment on
  column customers.email: attribute number 5 vs 2" or similar to understand it.
- Guess: the differ creates tables before the types they use, then adds the
  columns that depend on those types afterwards. Probably also affects
  composite-type and enum columns.
- Workaround I used: put domain-typed columns last in the `CREATE TABLE`.

### Triage, 2026-10-20

**Verification:** CONFIRMED on PostgreSQL 18. The problem is wider than the report says.

**Reproduction:**
- The reporter's draft is reproduced exactly: `CREATE TABLE` without `email`, then `CREATE DOMAIN`, then `ADD COLUMN "email"`.
- `rehearse` fails with `catalog: - comment: pg_class customers sub=5 Login e-mail (and 1 more)`, and running `draft` again changes nothing.
- A composite-typed column does the same.

**Wider than reported:**
- Migration 1 has `t(id, b)` with a comment on `b`. Migration 2's desired schema is `t(id, a, b)`. Every later rehearsal then fails, with `- ... sub=2 bee` and `+ ... sub=3 bee`.
- So adding *any* column before a commented column breaks rehearsals for good. Domain columns are just one way to get there.

**Root cause:**
- The catalog comparison writes a column comment's fact with `objsubid`, which is the column's attnum.
- That contradicts its own rule (`verification/catalog.ts` header: "Column order (attnum) is never compared, except for composite types").
- pg-delta's ordering (table, then type, then `ADD COLUMN`) is valid SQL and harmless once the comparison is fixed.

**Corrections:**
- The rehearsal ignoring column order, the reporter's second point, is by design: spec ("Table column order is never a difference"), REFINEMENTS "The differ engine", and the pg-delta prototype research §1.
- Not run, but the same fact feeds drift and `mark`, so a target built in a different column order (for example an adopted one) would show the same false difference.

## Agent Brief

**Category:** bug

**Summary:** The catalog comparison must identify a column comment by the column's name, not its position, so column order never causes a difference.

**Current behavior:**
A comment on a table column is compared together with the column's attribute number. Any change that shifts the column's position makes `rehearse` (and so `finalize`) fail permanently with "The rehearsal does not match the desired schema; run draft again", and re-drafting can't fix it. Ways to shift it include:
- adding a column before it;
- a domain- or composite-typed column, which the differ adds at the end.

The message shows catalog notation (`pg_class customers sub=5`).

**Desired behavior:**
- A column comment's fact names the table and column (`comment on column customers.email`), not the attnum.
- Comments on the same column with different text are still a difference.
- Composite type attributes keep comparing position, as they do through their own position fact. Comments on composite type attributes may still use position.
- Rehearsals, drift and `mark` all share this comparison, so all three stop reporting false differences.

**Key interfaces:**
- `catalogFacts` / `catalogDifferences` in the verification module: the comment fact's key and text for `pg_class` objects with a non-zero `objsubid`.

**Acceptance criteria:**
- [x] The report's schema (domain-typed column with a comment) drafts and `rehearse` passes. API seam.
- [x] Migration 1 has `t(id, b)` with a comment on `b`; migration 2 has desired schema `t(id, a, b)` with the same comment. Drafting migration 2 then rehearses and finalizes.
- [x] Changing a column comment's text is still caught by `rehearse` and by drift.
- [x] A target whose commented column sits at a different attnum from the replica shows no drift.
- [x] Composite type attribute reordering is still caught (the existing ticket-27 tests pass).

**Out of scope:**
- Making the differ create domain or composite columns in place. Column order is not a difference by design.
- Rewording the generic "run draft again" message (17) and showing every difference instead of "(and 1 more)" (02).

### Resolved, 2026-10-20 (6103dc5)

- The comment fact for a table column now names the column (`comment: pg_class customers.email Login e-mail`), not its attnum. Comments on whole objects drop the always-zero `sub=0`.
- Composite type attributes compare their position through their own column fact, as before. Their comments also use the name.
- Tests: `rehearse.test.ts` covers the report's domain-column case, `t(id, b)` → `t(id, a, b)` through `finalize`, and a changed comment text. `drift.test.ts` covers a commented column at another attnum (no drift) and a changed comment text (drift).
