# 106: finalize and discard-draft at the same time leave a finalized migration with no schema-change.sql, and validate accepts it

**Status:** ready-for-agent
**Category:** bug
**Severity:** medium
**Area:** newproj
**Round:** 2

## What I did
In a project with a draft that adds a column (`draft --name note2`), I ran these two at the same time (for example, in two
terminals, or the menu in one and a script in the other):
```sh
(pnpm exec super-deploy finalize > fa.log 2>&1; echo "exit=$?" >> fa.log) &
(sleep 0.3; pnpm exec super-deploy discard-draft --acknowledge-overwrite > fb.log 2>&1; echo "exit=$?" >> fb.log) &
wait; cat fa.log fb.log
ls data-model/migrations/00003-note2
pnpm exec super-deploy validate
pnpm exec super-deploy deploy --target dev
```
Reproduced twice (00003-note2 and 00004-note3).

Also two `finalize` commands at the same time.

## Expected
The second command waits for the first, or refuses because another command is changing the project. Whatever happens,
no half-written migration. `validate` refuses a migration without `schema-change.sql`.

## Actual
Both report success:
```
Finalized migration 00003-note2 in data-model/migrations/00003-note2
exit=0
Discarded draft note2 (data-model/draft)
exit=0
```
The migration folder holds only `desired-schema/` and `metadata.json`: no `schema-change.sql`. `index.json` lists it with
hashes. Then:
```
$ pnpm exec super-deploy validate
Validated 3 migrations
$ pnpm exec super-deploy deploy --target dev
pg-delta: ALTER TABLE "public"."a" ADD COLUMN "note2" text;
catalog: from the desired schema: column: a.note2 text ...
Error: The deployment rehearsal does not match the desired-schema snapshot of 00003-note2 (2 differences, listed above)
```
With two `finalize` at once, one finalizes and the other fails with a raw error:
```
Error: ENOENT: no such file or directory, open '/tmp/sd-qa2/newproj/colorder/data-model/draft/schema-change.sql'
```

## Notes
- The deployment rehearsal stops the broken migration from reaching a target, which is good. But the pre-commit hook
  (`validate --strict --allow-draft`) would let it be committed, and the user was told both that it was finalized and that
  the draft was discarded.
- The servers are shared between commands under a lease now, but the project's files don't seem to be.
- Recovery: `unfinalize --acknowledge-overwrite`, `draft` again, `finalize` (only because no target had recorded it).

### Triage, 2026-10-21

**Verification:** CONFIRMED with the built CLI.
- I ran `finalize` and, 0.3 s later, `discard-draft --acknowledge-overwrite`. Both exit 0. `00002-addb` holds only `desired-schema/` and `metadata.json`, and `validate` and `validate --strict` both pass with "Validated 2 migrations".
- Two `finalize` at once: one succeeds. The other fails with a raw `ENOTEMPTY: directory not empty, rename '…/.finalizing-00003-addc' -> '…/00003-addc'` (the reporter got `ENOENT`; which one depends on timing). It leaves a read-only `.finalizing-00003-addc` behind, which `validate` then reports.

**Root cause:**
- `finalize` rehearses the draft, then reads the draft's files from disk again to freeze them (`readHashedFiles(root, paths.draft, …)` in `commands/finalize.ts`). Whatever another command deleted or changed in between is what gets hashed and frozen. A missing draft folder reads as no files.
- Nothing requires a migration to contain `schema-change.sql`: the integrity check (`store/integrity.ts`) compares hashes and folder names only. So `validate` and the pre-commit hook accept the broken migration. Only the deployment rehearsal stops it.
- Project files have no lock between commands. Servers are shared under a lease (14), files aren't.

## Agent Brief

**Category:** bug
**Summary:** `finalize` freezes exactly the draft it rehearsed, or refuses; a migration without its schema change fails `validate`.

**Current behavior:**
When the draft is discarded, regenerated or finalized by another command while `finalize` runs, `finalize` can:
- write a migration that lacks `schema-change.sql` (or holds files it never rehearsed), and report success;
- fail with a raw `ENOENT`/`ENOTEMPTY` and leave a read-only `.finalizing-*` folder behind.

`validate` accepts a migration with no `schema-change.sql`.

**Desired behavior:**
- `finalize` freezes the files it rehearsed. Just before writing the migration, it checks that the draft on disk still holds the same files with the same contents. If not (gone, changed, or already finalized), it refuses with a typed error: the draft changed while `finalize` was running, nothing was finalized, run it again. Nothing is written.
- If writing or renaming the new folder fails anyway (e.g. the folder now exists), `finalize` removes its staging folder and refuses with a typed error naming the migration folder, never a raw file-system error.
- `validate` (and so the hook) reports a migration folder without `schema-change.sql` as an error. Every finalized migration has one, even an empty schema change (header only); a Recovery folder never does (it runs its migration's).

**Key interfaces:**
- `finalize` and the files it hashes (`readHashedFiles` over the draft).
- The integrity check behind `validate` (`checkMigrations`): a required-file check, with its own finding code.
- A new error exported from the public API, with a stable `code`.

**Acceptance criteria:**
- [ ] API seam: `finalize` whose draft is deleted during its rehearsal (e.g. from a rehearsal adapter that pauses, as the fault-injection helpers do) throws the new error and writes no migration folder and no `index.json` entry.
- [ ] Same with the draft's `schema-change.sql` edited during the rehearsal.
- [ ] Two concurrent `finalize` calls: one succeeds, the other throws a typed error, and no `.finalizing-*` folder remains.
- [ ] API seam: `validate` on a migration folder lacking `schema-change.sql` (index entry rehashed to match) reports an error.
- [ ] Existing finalize and Recovery tests pass.

**Out of scope:**
- A project-wide lock across all commands. If the maintainer wants one, it is a separate ticket.
- `finalize` accepting a hand-edited schema change (108).
