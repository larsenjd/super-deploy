# 29: README doesn't show how to add a real target or choose the managed schema (`postgresTarget`, `managedSchema`)

**Status:** wontfix
**Category:** enhancement
**Severity:** medium
**Duplicate of:** 03
**Area:** adopt

## What I did
Following the README to adopt an existing database whose objects live in schema `app`:

> Add real targets (QA, production) to `super-deploy.config.ts`; keep credentials out of it, for example by reading a connection string from an environment variable.

> To bring a database that already exists under management, add it as a target in `super-deploy.config.ts` ...

The generated `super-deploy.config.ts` only shows `postgres.target("dev")` from `super-deploy/embedded-postgres`.

## Expected
A short example of a real target, for example:

```ts
import { defineConfig, postgresTarget } from "super-deploy";
...
targets: {
  dev: { adapter: postgres.target("dev") },
  production: { adapter: postgresTarget({ connectionString: process.env.PRODUCTION_DATABASE_URL! }) },
},
```

and a mention of the `managedSchema` setting (and its default). The README talks about "the managed schema", uses `app` in examples and mentions `externalSchemas`, but never says how to pick the managed schema.

## Actual
None of `postgresTarget`, `ConnectionSource` or `managedSchema` appears in the README or `--help`. I found them by listing the module's exports (`node -e "import('super-deploy').then(m => console.log(Object.keys(m)))"`) and by making `tsc` print type errors. That's how I learnt the config keys `directory, externalSchemas, historySchema, managedSchema, ...` and the target keys `adapter, lockTimeout, statementTimeout`.

## Notes
- Adoption depends on `managedSchema` being right. Getting it wrong leads to issue 24.
- `lockTimeout`, `statementTimeout` and `historySchema` are also undocumented.
