# 25: Adoption reports external-schema references one at a time, citing files it never wrote

**Status:** ready-for-agent
**Category:** bug
**Severity:** medium
**Area:** adopt

## What I did
```sql
-- as postgres in qa_adopt_ext
grant connect, create on database qa_adopt_ext to adopt_deployer;
create schema auth;
create table auth.users (id bigint primary key, name text);
grant usage on schema auth to adopt_deployer;
grant select, references on auth.users to adopt_deployer;
set role adopt_deployer;
create schema app;
create table app.profiles (user_id bigint primary key references auth.users(id), bio text);
create view app.profile_names as select p.user_id, u.name from app.profiles p join auth.users u on u.id = p.user_id;
create function app.user_name(uid bigint) returns text language sql stable as $$ select name from auth.users where id = uid $$;
```

Config: `managedSchema: "app"`, `externalSchemas: ["auth"]`, target `ext` from `EXT_DATABASE_URL`.

```sh
pnpm exec super-deploy init --adopt ext </dev/null
```

## Expected
The README says that when a database holds anything super-deploy doesn't support, "nothing is written and every such object is listed". So: one refusal listing the foreign key, the view and the SQL function, each by object name.

## Actual
Each run reports only the first problem, and points at a file and line that don't exist (nothing was written; `data-model/desired-schema/` holds only `.gitkeep`):

```
Error: data-model/desired-schema/routines.sql:8: PostgreSQL refused the desired schema: relation "auth.users" does not exist. Hint: this statement references external schema "auth", which rehearsals don't contain. Only PL/pgSQL bodies may reference external schemas: views, defaults, foreign keys, triggers, LANGUAGE sql and BEGIN ATOMIC bodies, and PL/pgSQL variable declarations bind their references at CREATE
```

After dropping the function:

```
Error: data-model/desired-schema/views.sql:7: PostgreSQL refused the desired schema: relation "auth.users" does not exist. Hint: ...
```

After dropping the view:

```
Error: data-model/desired-schema/tables.sql:6: PostgreSQL refused the desired schema: schema "auth" does not exist. Hint: ...
```

It took three runs, and three changes to the target, to find all three.

## Notes
The hint text itself is good. The fix is to name the object (`view app.profile_names`, `function app.user_name(bigint)`, `foreign key profiles_user_id_fkey on app.profiles`) instead of a non-existent file, and to collect all of them in one refusal like the other unsupported objects.

### Triage, 2026-10-20

**Verification:** CONFIRMED. With the reporter's setup, adoption threw a `DesiredSchemaLoadError` (`data-model/desired-schema/routines.sql:8: PostgreSQL refused the desired schema: relation "auth.users" does not exist. Hint: ...`) rather than an `AdoptUnsupportedError`, so the CLI's list wasn't printed. Afterwards only `package.json` and the config existed, so the file in the message was never on disk. Root cause: adoption's drift stage loads the generated desired schema into a throwaway database (`loadDesiredSchema`), which throws at the first failing statement. The static check `externalSchemasBoundAtCreate` (`sql-analysis/routine-bodies.ts`, already exported) can find these references without a database, but adoption doesn't run it.

## Agent Brief

**Category:** bug
**Summary:** Adoption reports every external-schema reference bound at CREATE in one refusal, named by object, instead of one at a time against files it never wrote.

**Current behavior:**
When the target's managed schema has views, foreign keys, `LANGUAGE sql` functions, defaults or similar that reference a declared external schema (which rehearsals don't contain), adoption fails on the first one PostgreSQL refuses while loading the generated desired schema. The error cites a desired-schema file and line that was never written, because adoption writes nothing when it refuses. Users need one run, and one change to the target, per offending object.

**Desired behavior:**
- Before loading the generated desired schema, adoption runs the existing static check for external-schema references bound at CREATE time (`externalSchemasBoundAtCreate`) on every generated statement.
- Every hit becomes an entry in the single `AdoptUnsupportedError`, alongside the other unsupported objects. Each entry names the object (e.g. `view app.profile_names`, `function app.user_name(bigint)`, `foreign key profiles_user_id_fkey on app.profiles`) and keeps the existing explanation (only PL/pgSQL bodies may reference external schemas).
- If loading the desired schema still fails during adoption, the failure is reported as an adoption refusal entry naming the object of the failing statement, not as a `DesiredSchemaLoadError` with a file path.
- Nothing is written to the project or the target, as today.

**Key interfaces:**
- `externalSchemasBoundAtCreate` (SQL analysis): reused, unchanged.
- `AdoptUnsupportedError`: gains these entries. Its existing per-object naming (as used for override objects) should name them.
- `DesiredSchemaLoadError` as thrown inside adoption: caught and turned into an adoption entry.

**Acceptance criteria:**
- [ ] Adopting the reporter's database (a foreign key, a view and a `LANGUAGE sql` function, all referencing `auth.users`, with `externalSchemas: ["auth"]`) gives one `AdoptUnsupportedError` listing all three objects by name (API seam).
- [ ] No message produced by that adoption names a file under `data-model/desired-schema/`.
- [ ] A PL/pgSQL function referencing the external schema is not listed (it is allowed).
- [ ] Adopting a database with no such references is unaffected.

**Out of scope:**
- Allowing more kinds of external-schema references.
- The refusal's closing advice; that is issue 35.
