# 132: Without a terminal, functions that only need an override reason are counted as "things V1 doesn't support"

**Status:** resolved
**Category:** bug
**Severity:** low
**Area:** adopt
**Round:** 2

## What I did
`public`-schema database `qa2_adopt_pub` with three PL/pgSQL functions: `count_rows` (uses `EXECUTE`), `notify_event` (calls `pg_notify`), `purge_kind` (both).

```sh
pnpm exec super-deploy init --adopt qa </dev/null
```

## Expected
The same framing as in a terminal, where it says `Target qa has 3 objects that need an override marker:` and asks one reason per object. Without a terminal: "3 objects need an override reason; run adoption in a terminal".

## Actual
```
Target qa has 4 things V1 doesn't support:
  CREATE FUNCTION public.count_rows(tbl text)
    plpgsql-dynamic-sql: EXECUTE (dynamic SQL) is not allowed in PL/pgSQL bodies: ...
  CREATE FUNCTION public.notify_event()
    denylisted-call: pg_notify() is not allowed: ...
  CREATE FUNCTION public.purge_kind(k text)
    plpgsql-dynamic-sql: ...
  CREATE FUNCTION public.purge_kind(k text)
    denylisted-call: ...
Error: Cannot adopt target qa: its managed schema has 4 things V1 doesn't support, listed above. Nothing was written; run adoption in a terminal to give an override reason for each object that breaks only risk rules
```

"4 things V1 doesn't support" is wrong on both counts: these are supported with a marker, and there are 3 objects (the terminal asks 3 questions; `purge_kind` is listed twice here). A reader skimming the first line could conclude these functions have to be rewritten.

## Notes
When the list mixes both kinds (e.g. a `SECURITY DEFINER` function plus a `pg_notify` one), the terminal output handles it well: it lists the unsupported one and adds "Once nothing else is refused, adoption will ask an override reason for 1 object ...: function n()". The non-terminal output could follow the same split.

### Triage, 2026-10-21

**Verification:** CONFIRMED on `qa2t_adopt_pub` (the reporter's three functions).
- `init --adopt qa </dev/null` printed `Target qa has 4 things V1 doesn't support`, with `purge_kind` listed twice (once per rule). The advice was correct: run adoption in a terminal.
- In a pseudo-terminal, the same adoption printed `Target qa has 3 objects that need an override marker:`, with `purge_kind` once under both rules, then asked a reason per object.

**Cause:** without the `overrideReason` callback, adoption's `readTarget` (`commands/adopt.ts`) doesn't compute `overrideCandidates`. The risk-rule violations go into `objects` one per violation, under the "things V1 doesn't support" heading of `AdoptUnsupportedError`. The spec (Q51) says that "without a terminal it refuses them, listing them". The refusal is intended; the framing and count are wrong.

## Agent Brief

**Category:** bug
**Summary:** Without a terminal, adoption lists objects that only need an override reason separately, one per object, and doesn't count them as unsupported.

**Current behavior:**
Risk-only functions are listed as "things V1 doesn't support", once per rule broken, so the count is wrong and the heading suggests they must be rewritten.

**Desired behavior:**
- Without the callback, statements that break only risk rules are grouped per object, as in a terminal (`overrideCandidates`), and kept out of the "things V1 doesn't support" list and count.
- They are listed under their own heading, e.g. `Target qa has 3 objects that need an override reason, asked only in a terminal:`, each with all its rules.
- When nothing else is refused, the `Error:` line says only that, e.g. `Cannot adopt target qa without a terminal: 3 objects need an override reason. Nothing was written; run adoption in a terminal ...`.
- When other things are refused too, both lists appear, as the terminal does today ("Once nothing else is refused, adoption will ask ...").

**Key interfaces:**
- `AdoptUnsupportedError`: `objects` excludes the risk-only objects, and `overridesNeeded` lists them even without the callback. `objects` may be empty when they are all there is. Update its doc comments ("never empty", "empty without the callback").
- `adoptionAdvice`, and the error's `details` and `summary`.

**Acceptance criteria:**
- [ ] API seam, no callback: adopting the reporter's database rejects with `objects` empty, and `overridesNeeded` holding 3 entries, `purge_kind` with both rules.
- [ ] CLI seam (no terminal): the output contains no "doesn't support" heading, names 3 objects, and advises a terminal. Exit 1.
- [ ] With an enum added to the target, the refusal counts 1 unsupported thing and lists the 3 override objects separately.
