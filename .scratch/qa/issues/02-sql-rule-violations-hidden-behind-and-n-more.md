# 02: Desired-schema rule violations are shown one at a time ("and 4 more"), and the naming rule isn't documented

**Status:** resolved
**Category:** enhancement
**Severity:** medium
**Merged:** 36
**Area:** newproj

## What I did
Fresh project. Wrote a desired schema the way most people write SQL, with
inline unnamed constraints:

```sql
-- data-model/desired-schema/types.sql
create domain email_address as text check (value ~ '^[^@\s]+@[^@\s]+$');

-- data-model/desired-schema/tables/customers.sql
create table customers (
  id bigint generated always as identity primary key,
  email email_address not null unique,
  full_name text not null
);

-- data-model/desired-schema/tables/orders.sql
create table orders (
  id bigint generated always as identity primary key,
  customer_id bigint not null references customers (id),
  status text not null default 'new' check (status in ('new', 'paid')),
  total_cents integer not null check (total_cents >= 0)
);
```

```sh
pnpm exec super-deploy draft --name "initial schema"
pnpm exec super-deploy draft --name "initial schema" --debug
```

## Expected
Every violation listed at once (file:line for each), so I can fix them in one
pass. And the README's getting-started step 1 ("Describe the schema you want
as CREATE statements") mentions that constraints must be named.

## Actual
Only the first violation is printed; the rest are a count. `--debug` adds a
stack trace but still hides them:
```
Error: data-model/desired-schema/tables/customers.sql:1: The unique constraint on customers.email has no name; name it (CONSTRAINT <name> ...), because generated names can depend on load order [unnamed-constraint] (and 4 more)
```
I needed four edit/draft rounds to find all five (unique, FK, two checks, domain
check):
```
... customers.sql:1: The unique constraint on customers.email has no name ... (and 4 more)
... orders.sql:1: The foreign key constraint on orders.customer_id has no name ... (and 3 more)
... types.sql:1: The check constraint on domain email_address has no name ... 
```

## Notes
- The line number is always the line of the `CREATE` statement (`:1`), not the
  line of the constraint, which makes it harder to find in a big table.
- The README never says constraints must be named, or lists the other
  `[rule-id]` rules the desired schema must follow. Unnamed primary keys are
  accepted, which is inconsistent with the stated reason ("generated names can
  depend on load order").
- The same "(and 1 more)" truncation appears on rehearsal mismatches
  ("First difference: ... (and 1 more)") with no way to see the rest.

## Agent Brief

**Category:** enhancement
**Summary:** Report every desired-schema rule violation, and every rehearsal difference, instead of the first plus "(and N more)".

**Current behavior:**
`SqlRuleViolationError` carries every violation, but its message names only the first and ends "(and N more)". The CLI prints only the message, and `--debug` adds stack traces but not the rest. Each violation's line is the line of the `CREATE` statement it is in, even when the problem is a constraint further down. A rehearsal that doesn't match the desired schema behaves the same way: "First difference: ... (and 1 more)", and the remaining differences are never shown.

**Desired behavior:**
- When `draft`, `validate`, `rehearse`, `finalize` or adoption refuses on rule violations, the CLI prints one line per violation, each as `<file>:<line>: <message> [<rule-id>]`, followed by a summary error line. The CLI already prints drift this way.
- Where the parser gives a location for the offending node (for example an unnamed constraint), that violation's line is the node's line, not the statement's.
- A rehearsal mismatch lists every difference, one per line, in the same way.
- The programmatic API keeps the structured lists (`violations`, differences) on the errors.

**Key interfaces:**
- `SqlRuleViolationError`: its `violations` already holds them all. The CLI's error rendering needs to print them, the same way it prints listed drift.
- The violation type produced by the reference/statement analysis (`statementFacts` and the checks behind `checkRules`) should carry an optional location. Its line is worked out from the parser's node `location`.
- The rehearsal's same-structure check (`requireSameStructure`) and its error: expose all differences and print them all.

**Acceptance criteria:**
- [ ] At the CLI seam, `draft` on the reporter's schema (unnamed unique, foreign key, two checks and a domain check) prints all five violations, with no "(and N more)", and exits 1.
- [ ] An unnamed constraint on line 3 of a `CREATE TABLE` that starts on line 1 is reported at line 3 (API seam or SQL-analysis unit test).
- [ ] A rehearsal mismatch with two differences prints both.
- [ ] The error's one-line message stays usable on its own for API callers: the first violation plus a count is fine, as long as the CLI prints the full list.

**Out of scope:**
- The wording of "run draft again" on rehearsal mismatches (issue 17).
- Changing which constraints must be named.
- README documentation of the rules (issue 18).
