# 42: Connection refused on `localhost` gives an empty reason: "failed to connect: "

**Status:** ready-for-agent
**Category:** bug
**Severity:** medium
**Area:** fail

## What I did
A target whose server is down (nothing listens on port 54899):

```ts
down: { adapter: postgresTarget({ env: "FAIL_DOWN_URL" }) },
```
```sh
export FAIL_DOWN_URL=postgres://fail_deployer:dep@localhost:54899/qa_fail_down
pnpm exec super-deploy status --target down
pnpm exec super-deploy deploy --target down
```

## Expected
Something like `failed to connect to localhost:54899: connection refused (is the server running?)`.

## Actual
```
Error: The deployment adapter of target down failed to connect: 
```
(the message ends after the colon) with exit 1, for both commands. The interactive menu shows the same empty message. With `--debug`:
```
Caused by:
AggregateError [ECONNREFUSED]: 
    at internalConnectMultiple (node:net:1430:18)
```
With `127.0.0.1` instead of `localhost` the reason is there: `connect ECONNREFUSED 127.0.0.1:54899`.

## Notes
`localhost` resolves to both `::1` and `127.0.0.1`. Node then raises an `AggregateError` with an empty `message`, and its per-address errors are in `.errors`. "Server down" is probably the most common connection failure, and `localhost` the most common host.

### Triage, 2026-10-20

**Verification:** CONFIRMED. `postgres://u:p@localhost:1/x` gives `...failed to connect: ` (empty), while `127.0.0.1:1` gives `connect ECONNREFUSED 127.0.0.1:1`. `--debug` shows `AggregateError [ECONNREFUSED]:` with an empty message. Root cause: the adapter-call error wrapper (`adapterCall` in `rehearsal/throwaway.ts`) and the attempt log's `errorMessage` (`deploy/attempts.ts`) both use only `error.message`. Node's `AggregateError` for a multi-address connect has an empty message, and its per-address errors are in `.errors`.

## Agent Brief

**Category:** bug
**Summary:** A connection error from a host with several addresses (e.g. `localhost`) shows the per-address reasons instead of an empty message.

**Current behavior:**
When a target's server is down and its host resolves to several addresses (`localhost` gives `::1` and `127.0.0.1`), Node raises an `AggregateError` with an empty `message`. The CLI prints `The deployment adapter of target down failed to connect: ` with nothing after the colon. The attempt log records the same empty reason.

**Desired behavior:**
- When describing an error from an adapter call, and when recording an attempt's failure reason, an `AggregateError` is described by its inner errors' messages, deduplicated and joined (e.g. `connect ECONNREFUSED ::1:54899; connect ECONNREFUSED 127.0.0.1:54899`).
- If an error (aggregate or not) has an empty message, fall back to its `code` (e.g. `ECONNREFUSED`), so the reason is never empty.
- Errors with a message are described as today.

**Key interfaces:**
- The shared helper that turns a thrown value into a message for adapter-call errors, and the attempt log's error-message helper. Ideally one helper used by both.

**Acceptance criteria:**
- [ ] `status` against `postgres://u:p@localhost:<closed port>/x` gives an error message containing `ECONNREFUSED` and the port (API or CLI seam).
- [ ] The attempt recorded for a failed command never has an empty reason when the cause is an `AggregateError` (unit test of the helper with a synthetic `AggregateError` is enough).
- [ ] An ordinary connection error (e.g. wrong password) is described exactly as today.

**Out of scope:**
- Connect timeouts; that is issue 43.
- Rewording connection errors beyond filling in the reason.
