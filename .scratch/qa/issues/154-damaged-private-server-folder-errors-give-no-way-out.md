### Triage, 2026-10-21

**Verification:** CONFIRMED, both cases, on my own copy of the project.
- A `postmaster.pid` in `.super-deploy/rehearsal` naming a live `sleep` and port 40000: `status --target qa` failed with `Embedded PostgreSQL in …/.super-deploy/rehearsal does not accept connections: connect ECONNREFUSED 127.0.0.1:40000`. Deleting the pid file fixed it.
- `PG_VERSION` moved out of `.super-deploy/dev`: `Embedded PostgreSQL failed to initialise …/.super-deploy/dev`; `--debug` shows `ENOTEMPTY … rename '…/dev.initdb-…' -> '…/dev'`. Putting it back fixed it; nothing else was touched.

**Root cause:**
- `runningPort` (embedded server) trusts `postmaster.pid` when its pid is alive, without checking that the process is that folder's postmaster. The client then retries the recorded port for up to 30 s (ECONNREFUSED counts as "starting up") before failing.
- `initialise` decides a folder is uninitialised from `PG_VERSION` alone, runs `initdb` beside it, and the rename fails on the non-empty folder. The message doesn't say the folder exists but looks damaged.
- The README says `.super-deploy` is private and that `dev` can be rebuilt, but not that `.super-deploy/rehearsal` can always be deleted safely when no command runs.

## Agent Brief

**Category:** enhancement
**Summary:** When a private embedded server's folder is stale or damaged, the error names the folder, says what looks wrong, and says how to recover.

**Current behavior:**
- A `postmaster.pid` whose pid now belongs to an unrelated process (after a reboot or crash) makes every command that needs that server wait, then fail with `does not accept connections: connect ECONNREFUSED 127.0.0.1:<port>`.
- A non-empty data folder missing `PG_VERSION` fails with `failed to initialise <folder>`, the reason only under `--debug`.
- Neither says what to do.

**Desired behavior:**
- Stale pid file: when nothing accepts connections on the port `postmaster.pid` records, the error says so, e.g. `.super-deploy/rehearsal/postmaster.pid names process 1234 and port 40000, but no server answers there: if no super-deploy command is running, delete that file and try again`.
- Damaged folder: a non-empty data folder without `PG_VERSION` is refused before `initdb` runs, saying it isn't a complete PostgreSQL data folder.
- Both messages give the way out for that folder. For the rehearsal server: with no command running, delete the folder; nothing is lost. For `dev`: delete it and run `deploy --target dev` again, losing whatever was added by hand.
- Nothing is deleted automatically.
- The README's "Connecting to dev" (or the configuration section) says the rehearsal folder can be deleted whenever no command is running.

**Key interfaces:**
- The embedded server's start/attach path: `runningPort`, the wait for connections, and `initialise`. `postmaster.pid`'s status line (`starting`, `ready`) can tell a server still starting from a stale file.
- `AdapterError` messages, with project-relative folder paths where the project is known.
- The template README.

**Acceptance criteria:**
- [ ] API seam: a data dir whose `postmaster.pid` names a live non-postgres process (the test's own pid, or a child it spawns) fails with a message naming the pid file and the recovery step, within a few seconds.
- [ ] A non-empty data dir without `PG_VERSION` fails with a message naming the folder and the recovery step, and its contents are untouched.
- [ ] Normal starts, attaches and concurrent commands behave as before (existing embedded-server tests pass).
- [ ] The README says the rehearsal folder can be deleted.

**Out of scope:**
- Repairing or deleting folders automatically.
- Servers left running after a signal (141).
