# 174: A failed deploy-draft doesn't say the target was rolled back, unlike deploy and rebuild

**Status:** resolved
**Category:** enhancement
**Severity:** low
**Area:** disp
**Round:** 2

## What I did
Project (`managedSchema` `public`) with `00001-items`. A disposable target `qa` at migration 1, with one row in `items`.
```sh
# desired schema: add "code text not null" to items
pnpm exec super-deploy draft --name "item code"
pnpm exec super-deploy deploy-draft --target qa      # YES
```
For comparison, the same change finalized and deployed to another database at migration 1 with one row:
```sh
pnpm exec super-deploy finalize
pnpm exec super-deploy deploy --target qa
```

## Expected
deploy-draft's error says what state the target is in and what to do next, as `deploy` and `rebuild` do.

## Actual
deploy-draft:
```
Error: data-model/draft/schema-change.sql:4: PostgreSQL refused it: column "code" of relation "items" contains null values.
```
deploy:
```
Error: data-model/migrations/00002-item-code/schema-change.sql:4: PostgreSQL refused it: column "code" of relation "items" contains null values. The deployment rolled back: target qa is unchanged, still at migration 00001-items. Next: super-deploy recovery --migration 2, with seed data that reproduces the problem rows in the rehearsal.
```
rebuild (lock timeout): `... The rebuild rolled back: target qa is unchanged`.

## Notes
The target was in fact unchanged (status shows no deployed draft, and `deploy-draft failed` in the attempts). Something like "The deploy-draft rolled back: target qa is unchanged, still at 00001-items. Fix the draft's scripts (or its seed data) and run deploy-draft again" would fit. The same applies when `--with-seed` clashes with existing rows (`seed-data.sql:1: PostgreSQL refused it: duplicate key value ...`).

## Agent Brief

**Category:** enhancement
**Summary:** When a file fails during `deploy-draft` (or during `rebuild`'s replay), the error says the command rolled back, what state the target is still in, and what to do next.

**Current behavior:**
A failing draft file gives only `<file>:<line>: PostgreSQL refused it: <message>` (with DETAIL and HINT). `deploy` says "The deployment rolled back: target qa is unchanged, still at migration ..." and gives a next step.

**Desired behavior:**
- `deploy-draft`: the error adds e.g. `The deploy-draft rolled back: target qa is unchanged, still at migration 00005-add-tags (no draft deployed).` For a data error (SQLSTATE classes 22 and 23), the next step is to fix the draft's scripts (or its seed data, when loaded with `--with-seed`) and run `deploy-draft` again. It never suggests `recovery`: the draft isn't finalized.
- `rebuild`: a migration file failing during the replay adds `The rebuild rolled back: target qa is unchanged.` (the wording `WipeDropFailedError` uses), with no `recovery` suggestion.
- The lock and statement timeout next steps stay as they are for all three.
- `deploy`'s message is unchanged.

**Key interfaces:**
- `SqlFileFailedError` and its rollback payload (`DeploymentRollback`, `rolledBack()`): today the wording is fixed to "deployment" and the next step to `recovery --migration N`. Let the payload name the command and choose its next step.
- `deployDraft`'s and `rebuild`'s guarded `run`.

**Acceptance criteria:**
- [ ] Pseudo-terminal: a draft whose schema change fails on existing rows makes `deploy-draft` exit 1 with a message saying it rolled back, naming the migration the target is still at, and suggesting fixing the draft, not `recovery`.
- [ ] The same with `--with-seed` when the seed data clashes with existing rows.
- [ ] `deploy`'s failure message is unchanged (its existing tests pass).

**Out of scope:**
- Interrupted commands not saying the target is unchanged (110).
- Lock-timeout messages naming the blocking session (146) or the configured value (145).
