# 104: Changing the type of a column a generated column uses: draft succeeds, but its schema change can never run

**Status:** ready-for-human
**Category:** bug
**Severity:** medium
**Area:** newproj
**Round:** 2

## What I did
Fresh project, migration 1 finalized:
```sql
create table a (
  id bigint generated always as identity primary key,
  price numeric(10,2) not null,
  qty integer not null,
  total numeric generated always as (price * qty) stored
);
```
Desired schema changed to `price numeric(6,2) not null,` (or `qty smallint not null`), then:
```sh
pnpm exec super-deploy draft --name narrow2
pnpm exec super-deploy rehearse
```
(no seed data, no scripts)

## Expected
`draft` produces a schema change that runs (for example dropping the generated expression, changing the type, and
setting it again), or refuses and says what to do in the pre-migration script.

## Actual
```
Regenerated draft narrow2: 6 statements in data-model/draft/schema-change.sql
warning: Column a.price changes type by a plain cast (no non-null values in the rehearsal data): convert it in the pre-migration script if the cast could fail or lose data
...
exit 0
```
```
ALTER TABLE "public"."a" ALTER COLUMN "price" DROP DEFAULT;
ALTER TABLE "public"."a" ALTER COLUMN "price" TYPE numeric(6,2) USING "price"::numeric(6,2);
```
`rehearse`:
```
Error: data-model/draft/schema-change.sql:10: PostgreSQL refused it: cannot alter type of a column used by a generated column. Detail: Column "price" is used by generated column "total".
```

## Notes
- The failure doesn't depend on data, so `draft` could notice it: it rehearses enough to count "values in the rehearsal
  data", yet reports success for a schema change that can't run.
- Neither the error nor the README says how to get past it.

### Triage, 2026-10-21

**Verification:** CONFIRMED with the built CLI.
- Migration 1 has `a (price numeric(10,2), qty, total … generated always as (price * qty) stored)`. Changing it to `price numeric(6,2)` drafts `ALTER COLUMN price DROP DEFAULT; ALTER COLUMN price TYPE numeric(6,2) USING …`, exits 0, and warns only "changes type by a plain cast".
- `rehearse` fails: `schema-change.sql:6: PostgreSQL refused it: cannot alter type of a column used by a generated column`. No data is involved.
- Workaround that rehearses: in `pre-migration.sql`, `alter table a drop column total; alter table a alter column price type numeric(6,2); alter table a add column total numeric generated always as (price * qty) stored;`. `draft` then generates nothing. `finalize` asks to acknowledge the drop and the type change, which is correct.

**Root cause:**
- pg-delta's column type change (`plan/rules/tables.ts`, `type.alter`) never touches the generated columns that depend on the column, and PostgreSQL refuses the change while they exist.
- `draft` never runs what it generates (see 102), so a statement that can never succeed is only found by `rehearse`.
- Neither the error nor the README says how to get past it.

**Aside:** `numeric(10,2)` → `numeric(6,2)` (smaller precision, same scale) isn't classed as a narrowing, so it gets the generic "plain cast" warning. Values over 9999.99 make the deployment fail, and neither message says so (see 111).

## Brief (ready-for-human)

**Category:** bug
**Summary:** Changing the type of a column a generated column uses either generates a schema change that runs, or `draft` and the rehearsal say what to put in the pre-migration script.

**Current behavior:**
`draft` writes `ALTER COLUMN … TYPE` for the column and exits 0. Every rehearsal fails with PostgreSQL's "cannot alter type of a column used by a generated column", and nothing says what to do.

**Desired behavior (once decided):**
- Option 1: the schema change stays as pg-delta generates it.
  - With 102's option 1, `draft` warns right away with PostgreSQL's refusal.
  - When a type change hits a column that stored generated columns use, the warning (and the rehearsal's error for this refusal) says to drop the generated column, change the type, and add the generated column again, in the pre-migration script.
  - The README's pre-migration recipes show it.
- Option 2: our differ (or a patched pg-delta) wraps the type change itself: drop the dependent generated columns, change the type, add them back. That is destructive by our rules and moves the columns to the end (101).

**Key interfaces:**
- `draft`'s findings (102's decision).
- `SqlFileFailedError`'s next step for this refusal. It is a SQLSTATE/message pattern, like the lock and data hints from 46.
- The `Differ` seam, for option 2.

**Acceptance criteria (once decided):**
- [ ] API seam: the report's change (`price numeric(10,2)` → `numeric(6,2)` with `total` generated from it) gives the decided result. Under option 1, a draft warning (if 102 option 1) and a rehearsal error naming the pre-migration fix. Under option 2, a schema change that rehearses.
- [ ] The workaround above, documented in the README, rehearses and deploys with `total` recomputed.
- [ ] A type change of a column no generated column uses is unchanged.

**Out of scope:**
- `draft` running its schema change in general (102).
- Changing a generated column's own expression (103).
- Narrowing classification of numeric precision (aside above; 111).

**Why not delegated:** option 2 changes the generated output (the decision on 09 kept pg-delta's). Option 1 depends on 102's decision.

**Decision needed:**
1. **(recommended)** Keep the generated output. Detect it at `draft` (with 102's option 1). Name the pre-migration fix in the warning and in the rehearsal error, and add it to the README.
2. Generate the drop / retype / re-add sequence in our differ, or in a patched pg-delta (with 101's option 1).
