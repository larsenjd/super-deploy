# 150: When the deploy's client stops responding, its session stays "idle in transaction" holding table locks, with no timeout

**Status:** resolved
**Category:** bug
**Severity:** medium
**Area:** fail
**Round:** 2

## What I did
To simulate a client whose network or machine goes away mid-deploy, I put a TCP proxy (`node proxy.mjs 54830 54818`, a plain `net` pipe) between the CLI and the shared server and froze it with SIGSTOP partway through a deploy:

```sh
export QA_DATABASE_URL=postgres://qa2_fail_deployer:dep@127.0.0.1:54830/qa2_fail_main
node hold.mjs qa2_fail_main 10 "lock table app.t2 in share mode" &    # makes the deploy wait
pnpm exec super-deploy deploy --target qa &                           # pending: COMMENT ON TABLE t2 …
sleep 4; kill -STOP <proxy pid>
# the holder releases at 10 s; then, directly against the server:
pnpm exec super-deploy status --target qa
select pid, state, now()-state_change from pg_stat_activity where usename='qa2_fail_deployer';
select l.mode, c.relname from pg_locks l left join pg_class c on c.oid=l.relation where l.pid=<deploy pid>;
```

## Expected
README, "Targets": "If the CLI dies during a deployment (killed, or its machine lost), the server rolls the deployment back once it notices the connection is gone. super-deploy has the server check every 5 seconds while a statement runs". I expected the deployment to roll back and the locks to be released within seconds, or at least within a bound super-deploy sets.

## Actual
Once the lock came free, the server ran the `COMMENT ON` statement and then sat idle in the open transaction. Three minutes later it still held its locks:
```
Locked by attempt #34 (deploy by jonathanl, …, server process 2580499, idle in transaction, last statement started 2026-10-21T15:47:56.745Z: COMMENT ON TABLE "app"."t2" IS 't2b')
[{"pid":2580499,"state":"idle in transaction","idle_for":{"minutes":2,"seconds":48}}]
[{"mode":"ShareUpdateExclusiveLock","relname":"t2"}, …]
```
`idle_in_transaction_session_timeout` is 0, and the 5-second `client_connection_check_interval` doesn't apply, because no statement is running. It ended only when I ran the suggested `pg_terminate_backend`.

## Notes
- With a migration that does `ALTER TABLE`, the orphaned session would hold ACCESS EXCLUSIVE on the table, blocking every application read and write of it until someone notices.
- My simulation keeps the TCP connection alive at the kernel level, so it is closer to a hung client than to a lost machine. For a truly lost machine the server finds out only through TCP keepalives. On this host that is `tcp_keepalives_idle` 120 + 9 × 75 s ≈ 13 min; the usual Linux default is about 2 h 11 min. Either way that is far from "every 5 seconds". Guess: the 5-second check only helps when the socket is closed (CLI killed, so the OS sends FIN/RST), and only while a statement is running.
- Possible fixes: set `idle_in_transaction_session_timeout` (and TCP keepalive settings) on the deploy session, and reword the README so it doesn't promise a fast rollback for a lost machine.

### Triage, 2026-10-21

**Verification:** CONFIRMED with the reporter's frozen-proxy setup on my own target. 20 s after the holder released its lock, the deploy's session was `idle in transaction` after running `COMMENT ON TABLE "app"."t2" IS 'g6'`, holding ShareUpdateExclusiveLock on `t2` and RowExclusiveLock on `pg_description`. The server has `idle_in_transaction_session_timeout` 0 and `tcp_keepalives_idle` 120 s, interval 75 s, count 9. It ended only on `pg_terminate_backend`. Resuming the proxy then gave 142's "deferred constraints … not queryable" error.

**Root cause:** target sessions set only `client_connection_check_interval` (5 s; `deploy/target.ts`), which PostgreSQL applies only while a statement runs. Between statements, the server finds out the client is gone only from TCP keepalives, or never if the connection stays up (a hung client). The README's "Targets" paragraph promises more than that.

**Checked:** no target transaction stays open while the CLI does slow work of its own. The YES prompt comes before `withLockedTarget`, the drift check's `BEGIN READ ONLY` is one short read, and rehearsals run on throwaway databases while the target session holds only its session-level advisory lock (idle, not in a transaction). So a timeout of the order of a minute on idle transactions doesn't cut a healthy command short. The test suite should confirm it.

## Agent Brief

**Category:** bug
**Summary:** A target session whose client stops responding mid-transaction is ended by the server within about a minute, and the README says what it really guarantees.

**Current behavior:**
If the CLI hangs, or its machine or network disappears, between two statements of a deploy transaction, the server keeps the transaction open, holding its table locks (ACCESS EXCLUSIVE for most `ALTER TABLE`s) and the target lock, until someone runs `pg_terminate_backend`, or for a vanished machine until TCP keepalives give up (13 min on the test host, about 2 h 11 min with Linux defaults). The README says the server checks every 5 seconds.

**Desired behavior:**
- Every target session sets `idle_in_transaction_session_timeout` (1 minute), so a transaction left idle by a hung or vanished client rolls back and releases its locks.
- Every target session sets the server-side TCP keepalives (`tcp_keepalives_idle` 30 s, `tcp_keepalives_interval` 10 s, `tcp_keepalives_count` 3, all user-settable), so a vanished client's connection is detected in about a minute even while idle outside a transaction. Unix-socket connections ignore them.
- A server that refuses one of these settings runs without it, as for `client_connection_check_interval` today.
- The README's "Targets" paragraph says: a statement whose client is gone is ended within seconds; a session left idle in its transaction is ended after a minute; a vanished machine is detected within about a minute.

**Key interfaces:**
- The per-session setup that sets `client_connection_check_interval` for every target session.
- The template README's "Targets" paragraph on a CLI that dies.

**Acceptance criteria:**
- [ ] API seam: a fault-injection adapter that stops sending statements (hangs) after a statement inside the deploy transaction leaves a session that the server ends within about the timeout; a test session can then take the locks. Use a shorter timeout in the test, if the value is injectable, rather than waiting a minute.
- [ ] `SHOW idle_in_transaction_session_timeout` and `SHOW tcp_keepalives_idle` on a target session (e.g. through a wrapper adapter) give the set values.
- [ ] The full suite passes: no command keeps a target transaction idle for longer than the timeout.
- [ ] The README paragraph matches the behaviour.

**Out of scope:**
- Making the timeouts configurable.
- How the CLI reports the lost session when it comes back (142).
- `idle_session_timeout`, which would end the session-level target lock during a long rehearsal.
