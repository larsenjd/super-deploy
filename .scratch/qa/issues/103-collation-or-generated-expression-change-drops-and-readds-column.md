# 103: Changing a column's collation or a generated column's expression drops and re-adds the column

**Status:** resolved
**Category:** bug
**Severity:** medium
**Area:** newproj
**Round:** 2

## What I did
**Collation.** Deployed migrations have `customers.nickname text` (with an index `customers_nick_idx` on it). In the desired
schema I changed it to `nickname text collate "C",` and added seed data:
```sql
-- data-model/draft/seed-data.sql
insert into customers (email, display_name, nickname) values ('n@x.y','N','nick');
```
```sh
pnpm exec super-deploy draft --name "misc attrs"
```

**Generated expression.** Fresh project, migration 1:
```sql
create table a (
  id bigint generated always as identity primary key,
  price numeric(10,2) not null,
  qty integer not null,
  total numeric generated always as (price * qty) stored
);
```
then in the desired schema `total numeric generated always as (price * qty * 1.2) stored`, and `draft --name changes`.

## Expected
`ALTER TABLE customers ALTER COLUMN nickname TYPE text COLLATE "C"` (keeps the data and the column's position), and
`ALTER TABLE a ALTER COLUMN total SET EXPRESSION AS (...)` (PostgreSQL 17+). Neither is destructive.

## Actual
Collation:
```
warning: Column customers.nickname is dropped with its data (1 non-null value in the rehearsal data): rename it, or copy what you need, in the pre-migration script

DROP INDEX "public"."customers_nick_idx";
ALTER TABLE "public"."customers" DROP COLUMN "nickname";
ALTER TABLE "public"."customers" ADD COLUMN "nickname" text COLLATE pg_catalog."C";
CREATE INDEX customers_nick_idx ON public.customers USING btree (nickname);
```
`rehearse` then lists `ALTER TABLE public.customers DROP COLUMN nickname drops the column and its data` as destructive.

Generated column:
```
warning: Column a.total is dropped with its data (no non-null values in the rehearsal data): rename it, or copy what you need, in the pre-migration script
ALTER TABLE "public"."a" DROP COLUMN "total";
ALTER TABLE "public"."a" ADD COLUMN "total" numeric GENERATED ALWAYS AS (((price * (qty)::numeric) * 1.2)) STORED;
destructive: ... ALTER TABLE public.a DROP COLUMN total drops the column and its data (finalize needs it acknowledged)
```

## Notes
- The collation case loses every value in the column on every target, unless the user notices the warning.
  The warning says the column "is dropped", which the user never asked for, and suggests renaming it.
- Both cases also move the column to the end of the table.
- The generated-column case loses nothing (values are recomputed) but is reported as destructive.
- Workaround for the collation: `alter table customers alter column nickname type text collate "C";` in
  `pre-migration.sql`, then `draft` again. That rehearsed and deployed cleanly, data kept.

### Triage, 2026-10-21

**Verification:** CONFIRMED with the built CLI, in one project.
- `nickname text` (indexed) → `text collate "C"` gives `DROP INDEX`, `DROP COLUMN nickname`, `ADD COLUMN nickname … COLLATE "C"`, `CREATE INDEX`.
- `total … generated always as (price * qty) stored` → `(price * qty * 1.2)` gives `DROP COLUMN total`, `ADD COLUMN total …`.
- With one seed row, `draft` warns `Column a.nickname is dropped with its data (1 non-null value …): rename it, or copy what you need`. It gives the same advice for `total`.
- Both of the reporter's in-place statements in `pre-migration.sql` work. `alter table a alter column nickname type text collate "C"` and `alter table a alter column total set expression as (price * qty * 1.2)` pass the deploy-time rules. `draft` then generates 0 statements, and `rehearse` passes, with lock warnings only.

**Root cause:**
- pg-delta declares a column's `collation` and `generatedExpr` attributes as `"replace"` (`plan/rules/tables.ts`, the column kind's `attributes`). So it drops and adds the column, though PostgreSQL 18 can change both in place: `ALTER COLUMN … TYPE … COLLATE`, and `SET EXPRESSION` (PG 17+).
- Our side reports the drop as destructive, correctly, and the coverage warning's advice ("rename it, or copy what you need") fits a dropped column, not a replaced one. Nothing tells the user that the column is replaced or how to avoid it.
- The data really is lost for the collation case on every target if the drop is acknowledged. The generated case loses nothing (the values are recomputed) but is still acknowledged as destructive. Both move the column to the end (101's subject).

## Brief (ready-for-human)

**Category:** bug
**Summary:** A collation or generated-expression change doesn't silently become a column drop: either it is generated in place, or `draft` and `finalize` say exactly what in-place statement to use instead.

**Current behavior:**
Changing a column's collation, or a stored generated column's expression, generates `DROP COLUMN` + `ADD COLUMN` (plus dropping and recreating dependent indexes). `draft` warns that the column "is dropped with its data" and suggests renaming it. `finalize` asks to acknowledge a destructive drop. Acknowledged, the collation case empties the column on every target.

**Desired behavior (once decided):**
- Option 1: the generated schema change stays as it is. A `DROP COLUMN x` followed by `ADD COLUMN x` on the same table in one schema change is recognised as a *replaced* column, and named so by `draft`'s warning and `finalize`'s destructive reason.
  - For a changed collation, the message says the values are lost, and gives the in-place statement for the pre-migration script (`ALTER TABLE t ALTER COLUMN x TYPE <type> COLLATE <collation>`), after which `draft` generates nothing for it.
  - For a changed generation expression, it gives `ALTER TABLE t ALTER COLUMN x SET EXPRESSION AS (…)`. No data is lost, but the drop still needs acknowledging unless that statement is used.
- Option 2 or 3: the schema change itself uses the in-place statements, so nothing is destructive and the column keeps its position.
- The README's destructive-changes section lists both cases and their pre-migration statements.

**Key interfaces:**
- Option 1: the draft's script coverage (`dropped-column` kind and its message) and `finalize`'s destructive analysis (`sql-analysis/destructive.ts`).
- Options 2 and 3: the `Differ` seam's pg-delta implementation.

**Acceptance criteria (once decided):**
- [ ] API seam: the collation change on a table with a seed row gives the decided output. Under option 1, the warning names the replacement and the in-place statement. Under option 2 or 3, `ALTER COLUMN … TYPE text COLLATE "C"` with the value kept after deploy.
- [ ] The same for the generated-expression change (`SET EXPRESSION`).
- [ ] A real drop of a column (no `ADD COLUMN` of the same name) keeps today's message.
- [ ] README lists the two cases.

**Out of scope:**
- Column order generally (101).
- Changing the type of a column a generated column uses (104).

**Why not delegated:** options 2 and 3 change what pg-delta generates, and for 09 the maintainer chose to keep its output. Option 1 keeps a known data-loss path open behind a clearer warning.

**Decision needed:**
1. **(recommended)** Keep pg-delta's output, consistent with the decision on 09, and recognise the replaced column in the warning and the destructive reason, with the in-place statement to use. This is cheap and needs no differ change.
2. Post-process our pg-delta differ's output: rewrite such a drop-and-add pair into `ALTER COLUMN … TYPE … COLLATE` or `SET EXPRESSION`, and record it in research §8.
3. Patch pg-delta (with 101's option 1, if chosen) so these attributes are altered, not replaced, and report upstream.

### Decided, 2026-10-21

Policy decided for 101, 103, 104 and 127 together: **keep pg-delta's output** (as with 09) and warn, refuse or document; never patch or post-process it. Report each case upstream and record it in pg-delta research §8 ("Known behaviours").

For 103: **keep the drop-and-add, and say so precisely.**
- When a migration drops a column and adds one of the same name and type in the same table (pg-delta's way of changing a collation or a generated column's expression), the destructive reason at `finalize` and the warning at `draft` name it as a replaced column: `orders.code is dropped and re-added to change its collation: its values are lost. To keep them, change it in place in the pre-migration script: ALTER TABLE orders ALTER COLUMN code TYPE text COLLATE "C"` (for an expression: `ALTER TABLE ... ALTER COLUMN ... SET EXPRESSION AS (...)`).
- README's destructive-changes section and research §8 describe it.

**Acceptance criteria:**
- [ ] A collation change and a generated-expression change each give the replaced-column reason with the in-place statement (SQL-analysis and API seams).
- [ ] A real drop of one column and add of a different one keeps today's messages.
