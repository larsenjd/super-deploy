# 20: Adoption refuses tables whose columns use a domain, a managed function default or a generated expression

**Status:** ready-for-agent
**Category:** bug
**Severity:** high
**Merged:** 22
**Area:** adopt

## What I did
On the shared server (as `postgres`):

```sql
create role adopt_pubowner login password 'pubowner';
create database qa_adopt_gen owner adopt_pubowner;
-- in qa_adopt_gen, as adopt_pubowner:
create domain email as text check (value like '%@%');
create function make_code() returns text language sql volatile as $$ select 'ABC' || (floor(random()*1000))::int $$;
create table people (
  id bigint generated always as identity primary key,
  first text not null,
  last text not null,
  contact email,
  code text not null default make_code(),
  full_name text generated always as (first || ' ' || last) stored
);
```

New project: `node .../dist/cli.js init`, `git init`, `pnpm install`, then add a target to `super-deploy.config.ts`:

```ts
gen: { adapter: postgresTarget({ connectionString: process.env.GEN_DATABASE_URL ?? "" }) },
```

```sh
export GEN_DATABASE_URL=postgres://adopt_pubowner:pubowner@localhost:54818/qa_adopt_gen
pnpm exec super-deploy init --adopt gen
```

## Expected
Adoption succeeds. Each of these columns is accepted when written by hand: in a fresh project, a desired schema with `create domain email ... constraint email_check check (...)`, a column of type `email`, a `default make_code()` column and a `generated always as (...) stored` column drafts and finalizes fine. (`draft` emits them as `ALTER TABLE ... ADD COLUMN` in the schema change, which is fine there.)

## Actual
Adoption puts the differ's split `ALTER TABLE ... ADD COLUMN` into the desired schema and then refuses its own output under the desired-schema statement rule. These are excerpts from three adoptions (targets `ledger`, `gen` and `deps`):

```
Target ... has N things V1 doesn't support:
  ALTER TABLE "public"."accounts" ADD COLUMN "contact" public.email
    desired-schema-statement: Only ALTER TABLE ... ENABLE ROW LEVEL SECURITY, FORCE ROW LEVEL SECURITY or ADD CONSTRAINT is allowed in the desired schema; declare everything else in CREATE TABLE
  ALTER TABLE "public"."people" ADD COLUMN "full_name" text GENERATED ALWAYS AS (((first || ' '::text) || last)) STORED
    desired-schema-statement: Only ALTER TABLE ... ENABLE ROW LEVEL SECURITY, ...
  ALTER TABLE "shop"."UserAccounts" ADD COLUMN "code" text NOT NULL DEFAULT shop.make_code()
    desired-schema-statement: Only ALTER TABLE ... ENABLE ROW LEVEL SECURITY, ...
Error: Cannot adopt target ...: ... Nothing was written; change the target first, then adopt again
```

I saw this in three databases (`qa_adopt_pub`: domain column + stored generated column; `qa_adopt_gen`: stored generated column with no domain at all; `qa_adopt_deps`: `default shop.make_code()`). In each case the only way forward was to change the production table (drop the generated column, change the domain column to `text`, drop the default), which isn't acceptable for a real database.

## Notes
- Guess: adoption writes the desired schema from the differ's output, which adds dependent columns afterwards with `ALTER TABLE ... ADD COLUMN`. The adopted `tables.sql` should fold these columns into the `CREATE TABLE`, like it already does for plain columns.
- Stored generated columns and domain-typed columns are common in grown databases, so this blocks many adoptions.

### Triage, 2026-10-20

**Verification:** CONFIRMED, along with 22. Run at the API seam with one database per column kind.

**20:** each case fails with `AdoptUnsupportedError` and a single `[desired-schema-statement]` entry.

| Column kind | Statement adoption refuses |
|---|---|
| Domain column | `ALTER TABLE "public"."people" ADD COLUMN "contact" public.email` |
| Function default | `... ADD COLUMN "code" text NOT NULL DEFAULT public.make_code()` |
| Stored generated | `... ADD COLUMN "full_name" text GENERATED ALWAYS AS (upper(first)) STORED` |

- A plain column with a constant default adopts fine.
- The hand-written folded form of all three columns drafts and finalizes.

**22:** reproduced. These entries appear besides the real reasons:
- `ALTER TABLE child ADD COLUMN "extra" text` for an `INHERITS` child.
- `ALTER TABLE orders ADD COLUMN "status" public.order_status ...` for an enum column.
- `ALTER TABLE "public"."tmp_like" SET (fillfactor=70)`, which never mentions storage parameters.

**Root cause:**
- Folding columns into `CREATE TABLE` is pg-delta's doing, not adoption's.
- pg-delta never gives generated columns a fold hint.
- It refuses a fold when a predecessor (the domain, the function) sorts after the `CREATE TABLE`, and it won't fold into an `INHERITS` create.
- It emits storage parameters as a separate `ALTER TABLE ... SET (...)`.
- Adoption files every `ALTER TABLE` into `tables.sql` unchanged, and the desired-schema statement rule then refuses it.

**Correction:** refusing enums, inheritance and storage parameters is by design (REFINEMENTS "Enums", "Object types refused in the desired schema", "Physical storage settings"). Only the extra entries and their reasons are wrong.

## Agent Brief

**Category:** bug

**Summary:** The desired schema that adoption generates must declare every column inside its table's `CREATE TABLE`, and storage parameters inside `WITH (...)`. Adoption then never refuses its own output, and refusals name the real unsupported feature.

**Current behavior:**
For domain-typed columns, columns with a default that calls a managed function, and stored generated columns, the differ emits `ALTER TABLE ... ADD COLUMN` after the `CREATE TABLE`. Adoption writes these into the desired schema as they are, then refuses them under the desired-schema statement rule ("declare everything else in CREATE TABLE"). There is no way forward short of changing a production table.

The same mechanism adds misleading entries to refusals:
- `ADD COLUMN` for enum-typed columns and inheritance children;
- `ALTER TABLE ... SET (fillfactor=...)` instead of the storage-parameter reason.

**Desired behavior:**
- Before the adopted desired schema is checked, each single-command `ALTER TABLE <managed table> ADD COLUMN` is folded into that table's `CREATE TABLE` column list, in the target's column order (`pg_attribute.attnum`).
- Each `ALTER TABLE <managed table> SET (<storage params>)` is folded into the `CREATE TABLE ... WITH (...)`, so the existing "Table storage parameters are not supported" rule reports it.
- Desired-schema ordering then places each table after the domains and functions it uses.
- Adoption of tables with these columns succeeds, and the rehearsal of the adopted schema matches the target.
- When adoption does refuse (enums, inheritance, storage parameters), each object appears once, with its real reason, and no `desired-schema-statement` entries for statements adoption itself produced.

**Key interfaces:**
- `adopt` / `init --adopt`.
- The function that turns the differ's statements into the adopted desired-schema files (`adoptedDesiredSchema`).
- `AdoptUnsupportedError`'s list of entries.

**Acceptance criteria:**
- [ ] Adopting a target whose table has a domain-typed column, a `default <managed function>()` column and a `generated always as (...) stored` column succeeds. The adopted `tables.sql` declares all three in `CREATE TABLE`. API seam.
- [ ] The adopted desired schema keeps the target's column order.
- [ ] A target table `with (fillfactor = 70)` is refused with the storage-parameter reason, and no `desired-schema-statement` entry.
- [ ] A target with an enum column and an `INHERITS` child is refused with the enum and inheritance reasons only, with no `ADD COLUMN` entries.
- [ ] Existing adoption tests pass.

**Out of scope:**
- Virtual generated columns, which pg-delta renders as `STORED` (21, which depends on this).
- Extension members and serial sequences in refusals (23).
- Adding support for enums, inheritance or storage parameters.
