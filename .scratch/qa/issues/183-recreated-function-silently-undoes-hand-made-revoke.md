# 183: A migration that recreates a function silently undoes a hand-made `REVOKE EXECUTE ... FROM PUBLIC`, widening access

**Status:** resolved
**Category:** bug
**Severity:** medium
**Area:** privs
**Round:** 2

## What I did
Target `qa` set up as in 180 (deploy role `qa2_privs_deploy`, app roles
`qa2_privs_reader`, `qa2_privs_writer`). Desired schema has

```sql
create function order_count(cid bigint) returns integer
language sql stable as $$ select count(*)::int from app.orders where customer_id = cid $$;
```

deployed. Then, by hand, as a DBA restricting it to one role:

```sql
revoke execute on function app.order_count(bigint) from public;
grant execute on function app.order_count(bigint) to qa2_privs_writer;
```

`select app.order_count(1)` as `qa2_privs_reader` -> `permission denied for function order_count`.

Then change the return type to `bigint` (and `count(*)`), `draft --name "fn back"`,
`finalize`, `deploy --target qa`. `draft` generated
`DROP FUNCTION "app"."order_count"(bigint);` + `CREATE OR REPLACE FUNCTION ...`.

## Expected
The README's warning covers this case, or deploy warns that it is about to drop an
object whose privileges differ from the defaults.

## Actual
```
Deployed 1 migration to qa: 00007-fn-back
proacl: null                                   -- PUBLIC can execute again
select app.order_count(1)  (as qa2_privs_reader) -> [{"order_count":"0"}]
```

Nothing in `draft`, `finalize` or `deploy` output mentions it.

## Notes
- README "Two things to know about grants and policies made by hand" says a
  recreated object "loses the grants and policies made on it by hand ... Default
  privileges grant the new object again". Losing a *revoke* is the opposite
  direction: access silently widens to everyone, and the recommended recipe
  (default privileges `on tables` only) doesn't help.
- The fix for users is `alter default privileges for role <deploy role> revoke
  execute on functions from public` on each target (and grant execute to app roles
  via default privileges). The README's recipe should mention it, since functions
  (and types) default to `PUBLIC` access.
- Changing only a function's body uses `CREATE OR REPLACE` and keeps grants
  (verified), so this hits only signature/return-type changes, which a user can't
  easily predict from the desired schema.

### Triage, 2026-10-21

**Verification:** CONFIRMED. On target `qa`, `revoke execute on function app.order_count_pl(bigint) from public` and a grant to the writer role made the reader get `permission denied`. Changing the return type from `integer` to `bigint` drafted `DROP FUNCTION` + `CREATE OR REPLACE FUNCTION`; after `deploy`, `proacl` was null and the reader could call it again. Nothing in `draft`, `finalize` or `deploy` mentioned it.

Also checked: `alter default privileges for role <deploy role> in schema app revoke execute on functions from public` has no effect (a new function still gets `PUBLIC` execute), because per-schema default privileges can only add to the global ones. Without `in schema`, the same statement works (`proacl = {deploy=X/deploy}`).

**Root cause:** PostgreSQL gives functions (and types) `EXECUTE` (`USAGE`) to `PUBLIC` by default. A recreated function gets the defaults again, and the README's recipe (`packages/template/README.md:427-439`) only covers tables. Its "Default privileges grant the new object again" (`:445`) reads as if default privileges restore what was lost, when for a revoke they bring back the access that was removed.

**Intended?** Losing hand-made privileges on a recreated object is documented (ADR-0006, README). Not saying that revokes are lost too, and that the loss widens access, is a docs gap; this is a docs brief.

## Agent Brief

**Category:** bug
**Summary:** The README's permissions recipe covers functions: a recreated function goes back to `PUBLIC` execute unless default privileges revoke it, and that revoke must be global, not `in schema`.

**Current behavior:**
The README warns that a recreated object loses hand-made grants and policies and that default privileges grant it again. It doesn't say that a hand-made `REVOKE EXECUTE ... FROM PUBLIC` is lost too, so a recreated function becomes callable by every role. Its recipe grants on tables only. A user who adds `in schema app revoke execute on functions from public` by analogy gets a statement that silently does nothing.

**Desired behavior:**
- The recipe in "The application's grants and any policies" adds, run as the deploy role on each target:
  ```sql
  alter default privileges for role deploy_role
    revoke execute on functions from public;
  alter default privileges for role deploy_role in schema app
    grant execute on functions to app_writer;
  ```
  with a sentence saying functions and procedures are callable by `PUBLIC` by default, and that the revoke has to be global (without `in schema`) because per-schema default privileges can only add privileges.
- The first "Two things to know" point says a recreated object also loses hand-made *revokes*, so access can widen, and that a function is recreated when its arguments or return type change (a body-only change keeps its privileges).
- The spec's target-setup paragraph matches.

**Key interfaces:**
- The template README's "Permissions" section and the spec's "Target setup that stays outside super-deploy".

- [ ] The README recipe includes the global `revoke execute on functions from public` and a per-schema `grant execute on functions`, with the reason the revoke is global.
