# 184: Nothing warns that a deployment will drop and recreate objects carrying hand-made grants (e.g. a view recreated only because a column it reads changed type)

**Status:** ready-for-human
**Category:** enhancement
**Severity:** medium
**Area:** privs
**Round:** 2

## What I did
Target `qa` as in 181, with view `app.customer_orders` (reads `orders.total`). A
reporting role gets access by hand, not through default privileges:

```sql
create role qa2_privs_report login password 'pw';
grant connect on database qa2_privs_qa to qa2_privs_report;
-- as the deploy role:
grant usage on schema app to qa2_privs_report;
grant select on app.customer_orders to qa2_privs_report;
```

Then a change that doesn't touch the view at all: `total numeric(10,2)` ->
`numeric(12,2)` in the desired schema.

```
$ pnpm exec super-deploy draft --name "wider total"
Created draft wider-total: 4 statements in data-model/draft/schema-change.sql
$ pnpm exec super-deploy finalize
warning: ...schema-change.sql:8: ALTER TABLE app.orders ALTER COLUMN total TYPE numeric(12,2) can rewrite orders ...
Finalized migration 00005-wider-total ...
$ pnpm exec super-deploy deploy --target qa
Deployed 1 migration to qa: 00005-wider-total
```

## Expected
Some notice that the migration drops and recreates `view app.customer_orders`, and
(at deploy, where super-deploy can read the target's ACLs) that it holds grants
default privileges won't restore.

## Actual
The schema change contains `DROP VIEW "app"."customer_orders";` ... `CREATE VIEW ...`,
but no output mentions it. After deploy:

```
select * from app.customer_orders  (as qa2_privs_report)
ERROR: permission denied for view customer_orders
```

## Notes
- README "Two things to know about grants and policies made by hand" documents the
  loss, and "Destructive changes" says a view dropped and created again isn't
  destructive, so `finalize` doesn't list it. That's reasonable for data, but means
  the only way to know is to read `schema-change.sql`, and the user here never
  edited the view.
- Suggestion: `draft`/`finalize` could list objects the migration recreates, and
  `deploy`/`status` could compare the target's ACLs on those objects with what
  default privileges would give and warn about grants (or revokes, see 183) that
  will be lost.

### Triage, 2026-10-21

**Verification:** CONFIRMED. On target `qa`, `grant select on app.customer_orders` to a report role by hand, then `orders.total` from `numeric(10,2)` to `numeric(12,2)`. The schema change was `DROP VIEW "app"."customer_orders"`, `ALTER COLUMN ... TYPE`, `CREATE VIEW ...`. `draft` said "4 statements", `finalize` warned only about the table rewrite, `status` listed the pending migration with no warning, `deploy` succeeded, and the report role then got `permission denied for view customer_orders`.

**Root cause:** nothing reads a target's ACLs or policies (ADR-0006, by design), and nothing lists the objects a schema change drops and recreates: "Destructive changes" only counts drops that lose data.

**Intended?** Partly. ADR-0006 and the README say the loss happens and super-deploy "can't notice". REFINEMENTS "Privileges, ownership and row-level security" already names this fix as the one to make "if either bites": "warn when a schema change drops an object that has grants or policies on the target". This report, together with 183 (a lost revoke widens access), is that evidence, so it needs a call on whether to build it now.

## Brief (ready-for-human)

**Category:** enhancement
**Summary:** Warn before a deployment drops and recreates an object whose hand-made grants, revokes or policies on the target will be lost.

**Current behavior:**
A migration that drops and recreates a view (for example because a column it reads changed type), a function (signature or return type change) or a table loses the privileges and policies set on it by hand. Nothing in `draft`, `finalize`, `status` or `deploy` says so; the user has to read `schema-change.sql`.

**Desired behavior (once decided):**
- `status` and `deploy` (and `deploy-draft`) list, as warnings, each object the pending migrations drop that has privileges or policies on the target that default privileges won't restore: the object, the grants or revokes that will be lost, and its policies.
- "Default privileges won't restore" means the object's ACL differs from what PostgreSQL's built-in defaults plus the deploy role's `pg_default_acl` entries (global and for the managed schema) would give a new object. So the README's recommended setup produces no warning.
- Optionally, `draft`/`finalize` print one line naming the objects the schema change recreates, since they can't see a target.
- A warning, not a refusal: the deployment goes ahead.

**Key interfaces:**
- The pre-flight findings and warnings `status` and `deploy` share (like the deploy-role warnings).
- The pending migrations' parsed schema changes (their `DROP` statements and the objects they name).
- A catalog read on the target of `relacl` / `proacl` / `typacl`, `pg_default_acl` and `pg_policy` for those objects.

**Acceptance criteria (once decided):**
- [ ] The reporter's case (view granted by hand, column type change) makes `status` and `deploy` warn, naming the view and the lost `SELECT` for the report role (API seam, `postgresTarget`).
- [ ] 183's case (function with `PUBLIC` execute revoked, return type changed) warns about the lost revoke.
- [ ] A table with a policy that a migration drops and recreates warns about the policy.
- [ ] With only the README's default-privileges recipe in place, no warning.
- [ ] Objects the migration only alters, or creates anew, never warn.

**Out of scope:**
- Re-applying the lost grants or policies (ADR-0006).
- Comparing grants as drift.
- The README's own recipe for functions (183).
- A column change under a policy failing at deploy, already documented.

**Why not delegated:** ADR-0006 and REFINEMENTS deliberately left this out of V1. Building it means super-deploy reads ACLs and policies on targets for the first time since privileges went out of scope.
**Decision needed:** build the warning now?
- Yes: `status`/`deploy`/`deploy-draft` warnings compared against default privileges, as above; update ADR-0006's consequence and the REFINEMENTS entry (recommended). 183 shows the silent loss can widen access, which is the case REFINEMENTS was waiting for.
- Only an offline line in `draft`/`finalize` listing recreated objects, with no target read: cheaper, but warns for every recreated object, and says nothing about whether anything is lost.
- No: keep it in REFINEMENTS; the README's warning (with 183's wording) is enough. Close as wontfix.
