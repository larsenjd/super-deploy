# 148: Invalid `sslmode` values are accepted silently (as verify-full) rather than refused as libpq does

**Status:** ready-for-agent
**Category:** bug
**Severity:** low
**Area:** fail
**Round:** 2

## What I did
Against the shared server (no TLS):
```sh
B=postgres://qa2_fail_deployer:dep@localhost:54818/qa2_fail_main
for m in bogus DISABLE verify_full; do QA_DATABASE_URL="$B?sslmode=$m" pnpm exec super-deploy status --target qa; done
QA_DATABASE_URL="$B?ssl=true" pnpm exec super-deploy status --target qa
```
And against a private PG18 of my own with `ssl=on` and a self-signed certificate (port 54899): `sslmode=verify_full`, `verify-ful`, `VERIFY-FULL` and `require`.

## Expected
README: "super-deploy reads it as `psql` and libpq do". libpq refuses an unknown value: `invalid sslmode value: "DISABLE"`. I expected a refusal naming the valid values (`disable`, `allow`, `prefer`, `require`, `verify-ca`, `verify-full`).

## Actual
Shared server, every case:
```
Error: The deployment adapter of target qa failed to connect: The server does not support SSL connections
```
So `sslmode=DISABLE` (wrong case) means "encrypt", and the error then blames the server.

TLS server with a self-signed cert: `verify_full`, `verify-ful` and `VERIFY-FULL` all fail with `self-signed certificate; …` (the same as `verify-full`), while `require` connects. So unknown values behave as `verify-full`. That is safe, but surprising and undocumented.

`?ssl=true` (not a libpq option) is also accepted and turns on TLS.

## Notes
Failing safe is good. A typo is still better reported as a typo than as "the server does not support SSL".

### Triage, 2026-10-21

**Verification:** CONFIRMED against the shared (non-TLS) server: `sslmode=bogus`, `DISABLE`, `allow` and `ssl=true` all gave `failed to connect: The server does not support SSL connections`. `sslmode=disable` connected. The TLS-server half wasn't rerun; the code explains it.

**Root cause:** with `uselibpqcompat=true` (round 1's 53), pg-connection-string turns on TLS with default options (`config.ssl = {}`, so the certificate is verified) for any `sslmode`, then adjusts only for `disable`, `prefer`, `require`, `verify-ca` and `verify-full`. Any other value, including libpq's `allow` and wrong case, falls through as verify-full. super-deploy doesn't check the value. `ssl=true` is a node-postgres parameter that libpq would refuse.

## Agent Brief

**Category:** bug
**Summary:** An `sslmode` value libpq wouldn't accept is refused before connecting, naming the valid values.

**Current behavior:**
Any `sslmode` other than the five node-postgres knows (typos, wrong case such as `DISABLE`, and libpq's `allow`) silently means verify-full. Against a server without TLS the user gets `The server does not support SSL connections`, which blames the server for a typo.

**Desired behavior:**
- A connection string whose last `sslmode` isn't exactly one of `disable`, `allow`, `prefer`, `require`, `verify-ca`, `verify-full` (case-sensitive, as libpq) is refused before connecting, as a `ConnectionStringError` naming the target, the value and the valid values. Never echo the password.
- `allow` behaves as `disable`, as libpq's `allow` does unless the server insists on TLS. The README's TLS paragraph lists it next to `prefer`: "Unlike `psql`, `allow` never upgrades to an encrypted connection."
- The same check covers `postgresRehearsal`.

**Key interfaces:**
- `ConnectionStringProblem` / `ConnectionStringError`: a new problem kind for an invalid `sslmode`.
- The pre-connect check of the connection string.
- The template README's TLS paragraph.

**Acceptance criteria:**
- [ ] `sslmode=bogus`, `sslmode=DISABLE` and `sslmode=verify_full` are each refused with a message naming the value and the six valid ones, with no connection attempted.
- [ ] `sslmode=allow` connects to a server without TLS.
- [ ] The five values that work today behave as before (existing TLS tests pass).
- [ ] The README lists `allow`.

**Out of scope:**
- `ssl=true` and other node-postgres-only parameters, which libpq would refuse. `ssl=true` verifies the certificate, so it fails safe.
- Unreadable certificate files (147).
