**Status:** resolved

**Severity:** low
**Area:** adopt
**Round:** 2

## What I did
A legacy database whose `shop` schema and its 13 objects were created by the superuser `postgres`; deploy role `qa2_adopt_deployer`.

```sh
export QA_DATABASE_URL=postgres://qa2_adopt_deployer:dep@localhost:54818/qa2_adopt_shop
pnpm exec super-deploy init --adopt qa
```

## Expected
As the unsupported-object refusal does: one object per line, and the fixes in a form a DBA can copy and run as a script.

## Actual
One line of about 2,700 characters:

```
Error: The deploy role on target qa doesn't own everything in the managed schema: schema shop is owned by postgres, whose privileges the deploy role doesn't have (fix: ALTER SCHEMA shop OWNER TO qa2_adopt_deployer); domain shop.email is owned by postgres, whose privileges the deploy role doesn't have (fix: ALTER DOMAIN shop.email OWNER TO qa2_adopt_deployer); ... function shop.customer_order_count(cid bigint) is owned by postgres, ... (fix: ALTER FUNCTION shop.customer_order_count(cid bigint) OWNER TO qa2_adopt_deployer); ... view shop.open_orders is owned by postgres, whose privileges the deploy role doesn't have (fix: ALTER VIEW shop.open_orders OWNER TO qa2_adopt_deployer)
```

"whose privileges the deploy role doesn't have" is repeated for each object. To run the fixes I had to extract them with a regex; a naive `grep -o 'fix: [^)]*'` cuts every function signature at its first `)` (`ALTER FUNCTION shop.new_order_ref(;`).

## Notes
A list like the unsupported-object one (object on one line, fix indented under it), or a block of `ALTER ... OWNER TO ...;` statements at the end, would be much easier to read and hand to a DBA. The README ("What each target needs set up outside super-deploy") says it lists "each object with the `ALTER ... OWNER TO` that fixes it", which it does, just not readably.

**Verification:** CONFIRMED. `qa2t_adopt_shop`, with all 14 objects owned by `postgres`: `init --adopt qa` printed one `Error:` line of about 2,700 characters. `status --target qa` already prints the same findings one per line under "Deploy would refuse". `NotOwnedError` (`deploy/ownership.ts`) joins `notOwnedMessage` for every object with `; ` into its message. ## Agent Brief

**Category:** enhancement
**Summary:** The ownership refusal lists one object per line, followed by its fixes as a script a DBA can copy and run.

**Current behavior:**
`init --adopt` and `mark` refuse with `NotOwnedError`, and `deploy` and `deploy-draft` with `PreflightFailedError`. Each prints every object, its owner and its fix on a single `Error:` line, separated by `; `, and repeats "whose privileges the deploy role doesn't have" for every object. Function signatures contain `)`, so even extracting the fixes with a regex is error-prone.

**Desired behavior:**
- In the CLI, before the `Error:` line, the refusal lists each object on its own line with its owner, e.g. `  table shop.customers (owned by postgres)`.
- After the list comes a block headed with who must run it, e.g. "To fix, run as a superuser or as each object's owner:". It holds every `ALTER ... OWNER TO ...;` statement, one per line, each ending in `;`, so the block can be pasted into psql as it is.
- The `Error:` line is a summary that names no object, e.g. `The deploy role on target qa doesn't own 14 objects in the managed schema, listed above. Nothing was written`.
- `PreflightFailedError` (deploy, deploy-draft) prints its findings one per line the same way, and its not-owned findings get the same fix block.
- The API errors' messages stay self-contained for callers that don't print the list.

**Key interfaces:**
- `NotOwnedError` and `PreflightFailedError`: add `details` and `summary`, as `AdoptUnsupportedError` has.
- `listedDetails` / `describeError` in the CLI.
- `NotOwnedObject` (object, owner, fix) is unchanged.

**Acceptance criteria:**
- [ ] CLI seam: adopting a target with three objects owned by another role prints three object lines, a block of three `ALTER ... OWNER TO ...;` statements, and an `Error:` line naming none of the objects. Exit code 1.
- [ ] Running the printed block as a superuser makes the same adoption get past the ownership check. API or CLI seam, with a function whose signature has arguments.
- [ ] `deploy` on a target that fails the ownership pre-flight prints the same block.
- [ ] `status` output is unchanged.

**Out of scope:**
- The fix offered for `public` (126, which also covers 188).
- Refusing in one round together with the unsupported objects (122).
