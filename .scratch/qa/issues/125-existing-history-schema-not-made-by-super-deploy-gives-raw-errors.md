# 125: A history schema that exists but wasn't made by super-deploy gives raw PostgreSQL errors in adopt and status

**Status:** resolved
**Category:** bug
**Severity:** medium
**Area:** adopt
**Round:** 2

## What I did
Case A, a DBA pre-creates the history schema (an obvious way to avoid granting `CREATE` on the database, which the first refusal asks for):

```sql
-- database qa2_adopt_nocreate, schema inv owned by qa2_adopt_deployer, no CREATE on the database
create schema deployment_history authorization qa2_adopt_deployer;
```
```sh
pnpm exec super-deploy init --adopt qa       # managedSchema: "inv"
pnpm exec super-deploy status --target qa
```

Case B, `historySchema` set to a schema that already holds unrelated tables:

```sql
create schema audit; create table audit.migrations (x int); create table audit.log (y int);
```
```ts
managedSchema: "app", historySchema: "audit",
```
```sh
pnpm exec super-deploy init --adopt qa
pnpm exec super-deploy status --target qa
```

## Expected
A refusal that names the schema and says what's wrong: e.g. "schema deployment_history exists but isn't a super-deploy history schema (it has no table migrations); drop it, or let super-deploy create it (needs CREATE on the database), or set historySchema". For case A, possibly super-deploy could create its tables in an empty schema the deploy role owns.

## Actual
Case A:
```
Error: relation "deployment_history.migrations" does not exist
```
(`--debug` shows it coming from `readRecordedMigrations` in `deploy/history.js`, called from `adopt`.)
`status`: `Error: relation "deployment_history.attempts" does not exist`

Case B:
```
Error: column "number" does not exist
```
`status`: `Error: relation "audit.attempts" does not exist`

Nothing was written in either case.

## Notes
The README says `historySchema` is "the schema super-deploy creates on each target" and that `CREATE` on the database is needed "for the first deployment, which creates the history schema"; it doesn't say the schema must not exist beforehand.

## Comments

> *This was generated by AI during triage.*

### Triage, 2026-10-21

**Verification:** CONFIRMED, and wider than adoption.
- Case A (`qa2t_adopt_nocreate`): an empty `deployment_history` owned by the deploy role. `init --adopt qa` gave `Error: relation "deployment_history.migrations" does not exist`, and `status` gave `relation "deployment_history.attempts" does not exist`.
- Case B (`qa2t_adopt_audit`): `historySchema: "audit"`, a schema holding unrelated `migrations` and `log` tables. Adoption gave `Error: column "number" does not exist`. `status` and `deploy` gave `relation "audit.attempts" does not exist`.
- The same schema owned by `postgres` (deploy role without USAGE) gave `permission denied for schema audit` from every command.
- Nothing was written in any case.

**Cause:** `deploy/history.ts` treats "the schema exists" as "the history schema is there" (`schemaExists`). `ensureHistorySchema` returns early, and every reader (`readRecordedMigrations`, `readRecentAttempts`, `readTargetSettings`, `readDeployedDraft`) queries its tables directly. The CREATE-on-database pre-flight (`historySchemaNotCreatable`) only runs when the schema is missing, so a pre-created schema already gets past it. Nothing checks what the schema holds.

## Brief (ready-for-human)

**Category:** bug
**Summary:** Every command should recognise a history schema that super-deploy didn't make and say what to do, instead of failing with a raw PostgreSQL error.

**Current behavior:**
An existing schema with the history schema's name is taken to be super-deploy's. If it is empty, holds other tables, or the deploy role can't use it, `init --adopt`, `status`, `deploy` (and every other command reading history) fail with raw `relation ... does not exist`, `column ... does not exist` or `permission denied` errors.

**Desired behavior (once decided):**
- Commands tell three states apart: no history schema, super-deploy's history schema, and some other schema with that name.
- For the third, they refuse before doing anything, naming the schema, what is wrong (empty, holds other objects, not usable by the deploy role), and the fixes (drop it, set `historySchema`, or as decided below). `status` lists it under "Deploy would refuse".
- Optionally, as decided below, an empty schema the deploy role owns is completed with super-deploy's tables. A DBA can then pre-create it instead of granting CREATE on the database.

**Key interfaces:**
- The history module: `schemaExists` as used for the history schema, `ensureHistorySchema`, and the readers listed above. A single "history schema state" check would serve all of them.
- The deploy pre-flight findings (`PreflightFindings`) and adoption's target checks (`requireHistorySchemaCreatable`).
- The README's `historySchema` setting and its Permissions note on CREATE.

**Acceptance criteria (once decided):**
- [ ] Case A and case B from the report give a refusal naming the schema and the fix, from both `init --adopt` and `status`/`deploy`, with nothing written. API seam.
- [ ] A history schema owned by another role, without USAGE for the deploy role, gives the same kind of refusal, not `permission denied`.
- [ ] Targets with a real history schema, or with none, behave as today.
- [ ] Per the decision: an empty, deploy-role-owned schema is either filled and used, or refused.

**Out of scope:**
- Upgrading older history layouts (`layout_version`).
- The CREATE-on-database refusal itself (round-1 issue 37, resolved).

**Why not delegated:** whether a pre-created empty schema is accepted changes what the README tells DBAs about CREATE on the database.
**Decision needed:**
- Accept an existing schema that is empty and owned by the deploy role (or by a role whose privileges it has): create super-deploy's tables in it. Refuse any other non-super-deploy schema with a clear message. The README says a DBA may pre-create the history schema instead of granting CREATE on the database (recommended).
- Refuse any existing schema that super-deploy didn't make, empty ones included. The README says the history schema must not exist beforehand.

### Decided, 2026-10-21

The maintainer chose **accept an empty schema, refuse anything else.**
- An existing history schema that is empty and owned by the deploy role (or a role it is a member of) is accepted: super-deploy creates its tables in it.
- Any other existing schema of that name that super-deploy didn't make is refused by every command with a clear message naming the schema and what's in it, and the config setting to choose another name.
- README: a DBA may pre-create the history schema (owned by the deploy role) instead of granting CREATE on the database.

**Acceptance criteria:**
- [ ] Pre-created empty history schema owned by the deploy role, no CREATE on the database: adopt and deploy succeed (API seam).
- [ ] A history schema holding an unrelated table: `adopt`, `status` and `deploy` refuse with the message, no raw PostgreSQL error.
