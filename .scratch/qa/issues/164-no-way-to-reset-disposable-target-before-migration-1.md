# 164: A disposable target can't be reset to before migration 1, so a Recovery of migration 1 can be tried only once per database

**Status:** ready-for-agent
**Category:** enhancement
**Severity:** low
**Area:** disp
**Round:** 2

## What I did
Project with `managedSchema` `public` and one migration, `00001-items`. A disposable target `qa` on a database owned by the deploy role, with nothing deployed.
```sh
pnpm exec super-deploy recovery --migration 1
pnpm exec super-deploy deploy-draft --target qa             # YES: deployed "on top of no recorded migration"
pnpm exec super-deploy status --target qa
pnpm exec super-deploy rebuild --target qa --to 0
pnpm exec super-deploy rebuild --target qa --to 1           # YES
pnpm exec super-deploy deploy-draft --target qa             # try the Recovery again
```

## Expected
I can reset the disposable target to "no migrations" and try the Recovery draft again, as the README describes for other migrations ("a Recovery draft of migration N needs the target at N-1").

## Actual
`status` tells me to use a placeholder:
```
the target holds draft items (deployed by attempt #2 before any migration, without seed data), not a finalized migration: reset it with rebuild --to N
```
`--to 0` is refused:
```
Error: Option --to must be a migration number, e.g. 3 or 00003. Run "super-deploy rebuild --help" for usage.
```
After `rebuild --to 1`, deploy-draft refuses:
```
Error: The Recovery draft of migration 00001-items runs on top of no recorded migration, but target qa is at 00001-items: use a target with no recorded migrations
```
So each try needs a brand-new database, and nothing says how to get one back to zero recorded migrations.

## Notes
Workaround: create a new database, flag it disposable, deploy-draft there. A `rebuild --to 0` that wipes and records nothing would close the gap. The README doesn't say whether N may be 0.

### Triage, 2026-10-21

**Verification:** CONFIRMED in a pseudo-terminal, on a new disposable database with nothing deployed and a Recovery draft of migration 1.
- `deploy-draft` deployed the draft "on top of no recorded migration".
- `status` then said `... not a finalized migration: reset it with rebuild --to N`, with a literal `N`.
- `rebuild --to 0` was a usage error: `Option --to must be a migration number, e.g. 3 or 00003`.
- After `rebuild --to 1`, `deploy-draft` refused: `... runs on top of no recorded migration, but target qa is at 00001-add-customers: use a target with no recorded migrations`.
- Causes:
  - The CLI only accepts numbers from 1 for a migration option (`cli/parse.ts:155`), and `rebuild` requires `to` to be a finalized migration.
  - The held-draft advice falls back to the placeholder `rebuild --to N` when the draft went on top of no migration (`describeHeldDraft`, `deploy/preflight.ts:355-358`).
  - `RecoveryBaseMismatchError` says "use a target with no recorded migrations" for N = 1 (`commands/deploy-draft.ts:318-321`).
- ADR-0005 calls `rebuild --to N` "the only way back" from a deployed draft and never considers N = 0. So a draft deployed before any migration can't be reset at all; only a new database gets the target back.

## Brief (ready-for-human)

**Category:** enhancement
**Summary:** A disposable target can be reset to "no migrations", so a draft deployed before any migration (a Recovery of migration 1, or a first draft) can be cleared and tried again.

**Current behavior:**
`rebuild` only takes N ≥ 1. A target holding a draft deployed on top of no migration can't be reset: `status` and `deploy` advise `rebuild --to N` with a literal `N`, and a Recovery draft of migration 1 can be tried once per database.

**Desired behavior (once decided):**
- `rebuild --target X --to 0` wipes the managed schema, deletes the recorded migrations and any deployed draft, and replays nothing, in one transaction with the same confirmation, checks and attempt as any rebuild. The confirmation says it replays no migrations.
- The held-draft advice says `rebuild --to 0` when the draft went on top of no migration, and `RecoveryBaseMismatchError` for migration 1 says `run rebuild --to 0 first`.
- The menu's `--to` list offers 0 for `rebuild` (e.g. `(none: no migrations)`). Other migration options still refuse 0.
- The README's `rebuild` bullet and ADR-0005 say that N may be 0.

**Key interfaces:**
- `RebuildOptions.to` and its validation (`UnknownMigrationError` for numbers the repo lacks).
- The CLI's `migration` option kind: a way for one option to accept 0.
- `describeHeldDraft` and `RecoveryBaseMismatchError`.

**Acceptance criteria (once decided):**
- [ ] Pseudo-terminal: a target holding a draft deployed before any migration is reset by `rebuild --to 0`. Afterwards it records no migrations and no draft, and its managed schema is empty.
- [ ] A Recovery draft of migration 1 can then be deployed again with `deploy-draft`.
- [ ] `status` on such a target advises `rebuild --to 0`, never a literal `N`.
- [ ] `--to 0` is still a usage error for other commands' migration options (`recovery --migration 0`).

**Out of scope:**
- A target that is behind or holds a draft on top of migration N ≥ 1 (works today).
- 167 (the held-draft advice on a target that is no longer disposable).

**Why not delegated:** it extends `rebuild`'s grammar and ADR-0005's "rebuild --to N", and adds a special value to one migration option.
**Decision needed:**
- **(recommended)** Allow `rebuild --to 0` as described.
- No new value: fix the messages to say a draft deployed before any migration can't be reset and the target must be a new database (or dropped and recreated by hand), and say so in the README.

### Decided, 2026-10-21

The maintainer chose **allow `rebuild --to 0`**: it wipes the managed schema, the recorded migrations and any deployed draft, and replays nothing. The menu offers 0 as "no migrations" below migration 1; the confirmation says so; `--help` and the README document it.

**Acceptance criteria:**
- [ ] Pseudo-terminal test: after `deploy-draft` of a first draft, `rebuild --to 0` leaves the target with no migrations and no deployed draft, and `deploy-draft` can run again.
