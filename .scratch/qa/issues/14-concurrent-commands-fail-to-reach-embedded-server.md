# 14: Two commands run at the same time in one project: one fails with ECONNREFUSED / "the database system is starting up"

**Status:** resolved
**Category:** bug
**Severity:** medium
**Merged:** 49
**Area:** newproj

## What I did
In a project created by `init` (default embedded server, `dev` target), run
two commands at once, e.g. `status` in a terminal while an editor task or a
second terminal runs another:
```sh
for i in 1 2 3; do
  (pnpm exec super-deploy status --target dev 2>&1 | grep -v warning | head -1) &
  (pnpm exec super-deploy status --target dev 2>&1 | grep -v warning | head -1) &
  wait; echo ---
done
```
and once with three at the same time (`status --target dev`, `rehearse`,
`status --target dev`).

## Expected
Both commands succeed: they share the server, or the second waits for the
first.

## Actual
One of the two fails every time (3/3):
```
Error: The deployment adapter of target dev failed to connect: connect ECONNREFUSED 127.0.0.1:34493
Target dev: 6 migrations recorded, 0 pending
---
Error: The deployment adapter of target dev failed to connect: connect ECONNREFUSED 127.0.0.1:35087
Target dev: 6 migrations recorded, 0 pending
---
Error: The deployment adapter of target dev failed to connect: connect ECONNREFUSED 127.0.0.1:42665
Target dev: 6 migrations recorded, 0 pending
```
With three in parallel:
```
Error: The deployment adapter of target dev failed to connect: the database system is starting up
```

## Notes
- Guess: each process starts the server in `.super-deploy/postgres` on its own
  free port; the loser's postmaster can't start on a locked data directory (or
  the winner stops it when it finishes), and the loser connects to its own
  port where nothing is listening.
- The message doesn't say another super-deploy command is using the server,
  or that a retry will work.
- I didn't manage to make a concurrent `status` break a running `deploy --target dev`,
  but if one process can stop the server while another is still using it, a
  deploy or rehearsal could be cut off mid-way.

## Comments

### Triage, 2026-10-20

**Verification:** CONFIRMED, and worse than reported.
- Two `status --target dev` at once, 4 runs: one failed every time, three times with `the database system is starting up` and once with `connect ECONNREFUSED`.
- Three at once: `rehearse` failed with `failed to drop throwaway database ...: the database system is shutting down`. So a running command does get cut off mid-way.
- Cause: the embedded adapter attaches as soon as `postmaster.pid` exists, without waiting for the server to accept connections (SQLSTATE 57P03; `src/adapters/embedded-postgres.ts:72-76`). The process that started the server stops it in `stop()` (`:147-152`) even while others are attached. The reporter's guess (separate ports) is wrong: the losers attach to the winner's port, then the winner stops it.
- From 49: after the owner is SIGKILLed, the orphaned postmaster keeps running. Later commands attach to it but never stop it, and never sweep leftover throwaway databases, because `sweepLeftovers` only runs on an owned server.

## Brief (ready-for-human)

**Category:** bug
**Summary:** Commands in one project must be able to share the private embedded server safely, and an orphaned server must get cleaned up.

**Current behavior:**
The first command starts the server; others attach to it if `postmaster.pid` exists. An attacher can connect before the server is ready and fail. The starter stops the server when it finishes, cutting off any other command still using it. After the starter is SIGKILLed, the server runs until reboot: attachers never stop it or sweep its leftover throwaway databases.

**Desired behavior (once decided):**
- Concurrent commands in one project all succeed.
- No command stops the server under another.
- A server left behind by a dead process is cleaned up by a later command.

**Key interfaces:**
- The embedded adapter's start, attach and `stop()` (and its `owned` state).
- Leftover sweeping (`sweepLeftovers`).
- The adapter types' `close()` contract.

**Acceptance criteria (once decided):**
- [ ] Attaching retries while the server reports 57P03 ("starting up"), within a bounded time.
- [ ] Two and three concurrent commands (`status`, `rehearse`) in one project all succeed, in a CLI test.
- [ ] A rehearsal is never cut off by another command finishing.
- [ ] After a SIGKILLed command, the next command's run leaves no server running and no leftover throwaway databases.
- [ ] The README says the server stops when the last command ends.

**Out of scope:**
- Rehearsal-cluster separation (06).
- Signal handling of `deploy` (40).

**Why not delegated:** the sharing protocol (lease, refcount, owner pid file) is a design choice with cross-platform consequences. The 57P03 retry alone is mechanical and could ship first.
**Decision needed:**
- A lease: each process registers in the data dir (pid file per client), and the last live client stops the server. A dead owner's server is adopted by the next command (recommended).
- Before stopping, the owner checks `pg_stat_activity` for other clients and leaves the server running if any are there (simpler, racier).
- Never stop the server automatically; document a stop command.

### Decided, 2026-10-21

The maintainer chose: **a lease file.** Each command using an embedded server registers in that server's data directory, and the last live one stops it. A server left by a dead command is taken over by the next one.

- Registration: a file per client process (pid, start time) in the data directory. A command removes its own file when it closes; the one that removes the last file stops the server.
- A client file whose process is gone counts as dead. A command that finds a server with only dead clients takes it over: it registers, sweeps leftover throwaway databases, and stops the server at the end like any last client.
- Attaching retries while the server reports 57P03 ("starting up"), within a bounded time.
- Applies to each embedded server separately (06 gives rehearsals and `dev` one each).
- Keep it cross-platform: no reliance on signals to other processes to test liveness beyond what Node offers on Windows (`process.kill(pid, 0)` works there).

**Blocked by:** 06 (it reshapes the embedded adapter and adds the second server).

**Acceptance criteria:** the brief's five, plus: a server whose only client file belongs to a dead pid is stopped by the next command's close.
