# 141: Closing the terminal during a command leaves the embedded rehearsal server running

**Status:** ready-for-human
**Category:** bug
**Severity:** medium
**Merged:** 162
**Area:** fail
**Round:** 2

## What I did
Fresh project from `init`, `git init`, `pnpm install`, a few finalized migrations, and a draft whose `seed-data.sql` makes the rehearsal take about 7 seconds:

```sql
insert into customers (email, name) select 'u' || g.n || '@x.com', 'n' || g.n from generate_series(1, 3000000) as g(n);
```

**Case A: closing the terminal mid-command.** Run `pnpm exec super-deploy rehearse` in a pseudo-terminal (Python `pty.fork()`), and after 3 seconds close the terminal's master fd, which is what closing a terminal window or losing an SSH session does. Then list processes:

```sh
pgrep -af "/tmp/sd-qa2/fail/p1/.super-deploy"
```

**Case B: hang-up at a YES prompt.** Run `pnpm exec super-deploy mark --target qa` in a pty. When `Type YES to mark migration … on target qa` appears, either close the terminal, or send SIGHUP to the foreground process group.

## Expected
The command is interrupted (as it is for SIGINT and SIGTERM) and stops the private servers it started, or at least the next command cleans up. README ("Connecting to dev") says only a command "killed outright (`kill -9`, a crash)" can leave a server running.

## Actual
Case A: the CLI dies (the pty child's exit status is "killed by SIGHUP") and the rehearsal server keeps running, checked at 2, 4, 6, 8, 10 and 12 seconds afterwards:
```
[pty closed]
[exit] -1
t+12s:
2566485 …/native/bin/postgres -D /tmp/sd-qa2/fail/p1/.super-deploy/rehearsal -p 38659 -c listen_addresses=127.0.0.1 -c unix_socket_directories=
```
`.super-deploy/rehearsal/super-deploy-clients/` still holds the dead command's file `2566462-….json`.

Case B (SIGHUP at the prompt):
```
Interrupted by SIGHUP: cleaning up before exiting (interrupt again to exit at once)
[exit] -1
```
The rehearsal server (`-D …/.super-deploy/rehearsal -p 42407`) was still running 13 seconds later, this time with `super-deploy-clients/` empty. Closing the terminal at the prompt left it running the same way (seen twice).

The next command that needs the rehearsal server takes the old one over and stops it, so it doesn't pile up. Until then a postgres process stays behind, which the user doesn't know about.

## Notes
- Ctrl+C at the same prompt is clean (`not confirmed (cancelled): nothing changed`, no server left). So are SIGINT, SIGTERM and SIGHUP during `deploy` or `rehearse` while the terminal stays open, a double Ctrl+C, and SIGKILL.
- Guess: when the terminal goes away, the cleanup itself fails, maybe writing its message to a dead tty or the prompt reading EOF/EIO, and the process exits before the server is stopped.
- README's "Connecting to dev" describes leftover servers only for `kill -9` or a crash, and only for `dev`.

### Triage, 2026-10-21

**Verification:** CONFIRMED, together with merged issue 162. The guess is half right: the cleanup doesn't fail, it is cut short by a second signal.
- `pnpm exec super-deploy rehearse` in a pty, terminal closed after 3 s: the CLI was gone within 0.2 s, and the rehearsal server (ppid 1) kept running.
- With a `--require` hook logging the CLI's signals: `got SIGHUP` at +2946 ms, `got SIGHUP` again at +2948 ms, then `process.exit(129)` from `cli/process.js`, the "interrupt again to exit at once" branch.
- The same in a pty with a signal to the foreground process group: SIGTERM and SIGHUP each arrived twice, exited at once and left the server running. SIGINT and a typed Ctrl+C arrived once and cleaned up (exit 130, no server left).
- At the YES prompt (`disposable --target dev --set yes`, as in 162): SIGHUP to the group arrived twice and left both the dev and rehearsal servers running.
- Running `node_modules/.bin/super-deploy rehearse` directly and closing the terminal: one SIGHUP, the server was stopped, exit 129.

**Root cause:**
- In a terminal, `pnpm-native` runs the CLI in the terminal's foreground process group. A hang-up, or a SIGTERM or SIGHUP to that group, reaches the CLI from the kernel, and `pnpm-native` forwards the same signal to it a few milliseconds later. It doesn't forward SIGINT.
- `watchInterruptions` (`cli/process.ts`) treats any second signal as "interrupt again" and calls `process.exit` before cleanup has stopped the embedded servers. Throwaway databases may be left too, until the next client sweeps them.
- Without a terminal, `pnpm-native` puts the CLI in a process group of its own, so a group signal reaches it only once. That is why the reporter's `setsid` runs were clean.
- The README is right that the next command takes the server over and stops it. It is wrong that only `kill -9` or a crash leaves one behind.

## Brief (ready-for-human)

**Category:** bug
**Summary:** One interruption delivered twice (by the terminal and by a wrapper such as pnpm) must not count as "interrupt again", so closing a terminal or signalling the foreground group still cleans up.

**Current behavior:**
After the first SIGINT, SIGTERM or SIGHUP, any second signal exits at once. Under `pnpm exec` in a terminal, SIGTERM and SIGHUP always arrive twice, so closing the terminal, losing an SSH session or `kill -TERM -<pgid>` leaves the private embedded servers running, during a command or at a YES prompt.

**Desired behavior (once decided):**
- Closing the terminal, or SIGTERM/SIGHUP to the foreground group, during a command or at a YES prompt run through `pnpm exec`, cleans up as a single signal does: servers stopped, any attempt recorded as abandoned, exit 129 or 143.
- A person who presses Ctrl+C a second time, deliberately, still gets an immediate exit.
- The README's "Connecting to dev" stays true: only a command killed outright leaves a server running.

**Key interfaces:**
- `watchInterruptions` and its rule for a second interruption.
- The spec's interruption line ("a second interrupt exits at once").

**Acceptance criteria (once decided):**
- [ ] Pseudo-terminal test: a command running via a wrapper that forwards the signal (or the test sending the same signal twice within a few milliseconds) and SIGHUP or SIGTERM to the foreground group leaves no postmaster for the project, and exits 129 or 143.
- [ ] The same at a guarded command's YES prompt (162's case).
- [ ] Two SIGINTs a second or more apart still exit at once (the existing test passes).
- [ ] The README and the spec state the rule.

**Out of scope:**
- SIGTERM to corepack's `pnpm` launcher not reaching the CLI at all (140).
- What an interrupted deploy prints (110, 143) and the exit code after a command has finished (144).
- Shutting servers down from a cleanup that is itself SIGKILLed (14's lease handles the next command).

**Why not delegated:** it changes the documented meaning of "interrupt again", and the choice trades a timing window against which signals may escalate.
**Decision needed:**
- A repeat of the same signal within about 1 s of the first counts as the same interruption, and SIGHUP never forces an immediate exit (no one is at the terminal to insist). A later second signal still exits at once (recommended: covers any wrapper that forwards signals, including ones that forward SIGINT).
- Only a second SIGINT exits at once. Repeated SIGTERM and SIGHUP are ignored while cleaning up; supervisors escalate with SIGKILL anyway.
- Keep the rule, and document that `pnpm exec` in a terminal doubles SIGTERM and SIGHUP.
