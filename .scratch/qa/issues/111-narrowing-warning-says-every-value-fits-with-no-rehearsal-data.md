# 111: The narrowing warning says "every value in the rehearsal data fits" when there is no rehearsal data

**Status:** resolved
**Category:** bug
**Severity:** low
**Area:** newproj
**Round:** 2

## What I did
Deployed: `orders.note text`, `orders.total numeric(10,2)`. Desired schema: `note varchar(5)`, `total numeric(4,1)`.
No seed data.
```sh
pnpm exec super-deploy draft --name narrow
```
Then with seed data holding `total = 1234.56` and `note = 'a long note here'`, `draft` again, then `rehearse`.

## Expected
With no rows, say so, as the other draft warnings do (`(no rows in the rehearsal data)`, `(no non-null values in the
rehearsal data)`). With a value too large for the new `numeric`, say the rehearsal (and a deployment) will fail on it,
not just that it "doesn't fit".

## Actual
No seed data:
```
warning: orders.note narrows from text to varchar(5): ... (every value in the rehearsal data fits): if a target holds values that don't, ...
warning: orders.total narrows from numeric(10,2) to numeric(4,1): ... (every value in the rehearsal data fits): ...
```
"Every value fits" reads like a reassurance, but there were no values.

With the seed data:
```
warning: orders.total narrows from numeric(10,2) to numeric(4,1): values are rounded to 1 decimal place ..., and values too large for numeric(4,1) make the deployment fail (1 value in the rehearsal data doesn't fit): shorten or move them in the pre-migration script if they matter
```
`draft` exits 0, and `rehearse` then fails:
```
Error: data-model/draft/schema-change.sql:12: PostgreSQL refused it: numeric field overflow. ...
```
The warning didn't distinguish a value that is rounded (harmless) from one that fails the rehearsal.

### Triage, 2026-10-21

**Verification:** CONFIRMED with the built CLI, and worse than reported.
- `note text` → `varchar(5)` and `amount numeric(10,2)` → `numeric(4,1)` with no seed data: both warnings say "(every value in the rehearsal data fits)".
- With seed rows `1234.56` and `1.25`: "2 values in the rehearsal data don't fit", with no distinction between the one that is rounded and the one that fails. `rehearse` then fails with `numeric field overflow`.
- **New:** seed data holding only `1234.50`, which overflows `numeric(4,1)` but needs no rounding, gives "**every value in the rehearsal data fits**". `rehearse` then fails with `numeric field overflow`.

**Root cause** (`rehearsal/script-coverage.ts`):
- `messageFor` prints "every value in the rehearsal data fits" whenever the count is 0. It never checks whether there are any values. The other kinds use `count()`, which says "no rows" or "no non-null values".
- For a scale narrowing, the counted condition is `col <> round(col, s)`. That counts the rounded values, misses an overflowing value that is already at the new scale, and puts both kinds in one number. The reason text (`narrowingReason` in `sql-analysis/destructive.ts`) does say that values too large make the deployment fail.

## Agent Brief

**Category:** bug
**Summary:** The narrowing warning reports the rehearsal data accurately: no values, values that are cut or rounded, and values that make the deployment fail, counted separately.

**Current behavior:**
A narrowing type change's `draft` warning says "every value in the rehearsal data fits" when the table has no non-null values in the rehearsal data. For `numeric`, it counts only values that change when rounded. So it says "every value … fits" for a value that overflows the new precision without needing rounding, and it lumps rounded and overflowing values into one count. The rehearsal then fails with "numeric field overflow" after a warning that suggested it wouldn't.

**Desired behavior:**
- No non-null values in the rehearsal data: the warning says "(no non-null values in the rehearsal data)", like the other coverage warnings, and keeps the "if a target holds values that don't fit" advice.
- Some values, all fitting: "(every value in the rehearsal data fits)", as today.
- For a `numeric` narrowing whose new precision can overflow, values too large for the new type are counted separately from values only rounded. The warning says how many make the deployment (and the rehearsal) fail, e.g. "(1 value in the rehearsal data is rounded; 1 is too large for numeric(4,1) and makes the rehearsal fail)".
- The length narrowings (`varchar(n)`, `char(n)`, `bit(n)`) keep one count: values longer than n are cut.
- The finalize reason (`narrowingReason`) is unchanged.

**Key interfaces:**
- `ScriptCoverage` for `changed-type` with a narrowing: `rows` stays the affected count. A separate count of overflowing values may be added if the message needs it.
- `affectedCondition` / the narrowing count and `messageFor` in the draft's script coverage.
- `Narrowing` (`kind: "scale"`, `overflows`) from the destructive analysis: the overflow test needs the new precision and scale.

**Acceptance criteria:**
- [ ] API seam: `text` → `varchar(5)` with no seed data warns "no non-null values in the rehearsal data", not "every value … fits".
- [ ] API seam: `numeric(10,2)` → `numeric(4,1)` with seed values `1234.50` and `1.25` reports one rounded and one too large, the latter as failing the rehearsal.
- [ ] With seed values that all fit, "every value in the rehearsal data fits" is unchanged.
- [ ] Round 1's 09 narrowing tests still pass (wording updated where the count text changes).

**Out of scope:**
- Classing a precision-only change (`numeric(10,2)` → `numeric(6,2)`, same scale) as a narrowing. It gets the generic "plain cast" warning today (seen in 104). Worth a separate ticket if wanted.
- `draft` running its schema change to catch the failure itself (102's decision).
