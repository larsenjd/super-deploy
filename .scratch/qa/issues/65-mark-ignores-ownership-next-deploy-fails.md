# 65: mark accepts hand-applied objects owned by another role; the next deploy then fails "must be owner"

**Status:** wontfix
**Category:** bug
**Severity:** medium
**Duplicate of:** 28
**Area:** disp

## What I did
Non-disposable target `qa` (deploy role `disp_deploy`, owner of the database,
not a superuser), migrations 1-3 deployed. Migration 4 creates a table:

```sql
CREATE TABLE "public"."tags" ("id" bigint GENERATED ALWAYS AS IDENTITY NOT NULL, "label" text NOT NULL, CONSTRAINT "tags_label_key" UNIQUE (label), CONSTRAINT "tags_pkey" PRIMARY KEY (id));
GRANT SELECT ON TABLE "public"."tags" TO "disp_reader";
```

A DBA applies it by hand as the superuser (a very likely way to "fix a target
by hand"):

```sh
node sql.mjs qa_disp_qa "$(cat data-model/migrations/00004-add-tags/schema-change.sql)"   # connects as postgres
pnpm exec super-deploy mark --target qa     # at a terminal, typed YES
pnpm exec super-deploy status --target qa
```

Then migration 5 adds a column (`alter table tags add column color text`):

```sh
pnpm exec super-deploy deploy --target qa
```

## Expected
`mark` says the target doesn't match (the replica's `tags` is owned by the
deploy role; the target's by `postgres`), or at least warns that the deploy
role won't be able to alter objects it doesn't own. `status` reports it.

## Actual
mark's confirmation:

```
│  The target matches a replica of migrations up to 00004-add-tags (column order and ownership aside).
...
Marked migration 00004-add-tags as deployed on target qa (attempt #3)
```

`status --target qa`: no drift, exit 0. Next deploy:

```
Error: data-model/migrations/00005-tag-color/schema-change.sql: PostgreSQL refused it: must be owner of table tags
```

No hint that the cause is the ownership of a table that was marked rather
than deployed. `alter table tags owner to disp_deploy` fixes it.

Also checked: `alter table notes owner to postgres` on a fully deployed target
isn't reported by `status` either.

## Notes
README ("The deploy role's own privileges") says it "owns every object it
deploys", which is what makes later migrations work; mark is the one path where
that isn't guaranteed. The "ownership aside" note only appears in the
confirmation box, and doesn't say why that matters.
