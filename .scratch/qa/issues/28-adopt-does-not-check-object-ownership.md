# 28: Adoption doesn't check that the deploy role owns the adopted objects, so the first change fails at deploy

**Status:** ready-for-human
**Category:** enhancement
**Severity:** medium
**Merged:** 65
**Area:** adopt

## What I did
A grown database whose objects were created by another role (here, an admin) rather than the deploy role:

```sql
-- as postgres
create database qa_adopt_owned;
grant connect, create on database qa_adopt_owned to adopt_deployer;
grant create on database qa_adopt_owned to adopt_admin;
-- in qa_adopt_owned
set role adopt_admin;
create schema app;
create table app.widgets (id bigint generated always as identity primary key, name text not null);
create view app.widget_names as select name from app.widgets;
create function app.widget_count() returns bigint language sql security definer set search_path = pg_catalog as $$ select count(*) from app.widgets $$;
grant usage, create on schema app to adopt_deployer with grant option;
```

Project with `managedSchema: "app"`, target `owned` connecting as `adopt_deployer`:

```sh
pnpm exec super-deploy init --adopt owned      # succeeds, no warning
# add a column "color" text to app.widgets in desired-schema/tables.sql
pnpm exec super-deploy draft --name color
pnpm exec super-deploy finalize
pnpm exec super-deploy status --target owned   # 1 pending, nothing about ownership
pnpm exec super-deploy deploy --target owned
```

## Expected
`init --adopt` (or at least `status`/the deploy pre-flight checks) says that `app.widgets`, `app.widget_names` and `app.widget_count()` are owned by `adopt_admin`, not the deploy role. It tells the user to run `ALTER ... OWNER TO adopt_deployer` (or `REASSIGN OWNED`) first, and that ownership decides who a `SECURITY DEFINER` function runs as.

## Actual
```
Error: data-model/migrations/00002-color/schema-change.sql: PostgreSQL refused it: must be owner of table widgets
```

After `alter table app.widgets owner to adopt_deployer` (and the same for the view and function), `status` showed no drift and the deploy succeeded.

## Notes
- README, "What each target needs set up outside super-deploy", says the deploy role "owns every object it deploys", but nothing covers objects that existed before adoption. The "Adopting an existing database" section could list this as a prerequisite.
- Changing the owner of a `SECURITY DEFINER` function changes whose privileges it runs with, so this is worth saying explicitly.

### Triage, 2026-10-20

**Verification:** CONFIRMED; partly by design.
- *Adoption (28):* a schema, table and SECURITY DEFINER function owned by an admin. `init --adopt` succeeded with no warning; `status` showed no drift and 1 pending; `deploy` failed with `must be owner of table widgets`. Adoption has no ownership check, and the adoption analysis drops `ALTER ... OWNER TO` (`src/sql-analysis/adoption.ts:12`).
- *Mark (65):* migration 2 applied by hand as the superuser, then `mark` printed "(column order and ownership aside)" and `Marked`. `status` showed no drift; the next `deploy` failed with `must be owner of table tags`. `cli-mark.test.ts` already asserts that mark accepts a table owned by another role. An `alter table ... owner to <superuser>` on a deployed table isn't reported by `status` either.
- *By design:* drift and `mark` don't compare owners (REFINEMENTS "Roles, grants and ownership": "ownership is not diffed").
- *Not by design:* the same REFINEMENTS entry and the README promise that objects belong to the deploy role and that "a SECURITY DEFINER function always runs as the deploy role". Adoption and `mark` break that silently. A hand-applied, marked or adopted SECURITY DEFINER function runs as its real owner, possibly a superuser. That's worse than the failing deploy.

## Brief (ready-for-human)

**Category:** enhancement
**Summary:** Adoption and `mark` should flag managed-schema objects the deploy role doesn't own, before they're recorded.

**Current behavior:**
`init --adopt` and `mark` record targets whose objects are owned by another role. Nothing says so, and `status` and the pre-flight checks don't either. The next migration that alters such an object fails with "must be owner". A SECURITY DEFINER function among them runs as its real owner, contrary to the README.

**Desired behavior (once decided):**
Before recording, adoption and `mark` list each managed-schema object whose owner isn't the deploy role (or a role it belongs to), with the `ALTER ... OWNER TO` that fixes it. SECURITY DEFINER functions are called out. Depending on the decision, `status` and the deploy pre-flight checks report the same.

**Key interfaces:**
- `adopt`'s target reading and its unsupported or conflict errors.
- `mark`'s replica comparison and confirmation details.
- The deploy pre-flight findings (if status and deploy check too).
- REFINEMENTS "Roles, grants and ownership", and the README's "Adopting an existing database" prerequisites.

**Acceptance criteria (once decided):**
- [ ] Adopting a target with a table, view and function owned by another role refuses (or warns), naming each object and its owner.
- [ ] `mark` on a hand-applied migration whose objects belong to another role does the same before asking YES.
- [ ] A SECURITY DEFINER function owned by another role is named with the privilege consequence.
- [ ] After `ALTER ... OWNER TO <deploy role>`, both succeed silently.
- [ ] REFINEMENTS and the README match the decision.

**Out of scope:**
- Diffing ownership in the catalog comparison in general.
- Managing a dedicated owner role for SECURITY DEFINER functions.

**Why not delegated:** it revises a recorded V1 decision (ownership isn't tracked) and chooses refuse versus warn.
**Decision needed:**
- Adoption and `mark` refuse, listing each object and the `ALTER ... OWNER TO` fix. `status` and pre-flight warn about objects not owned by the deploy role (recommended).
- Warn only, everywhere.
- Adoption and `mark` only, no `status` or pre-flight check.
