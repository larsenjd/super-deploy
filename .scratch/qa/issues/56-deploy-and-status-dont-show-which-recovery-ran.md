### Triage, 2026-10-20

**Verification:** CONFIRMED-BY-CODE. `deploy` and `status` copy only `{number, name, folder}` into their results (the `DeployedMigration` type), so the Recovery number is lost before the CLI prints anything. The attempt description in `cli/definitions.ts` has no Recovery variant. Only the history table's `migrations.recovery` column records which variant ran.

## Agent Brief

**Category:** enhancement
**Summary:** `deploy` and `status` show when a migration runs, or ran, as one of its Recoveries.

**Current behavior:**
When a migration has a finalized Recovery, `deploy` runs the Recovery's scripts and records the Recovery number in the history schema. But the deploy result, `status`'s pending list and the attempt lines print only the migration's number and name. So the user can't see which scripts ran, or will run, on a target without querying the history table.

**Desired behavior:**
- `status`'s pending list shows `00004-add-country (Recovery 1)` when the deploy would use Recovery 1.
- `deploy`'s summary shows `Deployed 1 migration to X: 00004-add-country (Recovery 1)`.
- An attempt in `status`'s "Recent attempts" that deployed a migration through a Recovery says so.
- Migrations without a Recovery print as they do today.

**Key interfaces:**
- `DeployedMigration` (and any pending-migration type in `status`'s result): add an optional `recovery?: number`.
- The deploy and status API results expose it, so API users get it too.
- The attempt description in the CLI: it needs the Recovery numbers of the migrations an attempt recorded, read from the history schema.

**Acceptance criteria:**
- [ ] API seam: after finalizing a Recovery of a failed migration, `status`'s result lists the pending migration with `recovery: 1`, and `deploy`'s result does too.
- [ ] CLI seam: the deploy summary and the status pending line contain "(Recovery 1)".
- [ ] `status`'s attempt line for that deploy mentions Recovery 1.
- [ ] A deploy without Recoveries prints exactly as before.

**Out of scope:**
- Listing every recorded migration in `status`.
- Changes to the history schema layout (the `recovery` column already exists).
