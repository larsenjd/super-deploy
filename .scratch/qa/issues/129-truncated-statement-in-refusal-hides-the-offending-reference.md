# 129: Adoption refusals truncate the CREATE statement, hiding the part that is refused

**Status:** ready-for-agent
**Category:** enhancement
**Severity:** medium
**Area:** adopt
**Round:** 2

## What I did
A common setup: extensions installed in `public`, used by tables in the app's schema.

```sql
-- database qa2_adopt_ext, as postgres
create extension citext; create extension pgcrypto;
create schema app authorization qa2_adopt_deployer;
-- as qa2_adopt_deployer
create table app.users (id int primary key, email public.citext not null, token bytea not null default public.gen_random_bytes(16));
```
```sh
pnpm exec super-deploy init --adopt qa      # managedSchema: "app"
```

## Expected
The refusal says which column (or which reference) breaks the rule: `column email of table app.users has type public.citext (extension citext)`, `column token's default calls public.gen_random_bytes`.

## Actual
```
Target qa has 1 thing V1 doesn't support:
  CREATE TABLE "app"."users" ("id" integer NOT NULL, "email" public.citext NOT NULL, "token" bytea NOT NULL DEFAULT publi…
    undeclared-schema: Schema "public" is not declared: the desired schema may reference only the managed schema "app" and pg_catalog (PL/pgSQL bodies may also reference the externalSchemas in super-deploy.config.ts)
Error: Cannot adopt target qa: its managed schema has 1 thing V1 doesn't support, listed above. Nothing was written; change the target first, then adopt again
```

The statement is cut at 120 characters, so the second offending reference (the `pgcrypto` default) is invisible; a wide table hides all of them. The same truncation hid `WITH (fillfactor=70)` in `CREATE TABLE "app"."logs" (... CONSTRAINT "logs_pkey" PRIMAR…` refused as "Table storage parameters are not supported".

## Notes
- Other entries in the same list are named by object (`column b of table app.virt`, `serial column app.people.id`), which is much clearer; table-level refusals could name the column or option too, or print the whole statement.
- "Schema public is not declared" suggests declaring it would help, but `externalSchemas` only applies to PL/pgSQL bodies, so for a table there is no declaration that fixes it. The README doesn't say what to do with an existing database that uses extension types/functions from `public` (convert to `text` + check, use built-ins like `gen_random_uuid()`?).

**Verification:** CONFIRMED on `qa2t_adopt_ext` (`citext` and `pgcrypto` in `public`, `app.users` using both, and `app.logs` `with (fillfactor=70)`). Both entries were statements cut at 120 characters:

The `bad` database shows the same for a sequence, a constraint trigger and partitions.

**Cause:** adoption's `analyse` (`commands/adopt.ts`) names a rule violation by `firstLine(violation.statement)`, truncated to 120 characters. `adoptedObject` already names a statement by its object, and is used for statements the throwaway database refuses (`refusedStatement`). Not every entry uses it yet. The `undeclared-schema` finding (`sql-analysis/schemas.ts`, `referenceFindings`) records only the schema, once per statement, not which names were qualified with it. Its message mentions `externalSchemas`, which can't help a reference bound at CREATE. Adoption's advice correctly doesn't suggest declaring the schema, but the reason line still reads as if it would help.

## Agent Brief

**Category:** enhancement
**Summary:** Adoption names every refused entry by its object, and the reason names the offending reference or option.

**Current behavior:**
Entries from the desired-schema rules show the generated statement's first line, cut at 120 characters, so the part that is refused is often invisible. An entry for a table that references an extension's type and function in `public` says only `Schema "public" is not declared`, which suggests a declaration that can't fix it. The README doesn't say what to do with an existing database whose tables use extension types or functions from another schema.

**Desired behavior:**
- Every adoption entry is named by its object (`table app.users`, `sequence app.ticket_seq`, `trigger ct on app.base`), as `adoptedObject` names them, never by a truncated statement.
- An `undeclared-schema` entry's reason names each qualified reference to the schema, e.g. `public.citext, public.gen_random_bytes`.
- For a reference bound at CREATE (anywhere but a PL/pgSQL body), the reason says that tables, views, defaults and types can only use the managed schema and `pg_catalog`, and that declaring the schema won't help. It applies to `draft` too, since the rule is shared.
- The storage-parameter entry names the parameters (`fillfactor=70`).
- The README's "Adopting an existing database" says that columns using another schema's types or functions (extensions in `public`, typically) must be changed on the target first, e.g. `text` with a CHECK instead of `citext`, and the built-in `gen_random_uuid()` instead of pgcrypto's functions.

**Key interfaces:**
- `UnsupportedObject.object` and `.reason` as adoption builds them from `SqlRuleViolationError`.
- `RuleViolation.reference` (`SchemaReference`): carry the qualified names, not only the schema.
- `referenceFindings` / `referencedSchemas`, and the storage-parameter rule in the desired-schema rules.

**Acceptance criteria:**
- [ ] API seam: adopting the reporter's `ext` database lists `table app.users` with both `public.citext` and `public.gen_random_bytes` in its reason, and `table app.logs` with `fillfactor`. No entry ends in `…`.
- [ ] No `object` in an adoption refusal is a statement's text, for tables, sequences, views, functions and triggers.
- [ ] A PL/pgSQL body referencing an undeclared schema still gets the advice to declare it in `externalSchemas`.
- [ ] `draft` with a desired-schema table column typed `public.citext` names `public.citext` in its violation.

**Out of scope:**
- Supporting extensions or storage parameters.
- Formatting of the ownership refusal (121).
