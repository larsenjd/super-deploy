## Agent Brief

**Category:** enhancement
**Summary:** Add template-README sections for the non-happy-path workflows, and stop Recovery drafts telling users to "run draft again".

**Current behavior:**
The template README (the user documentation `init` copies) covers only drafting, finalizing and deploying. Users learn everything below from `--help`, confirmation boxes and error messages:
- Recoveries.
- Destructive changes and `--acknowledge-destructive`.
- Draft housekeeping commands.
- Disposable targets and the guarded commands.
- The files a draft may contain.

A Recovery draft's `schema-change.sql` keeps the generated header saying "change the desired schema ... and run draft again", which `draft` refuses for a Recovery.

**Desired behavior:**
The template README gains these sections. Every fact must come from the code, `--help` and the spec, not from guesses.
1. **The files of a draft and a migration:** `schema-change.sql` (generated), the optional `pre-migration.sql` and `post-migration.sql`, and `seed-data.sql` (rehearsals only). Give the order they run in (seed data, then pre-migration, schema change, post-migration), and say that other files are not run.
2. **When a deploy fails:**
   - The deployment ran in one transaction and was rolled back.
   - The finalized migration can't be edited.
   - The Recovery workflow: `recovery --migration N`; reproduce the problem rows in `seed-data.sql`; fix the scripts; `rehearse` and `finalize` (which writes a Recovery folder); the next `deploy` uses it. The schema change never changes.
3. **Destructive changes:**
   - What counts as destructive.
   - That `finalize` asks in a terminal, and needs `--acknowledge-destructive` without one (CI).
   - What acknowledging means.
4. **Changing your mind:**
   - `discard-draft`, `restore-schema` and `unfinalize`.
   - Their `--acknowledge-overwrite` flag and when it's needed.
   - That `unfinalize` must never be used on a migration a target has recorded: the target will refuse, and the way out is to restore the original from version control.
5. **Disposable targets and the guarded commands:**
   - The disposable flag lives on the target (in its history schema), not in the config, and is set with `disposable --target X --set yes|no`.
   - `deploy-draft`, with and without `--with-seed`; the target then refuses `deploy` and `mark` until `rebuild` resets it.
   - `rebuild --to N`: what it drops and keeps, as the code does it today, and that it never loads seed data.
   - `mark`: when to use it, and that its comparison ignores column order and ownership.
   - All four need a terminal and refuse under CI.

Separately, `recovery` writes the draft's `schema-change.sql` with a header that fits a Recovery: the schema change is migration N's, is not regenerated, and must not be edited. The migration's own finalized, hashed file is unchanged.

**Key interfaces:**
- The template README.
- The `recovery` command: the header of the `schema-change.sql` it writes into the draft.
- The deploy-time file list (`deployTimeFileNames`, `recoveryFileNames`) is the source of truth for section 1.

**Acceptance criteria:**
- [ ] The template README has the five sections above, and the commands, flags and file names it mentions match `--help` and the code.
- [ ] A Recovery draft's `schema-change.sql` no longer says "run draft again" (API or CLI seam test on `recovery`).
- [ ] Finalizing a Recovery still produces a Recovery whose schema change matches the original migration's (existing Recovery tests pass).
- [ ] The template's precommit still passes.

**Out of scope:**
- Any change to rebuild's behaviour (issue 61) or to deploy failure messages (issue 46).
- Refusing unknown files in a draft (issue 44).
- Showing Recoveries in `deploy` and `status` output (issue 56).
- Making `unfinalize` warn (issue 10).
