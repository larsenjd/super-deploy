# 146: Lock-timeout failures and "Locked by" don't name the session that holds the lock

**Status:** resolved
**Category:** enhancement
**Severity:** low
**Area:** fail
**Round:** 2

## What I did
Another session (application_name `qa2_fail_holder`) runs `begin; select * from app.customers;` and stays open. Then:
```sh
pnpm exec super-deploy deploy --target qa        # migration runs ALTER TABLE customers … SET NOT NULL
```
And while one deploy waits on that lock, from another shell:
```sh
pnpm exec super-deploy status --target qa
```

## Expected
Round 2 made super-deploy's own lock refusals name the holder's session and how to end it. A lock timeout on a table could do the same, for example: "waiting for a lock on app.customers held by server process 2499007 (qa2_fail_holder, idle in transaction since …)". PostgreSQL's `pg_blocking_pids()` gives this.

## Actual
```
Error: data-model/migrations/00003-tighten/schema-change.sql:4: PostgreSQL refused it: canceling statement due to lock timeout. The deployment rolled back: target qa is unchanged, still at migration 00002-add-orders. The target's lockTimeout (default 5s) ran out waiting for a lock: retry once whatever held the lock has finished.
```
`status` during the wait:
```
Locked by attempt #5 (deploy by jonathanl, started …, server process 2501425, active, statement started …: ALTER TABLE "app"."customers" ALTER COLUMN "name" SET NOT NULL)
```
It doesn't say the deploy is itself waiting on a lock, or on whom.

## Notes
"Retry once whatever held the lock has finished" leaves the user to work out what that was, on production, under time pressure. Low priority.

### Triage, 2026-10-21

**Verification:** CONFIRMED. With a session holding SHARE on `app.t2`, `status` during the deploy's wait showed `Locked by attempt #9 (deploy …, server process 2618905, active, statement started …: COMMENT ON TABLE "app"."t2" IS 'g5')`, with nothing saying that statement is waiting, or on whom. The lock-timeout failure is as reported (and quotes the wrong value, 145).

**Notes:**
- Nothing in `src/` calls `pg_blocking_pids` or reads `wait_event_type`. Round 1's 46 left naming the blocker out of scope as "nice to have"; round 2's lock refusal (51) names super-deploy's own holder only.
- `status` can name the blockers cheaply: it already reads the holder's `pg_stat_activity` row, and `pg_blocking_pids(<holder pid>)` gives what it waits on.
- The lock-timeout error is harder. Once PostgreSQL cancels the statement, the transaction is aborted and the error carries no relation, so the blocker has to be sampled while the statement waits, from the attempt-log session.

## Brief (ready-for-human)

**Category:** enhancement
**Summary:** When a deployment waits on, or times out on, a lock held by another session, say which session holds it.

**Current behavior:**
A lock timeout says `retry once whatever held the lock has finished`. `status` during the wait shows the deploy's own statement as `active`, but not that it waits for a lock, or for whom.

**Desired behavior (once decided):**
- `status` and the target-lock refusal: when the holding attempt's statement waits for a lock, add `waiting for a lock held by server process N (<application_name>, <user>, <state> since …: <query>)` for each blocking process.
- A deploy failing on a lock timeout names the session(s) that held the lock when it gave up, and how to end one (`select pg_terminate_backend(N)`), if that option is chosen.

**Key interfaces:**
- The lock-holder description shared by `status` and `TargetLockedError`.
- `SqlFileFailedError`'s next step for SQLSTATE 55P03.
- The attempt-log session, which could sample `pg_blocking_pids` of the command session while a statement runs.

**Acceptance criteria (once decided):**
- [ ] API seam: while a deploy waits on a lock held through `testSession`, `status` names the test session's server process and its state.
- [ ] If chosen: a deploy failing on `lockTimeout` with a lock held through `testSession` names that session's server process.

**Out of scope:**
- The value quoted in the timeout message (145).
- Lost or ended sessions (142).
- Cancelling blockers automatically.

**Why not delegated:** sampling blockers during every deploy statement adds a second session's polling to the deploy path, for a low-severity message. Whether it's worth it is a product call.
**Decision needed:**
- `status` and the lock refusal name what the holder waits on; the lock-timeout error stays as it is but says how to find the blocker next time (`pg_blocking_pids`, `pg_stat_activity`) (recommended: cheap, and `status` is where an operator looks during a stuck deploy).
- Both: also sample blockers from the attempt-log session while a deploy statement waits, and name them in the lock-timeout error.
- Neither: wontfix.

### Decided, 2026-10-21

The maintainer chose **option 1**: `status` and the lock refusal name what the holding session is waiting on; the lock-timeout error stays as it is but adds how to find the blocker next time (`select pg_blocking_pids(<pid>)`, `pg_stat_activity`). No sampling during a deploy.

**Acceptance criteria:** the brief's first option.
