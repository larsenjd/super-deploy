# 180: Routines whose bodies use unqualified names deploy fine but fail for every caller when `managedSchema` isn't `public`

**Status:** ready-for-agent
**Category:** bug
**Severity:** high
**Area:** privs
**Round:** 2

## What I did
Shared server, as superuser `postgres`:

```sql
create role qa2_privs_deploy login password 'pw';
create role qa2_privs_writer login password 'pw';
create database qa2_privs_qa;
-- in qa2_privs_qa:
grant connect, create on database qa2_privs_qa to qa2_privs_deploy;
grant connect on database qa2_privs_qa to qa2_privs_writer;
create schema app authorization qa2_privs_deploy;
```

As `qa2_privs_deploy`, the README's recipe:
`grant usage on schema app to qa2_privs_writer; alter default privileges for role qa2_privs_deploy in schema app grant select, insert, update, delete on tables to qa2_privs_writer;`

Project: `init`, `git init`, `pnpm install`; config gets `managedSchema: "app"` and
`qa: { adapter: postgresTarget({ env: "QA_DATABASE_URL" }) }`,
`QA_DATABASE_URL=postgres://qa2_privs_deploy:pw@localhost:54818/qa2_privs_qa`.

Desired schema (the README says "Write object names unqualified"):

```sql
create table customers (id bigint generated always as identity primary key, email text not null);
create table orders (
  id bigint generated always as identity primary key,
  customer_id bigint not null,
  constraint orders_customer_fk foreign key (customer_id) references customers (id)
);
create function order_count(cid bigint) returns bigint
language sql stable as $$ select count(*) from orders where customer_id = cid $$;
```

`draft --name orders`, `finalize`, `deploy --target qa`: all succeed. Then call it
(`sqlas.mjs <role> <db> <sql>` is a small `pg` script like `sql.mjs` that logs in as
the given role):

```
node sqlas.mjs qa2_privs_writer qa2_privs_qa "select app.order_count(1)"
node sqlas.mjs qa2_privs_deploy qa2_privs_qa "select app.order_count(1)"
node sqlas.mjs postgres        qa2_privs_qa "select app.order_count(1)"
```

## Expected
The function works for its callers, or super-deploy refuses/warns at `draft` that
the body's unqualified `orders` will resolve against the caller's `search_path`.

## Actual
Every caller, including the deploy role and the superuser, gets:

```
ERROR: relation "orders" does not exist
```

`set search_path = app; select order_count(1)` works. The rehearsal, `finalize`
and `deploy` all pass, because super-deploy runs them with the managed schema on
the search path. The same applies to PL/pgSQL bodies (and triggers that call them),
which are resolved at call time too.

## Notes
- README "Rules for writing it" says "Write object names unqualified (or qualified
  with the managed schema)" and its own `load_staging` example uses an unqualified
  `staging`. With the default `managedSchema: public` that works by luck (public is
  on the default search path); with `app` it breaks at runtime only.
- Workarounds that super-deploy accepts: qualify names in bodies (`app.orders`), or
  give the routine `set search_path = app` (accepted by `draft`). Neither is
  documented. Alternatively `alter role ... set search_path` for every app role on
  every target.
- Suggestion: either document "qualify names inside routine bodies, or add
  `SET search_path`", or have the rules refuse/warn about unqualified relation
  names in bodies when `managedSchema` isn't on the default search path.

### Triage, 2026-10-21

**Verification:** CONFIRMED on PostgreSQL 18 with a fresh project (`managedSchema: "app"`, target `qa` with a non-superuser deploy role).
- A `LANGUAGE sql` function and a PL/pgSQL function, each reading unqualified `orders`, drafted, finalized and deployed. Calling either as the writer role, the deploy role and `postgres` gave `relation "orders" does not exist`.
- Both workarounds work: `SET search_path = app` on the routine, and a `BEGIN ATOMIC` body (its references bind at CREATE, so it works whatever the caller's search path).

**Root cause:**
- Every rehearsal and deployment pins `search_path` to the managed schema and `pg_catalog` (`rehearsal/throwaway.ts:83-91`, used by `deploy/engine.ts:192`). So unqualified names in a routine's string body validate at CREATE and work for triggers fired by the deployment's own scripts.
- PostgreSQL resolves a string body (`LANGUAGE sql` with `AS '...'`, and every PL/pgSQL body) again at each call, with the caller's `search_path`. With a managed schema other than `public`, nobody's default search path includes it.
- No rule looks at unqualified names in bodies. The header of `sql-analysis/routine-bodies.ts:9` says `LANGUAGE sql` string bodies "bind at CREATE like the rest of the statement", which is true only of their validation.
- The README tells users to "Write object names unqualified" (`packages/template/README.md:198`), and its `load_staging` example (`:523-526`) does. The only place that knows about this is the materialized-view hint (`rehearsal/throwaway.ts:194`).

**Intended?** No. The spec and ADRs say nothing about a routine's search path. The README's advice is wrong for any managed schema but `public`.

## Brief (ready-for-human)

**Category:** bug
**Summary:** A routine whose string body uses unqualified names of managed-schema objects works in rehearsals and deployments but fails for every caller when the managed schema isn't `public`. super-deploy should catch it, or at least the README must say how to write such bodies.

**Current behavior:**
`draft`, `rehearse`, `finalize` and `deploy` accept a function or trigger function whose body says `from orders`. On a target with `managedSchema: "app"`, every call fails with `relation "orders" does not exist`, including triggers fired by the application's DML. The README recommends unqualified names.

**Desired behavior (once decided):**
- The README's "Rules for writing it" says routine string bodies are resolved with the caller's search path, and gives the three ways to write them: qualify names with the managed schema, give the routine `SET search_path = <managed schema>, pg_catalog`, or (for `LANGUAGE sql`) use a `BEGIN ATOMIC` body. The `load_staging` example follows it.
- Depending on the decision, the desired-schema rules also refuse (or warn about) a routine whose string body refers to a managed-schema object by an unqualified name and has no `SET search_path`. The message names the routine and the three fixes.

**Key interfaces:**
- The desired-schema rules for `CREATE FUNCTION` / `CREATE PROCEDURE` and the routine-body analysis (`plpgsqlFindings`, `sqlBodyFindings`), which already parse embedded SQL.
- The set of names the desired schema creates (to tell `orders` from `count` or `now`).

**Acceptance criteria (once decided):**
- [ ] The README explains the caller's search path and the three fixes; `load_staging` qualifies its table or sets `search_path`.
- [ ] With `managedSchema: "app"`, a PL/pgSQL and a `LANGUAGE sql` string body reading unqualified `orders` get the chosen refusal or warning at `draft`, naming the routine and the fixes (unit seam).
- [ ] The same routines pass with `app.orders`, with `SET search_path = app, pg_catalog`, and (for `LANGUAGE sql`) with a `BEGIN ATOMIC` body.
- [ ] Unqualified built-ins (`count`, `now()`) are never flagged.
- [ ] With the default `managedSchema: "public"`, nothing changes.
- [ ] The comment in the routine-body analysis that says string bodies "bind at CREATE" is corrected.

**Out of scope:**
- Changing the pinned `search_path` of rehearsals and deployments.
- Rewriting users' bodies or adding `SET search_path` automatically.
- Materialized views, which PostgreSQL builds with `search_path = pg_catalog`; they already have their own hint.
- Other gaps in routine-body rules: privilege statements (185) and `SET ROLE` (190) inside bodies.

**Why not delegated:** a new rule changes what the desired schema accepts, and whether it is a refusal, an overridable risk or a warning, and whether `public` is exempt, are product calls.
**Decision needed:** how to stop this reaching a target.
- Refuse, as a structural rule, a routine with a string body that names a managed-schema object unqualified and has no `SET search_path`, only when `managedSchema` isn't `public`; document the three fixes (recommended). `public` is on every default search path, so exempting it keeps existing projects working.
- Warn instead of refusing (in `draft`, `finalize` and `validate`), same condition.
- Document only: the README section above, no rule.

### Decided, 2026-10-21

The maintainer chose **warn**, not refuse.
- When `managedSchema` isn't `public`, a routine whose string body names a managed-schema object unqualified and has no `SET search_path` gets a warning in `draft`, `finalize` and `validate` (so `validate --strict` fails CI), naming the routine and the unqualified names, and giving the fixes: qualify the names, add `SET search_path = <schema>, pg_catalog` to the routine, or use a `BEGIN ATOMIC` body.
- Projects whose managed schema is `public` get no warning.
- README: a section on writing routine bodies for a non-public managed schema.

**Acceptance criteria:**
- [ ] SQL-analysis seam: an unqualified reference in a `LANGUAGE sql` string body and in a PL/pgSQL body warns when the managed schema is `app`; no warning when qualified, with `SET search_path`, with `BEGIN ATOMIC`, or when the managed schema is `public`.
- [ ] API seam: `draft` reports the warning; `validate --strict` exits 1 on it.
