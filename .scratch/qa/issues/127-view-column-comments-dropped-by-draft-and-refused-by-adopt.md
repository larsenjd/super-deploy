# 127: Comments on view and materialized-view columns: adoption refuses them as "not-reproduced", and draft silently drops them

**Status:** ready-for-agent
**Category:** bug
**Severity:** medium
**Area:** adopt
**Round:** 2

## What I did
```sql
-- database qa2_adopt_cmt, owned by the deploy role
create schema app;
create table app.t (id int primary key, v text);
create view app.v as select id, v from app.t;
create materialized view app.mv as select id from app.t;
comment on column app.v.v is 'view col';
comment on column app.mv.id is 'mv col';
comment on view app.v is 'a view';
```
```sh
pnpm exec super-deploy init --adopt qa      # managedSchema: "app"
```

Then, in a project with no migrations, the same thing written as a desired schema:
```sql
create table t (id int primary key, v text);
create view v as select id, v from t;
comment on column v.v is 'view col';
```
```sh
pnpm exec super-deploy draft --name try
pnpm exec super-deploy rehearse
```

## Expected
README "What the desired schema supports": views, materialized views and "`COMMENT ON` the objects above" are supported. Column comments on views are common in existing databases (documentation tools write them), so adoption should reproduce them, and `draft` should generate them.

## Actual
Adoption:
```
Target qa has 2 things V1 doesn't support:
  column id of materialized view app.mv
    not-reproduced: The desired schema generated from the target creates it differently: on the target: comment: pg_class mv.id mv col
  column v of view app.v
    not-reproduced: The desired schema generated from the target creates it differently: on the target: comment: pg_class v.v view col
Error: Cannot adopt target qa: its managed schema has 2 things V1 doesn't support, listed above. Nothing was written; change the target first, then adopt again
```

Draft accepts the desired schema but leaves the comment out (`Created draft try: 2 statements`, only the table and the view). Rehearse then fails and blames the scripts, though the draft has none:
```
Error: The rehearsal does not match the desired schema, and running draft again won't change that: the desired schema hasn't changed since draft, so the pre-migration script, post-migration script or seed data cause the difference (...). First difference: catalog: from the desired schema: comment: pg_class v.v view col
```

## Notes
- The adoption refusal's wording ("comment: pg_class v.v view col") is internal; it doesn't say "comments on view columns can't be reproduced; remove them with `COMMENT ON COLUMN app.v.v IS NULL`".
- Workaround: `comment on column ... is null` on the target, then adopt (worked).
- Guess: the differ doesn't emit `COMMENT ON COLUMN` for view columns.

### Triage, 2026-10-21

**Verification:** CONFIRMED with the reporter's SQL (`qa2t_adopt_cmt`, and a fresh project for `draft`).
- Adoption refused `column v of view app.v` and `column id of materialized view app.mv` as `not-reproduced`, citing `comment: pg_class v.v view col`. The comments on the view and the materialized view themselves were reproduced.
- `draft` wrote only the table, the view and the materialized view, with no `COMMENT ON COLUMN`.
- `rehearse` then failed with both comments as differences and blamed the scripts ("the pre-migration script, post-migration script or seed data cause the difference"), though the draft has none.

**Cause:** pg-delta 1.0.0-alpha.59 doesn't plan comments on view and materialized-view columns. Table column comments work. The catalog comparison (`verification/catalog.ts`) does compare them, so the gap is caught, but only after the fact. This is the same kind of silent gap as F4 (comments on constraint-backing indexes) in `.scratch/super-deploy/research/pg-delta-prototype.md` §8. That one isn't refused up front either.

The README lists "`COMMENT ON` the objects above" as supported, so the README's promise is broken today.

## Brief (ready-for-human)

**Category:** bug
**Summary:** Comments on view and materialized-view columns should either be reproduced, or be refused up front with a clear reason, in drafts and in adoption alike.

**Current behavior:**
- `draft` silently leaves such comments out, and `rehearse`/`finalize` then fail with a message blaming scripts that don't exist.
- Adoption refuses them as `not-reproduced`, with catalog notation and no fix.

**Desired behavior (once decided):**
- Either the generated schema change carries `COMMENT ON COLUMN` for view and materialized-view columns, so `draft`, `rehearse` and adoption all work;
- or the desired-schema rules refuse such comments as `unsupported-object`, so `draft` names the statement and adoption lists `column v of view app.v` with the reason and the fix `COMMENT ON COLUMN app.v.v IS NULL`.
- The README's supported and refused lists match.

**Key interfaces:**
- The differ wrapper (`Differ`, pg-delta's plan), or the desired-schema rules (`checkComment` and the statement facts it needs to know the commented relation is a view).
- Adoption's refusal entries.
- The README's "What the desired schema supports"; pg-delta-prototype §8 "Known behaviours".

**Acceptance criteria (once decided):**
- [ ] The reporter's desired schema (a view with a column comment) either drafts and rehearses, or is refused by `draft` naming the comment statement.
- [ ] Adopting the reporter's `cmt` database either succeeds, or lists the two column comments with a readable reason and the `IS NULL` fix.
- [ ] Changing such a comment between migrations behaves consistently with that choice.
- [ ] §8 of the pg-delta research and the README record the behaviour.

**Out of scope:**
- The rehearsal-mismatch message blaming scripts when a draft has none, a follow-up to round-1 issue 17. File it separately if wanted.
- Comments on constraint-backing indexes (F4).

**Why not delegated:** choosing between adding our own planning beside pg-delta (ADR-0003's differ seam) and narrowing what the desired schema supports.
**Decision needed:**
- Refuse comments on view and materialized-view columns with a static desired-schema rule and list them in the README's "Refused". Adoption reports them under that rule with the `IS NULL` fix. Cheap, and loud where the gap is today silent (recommended).
- Add the missing statements: after pg-delta's plan, emit `COMMENT ON COLUMN` for view and materialized-view columns whose comment differs, including after a view is recreated. Keeps the README's promise, but adds planning of our own beside the differ.
- Report it upstream and wait for a pg-delta fix, with the first option until then.

### Decided, 2026-10-21

Policy decided for 101, 103, 104 and 127 together: **keep pg-delta's output** (as with 09) and warn, refuse or document; never patch or post-process it. Report each case upstream and record it in pg-delta research §8 ("Known behaviours").

For 127: **refuse** comments on view and materialized-view columns.
- A static desired-schema rule refuses `COMMENT ON COLUMN <view>.<column>` (views and materialized views), saying pg-delta doesn't reproduce them in V1. Listed in the README's "Refused".
- Adoption reports such comments under that rule, with the fix (`COMMENT ON COLUMN ... IS NULL` on the target, or keep it out of the desired schema).
- Report upstream; research §8 records it.

**Acceptance criteria:**
- [ ] The rule refuses a comment on a view column and on a materialized-view column; a comment on a table column is still accepted (SQL-analysis seam).
- [ ] Adopting a target with a view-column comment refuses it under the rule with the fix (API seam).
