# 142: A deploy whose session the server ends gets a raw driver error that doesn't say the deployment rolled back

**Status:** resolved
**Category:** bug
**Severity:** medium
**Area:** fail
**Round:** 2

## What I did
Target `qa` on the shared server, deployed as non-superuser `qa2_fail_deployer`, with migration 9 pending (`COMMENT ON TABLE orders …`). Another session holds `lock table app.orders in access exclusive mode`, so the deploy waits.

**A: the DBA ends the session**, as README's "Targets" section recommends for a stuck deployment:
```sh
pnpm exec super-deploy deploy --target qa > term.out 2> term.err &
sleep 4
# as qa2_fail_deployer:
select pg_terminate_backend(<the deploy's backend pid>);
```

**B: the target server shuts down mid-deploy** (my own private PG18 on port 54899, not the shared one): `pg_ctl -D … -m fast stop` while the deploy waits for a lock.

**C: the CLI is frozen** (`kill -STOP <cli.js pid>`), its session is ended with `pg_terminate_backend`, then the CLI resumes with `kill -CONT`.

**D: a frozen TCP path.** The deploy goes through a TCP proxy that I froze with SIGSTOP, then resumed after its session was terminated.

## Expected
Like any other failed deploy (round 2: "A failed deploy says it rolled back and points to Recovery"): the connection was lost or ended by the server, the deployment rolled back, target qa is unchanged at migration N, and what to do next (retry).

## Actual
A (exit 1):
```
Error: terminating connection due to administrator command
```
B (exit 1):
```
Error: terminating connection due to administrator command
```
C (exit 1):
```
Error: Client has encountered a connection error and is not queryable
```
D (exit 1). This one says it rolled back, but blames PostgreSQL and deferred constraints for a lost connection:
```
Error: data-model/migrations/00018-t2d/schema-change.sql: PostgreSQL refused it: deferred constraints checked at the end of the migration: Client has encountered a connection error and is not queryable. The deployment rolled back: target qa is unchanged, still at migration 00017-t2c.
```
`status` records these as `deploy failed migration 9 …: terminating connection due to administrator command`, and in case C `deploy failed migration 9 …: Client has encountered a connection error and is not queryable`. In case B the attempt is later settled as `abandoned` (`The command ended without recording an outcome; settled as abandoned`).

## Notes
The target was in fact unchanged each time (`status` shows the migration still pending), but none of A–C says so. "administrator command" and "not queryable" are PostgreSQL's and node-postgres's own wording. The user is left to wonder whether part of the deployment committed.

### Triage, 2026-10-21

**Verification:** CONFIRMED. Where the session ends decides what the user sees.
- A: with `lock table app.t2 in access exclusive mode` held, the deploy waits in the drift check's catalog read (`select class::oid … ` in `pg_stat_activity`), before the deploy transaction. `pg_terminate_backend` there gave a bare `Error: terminating connection due to administrator command`, recorded the same way.
- With `share mode` instead, the deploy waits on its own `COMMENT ON` inside the deploy transaction. Terminating it gave `schema-change.sql:4: PostgreSQL refused it: terminating connection due to administrator command. The deployment rolled back: target qa is unchanged, still at migration 00021-t2-g1.` That one is right about the rollback, but presents a terminated session as PostgreSQL refusing the SQL.
- D: reproduced through a frozen TCP proxy (also 150's setup): `PostgreSQL refused it: deferred constraints checked at the end of the migration: Client has encountered a connection error and is not queryable`. The connection error surfaced at the migration-boundary `SET CONSTRAINTS ALL IMMEDIATE`, which `runUnit` blames on deferred constraints.
- Also found: a lock timeout in the drift check (`lockTimeout: "2s"`, access exclusive held) gives a bare `Error: canceling statement due to lock timeout`, with no target, no setting and nothing about the target being unchanged.
- B and C weren't rerun; they take the same paths (57P01 or node-postgres's "not queryable", raised outside or inside the transaction).

**Root cause:**
- Errors outside the deploy transaction (pre-flight, the drift check's catalog read) propagate from `withLockedTarget` as they are.
- Inside it, `runFile` and `runUnit` (`rehearsal/replay.ts`) wrap every error as `SqlFileFailedError`, including a lost or terminated session (class 08, 57P01–57P03, or no SQLSTATE). The engine already tells these apart from server refusals for COMMIT (`refusedByServer`, `CommitOutcomeUnknownError`); the per-statement path doesn't.

## Agent Brief

**Category:** bug
**Summary:** When a target's session ends or its connection is lost during a command, the error says so, names the target, says the target is unchanged, and suggests retrying.

**Current behavior:**
- Before the deploy transaction (pre-flight, drift check), a terminated session, a lost connection or a lock or statement timeout is printed as the driver's bare message, e.g. `Error: terminating connection due to administrator command` or `Error: canceling statement due to lock timeout`.
- Inside the transaction, the same events are reported as `<file>:<line>: PostgreSQL refused it: …`, and a connection error noticed at a migration boundary is blamed on deferred constraints.

**Desired behavior:**
- A lost or ended session (SQLSTATE class 08, 57P01–57P03, or a connection error with no SQLSTATE) before COMMIT is reported as one error naming the target and what happened in words ("the server ended the session", "the connection was lost"), with PostgreSQL's or the driver's text after it.
  - Inside the deploy transaction it adds "The deployment rolled back: target qa is unchanged, still at migration N", as a failed file does now, without "PostgreSQL refused it" or a file and line.
  - Before the deploy transaction it says nothing was changed.
  - Next step: retry once the target is reachable. If the session was ended on purpose, find out why first.
- A lock or statement timeout in the drift check or pre-flight names the target and the setting, as a deploy-time timeout does (see 145 for the value it quotes), and says nothing was changed.
- Errors from a lost COMMIT keep `CommitOutcomeUnknownError`.
- The attempt log records the same message.
- The same applies to the other commands that run under the target lock (`mark`, `rebuild`, `deploy-draft`, `disposable`, `init --adopt`).

**Key interfaces:**
- The per-statement runner shared by rehearsals and deployments, and `SqlFileFailedError`: a lost session is not a refusal of the file.
- `withLockedTarget` and the deploy command's error handling, where the rollback sentence is added.
- The existing classification of class 08 and 57P errors (`refusedByServer`).

**Acceptance criteria:**
- [ ] API seam: `pg_terminate_backend` on a deploy waiting for a lock inside the deploy transaction gives an error that names the target, says the session ended and the deployment rolled back with the last recorded migration, and contains no "PostgreSQL refused it".
- [ ] The same while the deploy waits in the drift check (hold ACCESS EXCLUSIVE through `testSession`) gives an error naming the target and saying nothing changed.
- [ ] A lock timeout in the drift check names `lockTimeout` and the target.
- [ ] A fault-injection adapter that fails `SET CONSTRAINTS ALL IMMEDIATE` with a connection error (no SQLSTATE) isn't reported as a deferred-constraint failure.
- [ ] A real deferred-constraint violation is still reported as it is today.
- [ ] The lost-COMMIT tests still pass.

**Out of scope:**
- Ending an orphaned session sooner (150).
- What an interrupted deploy prints (110, 143).
- The configured value in timeout messages (145) and naming the blocking session (146).
