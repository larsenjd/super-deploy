# 24: Adopting a target that lacks the managed schema (e.g. a typo) records an empty adoption, and the docs don't say how to undo it

**Status:** resolved
**Category:** bug
**Severity:** medium
**Area:** adopt

## What I did
Target database `qa_adopt_ext2` has its objects in schema `app`. In the project's `super-deploy.config.ts` I mistyped the managed schema:

```ts
export default defineConfig({
  postgresVersion: 18,
  managedSchema: "ap",            // typo for "app"
  rehearsal: postgres.rehearsal,
  targets: {
    dev: { adapter: postgres.target("dev") },
    ext2: { adapter: postgresTarget({ connectionString: process.env.EXT2_DATABASE_URL ?? "" }) },
  },
});
```

```sh
export EXT2_DATABASE_URL=postgres://adopt_deployer:deploy@localhost:54818/qa_adopt_ext2
pnpm exec super-deploy init --adopt ext2
```

Then I fixed the typo, deleted the empty `data-model/migrations/`, and adopted again.

## Expected
The first adoption refuses: `schema "ap" does not exist on target ext2`. There's nothing to adopt, and a missing managed schema almost certainly means a config mistake.

## Actual
```
Adopted target ext2: migration 00001-adopt in data-model/migrations/00001-adopt, recorded on it as marked (attempt #1)
```

`00001-adopt/schema-change.sql` contains only the header comment, `desired-schema/` is empty, and the target now has a `deployment_history` schema recording migration 1.

The second adoption, after fixing the typo:

```
Error: Cannot adopt target ext2: it already records 1 migration in its history schema "deployment_history"
```

The README says nothing about undoing an adoption. I only got out by guessing: `drop schema deployment_history cascade` as a superuser.

## Notes
- The README's "Adopting an existing database" section could say how to start over if an adoption was wrong (if dropping the history schema is the answer, say so).
- An empty but *existing* managed schema may be a legitimate adoption. A schema that doesn't exist shouldn't be.

### Triage, 2026-10-20

**Verification:** CONFIRMED. With `managedSchema: "ap"` and every object in `app`, adoption succeeded with no desired-schema files. It wrote `00001-adopt/` (header-only `schema-change.sql` and `metadata.json`) and created `deployment_history` on the target, which recorded migration 1. Root cause: adoption's `readTarget` (`commands/adopt.ts`) never checks that the managed schema exists, and `catalogFacts` just returns nothing for a missing schema. The README's "Adopting an existing database" section has nothing on undoing an adoption.

**Follow-up needing a decision (not part of this brief):** how a user starts over after a wrong adoption. Either document dropping the history schema (`drop schema deployment_history cascade`, plus deleting `data-model/migrations/`), or add a command for it. That question needs a maintainer and should become its own ticket once decided.

## Agent Brief

**Category:** bug
**Summary:** `init --adopt` refuses a target whose managed schema doesn't exist, instead of recording an empty adoption.

**Current behavior:**
If the configured managed schema doesn't exist on the target (typically a typo in `managedSchema`), adoption succeeds. It writes an empty desired schema and migration `00001-adopt`, and records that migration on the target in a newly created history schema. A second adoption, once the typo is fixed, then refuses because the target already records a migration.

**Desired behavior:**
- Adoption checks that the managed schema exists on the target before it rehearses or writes anything.
- If the schema doesn't exist, adoption refuses with an `AdoptConflictError` (or the existing adoption refusal type for target conflicts). The message names the schema and the target, e.g. `Cannot adopt target ext2: its managed schema "ap" does not exist (check managedSchema in super-deploy.config.ts). Nothing was written`.
- Nothing is written to the project, and no history schema is created on the target.
- A managed schema that exists but is empty can still be adopted, as today.

**Key interfaces:**
- The adoption command (`adopt`, CLI `init --adopt <target>`) and its target-reading step.
- `AdoptConflictError` (or whichever existing adoption error carries target-state reasons): a new reason for a missing managed schema.

**Acceptance criteria:**
- [ ] Adopting a target whose managed schema doesn't exist throws the adoption refusal naming the missing schema (API seam).
- [ ] After that refusal, the project has no `data-model/migrations/` folder or desired-schema files from the attempt, and the target has no history schema.
- [ ] Adopting a target whose managed schema exists but is empty still succeeds.
- [ ] The CLI prints the refusal as one line and exits 1 (CLI seam, optional).

**Out of scope:**
- Undoing an adoption that already happened (documentation or a new command); see the follow-up above.
- Guessing the intended schema name.
