# 66: deploy-draft deploys a stale draft without warning

**Status:** ready-for-agent
**Category:** enhancement
**Severity:** low
**Area:** disp

## What I did
With a draft generated, I edited the desired schema without running `draft`
again:

```sh
echo 'create table stale_check (id int primary key);' >> data-model/desired-schema/schema.sql
pnpm exec super-deploy validate
pnpm exec super-deploy rehearse
pnpm exec super-deploy deploy-draft --target sandbox     # disposable; typed YES
```

## Expected
`deploy-draft` says the desired schema changed since the draft was generated,
as `validate` and `rehearse` do (refusing, or at least warning in the
confirmation box).

## Actual
`validate`:
```
warning: The desired schema has changed since draft zz was generated; run draft again
```
`rehearse`:
```
Error: The rehearsal does not match the desired schema; run draft again. ...
```
`deploy-draft`: the confirmation box shows nothing about it, and

```
Deployed draft zz to sandbox on top of 00005-tag-color, without seed data
```

`stale_check` isn't on the target. A user trying "my current work" on a
sandbox gets an older version and has to `rebuild` to try again.

## Notes
Related but fine: changing the draft *while* the YES prompt waits deploys the
version that was read before the prompt, not the new one.

## Agent Brief

**Category:** enhancement
**Summary:** `deploy-draft` refuses a stale draft before asking for YES, as `rehearse` does.

**Current behavior:**
When the desired schema has changed since the draft was generated, `validate` warns and `rehearse` fails ("run draft again"). `deploy-draft` doesn't check. It deploys the old draft to the disposable target, and the user then needs a `rebuild` to try again.

**Desired behavior:**
`deploy-draft` checks, before showing its confirmation, that the draft was generated from the current desired schema. This is the same comparison `validate` makes between the draft's recorded desired-schema hash and the hash of the desired-schema files on disk. If they differ, it refuses with a typed error saying the desired schema changed since the draft was generated and to run `draft` again. Nothing is asked and the target is untouched. A Recovery draft follows whatever rule `rehearse` applies to Recovery drafts.

**Key interfaces:**
- `deployDraft` (the API function behind `deploy-draft`) and its pre-confirmation check, run by `runGuarded` before the YES question.
- The draft metadata's `desiredSchemaHash` and the function that hashes the current desired-schema files (shared with `validate`).
- A new or reused error, exported from the public API, with a stable `code`.

**Acceptance criteria:**
- [ ] Pseudo-terminal: with a stale draft, `deploy-draft --target <disposable>` refuses before any YES prompt, names `draft` as the fix, and exits 1. The target's recorded state is unchanged.
- [ ] Pseudo-terminal: with an up-to-date draft, `deploy-draft` still prompts and deploys as today.
- [ ] API seam: refusal-only, as testing.md prescribes for guarded commands. If the check runs before the terminal check, the API call throws the new error. Otherwise skip this criterion.

**Out of scope:**
- Detecting a hand-edited `schema-change.sql` (issue 17).
- Changing the draft while the YES prompt waits (the report says that behaviour is fine).
