## What I did
Target `qa` at migration 9. As the deploy role, change it by hand:
```sql
alter table app.customers add column nickname text;
drop index app.orders_customer_idx;
alter table app.orders alter column notes set default 'n/a';
create table app.scratch (x int);
```
```sh
pnpm exec super-deploy status --target qa; echo $?
pnpm exec super-deploy deploy --target qa; echo $?
```
Then I looked in the README for what to do.

## Expected
A README section (e.g. under "When a deploy fails") on what drift is, that `deploy` refuses a drifted target, and how to get back: undo the hand changes, or capture them in the desired schema, draft and finalize, then `mark`. The refusal itself should point to that.

## Actual
`status` lists the differences (exit 1). `deploy`:
```
Error: Target qa has drifted from its recorded migrations: column nickname of table app.customers (only on the target), column notes of table app.orders (changed), index app.orders_customer_idx (missing from the target), table app.scratch (only on the target). Deployments refuse until it matches them again (status --target qa lists the differences)
```
"Until it matches them again" doesn't say how. `grep -i drift README.md` finds only three passing mentions: lines 271, 403 and 699 (that the timeouts apply to "its drift check", that grants "are not drift", and that a deployed draft isn't checked for drift). Nowhere does it say that deploy refuses on drift, or what to do.

Only after I added `nickname` to the desired schema and finalized migration 10 did the refusal add a hint:
```
… If its changes are those of the next pending migration applied by hand, mark --target qa records that migration as deployed
```
That works: `mark` then succeeded. A user has to stumble on it, though.

## Notes
Suggested README content: "Drift" (what `status` compares and what it ignores: grants, policies, RLS), the two ways back (revert by hand, or capture plus `mark`), and that `rebuild` is the answer only for disposable targets.
