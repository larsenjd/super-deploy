# 35: Adoption refusal always ends "change the target first", even when the fix is a terminal or the config

**Status:** resolved
**Category:** enhancement
**Severity:** low
**Area:** adopt

## What I did
1. A target whose only problems are a function using `EXECUTE` and one calling `pg_notify` (`qa_adopt_shop`), adopted without a terminal:
   ```sh
   pnpm exec super-deploy init --adopt shop </dev/null
   ```
2. A target whose PL/pgSQL trigger function reads `auth.users`, with `externalSchemas` not set in the config (`qa_adopt_ext2`):
   ```sh
   pnpm exec super-deploy init --adopt ext2 </dev/null
   ```
3. Every refusal also prints the full list twice: once as the list, and again inside the final `Error:` line.

## Expected
The last line says what to do in each case: (1) "run it in a terminal to give override reasons"; (2) "declare auth in externalSchemas in super-deploy.config.ts".

## Actual
(1):
```
In a terminal, adoption asks for an override reason for each object that breaks only risk rules, and writes its override marker
Error: Cannot adopt target shop: its managed schema has 2 things V1 doesn't support: CREATE FUNCTION app.count_rows(tbl text); CREATE FUNCTION app.notify_order(). Nothing was written; change the target first, then adopt again
```
(2):
```
  CREATE FUNCTION app.set_author_name()
    undeclared-schema: Schema "auth" is not declared: ... (PL/pgSQL bodies may also reference the externalSchemas in super-deploy.config.ts)
Error: Cannot adopt target ext2: its managed schema has 1 thing V1 doesn't support: CREATE FUNCTION app.set_author_name(). Nothing was written; change the target first, then adopt again
```

In (1) nothing on the target needs changing, and the error contradicts the line above it. In (2) the target is fine too; only the config is missing something. "Things V1 doesn't support" is also odd wording for a missing config setting, and "V1" isn't explained anywhere in the README.

## Agent Brief

**Category:** enhancement
**Summary:** The adoption refusal's closing advice matches what's actually wrong, and the CLI doesn't print the object list twice.

**Current behavior:**
Every `AdoptUnsupportedError` ends with "Nothing was written; change the target first, then adopt again", whatever the cause:
- objects that break only risk rules, which an override reason would allow in a terminal;
- a reference to a schema missing from `externalSchemas`, where the fix is in the config.

The CLI prints the list of objects, then the error message lists the first five again.

**Desired behavior:**
- The closing advice depends on the rules the entries hit:
  - If every entry breaks only risk (overridable) rules and there was no terminal to ask: "run it in a terminal to give an override reason for each".
  - If an entry is `undeclared-schema`: "declare <schema> in externalSchemas in super-deploy.config.ts" (naming the schemas).
  - Anything else: "change the target first, then adopt again", as today.
  - When several apply, give each relevant piece of advice once.
- When the CLI has already printed the list, the error line doesn't repeat it: it gives the count and the advice. The API error's message stays self-contained (it may still name objects) for callers that don't print the list.

**Key interfaces:**
- `AdoptUnsupportedError`: its message, or a structured field the CLI uses, carries the advice. The rule id and category of each entry (risk or not) come from the rule catalogue.
- The CLI's rendering of `AdoptUnsupportedError` in the `init --adopt` command definition.

**Acceptance criteria:**
- [ ] Adopting without a terminal a target whose only problems are risk-rule functions ends with advice to run in a terminal, not to change the target (API seam on the error message, or CLI seam).
- [ ] Adopting a target with an undeclared schema reference ends with advice naming the schema and `externalSchemas`.
- [ ] Adopting a target with an unsupported object (e.g. an enum) still ends with "change the target first".
- [ ] In the CLI output, no object name appears both in the list and in the final `Error:` line (CLI seam).

**Out of scope:**
- The "V1" wording (needs a decision, above).
- Grouping extension members or serial sequences; that is issue 23.
