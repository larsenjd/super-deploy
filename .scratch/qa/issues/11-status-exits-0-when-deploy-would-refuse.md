# 11: `status` exits 0 when it reports "Deploy would refuse"

**Status:** ready-for-human
**Category:** enhancement
**Severity:** low
**Area:** newproj

## What I did
1. Desired schema grants to a role that doesn't exist on `qa`:
   ```sql
   grant select on order_events to newproj_app_auditor;
   ```
   ```sh
   pnpm exec super-deploy draft --name "order events" && pnpm exec super-deploy finalize
   pnpm exec super-deploy status --target qa; echo "exit=$?"
   pnpm exec super-deploy deploy --target qa; echo "exit=$?"
   ```
2. Separately, after changing an already-deployed migration (see issue 10),
   the same `status`.

## Expected
A non-zero exit when status knows the next deploy will fail, so `status` can
gate a CI pipeline before the deploy step. `--help` only promises "exit 1 on
drift", but someone scripting it will assume "status OK = deployable".

## Actual
```
Target qa: 5 migrations recorded, 1 pending
Deploy would refuse:
  role "newproj_app_auditor" does not exist
...
exit=0
Error: Target qa failed the deploy pre-flight checks: role "newproj_app_auditor" does not exist (the desired schema grants to it; create it on the target)
exit=1
```
And in case 2: "Drift: not checked (the recorded history doesn't match the
project's migrations)", also exit 0. Drift isn't even checked, yet the exit
code says no drift.

## Notes
The deploy error message here is good. It says what to do.

### Triage, 2026-10-20

**Verification:** CONFIRMED, and it matches the spec. With a content-hash mismatch, `status` prints `Deploy would refuse: ...` and `Drift: not checked (...)` and exits 0. `status` throws only on non-empty drift (`src/cli/definitions.ts:735-738`). The spec says exit 1 means "failed or refused (and `status` on drift)" (spec line 257, story 54). Caveat: exit 0 while drift is *not checked* quietly defeats story 54's scheduled drift alert, whenever the history mismatches or a draft is held.

## Brief (ready-for-human)

**Category:** enhancement
**Summary:** Decide the `status` exit code when the next deploy would refuse or drift couldn't be checked.

**Current behavior:**
`status` exits 1 only on drift. It exits 0 when it reports "Deploy would refuse" (missing role, history mismatch, held draft) and when it says "Drift: not checked". So a pipeline gate on `status` passes a target that can't be deployed, or whose drift wasn't looked at.

**Desired behavior (once decided):**
A script can tell "deployable, no drift" from "would refuse" and from "drift not checked" by exit code alone.

**Key interfaces:**
- The `status` command's result (drift, refusal findings, drift-not-checked).
- The CLI's exit-code policy (`run` maps outcomes to 0/1/2) and `status --help`.
- Spec story 54 and the exit-code table.

**Acceptance criteria (once decided):**
- [ ] `status` exits as decided in each of: up to date, pending, drift, would refuse, drift not checked.
- [ ] `status --help` and the spec's exit-code table say so.
- [ ] CLI tests cover each case.

**Out of scope:**
- `status` failing while a deploy holds the target (41).
- The wording of the refusals (50, 67).

**Why not delegated:** it changes a documented exit-code contract.
**Decision needed:**
- Exit 1 for "would refuse" and for "drift not checked", so 0 means deployable with no drift (recommended).
- A distinct exit code for "would refuse", keeping 1 for drift.
- Keep exit 0 and document that `status` is not a deployability gate.
