# 162: Closing the terminal at a YES prompt leaves the dev and rehearsal servers running

**Status:** wontfix
**Category:** bug
**Severity:** medium
**Duplicate of:** 141
**Area:** disp
**Round:** 2

## What I did
A fresh `init` project (`pnpm install`, a few migrations), `dev` deployed and flagged disposable. No embedded server running.

1. In an interactive shell in a terminal (zsh in a pty), run:
   ```sh
   pnpm exec super-deploy rebuild --target dev --to 5
   ```
2. Wait for `Type YES to wipe target dev and replay migrations 1-5`.
3. Close the terminal (close the pty master, which hangs up the shell and the foreground job).
4. `ps -eo pid,args | grep "postgres -D <project>/.super-deploy"`

Variants with the same result: sending SIGHUP or SIGTERM to the foreground process group (pnpm plus the CLI) while it waits at the prompt.

## Expected
The command stops the servers it started before exiting. The README says only "A command that was killed outright (`kill -9`, a crash) can leave it running".

## Actual
Both servers keep running after the CLI and the shell are gone:
```
2578447 .../native/bin/postgres -D /tmp/sd-qa2/disp/p1/.super-deploy/dev -p 44081 ...
2578463 .../native/bin/postgres -D /tmp/sd-qa2/disp/p1/.super-deploy/rehearsal -p 43197 ...
```
With a group signal the CLI prints `Interrupted by SIGHUP: cleaning up before exiting (interrupt again to exit at once)`, then exits without stopping them. Reproduced with HUP, TERM and a real terminal close. Ctrl+C at the prompt and SIGINT to the group clean up properly. So does SIGTERM or SIGHUP sent to the CLI's node process alone (exit 143 / 129, no servers left).

## Notes
The next command that uses `dev` takes them over and stops them, as the README says, so the damage is limited to stray servers holding the dev port.
Guess: `pnpm exec` dies on the signal at once, the pty is hung up, and the CLI gets a second SIGHUP, which it treats as "interrupt again to exit at once". Closing a terminal window or tab is a normal way to abandon a prompt.
