# 108: finalize accepts a hand-edited schema-change.sql without a word

**Status:** ready-for-agent
**Category:** bug
**Severity:** low
**Area:** newproj
**Round:** 2

## What I did
```sh
# desired schema: add column note4 to table a
pnpm exec super-deploy draft --name note4
echo "create index a_note4_idx on a (note4);" >> data-model/draft/schema-change.sql
echo "create index a_note4_idx on a (note4);" >> data-model/desired-schema/s.sql
pnpm exec super-deploy rehearse
pnpm exec super-deploy finalize </dev/null
cat data-model/migrations/00005-note4/schema-change.sql
```
Reproduced twice (also with an index on `customers` in another project).

## Expected
The README: "`schema-change.sql` (generated by `draft`) ... Never edit it". `draft.json` holds a hash of the generated schema
change and `rehearse` detects hand edits when the rehearsal fails ("was edited by hand since draft generated it"). I'd
expect `finalize` to refuse (or at least warn) when the schema change isn't what `draft` generated, or when the desired
schema has changed since `draft`.

## Actual
```
Rehearsed draft note4 after 4 migrations: matches the desired schema
Finalized migration 00005-note4 in data-model/migrations/00005-note4
```
The migration is frozen with the hand-written line under the "generated ... Do not edit" header:
```
-- Schema change generated by super-deploy draft. Do not edit: change the
-- desired schema (or the pre-migration script) and run draft again.

ALTER TABLE "public"."a" ADD COLUMN "note4" text;
create index a_note4_idx on a (note4);
```

## Notes
The result rehearses correctly, so this isn't unsafe as such, but reviewers trust the header and don't read a generated
file the way they read a hand-written script. Data statements are refused (`UPDATE is not allowed in a schema change`),
so only DDL gets through.

## Brief (ready-for-human)

**Category:** bug
**Summary:** `finalize` (and `deploy-draft`, 161) notice a schema change that differs from what `draft` generated.

**Current behavior:**
A hand edit to the draft's `schema-change.sql` is caught only if the rehearsal fails. A passing edit is finalized under the "generated by super-deploy draft. Do not edit" header, and reviewers have no sign of it.

**Desired behavior (once decided):**
- When the draft's `schema-change.sql` hash differs from `draft.json`'s `schemaChangeHash`, `finalize` handles it as decided.
- The message names the file and says to move the hand-written statements into the pre-migration or post-migration script and run `draft` again.
- `validate` warns about it for a draft, as it does for a changed desired schema.
- A draft from before the hash existed is treated as not edited (as 17 decided). A Recovery draft keeps its own rule: its schema change is migration N's, and is checked as such.

**Key interfaces:**
- The draft metadata's `schemaChangeHash` and the hash function `draft` uses.
- `rehearseCurrentDraft` (shared by `rehearse` and `finalize`), or `finalize` itself; `validate`'s draft warnings.
- A new error exported from the public API with a stable `code` (if refusing).

**Acceptance criteria (once decided):**
- [ ] API seam: the report's case (an index appended to both `schema-change.sql` and the desired schema) makes `finalize` behave as decided, and writes no migration if it refuses.
- [ ] `draft` run again clears it: the regenerated schema change is accepted.
- [ ] `validate` with the edited draft lists the warning. `--strict --allow-draft` treats it as decided (it isn't a work-in-progress finding).
- [ ] A draft without `schemaChangeHash` finalizes as today.

**Out of scope:**
- `deploy-draft` (161), which should follow the same decision.
- The mismatch message for edits that fail the rehearsal (round 1, 17, done).

**Why not delegated:** refusing blocks anyone who edits the generated file on purpose (e.g. to work around a differ bug), and the README tells them to use the pre-migration script instead. Whether that is a hard rule is the maintainer's call.

**Decision needed:**
1. **(recommended)** Refuse in `finalize` (and `deploy-draft`), with the message above. No override: the scripts are the place for hand-written SQL.
2. Warn, and record in the migration's metadata that the schema change was edited by hand, so `validate` and reviewers see it.
3. Leave as is (the rehearsal proves the result).

### Decided, 2026-10-21

The maintainer chose **warn and record**, plus a **report file in the finalized migration** so a hand edit is easy to spot in a PR review. Decided for 108 and 161 together.

- `draft` keeps the generated schema change beside the draft as a known draft file (e.g. `schema-change.generated.sql`; add it to 44's list of known draft files), next to `draft.json`'s existing `schemaChangeHash`.
- `rehearse` and `finalize` warn when `schema-change.sql` differs from what `draft` generated: `schema-change.sql was edited by hand since draft generated it`. Rehearsal still proves the result.
- `finalize` of a hand-edited schema change:
  - records it in the migration's metadata (e.g. `schemaChangeEditedByHand: true`);
  - writes a report file into the migration folder, e.g. `HAND-EDITED.md`, saying the schema change was edited by hand after `draft` and containing a unified diff from the generated schema change to the final one. It is part of the migration's content hash like every other file.
  - `validate` lists hand-edited migrations as a notice (not a warning, so `--strict` doesn't fail on it).
- `deploy-draft` shows the hand edit in the YES confirmation (`schema-change.sql was edited by hand since draft generated it and hasn't been rehearsed`) and goes ahead on YES.
- A draft written before the generated copy existed counts as not edited.
- README: the files section mentions `HAND-EDITED.md`.

**Acceptance criteria:**
- [ ] API seam: hand-edit `schema-change.sql` in a way that still produces the desired schema; `finalize` warns, succeeds, records the flag, and the migration folder holds `HAND-EDITED.md` with the diff.
- [ ] An unedited draft writes no report file and no flag.
- [ ] Pseudo-terminal test: `deploy-draft` of a hand-edited draft shows the line in the confirmation.
- [ ] `validate` lists the hand-edited migration.
