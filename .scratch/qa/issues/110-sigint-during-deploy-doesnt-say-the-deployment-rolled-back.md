# 110: Interrupting a deploy doesn't say the deployment was rolled back

**Status:** ready-for-human
**Category:** enhancement
**Severity:** low
**Merged:** 143
**Area:** newproj
**Round:** 2

## What I did
With a pending migration that alters `customers`, hold a lock on it from another session, then interrupt the deploy
while it waits:
```sh
node holdlock.mjs postgres://postgres:qa@localhost:54818/qa2_newproj_qa public.customers 12 &   # begin; lock table ... in access share mode; sleep
pnpm exec super-deploy deploy --target qa &
sleep 2.5; kill -INT <pid of the cli.js process>
```
Reproduced twice.

## Expected
Like the lock-timeout failure, which says: `The deployment rolled back: target qa is unchanged, still at migration
00009-add-tier.`

## Actual
Exit code 130, and the only output is:
```
Interrupted by SIGINT: cleaning up before exiting (interrupt again to exit at once)
```
Nothing after the clean-up finishes. `status` shows `#15 deploy abandoned migration 16 ...: Interrupted (SIGINT)` and the
migration is still pending, so the target is fine, but the user is left guessing whether it was applied.

### Triage, 2026-10-21

Merged here: 143 (the same for Ctrl+C from the menu in a pty and `kill -INT` to the process group, and for SIGTERM (exit 143) and SIGHUP (exit 129)).

**Verification:** CONFIRMED with the built CLI. `dev` had pending migration `00002-nick` (adds a column to `people`), and another session held ACCESS SHARE on `people`. `deploy --target dev`, SIGINT after 3 s:
- exit 130;
- the only output is `Interrupted by SIGINT: cleaning up before exiting (interrupt again to exit at once)`;
- `status` shows `#3 deploy abandoned migration 2 …: Interrupted (SIGINT)` with the migration still pending.

**By design so far:** the spec's interruption rule says "print one notice" (spec "CLI shell and programmatic API"), and round 1 (40) kept it: "A final 'rolled back, nothing recorded' line: by design, one notice only". The notice can't say "rolled back" when it is printed: the outcome isn't known yet, and an interrupt after COMMIT has been sent can still end in a deployed target (144). Two testers independently found the silence unhelpful, on the command where it matters most.

## Brief (ready-for-human)

**Category:** enhancement
**Summary:** After an interrupted command that changes a target has cleaned up, the CLI says what happened to the target.

**Current behavior:**
Ctrl+C, SIGTERM or SIGHUP during `deploy` prints one notice when the signal arrives and exits 130, 143 or 129 after cleanup. Whether anything was committed is only visible through `status`.

**Desired behavior (once decided):**
- Option 1: once cleanup has finished, a command that changes a target (`deploy`, `deploy-draft`, `rebuild`, `mark`, `disposable`) prints one closing line with the outcome, like a failed deploy's:
  - "The deployment rolled back: target qa is unchanged, still at migration 00009-add-tier", when the deploy transaction rolled back or never started;
  - what was committed, when the interrupt came after COMMIT (see 144: the exit code for that case is its own question).
- Exit codes are unchanged. A closing line that can't be written (closed output, a hung-up terminal) is skipped silently.
- The spec's interruption rule changes from "print one notice" to "one notice, then the outcome for commands that change a target".

**Key interfaces:**
- The CLI's interruption handling (`watchInterruptions`) and `runCli`'s path for an aborted command.
- What `withLockedTarget` and the attempt settling know at the end: rolled back, committed or unknown, and the last recorded migration.

**Acceptance criteria (once decided):**
- [ ] CLI seam: SIGINT during a stalled deploy transaction exits 130, and stderr ends with the rolled-back line naming the target and its last recorded migration.
- [ ] The same with SIGTERM (143).
- [ ] The same with SIGHUP (129). Closed output (141) still prints nothing.
- [ ] An interrupt during the rehearsal (before the target is touched) says the target is unchanged.
- [ ] Commands that don't change a target print only the notice, as today.

**Out of scope:**
- An interrupt that lands after COMMIT (144) and SIGTERM through `pnpm exec` (140), apart from wording the closing line for them.
- `deploy-draft`'s failure message (174).
- Embedded servers left running after SIGHUP (141).

**Why not delegated:** it reverses the spec's "one notice" rule, which round 1 upheld.

**Decision needed:**
1. **(recommended)** A closing outcome line after cleanup, for commands that change a target, and the spec line amended.
2. Reword the single notice for those commands ("… cleaning up; the deployment will roll back unless it has already committed"). This keeps one line, but it can't state the outcome.
3. Keep one notice (spec) and close as wontfix; `status` shows the abandoned attempt.
