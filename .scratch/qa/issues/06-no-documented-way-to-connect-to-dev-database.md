# 06: No documented way to connect to the local `dev` database (to look at it, create roles or run the app)

**Status:** resolved
**Category:** enhancement
**Severity:** medium
**Merged:** 31
**Area:** newproj

## What I did
Deployed to `dev` and then wanted to look at the result (or point my app at
it). The README says the private server "starts on a free port whenever a
command needs it". After the command it's stopped again.
`.super-deploy/postgres/postmaster.opts` shows the last port (e.g. 43979),
`pg_hba.conf` requires `password`, and the user/password aren't written
anywhere I could find. There's no `psql` in the template and no command to
start the server and print a connection string.

## Expected
The README says how to get a connection to `dev` (a command that starts the
server and prints its URL, or a fixed port and credentials in the config).

## Actual
No way to inspect `dev` without reverse-engineering the embedded adapter.

## Notes
Related: the README says roles a grant names must exist on a target before
deploying ("`deploy` refuses otherwise"), but my first `deploy --target dev`
of a schema granting to `newproj_app_reader`/`newproj_app_writer` succeeded
without my creating those roles anywhere. Guess: the rehearsal's placeholder
`NOLOGIN` roles are created in the same embedded cluster that hosts `dev`, so
they leak into `dev`. Confirmed later: I added
`grant select on order_events to newproj_app_auditor`. `deploy --target qa`
refused with `role "newproj_app_auditor" does not exist`, but
`deploy --target dev` deployed it, and I never created that role for dev. So `dev` silently behaves differently from real
targets, and with no way to connect (above) I couldn't check.

### Triage, 2026-10-20

**Verification:** CONFIRMED, both halves.
- *Role leak:* a desired schema granting to a role nobody created. `deploy --target dev` succeeded; `deploy --target qa` (a second embedded server in its own data dir) refused with `role "qa_f_app_reader" does not exist`. Rehearsals create missing roles as `NOLOGIN` on their own server and never drop them (REFINEMENTS "Placeholder roles in rehearsals"). That server is the same cluster as `dev`, so `dev` accepts grants a real target refuses. Nothing in the README or REFINEMENTS points this out.
- *Connecting:* the README never says how. But the public `super-deploy/embedded-postgres` export already has `start()` and `connectionString(database?)` (`src/adapters/embedded-postgres.ts:42-46`, `:142-145`). A two-line script printed `postgres://super_deploy:super_deploy@127.0.0.1:35921/dev`. The server only lives as long as that process.
- *External schemas (from 31):* with `externalSchemas: ["auth"]`, `status --target dev` reports `external schema "auth" does not exist`. Nothing creates external schemas (by design: README "set up outside super-deploy"), and the only way to create one on `dev` is the undocumented `connectionString()` route.

## Brief (ready-for-human)

**Category:** enhancement
**Summary:** Make the local `dev` target inspectable and preparable, and stop it silently differing from real targets.

**Current behavior:**
`dev` runs on the project's private embedded server, which also hosts rehearsals. Its placeholder roles leak into `dev`, so grants to missing roles deploy there but are refused on real targets. There's no documented way to connect to `dev` (to look at it, point an app at it, or create roles and external schemas). So a project that uses `externalSchemas` can't deploy to `dev` at all.

**Desired behavior (once decided):**
- A user can connect to `dev` through a documented route.
- A user can prepare what a target needs outside super-deploy (external schemas, their grants, app roles) on `dev`.
- `dev` refuses a grant to a missing role as a real target does, or the README says clearly why it doesn't.

**Key interfaces:**
- The embedded adapter's exported `start()`, `connectionString()` and `target()`.
- The rehearsal's placeholder-role creation (`ensureRoles`), and which cluster rehearsals use.
- The CLI's command list, if a new command is added.
- The template README.

**Acceptance criteria (once decided):**
- [ ] The README shows how to get a connection string for `dev`, and how long the server stays up.
- [ ] A project with `externalSchemas` has a documented way to make `dev` deployable.
- [ ] `deploy --target dev` of a grant to a role created only by a rehearsal behaves as decided, and a test pins it.

**Out of scope:**
- The superuser warning on `dev` (05).
- Concurrent commands sharing the embedded server (14).

**Why not delegated:** three product decisions about what the embedded server is; the docs follow from them.
**Decision needed:**
- Rehearsal cluster: keep sharing it with `dev` and document the leniency (recommended for V1), or rehearse on a separate cluster or database so `dev` behaves like a real target.
- Connecting: document the exported `connectionString()` with a small script (recommended), or add a command that starts the server and prints its URL, or opens `psql`.
- External schemas on `dev`: a documented setup script that uses `connectionString()` (recommended), or a setup-SQL option on the embedded target that runs when it's created.

### Note, 2026-10-20

ADR-0006 puts privileges, ownership and row-level security outside the system in V1 (`.scratch/super-deploy/issues/28-privileges-out-of-scope.md`). Rehearsals stop creating placeholder roles and the pre-flight stops checking granted roles, so the role leak into `dev` goes away. What remains: a documented way to connect to `dev` (to look at it, point an app at it, or create external schemas). Ignore the role-specific acceptance criterion.

### Decided, 2026-10-21

The maintainer chose:
- **Rehearsals run on a separate embedded server from `dev`**, so `dev` is a database on a server of its own, like a real target.
- **The config declares how to connect to `dev`:** a fixed `port` option on `embeddedPostgres`, so `dev` is always at a known URL, documented in the README.
- **External schemas are the DBA's job:** the pre-flight no longer refuses a target that lacks a declared external schema. A routine that reads a missing one fails only when it runs, which is outside super-deploy's responsibility. No setup mechanism for external schemas on `dev` is added.

This supersedes the brief above (its placeholder-role parts went with ADR-0006).

## Brief (ready-for-agent)

**Summary:** `dev` lives on its own embedded server at a port the config declares, so users can connect to it; rehearsals use a separate embedded server; and a missing external schema no longer blocks a deployment.

**Desired behavior:**
- `EmbeddedPostgresOptions` gains `port?: number`. With a port, the server listens on `127.0.0.1:<port>`; if that port is taken by something else, the command fails naming the port and the config setting. Without one, behaviour is as today (a free port).
- The template's `super-deploy.config.ts` uses two embedded servers: one for `dev` with a `port`, in `.super-deploy/dev` (gitignored), and one for rehearsals on a free port, in `.super-deploy/rehearsal`. `init` writes a port that is free when it runs.
- The README's `dev` section gives the connection URL (`postgres://<deploy role from 05>:<password>@127.0.0.1:<port>/dev`), the superuser URL for DBA work on `dev` (creating app roles, external schemas, grants), and when the server runs (a command starts it; see 14 for when it stops). It says the port is set in `super-deploy.config.ts`.
- The pre-flight drops the "external schema does not exist" refusal. `deploy`, `deploy-draft`, `status` and `mark` go ahead on a target without a declared external schema. `PreflightFailedError` and the `status` result lose the missing-schemas finding.
- `externalSchemas` keeps its other jobs (which PL/pgSQL references the rules accept).
- Spec: story 66 is removed; the `deploy` sequence and "Target setup that stays outside super-deploy" say external schemas are set up by the DBA and are not checked. The README's `externalSchemas` entry says the same.

**Key interfaces:**
- `adapters/embedded-postgres.ts` (`EmbeddedPostgresOptions`, start and attach).
- The template's `super-deploy.config.ts`, `.gitignore` and README; `init`, which writes the config.
- `deploy/preflight.ts` and `PreflightFailedError`.

**Blocked by:** 05. 14 builds on this ticket's adapter changes.

**Acceptance criteria:**
- [ ] A fresh `init` project's `dev` is reachable at the URL the README gives, using the port in its config (API seam: connect with `pg` after `deploy --target dev` and read a deployed table).
- [ ] A rehearsal never creates a database on `dev`'s server (list the databases on both servers during a `rehearse`).
- [ ] A configured port that is already in use fails with a message naming the port and the setting.
- [ ] With `externalSchemas: ["auth"]` and no `auth` schema on the target, `deploy` succeeds and `status` reports no refusal.
- [ ] Spec story 66 and the README match; the template's precommit passes.
