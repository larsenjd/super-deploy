**Severity:** low

## What I did
Target `drift: { adapter: postgresTarget({ env: "FAIL_DRIFT_URL" }) }`, then:
```sh
FAIL_DRIFT_URL="not a url" pnpm exec super-deploy status --target drift
FAIL_DRIFT_URL="" pnpm exec super-deploy status --target drift
FAIL_DRIFT_URL="mysql://fail_deployer:dep@localhost:54818/qa_fail_drift" pnpm exec super-deploy status --target drift
FAIL_DRIFT_URL="postgres://fail_deployer:dep@localhost:54818/qa_fail_drift?sslmode=require" pnpm exec super-deploy status --target drift
```

## Expected
- `not a url`: "FAIL_DRIFT_URL is not a PostgreSQL connection string (postgres://user:password@host:port/database)".
- Empty: "FAIL_DRIFT_URL is empty".
- `mysql://`: refused as not a PostgreSQL URL.
- `sslmode=require`: no third-party warning text, or a super-deploy note on what `sslmode` values mean here.

## Actual
```
Error: The deployment adapter of target drift failed to connect: getaddrinfo ENOTFOUND base
```
(`base` is a host name that appears nowhere in the input.)
```
Error: Environment variable FAIL_DRIFT_URL is not set
```
(it is set, just empty)

`mysql://...` is accepted and connects (status prints normally).

`sslmode=require`:
```
(node:509857) Warning: SECURITY WARNING: The SSL modes 'prefer', 'require', and 'verify-ca' are treated as aliases for 'verify-full'.
In the next major version (pg-connection-string v3.0.0 and pg v9.0.0), these modes will adopt standard libpq semantics, ...
(Use `node --trace-warnings ...` to show where the warning was created)
Error: The deployment adapter of target drift failed to connect: The server does not support SSL connections
```
So `sslmode=require` means certificate verification here, unlike libpq, and the README never mentions TLS. Users of managed databases with self-signed certificates may be surprised.

## Brief (ready-for-human)

**Category:** bug
**Summary:** Decide and document what `sslmode` means for `postgresTarget`, and stop leaking node-postgres's raw warning.

**Current behavior:**
node-postgres treats `sslmode=prefer`, `require` and `verify-ca` as `verify-full`, unlike libpq, and prints a third-party `SECURITY WARNING` to stderr. Users of managed databases with self-signed certificates get a verification failure where libpq would connect. The README says nothing about TLS.

**Desired behavior (once decided):**
`sslmode` behaves as documented in the README, and no raw node-postgres warning reaches the user.

**Key interfaces:**
- `postgresTarget` and `ConnectionSource`, and how the connection string becomes a client config.
- The template README (a TLS paragraph near the real-target example from 03).

**Acceptance criteria (once decided):**
- [ ] A connection string with `sslmode=require` prints no node-postgres warning.
- [ ] Its behaviour (verify or not) matches the README, and a test pins it.
- [ ] The README says how to connect with TLS, including to a server with a private CA.

**Out of scope:**
- Connection-string validation (04).
- Client certificates beyond what the connection string already supports.

**Why not delegated:** it's a security policy: libpq semantics versus pg's stricter default.
**Decision needed:**
- Pass `uselibpqcompat=true` so `sslmode` means what libpq says, and document it (recommended: it matches what users expect from psql).
- Keep pg's verify-full aliasing, suppress the warning, and document that `require` verifies certificates.

### Decided, 2026-10-21

The maintainer chose: **the libpq meaning of `sslmode`**, as psql uses it.

- Connection strings are passed to node-postgres with `uselibpqcompat=true`, so `require` encrypts without verifying the certificate, `verify-ca` and `verify-full` verify, and no node-postgres warning is printed.
- The README's real-target section has a short TLS paragraph: what each `sslmode` does, and how to connect to a server with a private CA (`sslrootcert` with `verify-full`).

**Acceptance criteria:** as the brief above, with `require` not verifying the certificate.
