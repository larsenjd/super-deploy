# 21: Adoption shows a VIRTUAL generated column as STORED and refuses it for the wrong reason

**Status:** resolved
**Category:** bug
**Severity:** medium
**Area:** adopt

## What I did
In `qa_adopt_gen` (owner `adopt_pubowner`):

```sql
create table people (
  id bigint generated always as identity primary key,
  first text not null,
  v text generated always as (upper(first)) virtual
);
select attname, attgenerated from pg_attribute where attrelid = 'people'::regclass and attnum > 0;
-- v | v   (virtual)
```

Project with target `gen` (`postgresTarget({ connectionString: process.env.GEN_DATABASE_URL ?? "" })`), then:

```sh
pnpm exec super-deploy init --adopt gen
```

## Expected
The refusal says the virtual generated column isn't supported, as `draft` does for a hand-written one:

```
Virtual generated columns are not supported in V1 (a generated column without STORED is virtual in PostgreSQL 18): add STORED [unsupported-object]
```

## Actual
```
  ALTER TABLE "public"."people" ADD COLUMN "v" text GENERATED ALWAYS AS (upper(first)) STORED
    desired-schema-statement: Only ALTER TABLE ... ENABLE ROW LEVEL SECURITY, FORCE ROW LEVEL SECURITY or ADD CONSTRAINT is allowed in the desired schema; declare everything else in CREATE TABLE
```

The column shows up as `STORED`, and the reason is the generic ALTER TABLE rule from issue 20.

## Notes
- If issue 20 is fixed by folding generated columns into `CREATE TABLE`, this column would apparently be adopted as `STORED`. The desired schema would then not match the database, or a later deploy would rewrite the table. Adoption should keep `VIRTUAL` (and refuse it with the virtual-column reason) rather than turn it into `STORED`.
- Guess: the differ (`@supabase/pg-delta`) ignores `attgenerated = 'v'`. If the catalog comparison ignores it too, a virtual vs stored difference could also go unnoticed elsewhere.

## Agent Brief

**Category:** bug
**Summary:** Adoption refuses a virtual generated column with the virtual-column reason, read from the target's catalog.

**Current behavior:**
Adopting a table with a virtual generated column (`attgenerated = 'v'`) lists it as an `ALTER TABLE ... ADD COLUMN ... STORED` statement, refused under the generic desired-schema statement rule. The differ renders every generated column as STORED, so the refusal names the wrong kind of column and the wrong reason. Once issue 20 folds such columns into `CREATE TABLE`, the refusal would instead be a puzzling "not-reproduced" catalog difference.

**Desired behavior:**
Adoption reads the target's virtual generated columns in the managed schema from the catalog, and lists each as its own unsupported entry: column X of table Y, with the existing virtual-generated-column reason ("Virtual generated columns are not supported in V1 ...: add STORED"). It is listed alongside the other unsupported objects, and nothing is written. No entry for the same column appears as an `ALTER TABLE` statement or as a not-reproduced difference.

**Key interfaces:**
- Adoption's reading of the target (the step that turns catalog facts the desired schema can't express into unsupported entries) and `AdoptUnsupportedError`'s list.
- The existing `unsupported-object` rule's message for virtual generated columns: reuse its text.

**Acceptance criteria:**
- [x] At the API seam, adopting a database with `v text generated always as (upper(first)) virtual` refuses with `AdoptUnsupportedError`, whose entries include that column with the virtual-column reason.
- [x] No entry for that column says STORED or cites the desired-schema statement rule.
- [x] A STORED generated column still adopts (once issue 20 is fixed).

**Out of scope:**
- Supporting virtual generated columns.
- Folding split `ADD COLUMN` statements into `CREATE TABLE` (issue 20).

### Resolved, 2026-10-20 (f7bd5d6)

- `verification/catalog.ts`: `isVirtualGeneratedColumn` picks out the `column` facts with `generated=v`. Adoption already reads these facts from the target.
- `adopt` lists each virtual column as `column v of table people` with the rule `unsupported-object` and the rules' own virtual-column reason (`virtualGeneratedColumnFinding`). These entries sit alongside the `other` catalog objects. Because the list is refused before the reproduction check runs, no `not-reproduced` entry appears for the column.
- The reason now lives in one place, `refusedObjects.virtualGeneratedColumns`, used by both the desired-schema rule and adoption.
- Tests (API seam, `adopt.test.ts`): adopting the reproduction table is refused with exactly one entry, the column with the virtual reason, and nothing is written. Without the fix, the same test got `not-reproduced: ... generated=v` vs `generated=s`. The existing STORED test still adopts.
- Not done:
  - If the same table is also refused for something else (e.g. `with (fillfactor = 70)`), that table's entry is the first line of the generated `CREATE TABLE`, and that line still shows the column as `STORED`. The column's own entry is correct.
  - An inheritance child or partition of a table with a virtual column gets its own entry for the inherited column. Those tables are refused anyway.
