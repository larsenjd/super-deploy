# 102: Reordering a composite type's attributes gives an empty draft, then a rehearsal error that blames scripts that don't exist

**Status:** ready-for-human
**Category:** bug
**Severity:** medium
**Area:** newproj
**Round:** 2

## What I did
A finalized and deployed migration has
```sql
create type money_amount as (
  currency char(3),
  amount numeric(12,2)
);
```
(used by a column `orders.price money_amount`). I swapped the attributes in the desired schema:
```sql
create type money_amount as (
  amount numeric(12,2),
  currency char(3)
);
```
```sh
pnpm exec super-deploy draft --name "reorder money"
pnpm exec super-deploy rehearse
pnpm exec super-deploy finalize
ls data-model/draft
```

## Expected
Either `draft` generates the change (a new type, converting the column, dropping the old type), or it says it can't, and
tells me what to put in the pre-migration script. If the rehearsal fails, its message says what actually differs.

## Actual
```
Created draft reorder-money: 0 statements in data-model/draft/schema-change.sql
```
No warning. Then `rehearse` (and `finalize`):
```
catalog: from the migrations: column: money_amount.amount numeric(12,2) ... position=2
catalog: from the migrations: column: money_amount.currency character(3) ... position=1
catalog: from the desired schema: column: money_amount.amount numeric(12,2) ... position=1
catalog: from the desired schema: column: money_amount.currency character(3) ... position=2
Error: The rehearsal does not match the desired schema, and running draft again won't change that: the desired schema hasn't changed since draft, so the pre-migration script, post-migration script or seed data cause the difference (a column renamed in the pre-migration script needs its NOT NULL constraint renamed too: see the README, "Renaming a column") (4 differences, listed above)
```
The draft folder holds only `draft.json` and `schema-change.sql`: there is no pre-migration script, post-migration script or
seed data, so the message blames files that don't exist and the NOT NULL hint is irrelevant.

## Notes
Workaround that rehearsed, finalized and deployed fine (data kept), in `pre-migration.sql`:
```sql
create type money_amount_new as (amount numeric(12,2), currency char(3));
alter table orders alter column price type money_amount_new
  using case when price is null then null else row((price).amount, (price).currency)::money_amount_new end;
drop type money_amount;
alter type money_amount_new rename to money_amount;
```
The README doesn't say how to reorder (or insert an attribute in the middle of) a composite type.

### Triage, 2026-10-21

**Verification:** CONFIRMED with the built CLI. A migration has `money_amount (currency char(3), amount numeric(12,2))`. Swapping the attributes in the desired schema drafts `0 statements`, with no warning. `rehearse` then fails with the four `position=` lines and the "pre-migration script, post-migration script or seed data cause the difference" message. The draft holds only `draft.json` and `schema-change.sql`.

**Root cause:**
- pg-delta doesn't diff composite attribute order (pg-toolbelt #330/#332; research §8 "Silent gaps"). Ticket 27 made our catalog comparison catch it, so the rehearsal refuses the draft, as designed. A reorder can't be generated, only done by hand.
- `draft` never runs the schema change it generates (spec "Authoring commands": it diffs, writes and reports coverage). So it can't notice that its output doesn't reach the desired schema.
- The mismatch message (`draftMismatchSubject` in `rehearsal/rehearse-draft.ts`) assumes the differ is never wrong. When neither the desired schema nor the schema change changed since `draft`, it blames the scripts and seed data, even when the draft has none. The other cause, a change the differ can't generate, is never named.
- The README has no recipe for reordering a composite type or inserting an attribute in the middle. The reporter's pre-migration workaround works.

## Brief (ready-for-human)

**Category:** bug
**Summary:** When the generated schema change can't produce the desired schema, `draft` says so, and the rehearsal mismatch names that cause instead of blaming files that don't exist.

**Current behavior:**
A change pg-delta can't generate, such as reordering a composite type's attributes, drafts as an empty (or incomplete) schema change with no warning. `rehearse` and `finalize` then fail and blame "the pre-migration script, post-migration script or seed data", with a hint about renamed NOT NULL constraints, whether or not those files exist.

**Desired behavior (once decided):**
- Whatever is decided:
  - The draft rehearsal's mismatch, when neither the desired schema nor the schema change changed since `draft`, names only the draft files that exist. When the draft has no pre-migration script, post-migration script or seed data, it says the generated schema change can't produce the desired schema: the change has to be made by hand in the pre-migration script.
  - The NOT NULL rename hint appears only when a pre-migration script exists.
  - The README gains a recipe for reordering a composite type's attributes: create the new type, convert the columns with `USING`, drop the old type, rename the new one, all in the pre-migration script.
- Option 1: `draft` also warns, right after generating, when its schema change doesn't reach the desired schema. The warning lists the differences, as the rehearsal would, and says the change must be made in the pre-migration script. For a composite attribute order difference, it points to the README recipe.

**Key interfaces:**
- `RehearsalMismatchError` and the draft rehearsal's subject (`SinceDraft`, which needs to know which draft files exist).
- `draft` / `DraftResult`: a new advisory finding beside `toCover`, if option 1.
- The catalog comparison (`catalogDifferences`), shared, unchanged.

**Acceptance criteria (once decided):**
- [ ] API seam: the report's composite reorder, with no scripts or seed data, fails `rehearse` with a `RehearsalMismatchError` whose message doesn't mention scripts or seed data and does say the schema change can't produce the desired schema.
- [ ] A pre-migration rename that misses the NOT NULL constraint rename still gets the renaming hint.
- [ ] The README recipe, used as the pre-migration script, rehearses, finalizes and deploys with the data kept.
- [ ] Option 1: `draft` of the composite reorder returns the finding and the CLI prints it as a warning, and `draft` still exits 0.

**Out of scope:**
- Generating the reorder (pg-delta has no model for it).
- A generated statement that PostgreSQL refuses (104, which depends on the same decision).
- Column order of tables (101).

**Why not delegated:** option 1 changes what `draft` does (spec "Authoring commands": it diffs and writes, and `rehearse` proves). It costs a run of the schema change on every `draft`.

**Decision needed:**
1. **(recommended)** `draft` runs its generated schema change on the starting point it has already built: the migrations, seed data and pre-migration script. It then compares the result with the desired schema. A failure or a difference becomes a warning; `draft` still writes the draft and exits 0. This catches 102, 104 and 111's overflow at `draft` time, at the cost of applying the schema change once more per `draft`. The spec's `draft` line gains it.
2. Leave `draft` as it is. Only fix the rehearsal message and add the README recipe.
