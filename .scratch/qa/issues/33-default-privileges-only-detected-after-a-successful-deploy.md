# 33: Default privileges on the deploy role aren't flagged until a deploy has already drifted the target

**Status:** wontfix
**Category:** enhancement
**Severity:** low
**Duplicate of:** 27
**Area:** adopt

## What I did
On the adopted target `shop` (`qa_adopt_shop`, clean status), I did what the README's Permissions section warns against:

```sql
alter default privileges for role adopt_deployer in schema app grant select on tables to adopt_auditor;
```
```sh
pnpm exec super-deploy status --target shop      # clean, exit 0
# add table app.shipments to the desired schema
pnpm exec super-deploy draft --name "add shipments"
pnpm exec super-deploy finalize
pnpm exec super-deploy deploy --target shop      # "Deployed 1 migration", exit 0
pnpm exec super-deploy status --target shop
```

## Expected
The README says this leads to drift, and it does. But `status` and the deploy pre-flight checks could see the default privileges in `pg_default_acl` for the deploy role in the managed schema before deploying. They could warn (or refuse) up front, instead of letting the deploy commit and leaving the target blocked.

## Actual
`status` was clean before the deploy, the deploy reported success, and only afterwards:

```
Drift (the target differs from its recorded migrations):
  changed: table shipments
    - acl: shipments {...,adopt_auditor:SELECT/<owner>}
    + acl: shipments {...}
Error: Target shop has drifted from its recorded migrations: table shipments (changed). Deployments refuse until it matches them again ...
```

Neither command mentions default privileges, so a user who doesn't remember the README has to work out where the grant came from. The fix was `alter default privileges ... revoke ...` plus `revoke select on app.shipments from adopt_auditor`. The README doesn't spell out the second step ("deploy refuses until it is undone").

## Notes
Adoption already reacts to default privileges (issue 26), so the information is available.
