## Brief (ready-for-human)

**Category:** enhancement
**Summary:** Decide whether `unfinalize` checks the targets it can reach and asks before moving a migration one of them has recorded.

**Current behavior:**
`unfinalize` moves the newest migration (or Recovery) back into the draft and then warns, whatever any target recorded. When a target has recorded it, `deploy` and `status` refuse with "restore … from version control". That works, but so would finalizing the unchanged draft, which they don't mention.

**Desired behavior (once decided):**
- Option 1:
  - Before moving anything, `unfinalize` checks every target on the project's embedded servers (in the template, `dev`). Not real targets: they need credentials and the network.
  - If one records the migration, it names the target. In a terminal it asks whether to go ahead (default no). Without a terminal it refuses unless acknowledged by a flag.
  - The existing overwrite question, when asked, also carries the warning.
- Option 2: no target check. The warning moves before the move, into the overwrite question when there is one, and is printed first otherwise.
- With either: the history-mismatch refusal ("the target records migration N, which the repo doesn't have") adds, when the draft is the unfinalized migration N (same name, newest), that `finalize` with the draft unchanged puts it back.

**Key interfaces:**
- `unfinalize` and its options (a new acknowledgement flag and `Question`, if option 1). Reading a target's recorded migrations without the lock, as `status` does.
- The deploy pre-flight's history-mismatch refusal text (round 1, 50).

**Acceptance criteria (once decided):**
- [ ] Option 1, API seam: `unfinalize` with `dev` recording the newest migration asks the new question. Declining changes nothing on disk, and the flag lets it through without a terminal.
- [ ] Option 1: `unfinalize` with no embedded target, or one that hasn't recorded it, behaves as today, without starting a real target's connection.
- [ ] `status` on a target recording a migration that is now the draft suggests finalizing the unchanged draft.

**Out of scope:**
- Checking real (non-embedded) targets.
- `finalize` reproducing a migration byte for byte (it does).

**Why not delegated:** it revisits round 1's decision on 10 (warn after, no question). Checking `dev` also starts its server on every `unfinalize`.

**Decision needed:**
1. **(recommended)** Check the embedded targets and ask (or refuse without a terminal, unless acknowledged) when one has recorded the migration. Put the warning in the overwrite question too.
2. Keep "no question", but warn before the move and in the overwrite question.
3. Keep round 1's decision as it is. `status` still gets the "finalize the draft unchanged" hint.
