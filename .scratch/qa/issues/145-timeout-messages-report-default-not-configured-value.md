# 145: Timeout failure messages quote the default, not the configured lockTimeout and statementTimeout

**Status:** ready-for-agent
**Category:** bug
**Severity:** low
**Area:** fail
**Round:** 2

## What I did
```ts
qa: {
  adapter: postgresTarget({ env: "QA_DATABASE_URL" }),
  lockTimeout: "2s",            // also tried "3s"
},
```
With a pending `COMMENT ON TABLE t2 …`, another session holds `lock table app.t2 in share mode`:
```sh
pnpm exec super-deploy deploy --target qa
```
Then the same with `lockTimeout: "30s", statementTimeout: "2s"`.

## Expected
The message names the value that ran out, such as "The target's lockTimeout (2s) ran out", and the same for `statementTimeout (2s)`.

## Actual
```
Error: data-model/migrations/00018-t2d/schema-change.sql:4: PostgreSQL refused it: canceling statement due to lock timeout. The deployment rolled back: target qa is unchanged, still at migration 00017-t2c. The target's lockTimeout (default 5s) ran out waiting for a lock: retry once whatever held the lock has finished.
```
```
Error: data-model/migrations/00018-t2d/schema-change.sql:4: PostgreSQL refused it: canceling statement due to statement timeout. The deployment rolled back: target qa is unchanged, still at migration 00017-t2c. The target's statementTimeout (default none) cancelled the statement: retry once whatever held it up has finished, or raise the setting.
```
The configured values are applied: the deploy failed after about 2 s, and with `60s` it waited much longer. Only the message is wrong. "(default 5s)" reads as though my setting was ignored, and "statementTimeout (default none)" is self-contradictory, since a statement timeout did cancel the statement.

## Notes
The lockTimeout message also doesn't suggest raising the setting, while the statementTimeout one does.

### Triage, 2026-10-21

**Verification:** CONFIRMED. With `lockTimeout: "2s"` and a SHARE lock held on `app.t2`, the deploy failed after about 2.9 s with `The target's lockTimeout (default 5s) ran out …`. With `lockTimeout: "30s", statementTimeout: "2s"`: `The target's statementTimeout (default none) cancelled the statement …`.

**Root cause:** `nextStep` in `SqlFileFailedError` (`rehearsal/replay.ts`) only knows the SQLSTATE and quotes `targetDefaults`, not the target's resolved settings. The values themselves are applied correctly.

## Agent Brief

**Category:** bug
**Summary:** A lock or statement timeout failure quotes the value that ran out, and says how to change it.

**Current behavior:**
A deploy that hits its lock timeout says `The target's lockTimeout (default 5s) ran out …` whatever `lockTimeout` is set to. One that hits a statement timeout says `statementTimeout (default none)`, even when `statementTimeout` is set, or when the server's own `statement_timeout` cancelled it. The lock-timeout message doesn't mention raising the setting.

**Desired behavior:**
- Lock timeout: `The target's lockTimeout (2s) ran out waiting for a lock: retry once whatever held the lock has finished, or raise lockTimeout for target qa in super-deploy.config.ts.` Where the target doesn't set it: `(5s, the default)`.
- Statement timeout with `statementTimeout` set: `The target's statementTimeout (2s) cancelled the statement: …, or raise the setting.`
- Statement timeout without it: say the server's `statement_timeout` for the deploy role cancelled it, and that `statementTimeout` in the config overrides it.
- The attempt log records the same message.

**Key interfaces:**
- `SqlFileFailedError` and its next-step text: it needs the target's resolved `lockTimeout` and `statementTimeout` (e.g. carried with the rollback information, or added where the deploy wraps the error).
- The resolved target config.

**Acceptance criteria:**
- [ ] API seam: a target with `lockTimeout: "200ms"` failing on a held lock gives a message containing `lockTimeout (200ms)`.
- [ ] A target without `lockTimeout` gives `(5s, the default)`.
- [ ] A target with `statementTimeout: "200ms"` blocked by a held lock, with a longer `lockTimeout`, gives `statementTimeout (200ms)`.
- [ ] A statement timeout without `statementTimeout` names the server's `statement_timeout`.

**Out of scope:**
- Timeouts in the drift check and pre-flight, which are bare errors today (142).
- Naming the session holding the lock (146).
