# 168: The confirmation's Host line shows the resolved address, not the host in the connection string

**Status:** ready-for-agent

## What I did
```sh
export QA_DATABASE_URL=postgres://qa2_disp_deployer:dep@localhost:54818/qa2_disp_qa
pnpm exec super-deploy disposable --target qa --set yes    # in a terminal
```
The same for rebuild, deploy-draft and mark.

## Expected
`Host:      localhost:54818`, the host I configured. The README says the confirmation "shows the target's name, host, database" so the person typing YES can recognise the target.

## Actual
```
│  Target:    qa
│  Host:      [::1]:54818
│  Database:  qa2_disp_qa
```
With `127.0.0.1` in the URL it shows `127.0.0.1:54818`.

## Notes
Guess: it shows the connected socket's remote address. For a real target such as `prod-db.example.com`, the prompt would show a bare IP (often a cloud load balancer's), which makes it harder to tell production from QA at the moment it matters. Showing both (`localhost:54818 ([::1])`) would keep the resolved detail.

### Triage, 2026-10-21

**Verification:** CONFIRMED. With `localhost:54818` in the connection string, every confirmation (disposable, rebuild, deploy-draft, mark) showed `Host:      [::1]:54818`.
- Root cause: the guard reads the host from the server, `host(inet_server_addr())` and `inet_server_port()` (`guard/guard.ts:141-158`; `TargetView.host` documents it as "the server's address as it reports it").
- That is the address the server accepted the connection on, not the name the user configured. Behind a proxy or pooler (PgBouncer, RDS Proxy) it is the database server's own private address, which the user may never have seen.
- The guard can't show the configured host today. A `DeploymentAdapter` only has `connect()` and `close()`, so a custom adapter (secrets manager, IAM tokens, tunnel) may not even have a host name to give.
- The guard's fingerprint also compares this address before and after YES, which is useful, since it is what the session actually reached.
- Spec ("Guard sequence") and ticket 18 only say "host"; nothing decided which one.

## Brief (ready-for-human)

**Category:** enhancement
**Summary:** The guarded commands' confirmation shows the host the user configured, so the person typing YES recognises the target.

**Current behavior:**
`Host:` shows the address the server reports for the connection (`[::1]:54818` for `localhost:54818`; a private IP for a cloud host name).

**Desired behavior (once decided):**
- When the adapter can say what it connects to, `Host:` shows that (e.g. `localhost:54818`, `prod-db.example.com:5432`), followed by the server's address in brackets when it differs: `Host:      localhost:54818 (server [::1]:54818)`.
- An adapter that can't say keeps today's line.
- The fingerprint keeps comparing the server's address.

**Key interfaces:**
- `DeploymentAdapter`: an optional way to describe where it connects (e.g. a `describe?(): string` or `host` property). `postgresTarget` fills it from its connection string (host and port only, never credentials). The embedded adapter fills it with its configured host and port.
- `TargetView` and the guard's `describeTarget`.

**Acceptance criteria (once decided):**
- [ ] Pseudo-terminal: a `postgresTarget` whose URL names `localhost` shows `localhost:<port>` in the confirmation, with the server's address after it.
- [ ] A custom adapter without the new member shows the server's address as today.
- [ ] No credentials ever appear in the line.

**Out of scope:**
- Changing what the fingerprint compares.
- Showing the host in `status` or `deploy` output.

**Why not delegated:** it adds an optional member to a public adapter interface (spec story 94), and picks what the confirmation trusts.
**Decision needed:**
- **(recommended)** An optional adapter member describing the configured host, shown first, with the server's address in brackets.
- Show the configured host only, from the adapter, falling back to the server's address.
- Keep the server's address, and document in the README that `Host:` is the address the server reports.

### Decided, 2026-10-21

The maintainer chose **the configured host first, with the server's address in brackets**, and the box keeps naming the target.
- `Target:` stays (the target's name from config).
- `Host:` shows the host and port from the connection string, then the server's address in brackets when it differs: `Host: localhost:54818 ([::1]:54818)`, `Host: db.prod.internal:5432 (10.0.4.7:5432)`.
- Adapters expose the configured host through an optional member; without it, the server's address alone is shown as today.

**Acceptance criteria:** pseudo-terminal test of a guarded command against `localhost` shows `Target:` and `Host: localhost:<port> ([::1]:<port>)` (or the IPv4 form).
