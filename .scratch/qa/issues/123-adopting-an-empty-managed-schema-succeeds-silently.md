# 123: Adopting an empty managed schema succeeds silently when the tables are in another schema (forgotten managedSchema)

**Status:** ready-for-human
**Category:** bug
**Severity:** medium
**Area:** adopt
**Round:** 2

## What I did
Database `qa2_adopt_typo`, owned by the deploy role, whose tables live in schema `shop`; `public` is empty.

```sql
create schema shop authorization qa2_adopt_deployer;
create table shop.t (id int primary key);   -- as qa2_adopt_deployer
```

Fresh project (`init`, `git init`, `pnpm install`), `qa` target added as the README says, but `managedSchema` not set (an easy thing to forget; default `public`).

```sh
export QA_DATABASE_URL=postgres://qa2_adopt_deployer:dep@localhost:54818/qa2_adopt_typo
pnpm exec super-deploy init --adopt qa
```

## Expected
A refusal, or at least a warning, since the managed schema is empty while the database has a user schema full of tables: "schema public is empty; the database also has schemas shop (1 table). Set managedSchema?" Adoption guards against a typo in `managedSchema` (the schema must exist), but not against forgetting it.

## Actual
```
Adopted target qa: migration 00001-adopt in data-model/migrations/00001-adopt, recorded on it as marked (attempt #1)
```

exit 0. `00001-adopt/schema-change.sql` holds only its header comment, `data-model/desired-schema/` is empty, and the target now has a `deployment_history` schema recording migration 1. After correcting `managedSchema` to `shop`, `status --target qa` reports all of `shop` as drift, and adopting again is refused both ways (see issue 124): the user is stuck.

## Notes
Guess: refuse (or ask in a terminal) when the managed schema has no objects, or when other non-system schemas hold tables. The success line could also say how many objects were adopted ("Adopted 0 objects"), which would make this obvious at a glance.

## Brief (ready-for-human)

**Category:** bug
**Summary:** Adopting an empty managed schema should not succeed silently, especially when the target's tables are in another schema.

**Current behavior:**
An existing but empty managed schema is adopted: an empty migration 1 is recorded on the target. If `managedSchema` was simply forgotten, the user only finds out later, when `status` reports the real schema's contents as drift. Undoing it isn't documented (124).

**Desired behavior (once decided):**
- An empty managed schema is either refused or warned about. The message names the target's other non-system schemas that hold objects, with counts, e.g. `schema "public" is empty; the target also has shop (1 table)`, and says to set `managedSchema`.
- A successful adoption says how many objects it adopted.

**Key interfaces:**
- The adoption command's target-reading step and `AdoptConflictError` (a new reason), or a warning on `AdoptResult`.
- The query listing the target's other schemas can be shared with 133.

**Acceptance criteria (once decided):**
- [ ] Adopting a target whose managed schema is empty while another schema holds a table refuses (or warns), naming that schema. With a refusal, nothing is written to the project or the target.
- [ ] The success line of a normal adoption gives the number of objects adopted.
- [ ] The README's "Adopting an existing database" matches.

**Out of scope:**
- Undoing an adoption that already happened (124).
- Listing schemas when the managed schema doesn't exist (133).

**Why not delegated:** it reverses round-1 issue 24's explicit choice to keep adopting empty schemas.
**Decision needed:**
- Refuse any empty managed schema: there is nothing to adopt, and a plain `deploy` already works on an empty database. The refusal names the other schemas that hold objects (recommended).
- Refuse only when other non-system schemas hold objects. An empty schema in an otherwise empty database is still adopted.
- Keep adopting, but print a warning naming the other schemas, plus "Adopted 0 objects".
