# 170: rebuild's confirmation names a domain's constraint without saying which domain

**Status:** ready-for-agent
**Category:** enhancement
**Severity:** low
**Area:** disp
**Round:** 2

## What I did
On disposable target `qa` (`managedSchema: "app"`), as the deploy role:
```sql
create domain app.d_email as text check (value like '%@%');
```
Then `pnpm exec super-deploy rebuild --target qa --to 4`.

## Expected
`constraint d_email_check on domain app.d_email`, like table constraints (`constraint customers_name_not_null on table app.customers`).

## Actual
```
│  Not from any recorded migration, in schema app:
│    constraint d_email_check
│    ...
│    type app.d_email
```

## Notes
Cosmetic. When several domains are listed it isn't clear which constraint belongs to which domain, and the line counts toward the 10-object cap.

### Triage, 2026-10-21

**Verification:** CONFIRMED, and not limited to `rebuild`. I created two domains with checks and a composite type by hand on my target.
- The rebuild confirmation listed `constraint d_code_check`, `constraint d_email_check`, `type app.d_code`, `type app.d_email`, and the composite type twice, as `composite type app.pair` and `type app.pair`.
- `status`'s drift listing and its `DriftError` show the same labels, so `mark`'s mismatch listing does too.
- Root cause: drift names objects with `pg_describe_object` (`verification/catalog.ts`, read at the end of `catalogFacts`). For a domain constraint PostgreSQL gives only `constraint <name>`; for a table constraint it gives `constraint <name> on table <table>`.
- `driftedObjects` (`verification/drift.ts`) folds an extra or missing table's parts into it by the ` of <object>` / ` on <object>` suffix. A domain constraint has no suffix, so it's listed separately.
- A composite type is two catalog objects (its `pg_class` row and its `pg_type` row), with two descriptions that don't fold either.

## Agent Brief

**Category:** enhancement
**Summary:** Drift names a domain's constraint with its domain and folds it into an extra or missing domain, and lists a composite type once.

**Current behavior:**
In `status`'s drift, `mark`'s mismatch and `rebuild`'s "Not from any recorded migration" list, a domain constraint is named `constraint d_email_check` with no domain. A whole extra domain is listed as both the type and its constraint, and a whole extra composite type as `composite type app.pair` and `type app.pair`. Each extra line also counts toward `rebuild`'s 10-object cap.

**Desired behavior:**
- A domain constraint is named with its domain, e.g. `constraint d_email_check on domain app.d_email` (or whatever form makes the fold below work).
- When the whole domain is extra or missing, its constraints fold into it, as a table's columns and constraints fold into the table: one entry, with the constraint's catalog lines under it.
- A composite type that is extra or missing is one entry, with its relation, attribute and type lines under it.
- A changed domain constraint (same domain on both sides) is still reported, named with its domain.

**Key interfaces:**
- The object description `catalogFacts` attaches to each fact (`pg_describe_object` today), and the folding in `driftedObjects`.

**Acceptance criteria:**
- [ ] A domain with a check constraint made by hand on a target appears in `status`'s drift as one object, the domain, with the constraint's line under it.
- [ ] Changing an existing domain's check by hand shows `constraint <name> on domain <schema>.<domain>` as changed.
- [ ] A composite type made by hand appears once.
- [ ] `rebuild`'s list shows the same single entries.
- [ ] Existing drift, mark and rehearsal-mismatch tests pass.

**Out of scope:**
- Multiline definitions breaking the drift listing's indentation (153).
- Inheriting and typed tables in "Also drops" (169).
