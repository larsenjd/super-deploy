# 51: After a SIGKILLed deploy, "locked by attempt #N ... try again when it has finished" gives no hint the CLI is gone

**Status:** ready-for-agent
**Category:** enhancement
**Severity:** low
**Area:** fail

## What I did
Target `kill` with 4M rows in `notes` and pending migration 8 (post-migration `update notes set body_len = length(body);`, ~10 s).
```sh
pnpm exec super-deploy deploy --target kill &   # in its own process group
sleep 3; kill -KILL -<pgid>                      # CLI killed mid-UPDATE
pnpm exec super-deploy deploy --target kill
pnpm exec super-deploy status --target kill
```
Also with the deploy blocked on a lock instead of running an UPDATE.

## Expected
The refusal and `status` say that attempt #N's session is still active on the server (backend pid, running for how long, current query), so the user can tell a live deploy from an orphaned one. For an orphaned one, they'd say to wait for it to roll back or cancel it (`pg_cancel_backend(<pid>)`).

## Actual
```
Error: Target kill is locked by attempt #4 (deploy by jonathanl, started 2026-10-20T20:00:39.562Z); try again when it has finished
```
`status` showed `#2 deploy running migrations 5-6 by jonathanl ...` for a process that no longer existed (or failed outright while the orphan held locks: issue 41). With no client-connection check, PostgreSQL keeps running the orphaned UPDATE to the end. On a big table that could be hours, with nothing pointing to the backend.

## Notes
Recovery afterwards was very good. Once the orphaned backend ended, the next `status`/`deploy` settled it automatically: `#4 deploy abandoned migrations 7-8 ... The command ended without recording an outcome; settled as abandoned: none of its migrations are recorded`. The following deploy then succeeded.

### Triage, 2026-10-20

**Verification:** CONFIRMED. I SIGKILLed a deploy's process group mid-UPDATE. The next `deploy` printed `Target ext2 is locked by attempt #2 (...); try again when it has finished`, and `status` failed as in 41. `pg_stat_activity` still showed the orphaned UPDATE running; once it ended, `status` settled #2 as abandoned. `TargetLockedError` drops the backend `pid` that `lockHolder` already finds (`src/deploy/lock.ts:124-142`). PostgreSQL keeps running an orphaned statement until it ends, because the deploy session doesn't set `client_connection_check_interval` (user-settable, PG14+).

## Brief (ready-for-human)

**Category:** enhancement
**Summary:** When a target is locked, say enough to tell a live deploy from an orphaned backend, and stop orphaned statements early.

**Current behavior:**
After a deploy's CLI dies, the target-lock refusal says "try again when it has finished". It names the attempt, but not the backend, what it's doing, or that the CLI may be gone. The orphaned statement can run for hours.

**Desired behavior (once decided):**
- The refusal (and `status`, see 41) names the holding backend's pid, how long its current statement has run, and the statement. It tells the user how to cancel it (`pg_cancel_backend(<pid>)`) if the deploy is known to be dead.
- The deploy session sets `client_connection_check_interval`, so the server cancels its statement soon after the client disappears. This part is in scope regardless of the decision.

**Key interfaces:**
- `TargetLockedError` and its payload (attempt, pid).
- `lockHolder()`.
- The deploy session's settings (where `lock_timeout` is set).
- The attempt record, if client host and pid are added.

**Acceptance criteria (once decided):**
- [ ] The lock refusal names the holding backend's pid, `pg_stat_activity` state, statement start and query.
- [ ] A deploy whose CLI is SIGKILLed mid-statement has its backend end within a few seconds plus the check interval, in an integration test.
- [ ] If the attempt records client host and pid, the refusal says when the recording process no longer exists on this host.

**Out of scope:**
- `status` handling of a held target (41), apart from sharing the message.
- Automatic cancellation of another attempt's backend.

**Why not delegated:** deciding how to detect a dead client (record host/pid in the attempt?) changes the history schema.
**Decision needed:**
- Set `client_connection_check_interval` (e.g. 5 s) and show the pid and `pg_stat_activity` details; no history change (recommended).
- Also record client host and pid in the attempt, so a same-host CLI can report "the process that started it is gone".

### Decided, 2026-10-21

The maintainer chose: **detect dead clients**, with no history change.

- The deploy session sets `client_connection_check_interval` (5 s), so PostgreSQL ends a dead CLI's session soon after it disappears.
- The lock refusal (shared with `status`, 41) names the holding backend's pid, its `pg_stat_activity` state, when its current statement started, and the statement, and says that if that deploy is known to be dead, `select pg_cancel_backend(<pid>)` ends it.

**Acceptance criteria:** the brief's first two; the third (client host and pid in the attempt) is dropped.
