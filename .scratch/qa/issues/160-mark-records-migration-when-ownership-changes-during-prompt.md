# 160: mark records the migration when an object's owner changes while it waits for YES

**Status:** resolved
**Category:** bug
**Severity:** medium
**Area:** disp
**Round:** 2

## What I did
Project with `managedSchema: "app"`, migrations 1-3 (3 creates `notes`), target `qa` = `postgresTarget({ env: "QA_DATABASE_URL" })`, deploy role `qa2_disp_deployer` (not a superuser, `CREATE` on the database). `qa` is at migration 2.

```sh
# make migration 3's change by hand, as the deploy role
node sql-as-deployer.mjs qa2_disp_qa "create table app.notes (id bigint generated always as identity primary key, body text not null)"
pnpm exec super-deploy mark --target qa      # in a terminal
```
The confirmation says: "The target matches a replica of migrations up to 00003-add-notes (column order aside), and the deploy role owns everything in its managed schema." While it waits for YES, in another session as the superuser:
```sql
alter table app.notes owner to postgres;
```
Then type `YES`.

## Expected
After YES, mark re-checks ownership as it re-checks the schema (changing a column during the wait is caught: "Target qa does not match a replica ... Nothing was recorded"), and refuses: the README says mark refuses a target where something in the managed schema is owned by another role.

## Actual
```
Marked migration 00003-add-notes as deployed on target qa (attempt #21)
```
and right after:
```
$ pnpm exec super-deploy status --target qa
Target qa (disposable): 3 migrations recorded, 0 pending
Deploy would refuse:
  table app.notes is owned by postgres, whose privileges the deploy role doesn't have (fix: ALTER TABLE app.notes OWNER TO qa2_disp_deployer)
```
Reproduced twice (attempts #21 and #23).

## Notes
Run without the race, mark does refuse before asking ("The deploy role on target qa doesn't own everything in the managed schema: table app.notes is owned by postgres ..."). Guess: the post-YES re-check compares the schema (which ignores ownership) but not the ownership check. Same scenario on a non-disposable target records a migration on a target that `deploy` then refuses.

### Triage, 2026-10-21

**Verification:** CONFIRMED in a pseudo-terminal, on a fresh database (deploy role not a superuser, managed schema `app`, target at migration 2).
- I created `app.notes` by hand as the deploy role and ran `mark --target qa`. While it waited for YES, I ran `alter table app.notes owner to postgres` as the superuser, then typed YES.
- The output was `Marked migration 00003-add-notes as deployed on target qa (attempt #4)`, and the next `status` listed `table app.notes is owned by postgres ...` under "Deploy would refuse".
- Root cause: `mark`'s `check()` runs the ownership check and the replica check before asking (`commands/mark.ts:70-79`). Under the lock, `markNextPending` repeats only the replica check (`deploy/mark.ts:258-281`). The catalog comparison ignores ownership by design, so a change of owner during the prompt is never seen. The guard's fingerprint (recorded migrations, draft, flag) doesn't cover it either.
- `init --adopt` has the same gap: it checks ownership before taking the lock (`commands/adopt.ts:314`), then records through the same `markNextPending`.
- The behaviour isn't intended. ADR-0006 and the README say `mark` refuses such a target, and `commands/mark.ts`'s header says the replica check runs again under the lock "because the target's structure ... may have changed while the person read the screen". Ownership needs the same treatment.

## Agent Brief

**Category:** bug
**Summary:** `mark` (and `init --adopt`) check ownership again under the target lock, right before recording, as they already do for the replica match.

**Current behavior:**
The ownership check runs only before the YES question. An object in the managed schema that changes owner while the prompt waits is recorded as marked, and the next `deploy` refuses the target. Without the race, `mark` refuses as documented.

**Desired behavior:**
- Under the lock, before the migration is recorded, the ownership check runs again. If it fails, `mark` refuses with the same `NotOwnedError` it gives before asking. Nothing is recorded and the attempt ends failed, as a replica mismatch found under the lock does.
- `init --adopt` gets the same check under the lock, since it records through the same path.

**Key interfaces:**
- `markNextPending` (shared by `mark` and adoption): add the ownership check (`requireOwnership`) next to its replica check.
- `NotOwnedError`: unchanged.

**Acceptance criteria:**
- [ ] Pseudo-terminal test: with a hand-made table matching the next migration, changing its owner to another role while `mark` waits for YES makes `mark` refuse after YES with `not-owned`. No `migrations` row is written, and the attempt is recorded as failed.
- [ ] `mark` without the race behaves as today (refuses before asking when something isn't owned, marks when everything is).
- [ ] Adoption's existing tests pass.

**Out of scope:**
- Comparing ownership as part of drift (ADR-0006).
- Other guarded commands' re-checks under the lock: 171 (a lock held by a running attempt) and 172 (`rebuild` and the managed schema's owner).
