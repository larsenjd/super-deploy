# 40: `deploy` exits 0 about 10 seconds after Ctrl+C or SIGTERM, though nothing was deployed

**Status:** ready-for-agent
**Category:** bug
**Severity:** high
**Area:** fail

## What I did
Project from `super-deploy init` (`git init`, `pnpm install`) with a real target on the shared server:

```ts
// super-deploy.config.ts (added to the template)
import { defineConfig, postgresTarget } from "super-deploy";
...
targets: {
  dev: { adapter: postgres.target("dev") },
  lock4: { adapter: postgresTarget({ env: "FAIL_LOCK4_URL" }) },
},
```

`FAIL_LOCK4_URL=postgres://fail_deployer:dep@localhost:54818/qa_fail_lock4` (a non-superuser role that owns the database). The target had migrations pending. The last one has a post-migration script that takes ~10 s on 4M rows (`update notes set body_len = length(body);`), but any pending migration will do.

Typed Ctrl+C in a real pty 3 s into the deploy:

```sh
pnpm exec super-deploy deploy --target lock4   # then Ctrl+C
echo $?
```

I also sent SIGINT to the process group at 0.3 s, 0.5 s, 0.6 s, 1.2 s and 2.5 s (during the rehearsal, while blocked on a lock, and during a long UPDATE), sent SIGTERM, and ran it both as `pnpm exec super-deploy` and as `node node_modules/super-deploy/dist/cli.js`. Every time:

## Expected
A non-zero exit code (130 for SIGINT, as `finalize`, `rehearse`, `draft` and `status` give), promptly, and a last line saying what happened to the target (rolled back, nothing recorded).

## Actual
```
^C
Interrupted by SIGINT: cleaning up before exiting (interrupt again to exit at once)

[exit=0 ctrl-c at 3.01s, exited 10.15s after]
```

- Exit code **0** every time (11 runs; SIGINT and SIGTERM; `pnpm exec` and plain `node`).
- The process exits 10.1–10.2 s after the signal, every time. The database work stops at once: the in-flight UPDATE is cancelled within ~0.4 s, the deploy's sessions are gone within a second, and the private embedded server has stopped. After that the node process sits idle for ~10 s.
- Nothing is printed after "cleaning up", so the user isn't told the outcome. `status` shows it correctly afterwards (`#8 deploy abandoned migration 8 ... Interrupted (SIGINT)`, migration still pending).
- A second Ctrl+C exits at once with 130.

By contrast, SIGINT during `finalize`, `rehearse`, `draft` and `status` exits 130 within 0.1 s.

## Notes
- This is dangerous in CI and scripts: `super-deploy deploy --target prod && ./restart-app.sh` carries on as if the deploy succeeded when the job is cancelled or times out (CI runners usually send SIGTERM).
- Guess: a 10 s timer or idle pool timeout keeps the event loop alive, and the exit code isn't set on the interrupted deploy path.

### Triage, 2026-10-20

**Verification:** CONFIRMED.

**Reproduction:** an external (non-embedded) target, with the rehearsal on the project's own embedded server.
- Signal sent to the whole process group:
  - SIGINT during the rehearsal: exit `0` after 10135 ms.
  - SIGINT during the deploy transaction: exit `0` after 10129 ms.
  - SIGTERM during the deploy transaction: exit `0` after 10139 ms.
- The same signals sent to the CLI process alone: 130 or 143 within about 150 ms.

**Root cause:**
- The group signal also stops the project's embedded postmaster.
- The adapter's `stop()` then calls embedded-postgres's `server.stop()`. That only resolves on the child's `exit` event, which has already fired, so it never resolves.
- With `runCli` stuck, the event loop drains. async-exit-hook's `beforeExit` handler, still installed after `importDeferringSignals` removed the library's signal handlers, calls `stop()` again, which hangs again.
- The hook's 10 s force-exit timer then calls `process.exit(0)`, and the CLI's own exit code is never set.
- Trace: SIGINT +872 ms, postgres exits +884, `kill` on the dead child +979, `beforeExit 0` +980, `exit 0` +10994.
- The 10 s is not `pg_terminate_backend(pid, 10000)`.

**Why the tests miss it:**
- `cli-deploy-interruption.test.ts` attaches to the test server, so the child never owns a server, and it signals the CLI only.
- The `signalGroup` test in `cli-interruption.test.ts` runs `draft`, which reaches `stop()` before the postmaster has exited.

**Correction:** no closing "what happened" line is by design (spec: "print one notice"). `status` shows the abandoned attempt.

## Agent Brief

**Category:** bug

**Summary:** An interrupted command must exit with its interruption code (130 for SIGINT, 143 for SIGTERM) promptly, even when the signal also stopped the project's own embedded PostgreSQL server.

**Current behavior:**
Suppose Ctrl+C or SIGTERM reaches the whole process group, and the command owns the project's private embedded server while doing slower cleanup (for example a deploy to an external target). The CLI prints the interruption notice, cleans up, then sits idle for about 10 s and exits **0**. Scripts and CI treat the cancelled deploy as a success.

**Desired behavior:**
- Stopping the embedded server is a no-op when its postmaster process has already exited (exit code or signal set), so close and cleanup never wait on an exit event that has already fired.
- No third-party exit hook can end the process with code 0 on an interrupted command. Remove or neutralise the embedded-postgres library's `beforeExit`/`exit` hooks, or make them honour the interruption's exit code.
- The process exits 130 (SIGINT) or 143 (SIGTERM) soon after cleanup finishes. Cleanup itself is unchanged: attempt recorded as abandoned, transaction rolled back.

**Key interfaces:**
- The embedded-postgres adapter's `stop()` / `close()`, and how it imports the library while deferring its signal handlers.
- The CLI's process shell (interruption → exit code 129–149).

**Acceptance criteria:**
- [ ] CLI seam regression test. Use a project whose rehearsal uses its own embedded server (it owns the data dir) and an external target on the test server. A pending migration stalls (stalling adapter / `TEST_STALL`). `spawnCli(..., { detached: true })` then `signalGroup("SIGINT")` exits 130 within a few seconds, not after about 10 s.
- [ ] The same with `SIGTERM` exits 143.
- [ ] After either, `status` shows the attempt abandoned with no migration recorded, and no postmaster is left running for the project.
- [ ] The existing interruption tests still pass.

**Out of scope / follow-up:**
- Side finding, not part of this fix: SIGTERM to the group while a rehearsal statement is stalled exits 143 only after the statement ends (about 60 s). Smart shutdown appears to refuse the new connection that cleanup needs (`DROP DATABASE ... WITH (FORCE)`), so nothing ends the running statement. File it separately if it matters.
- A final "rolled back, nothing recorded" line: by design, one notice only.
- Embedded server sharing between concurrent commands (14).
