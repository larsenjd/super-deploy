### Triage, 2026-10-21

**Verification:** CONFIRMED in a pseudo-terminal.
- Setup: a superuser session held ACCESS SHARE on `app.notes` for 35 s. A `rebuild --to 5` (YES typed) blocked on `DROP TABLE IF EXISTS app.notes CASCADE`.

- Root cause: `runGuarded` connects, reads the view, runs the command's `check()` and asks (`guard/guard.ts:88-115`). The target lock is only tried inside `withLockedTarget`, after YES (`:117`).
- Status already names the holder without taking the lock (`lockHolder`, `deploy/lock.ts`; decided for round 1's 41 and 51).
- The same order applies to all four guarded commands (`runGuarded` is shared); I saw it with `deploy-draft` only.
- Not run, but it follows from the order: `mark`'s and `rebuild`'s checks read the target's catalogs while another command's transaction may hold ACCESS EXCLUSIVE locks, so they could wait there instead.

## Agent Brief

**Category:** enhancement
**Summary:** A guarded command refuses before asking YES when another attempt holds the target lock.

**Current behavior:**
`disposable`, `deploy-draft`, `rebuild` and `mark` show their confirmation and ask for YES while another command holds the target. Only after YES do they refuse with `TargetLockedError`. Nothing runs, but the person has read and confirmed a description of a target state that the running command is about to change.

**Desired behavior:**
- Before the command's preconditions are checked and before asking, the guard checks without waiting whether the target lock is held. If it is, it refuses with the same `TargetLockedError` (holder's attempt, command, user, start, server process and activity, `pg_terminate_backend` advice) that it gives today after YES. Nothing is asked and no attempt is recorded.
- The check doesn't take the lock: two people can still both reach the question, and the try-lock under `withLockedTarget` after YES stays as the real guard.
- A target whose history schema doesn't exist yet passes the check.

**Key interfaces:**
- `runGuarded`: a non-blocking holder check (`lockHolder` or the same `pg_try_advisory_lock`/release pair) on the guard's read-only session, before `check()`.
- `TargetLockedError`: unchanged.

**Acceptance criteria:**
- [ ] Pseudo-terminal: while a test session holds the target's advisory lock as a running attempt (or a `rebuild` is blocked), `deploy-draft` refuses before any YES prompt with `target-locked`, naming the holder.
- [ ] The same for `disposable --set yes` (one more command is enough to show it is the guard's behaviour).
- [ ] With the lock free, every guarded command asks as today.
- [ ] Taking the lock between the question and YES is still refused after YES, as today.

**Out of scope:**
- `status`'s handling of a held lock (41, resolved).
