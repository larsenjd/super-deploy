# 185: A pre-migration trigger with a dynamic-SQL override runs GRANT and DISABLE ROW LEVEL SECURITY at deploy, despite "no override marker gets past these refusals"

**Status:** resolved
**Category:** bug
**Severity:** medium
**Area:** privs
**Round:** 2

## What I did
Project with `managedSchema: "app"` and a table `notes (id bigint generated always as
identity primary key, body text not null)` deployed to `dev`, which I flagged with
`disposable --target dev --set yes`. With no desired-schema change, `draft --name
scripts`, then `data-model/draft/pre-migration.sql`:

```sql
-- OVERRIDE SUPER-DEPLOY REFUSAL: grants via dynamic sql
create function sneaky() returns trigger language plpgsql as $$
begin
  execute 'grant select on app.customers to public';
  execute 'alter table app.orders disable row level security';
  return new;
end $$;

create trigger notes_sneaky before insert on notes for each row execute function sneaky();

insert into notes (body) values ('x');

drop trigger notes_sneaky on notes;

drop function sneaky();
```

```
$ pnpm exec super-deploy rehearse
Rehearsed draft scripts after 7 migrations: matches the desired schema
$ pnpm exec super-deploy deploy-draft --target dev     # typed YES
Deployed draft scripts to dev on top of 00007-fn-back, without seed data
```

Then on dev: `select relacl from pg_class where relname = 'customers'`.

## Expected
Refused, like the direct forms. The same file with `grant ...` directly, with a
`DO` block, or with `insert into notes (body) select sneaky()` is refused
(`[unsupported-object]`, `[do-statement]`, `[user-function-call]`).

## Actual
```
{deployer=arwdDxtm/deployer,=r/deployer}
```

`PUBLIC` was granted `SELECT` on `customers` by the deployment. Grants aren't
drift, so `status` would never report it on a real target, and the function and
trigger are gone afterwards, so nothing in the schema shows it either. The same
draft finalized would do this on every target `deploy` reaches.

## Notes
- README "What the desired schema declares": "No override marker gets past these
  refusals", and "[user-function-call] deploy-time SQL may not call user-defined
  functions"; a trigger fired by a script's DML is a call in all but name.
- The override reason is recorded and reviewers see it, which limits the risk; but
  the reason text is free-form ("loads the staging table", say), and a reviewer
  reading the README would believe privilege changes are impossible.
- Guess at a fix: refuse creating triggers (or functions with an override) in
  pre-/post-migration scripts that the same script then fires, or check
  `EXECUTE` string literals against the privilege rules.

### Triage, 2026-10-21

**Verification:** CONFIRMED, and wider than reported: no override marker is needed.
- The reporter's pre-migration script, deployed to `qa` as a finalized migration: `customers` got `=r/<deploy role>` (`PUBLIC` select) and `orders` lost row-level security. `finalize` did list the override.
- The same script with the statements written statically in the trigger body (`grant select on app.notes to public; alter table app.orders disable row level security;`, no `EXECUTE`, no marker) rehearsed, finalized and deployed, and `notes` got `PUBLIC` select.
- A desired-schema function whose PL/pgSQL body contains `grant select on notes to public`, or `set role ...`, drafts without a word. A `LANGUAGE sql` body can hold a `GRANT` too (checked on the server: calling it grants).

**Root cause:** the privilege refusals (`privilegeRefusal`, `sql-analysis/privileges.ts:76`) run only on top-level statements (`desired-schema-rules.ts:246`, `deploy-time.ts:512`). Routine bodies are parsed (`sql-analysis/routine-bodies.ts`), but each embedded statement is checked only for denylisted calls, `NOTIFY` and schema references (`plpgsqlNodeFindings`, `:81-142`; `sqlBodyFindings`, `:207-232`). Triggers fired by a script's DML are accepted by design (spec "Functions: ... triggers firing from DML is accepted"), so a body runs whatever it holds as the deploy role during the deployment.

**Intended?** No. The spec refuses privilege statements "in every deploy-time file", as "structural rules no override marker bypasses", and the README says the same. The dynamic-SQL case is different: an override exists exactly for SQL the rules can't see, so it can't be closed by rules, only documented.

## Agent Brief

**Category:** bug
**Summary:** The privilege refusals apply to every statement inside a routine body, and the README says that an overridden `EXECUTE` is the one thing the rules can't check.

**Current behavior:**
A function or procedure body (PL/pgSQL, or a `LANGUAGE sql` string body) may contain `GRANT`, `REVOKE`, `ALTER DEFAULT PRIVILEGES`, `CREATE POLICY`, `ALTER TABLE ... ENABLE/DISABLE/FORCE ROW LEVEL SECURITY`, `OWNER TO` and role statements, in the desired schema and in every deploy-time file. A trigger fired by a script's DML then runs them as the deploy role during the deployment, on every target. The README says "No override marker gets past these refusals", and a reviewer reading it believes privilege changes are impossible.

**Desired behavior:**
- Every SQL statement embedded in a PL/pgSQL body or a `LANGUAGE sql` string body gets the same privilege refusal as the same statement at top level, in the desired schema and in every deploy-time file kind, with the line of the statement inside the body. As at top level, no marker gets past it.
- The README's "Overriding a refusal" says an overridden `EXECUTE` runs SQL the rules never see, privilege statements included, so reviewers must read what it builds. "What the desired schema declares" keeps "No override marker gets past these refusals", qualified by a pointer to that sentence.

**Key interfaces:**
- `privilegeRefusal(statement)`: reused on the embedded statements.
- `plpgsqlFindings` / `sqlBodyFindings`: where embedded SQL is already parsed.
- The rule id stays `unsupported-object`.

**Acceptance criteria:**
- [ ] A desired-schema PL/pgSQL function containing `grant select on notes to public` is refused at `draft` with the `GRANT` refusal on the body's line (unit seam).
- [ ] The same for `revoke`, `alter table ... disable row level security`, `create policy` and `alter ... owner to` in a body, and for a `LANGUAGE sql` string body containing `grant`.
- [ ] The reporter's pre-migration script with the statements written statically (no `EXECUTE`) is refused by `rehearse`.
- [ ] An override marker before such a function doesn't get the embedded `GRANT` past the refusal.
- [ ] The README states the dynamic-SQL caveat.

**Out of scope:**
- Checking the text of `EXECUTE` strings; dynamic SQL stays unchecked behind its override.
- Restricting where dynamic-SQL overrides are allowed (e.g. not in scripts); a separate decision if wanted.
- Other statement rules inside bodies, such as `SET ROLE` (190's message, and the same gap: `set role` in a body is accepted).
- Unqualified names in bodies (180).
