# 122: Adoption refuses in separate rounds (ownership, then CREATE, then unsupported objects), not with one list as the README says

**Status:** ready-for-human
**Category:** bug
**Severity:** low
**Area:** adopt
**Round:** 2

## What I did
Database `qa2_adopt_bad`, owned by the deploy role `qa2_adopt_baddeploy`, with a schema `app` holding many objects super-deploy refuses (enum, serial column, standalone sequence, unlogged, partitioned and inherited tables, a rule, a `SECURITY DEFINER` function, a virtual generated column, `pgcrypto` installed in `app`, ...). Two of them owned by someone else:

```sql
create table app.owned_by_other (id int primary key);
alter table app.owned_by_other owner to qa2_adopt_other;
create statistics app.people_stats on id, name from app.people;   -- as postgres
```

```sh
pnpm exec super-deploy init --adopt qa
```

Similarly, on `qa2_adopt_shop` (everything owned by `postgres`, and the deploy role without `CREATE` on the database).

## Expected
README, "Adopting an existing database": "If the database holds anything super-deploy doesn't support ..., nothing is written and every such object is listed: that includes a `SECURITY DEFINER` routine, objects owned by another role (see "Permissions"), and views ... that reference an external schema". So one refusal listing the two ownership problems together with the 17 unsupported objects (and, ideally, the missing `CREATE`).

## Actual
Round 1: only ownership:

```
Error: The deploy role on target qa doesn't own everything in the managed schema: statistics app.people_stats is owned by postgres, whose privileges the deploy role doesn't have (fix: ALTER STATISTICS app.people_stats OWNER TO qa2_adopt_baddeploy); table app.owned_by_other is owned by qa2_adopt_other, ... (fix: ALTER TABLE app.owned_by_other OWNER TO qa2_adopt_baddeploy)
```

After running both fixes, round 2 lists 19 unsupported objects, including `statistics object app.people_stats` (CREATE STATISTICS is not supported), which I had just been told to re-own and now have to drop.

On `qa2_adopt_shop`: round 1 is 14 ownership fixes; round 2 is `Cannot create the history schema on target qa: the deploy role qa2_adopt_deployer needs CREATE on database ...`; only round 3 adopts.

## Notes
Each round needs a DBA (superuser) to act, so separate rounds are costly on a real server. Either list everything at once, or have the README say the checks happen in this order.

### Triage, 2026-10-21

**Verification:** CONFIRMED on both reporter setups (`qa2t_adopt_bad`, `qa2t_adopt_shop`).
- `bad`: round 1 listed only `statistics app.people_stats` and `table app.owned_by_other` as not owned. After both were re-owned, round 2 listed 19 unsupported objects, including `statistics object app.people_stats`.
- `shop`: 14 ownership fixes in round 1. Round 2 was `Cannot create the history schema on target qa: ... needs CREATE on database`. Only round 3 adopted.

**Cause:** adoption's `readTarget` (`commands/adopt.ts`) runs its checks one after another, each throwing as soon as it fails:
1. `requireOwnership`;
2. `requireHistorySchemaCreatable`;
3. pg-delta, the rule analysis and the external-schema check (the first full list);
4. the reproduction check.

The spec (init, Q51) says: "A target that fails the ownership check is refused before anything is rehearsed or written, naming each object". So the round order is what the spec asked for. The README ("Adopting an existing database") instead says objects owned by another role are among "every such object" in the one list. Spec and README disagree.

**Feasibility:** reading the target doesn't need ownership. `status` read and printed the drift of every `shop` object while the deploy role had no USAGE on the schema. pg-delta's extract wasn't tried in that state.

## Brief (ready-for-human)

**Category:** bug
**Summary:** Adoption should report its refusals in as few rounds as possible, and the README and spec should describe what it actually does.

**Current behavior:**
Ownership, then CREATE on the database, then unsupported objects: each is a separate refusal, and each needs a DBA. An object can be listed for re-owning in round 1 and then refused as unsupported in round 2. The README promises one list.

**Desired behavior (once decided):**
- One refusal gives everything that can be known without writing: ownership, CREATE on the database, and the unsupported objects.
- An object that is both unsupported and not owned is listed once, as unsupported, so nobody re-owns something they then have to drop.
- The README and the spec describe the same thing.

**Key interfaces:**
- `readTarget` in the adoption command, plus `requireOwnership`, `objectsNotOwned`, `requireHistorySchemaCreatable` and `historySchemaNotCreatable`.
- `AdoptUnsupportedError` (or a new error carrying all three kinds of finding), and its CLI listing.
- The spec's `init` paragraph (Q51) and the README's "Adopting an existing database".

**Acceptance criteria (once decided):**
- [ ] Adopting the reporter's `bad` database (an object owned by another role, a superuser-owned `CREATE STATISTICS` and 17 other unsupported objects) refuses once, listing all of them, with `people_stats` listed once.
- [ ] Adopting the `shop` database (everything owned by `postgres`, no CREATE on the database) refuses once, with the ownership fixes and the CREATE grant together.
- [ ] After all the listed fixes, the next adoption succeeds.
- [ ] The README and spec match the behaviour.

**Out of scope:**
- Formatting the ownership list (121).
- The reproduction check (`not-reproduced`), which can only run once the static checks pass.

**Why not delegated:** it reverses a spec sentence (ownership before anything is rehearsed) and chooses how far to merge the rounds.
**Decision needed:**
- One refusal for everything static: ownership, CREATE on the database and unsupported objects. Objects that are also unsupported are dropped from the ownership list. The spec's "before anything is rehearsed" goes (recommended).
- Merge only the two cheap target checks, ownership and CREATE on the database, into one refusal, as `status` already shows them. The README says that refusal comes before the list of unsupported objects.
- Keep three rounds, and have the README describe the order.
