# 182: A hand-made `FORCE ROW LEVEL SECURITY` silently filters a deployment's scripts: backfills update nothing, deploy reports success

**Status:** resolved
**Category:** bug
**Severity:** high
**Area:** privs
**Round:** 2

## What I did
Setup as in 181: target `qa` (deploy role `qa2_privs_deploy`), table `app.orders`
with rows owned by other users, and a hand-made policy with RLS enabled:

```sql
create policy orders_owner on app.orders using (owner_name = current_user and total >= 0);
alter table app.orders enable row level security;
alter table app.orders force row level security;   -- by hand, as postgres
```

Target rows: `(1, owner_name 'qa2_privs_writer')`, `(3, owner_name 'nobody')`.

Then a migration that adds a column and backfills it, the README's example use of
`post-migration.sql`:

```sh
# desired schema: add `priority integer,` to orders
pnpm exec super-deploy draft --name priority
echo "update orders set priority = 1 where priority is null;" > data-model/draft/post-migration.sql
pnpm exec super-deploy finalize
pnpm exec super-deploy deploy --target qa
```

## Expected
The backfill updates every row, or the deployment fails loudly because RLS would
hide rows from it.

## Actual
```
Deployed 1 migration to qa: 00010-priority
```
```
select id, owner_name, priority from app.orders  (as postgres)
[{"id":"1","owner_name":"qa2_privs_writer","priority":null},{"id":"3","owner_name":"nobody","priority":null}]
```

The backfill matched no rows (the policy hides them all from the deploy role), and
nothing says so. Rehearsals can't catch it: they have no hand-made policies.

The same thing happened to a materialized view created in the next migration
(`create materialized view order_totals as select customer_id, sum(total) ... from
orders group by customer_id`): it was populated as the deploy role and deployed
empty (`select * from app.order_totals` -> 0 rows).

## Notes
- README "Permissions" says policies and RLS are set up by hand and "deployments
  leave them alone", and warns only about a column type change failing. `FORCE ROW
  LEVEL SECURITY` isn't mentioned; with it the deploy role's own scripts are subject
  to the policies.
- Suggestion (guess): super-deploy pins session settings already; pinning
  `row_security = off` in deployments would make any statement that RLS would
  filter fail with an error instead of silently skipping rows (this is what
  `pg_dump` does). Failing that, `deploy`/`status` could warn when a managed table
  has `relforcerowsecurity`, and the README should say so.

### Triage, 2026-10-21

**Verification:** CONFIRMED. On target `qa` (deploy role owns `app.orders`), a hand-made policy `owner_name = current_user` with `ENABLE` and `FORCE ROW LEVEL SECURITY`. A migration adding `priority integer` with the post-migration backfill `update orders set priority = 1 where priority is null` printed `Deployed 1 migration to qa: 00002-priority`; both rows kept `priority = null`. As the deploy role, the same `UPDATE` after `SET LOCAL row_security = off` fails with `query would be affected by row-level security policy for table "orders"`.

**Root cause:** the pinned session settings (`rehearsal/throwaway.ts:83-91`, used by the deploy transaction at `deploy/engine.ts:192`) leave `row_security` at its default, `on`. With `FORCE`, the owner is subject to the table's policies, so a script's `UPDATE`, `DELETE` or `INSERT ... SELECT`, and a materialized view built in the deployment, silently see only the rows the policies allow the deploy role.

**Intended?** No. ADR-0006 says hand-made policies are left alone, not that they may change what a deployment's scripts do. `pg_dump` sets `row_security = off` for the same reason: anything a policy would filter fails instead of being silently partial.

## Agent Brief

**Category:** bug
**Summary:** Deployments pin `row_security = off`, so a script or materialized view that a hand-made policy would filter fails the deployment instead of silently skipping rows.

**Current behavior:**
On a target where a DBA set `FORCE ROW LEVEL SECURITY` on a managed table, a deployment's pre-/post-migration scripts and any materialized view it builds see only the rows the policies allow the deploy role. A backfill updates nothing, a materialized view is created empty, and `deploy` reports success. Rehearsals can't notice: they have no policies.

**Desired behavior:**
- The session settings pinned for every rehearsal and deployment include `row_security = off`. On tables without `FORCE`, where the owner already bypasses policies, nothing changes.
- On a target with a forced policy, a deployment whose files read or write that table fails with PostgreSQL's `query would be affected by row-level security policy for table "<t>"`, rolls back, and says so like any failed file.
- That failure's message adds a next step: the table has `FORCE ROW LEVEL SECURITY` on the target; turn it off (`ALTER TABLE ... NO FORCE ROW LEVEL SECURITY`) while deploying, or move the work out of the migration.
- The README's "Two things to know about grants and policies made by hand" gains this point.
- `deploy-draft` behaves the same, since it uses the same pinned settings.

**Key interfaces:**
- `pinnedSettings(managedSchema)`: the list of `SET LOCAL` statements shared by rehearsals and deployments.
- `SqlFileFailedError` and its SQLSTATE-based next step (42501 with this message).

**Acceptance criteria:**
- [ ] With a forced policy hiding rows from the deploy role, a migration whose post-migration script updates that table fails, and the target is unchanged (no history row, the column not added). API seam, non-superuser deploy role.
- [ ] The same for a migration creating a materialized view over that table.
- [ ] The error names the table and suggests `NO FORCE ROW LEVEL SECURITY` while deploying.
- [ ] With the policy enabled but not forced, the same migration deploys and the backfill updates every row.
- [ ] Rehearsals and the existing pinned-settings tests still pass.
- [ ] The README documents the behaviour.

**Out of scope:**
- Detecting forced tables in pre-flight or `status` (a deployment that doesn't touch them is fine).
- Views reading tables with policies (181).
- Anything that turns RLS on or off for the user (ADR-0006).
