# 27: Removing an adopted grant made by the schema's admin "deploys" successfully, but the role keeps access

**Status:** wontfix
**Category:** bug
**Severity:** high
**Merged:** 33, 62
**Area:** adopt

## What I did
The README's Permissions section allows an administrator to own the managed schema while the deploy role gets `usage, create ... with grant option`. Here, the administrator had already granted `USAGE` to an app role before adoption:

```sql
-- as postgres
create role adopt_admin nologin;  grant adopt_admin to postgres;
create role adopt_deployer login password 'deploy';
create role adopt_app_reader login password 'reader';
create database qa_adopt_revoke;
grant connect, create on database qa_adopt_revoke to adopt_deployer, adopt_admin;
grant connect on database qa_adopt_revoke to adopt_app_reader;
-- in qa_adopt_revoke
set role adopt_admin;
create schema app;
grant usage, create on schema app to adopt_deployer with grant option;
grant usage on schema app to adopt_app_reader;
reset role;
set role adopt_deployer;
create table app.t (id bigint generated always as identity primary key);
grant select on app.t to adopt_app_reader;
```

Project with `managedSchema: "app"`, target `revoke` from `REVOKE_DATABASE_URL=postgres://adopt_deployer:deploy@localhost:54818/qa_adopt_revoke`:

```sh
pnpm exec super-deploy init --adopt revoke
# desired-schema/grants.sql now has: GRANT USAGE ON SCHEMA "app" TO "adopt_app_reader";
git add -A && git commit -m adopt
# take the reader's access away, as the README says ("to take a grant away, remove the GRANT"):
sed -i '/ON SCHEMA "app" TO "adopt_app_reader"/d' data-model/desired-schema/grants.sql
pnpm exec super-deploy draft --name "revoke reader usage"     # REVOKE ALL ON SCHEMA "app" FROM "adopt_app_reader";
pnpm exec super-deploy finalize
pnpm exec super-deploy deploy --target revoke
pnpm exec super-deploy status --target revoke
```

## Expected
Either the reader loses `USAGE` on `app`, or `deploy` fails and rolls back, saying the deploy role can't revoke a grant made by `adopt_admin` (as the README describes for `rebuild`).

## Actual
```
Deployed 1 migration to revoke: 00002-revoke-reader-usage
```
Exit 0. The `REVOKE` only revoked grants made by the deploy role, so PostgreSQL silently did nothing. Straight after:

```
Drift (the target differs from its recorded migrations):
  changed: schema app
    - acl: schema app {<owner>:CREATE/<owner>,<owner>:USAGE/<owner>,adopt_app_reader:USAGE/<owner>}
    + acl: schema app {<owner>:CREATE/<owner>,<owner>:USAGE/<owner>}
Error: Target revoke has drifted from its recorded migrations: schema app (changed). ...
```

and `adopt_app_reader` can still `select count(*) from app.t`. Reproduced twice (`qa_adopt_owned` and `qa_adopt_revoke`).

## Notes
- This is a security problem: the history says access was revoked, and a user reading "Deployed" would believe it, but access remains. Deploy should verify the result before committing, or check up front that every revoke it plans is one the deploy role can perform.
- Adoption could also warn when it puts grants into the desired schema whose grantor isn't the deploy role, since they can never be removed through super-deploy.

### Triage, 2026-10-20

**Verification:** CONFIRMED, along with 33 and 62.

- **27.** Reproduced at the API seam with the reporter's setup: an admin owns `app`, the deploy role has `usage, create ... with grant option`, and the admin granted USAGE to the reader. Removing the grant drafted `REVOKE ALL ON SCHEMA "app" FROM "reader"`. `deploy` succeeded. Straight afterwards `status` showed drift, `has_schema_privilege(reader, 'app', 'USAGE')` was still true, and `nspacl` held `reader=U/admin`. PostgreSQL only revokes grants the current role made, so the REVOKE did nothing.
- **33.** Confirmed. A `pg_default_acl` entry for the deploy role in the managed schema left `status` clean and preflight with no warnings. The deploy of a new table succeeded, and drift appeared only afterwards.
- **62.** Confirmed in the pseudo-terminal. `rebuild` on a disposable target with the same kind of default privilege printed `Rebuilt` and exited 0. `status` then exited 1, because every table had the extra grant.

**Root cause:** nothing compares the target with the rehearsed result before COMMIT.
- `deploy` rehearses on a replica (drift check, replay, snapshot comparison), closes the replica, then runs BEGIN, the files, the history INSERT and COMMIT. It never reads the target again.
- The rehearsal can't catch these cases, because on the replica the rehearsal login owns everything, so its REVOKE works and no default privileges apply.
- `rebuild` already checks the grants it couldn't revoke after its wipe (`WipeFailedError`). Deploy has nothing equivalent.
- Neither `status` nor the preflight checks read `pg_default_acl`.

**Also found:**
- Drift writes every grantor as `<owner>`, so the drift line after 27 doesn't say that the grant was the admin's.
- Adoption writes grants made by another grantor into the desired schema without a word. super-deploy can never revoke those.
- Global default privileges (`defaclnamespace = 0`) cause the same problem. The README's warning only mentions "in the managed schema".

## Brief (ready-for-human)

**Category:** bug

**Summary:** A deployment (or rebuild) must not commit when the target's resulting structure differs from what the rehearsal produced. Today a no-op REVOKE, or grants added by default privileges, commit as success and leave the target drifted. For a REVOKE this means access the history says was removed is still there.

**Current behavior:**
- `deploy` reports `Deployed N migrations` when a REVOKE in the schema change silently did nothing, because the grant was made by another grantor. The next `status` shows drift, and every later deploy refuses until someone fixes the target by hand.
- `deploy` and `rebuild` also commit when `pg_default_acl` entries for the deploy role add grants to the objects they create (33, 62). `status` and the preflight checks don't mention default privileges before the deploy.

**Desired behavior:**
- A deployment, and `rebuild`'s replay, either leaves the target exactly matching the rehearsed replica or rolls back. The rollback names the differences and their likely cause:
  - "REVOKE ... had no effect: the grant was made by <grantor>; ask them to revoke it"
  - "default privileges for <deploy role> in <schema> added grants; remove them"
- `status` and the deploy pre-flight checks report default privileges set for the deploy role, in the managed schema or globally, before anything is applied.
- Drift output names the grantor when it isn't the object's owner, so a grant made by an admin can be recognised.

**Key interfaces:**
- `deploy`, `rebuild` (and `deploy-draft`, which replays the same way): the deploy transaction gains a verification step before COMMIT.
- The shared catalog comparison (`catalogFacts` / `driftBetween`): reused for the in-transaction comparison. The ACL facts' grantor rendering needs to change.
- Pre-flight findings (`status`'s "Deploy would refuse" / warnings): a new finding for `pg_default_acl` entries whose role is the deploy role.

**Acceptance criteria:**
- [ ] With an admin-made grant removed from the desired schema, `deploy` fails, rolls back (no history row, the grant still in place), and the error names the grant and its grantor. Test at the API seam with a non-superuser deploy role connected through `postgresTarget`.
- [ ] With `alter default privileges for role <deploy role> in schema <managed> grant select on tables to <r>`, `status` reports the default privilege, and `deploy` of a new table refuses or rolls back. The target is unchanged in either case.
- [ ] The same default privilege makes `rebuild` refuse before YES, or roll back, without wiping anything.
- [ ] A global default privilege (`defaclnamespace = 0`) is caught the same way.
- [ ] A normal deploy and a normal rebuild still succeed with no extra output.

**Out of scope:**
- Managing default privileges (REFINEMENTS "Roles, grants and ownership" keeps them out of scope).
- Ownership checks: see 28.
- Adoption's own handling of default privileges: see 26.

**Why not delegated:** choosing where verification happens changes the deploy engine's transaction (ADR-0001) and its cost: the replica stays alive through the apply, plus one more catalog read inside the transaction.

**Decision needed:**
1. **(Recommended)** An in-transaction drift check. Keep the post-pending replica open, and run the drift comparison between the target session and the replica inside the deploy transaction before COMMIT, rolling back on any difference. One change covers 27, 33, 62 and any future silent no-op. Add the `pg_default_acl` preflight finding as well, for a clear message before anything runs.
2. Targeted checks only:
   - a preflight that finds pending REVOKEs whose existing grants have another grantor;
   - a `pg_default_acl` finding that refuses and names the entries.

   This is cheaper, but each new silent-no-op case needs its own check.
3. A `pg_default_acl` finding only (fixes 33 and 62, not 27).

Also decide whether adoption should warn about, or refuse, adopted grants whose grantor isn't the deploy role, since super-deploy can never revoke them.

### Closed, 2026-10-20

Out of scope, with 33 and 62. ADR-0006 puts privileges, ownership and row-level security outside the system in V1 (`.scratch/super-deploy/issues/28-privileges-out-of-scope.md`). The desired schema can no longer declare a `REVOKE`, nothing compares ACLs, and `rebuild` no longer touches grants. So an admin-made grant stays as it is, and default privileges no longer drift a target.
