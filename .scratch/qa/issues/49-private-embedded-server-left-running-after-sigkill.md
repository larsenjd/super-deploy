# 49: After the CLI is SIGKILLed, the project's private PostgreSQL keeps running indefinitely

**Status:** wontfix
**Category:** bug
**Severity:** low
**Duplicate of:** 14
**Area:** fail

## What I did
In a project with a draft:
```sh
node node_modules/super-deploy/dist/cli.js rehearse & NP=$!
sleep 0.4; kill -KILL $NP       # e.g. an OOM kill or a CI job killed hard
ps -eo pid,ppid,args | grep .super-deploy/postgres
pnpm exec super-deploy rehearse
ps -eo pid,ppid,args | grep .super-deploy/postgres
```
(Reproduced twice, also with `deploy --target sigint`.)

## Expected
The next command that needs the server notices the leftover one (from `postmaster.pid`), uses it, and stops it when done. Or the README says how to stop it.

## Actual
```
after kill:
 528208       1 .../postgres -D /tmp/sd-qa/fail/proj/.super-deploy/postgres/ -p 43583 ...
Rehearsed draft labels after 8 migrations: matches the desired schema
after next command:
 528208       1 .../postgres -D /tmp/sd-qa/fail/proj/.super-deploy/postgres/ -p 43583 ...
```
Later commands reuse the orphan (good: no "port in use" or "postmaster.pid exists" failure) but never stop it, so it keeps running until reboot. The README only says the server "starts on a free port whenever a command needs it". It doesn't say it normally stops again, or how to stop it by hand. I stopped it with `<embedded-postgres bin>/pg_ctl -D .super-deploy/postgres stop`, a path a user would have to dig out of `node_modules/.pnpm`.

## Notes
SIGKILL can't be handled, so the orphan itself is expected. The problem is that nothing ever cleans it up afterwards.
