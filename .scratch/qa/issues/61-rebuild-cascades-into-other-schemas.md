# 61: rebuild silently drops views, foreign keys and columns in other schemas

**Status:** resolved
**Category:** bug
**Severity:** high
**Merged:** 63
**Area:** disp

## What I did
Project with migrations 1-5 (managed schema `public`, table
`public.customers(id bigint identity pk, name text not null)` among others).
Target `sb2` = `postgresTarget({ env: "SB2_URL" })`, deploy role `disp_deploy`
(owner of database `qa_disp_sb2`, not a superuser), flagged with
`disposable --target sb2 --set yes`, migrations 1-5 deployed.

As the deploy role, in a schema super-deploy doesn't manage:

```sql
set role disp_deploy;
create schema reporting;
create view reporting.customer_names as select name from public.customers;
create table reporting.orders_archive(
  id int primary key,
  customer_id bigint constraint archive_customer_fk references public.customers(id));
create table reporting.snap(id int, c public.customers);
insert into reporting.snap values (1, row(1,'kept?')::public.customers);
```

Then `pnpm exec super-deploy rebuild --target sb2 --to 5` at a terminal, typing
`YES`.

## Expected
The confirmation says what will go, and only that goes:

```
│  Drops everything in schema public, the recorded migrations, deployed draft labels2, then deploys in one
│  transaction:
```

So `reporting` should be untouched, or rebuild should refuse (or at least list)
objects outside `public` that depend on the managed schema, the way it refuses
admin-made grants.

## Actual
```
Rebuilt sb2 with 5 migrations: 00001-add-customers, 00002-add-orders, ...
```

Afterwards in `reporting`:
- view `customer_names` is gone;
- foreign key `archive_customer_fk` on `orders_archive` is gone;
- column `snap.c` is gone (`pg_attribute` shows `........pg.dropped.1........`),
  with its data; only `snap.id` remains.

```sql
select relname from pg_class where relnamespace='reporting'::regnamespace and relkind in ('r','v');
-- orders_archive, snap
select conname from pg_constraint where connamespace='reporting'::regnamespace and contype='f';
-- (none)
select * from reporting.snap;
-- [{"id":1}]
```

Reproduced twice (first time with a schema `keep`).

## Notes
Guess: the wipe uses `DROP ... CASCADE`. A disposable target is declared safe
to wipe, but the prompt scopes the wipe to `public`, and other schemas on the
same database (e.g. `externalSchemas`, reporting schemas owned by someone else)
are exactly what a user would expect to survive. Nothing is listed or warned.

### Triage, 2026-10-20

**Verification:** CONFIRMED in the pseudo-terminal, along with 63.

**61:**
- Setup: a disposable target at migration 1 with `public.customers`. Schema `reporting` held view `customer_names`, a foreign key `archive_customer_fk` on `orders_archive`, and `snap(id int, c public.customers)` with one row.
- `rebuild --to 1`, with YES typed, printed `Rebuilt dev with 1 migration` and exited 0.
- Afterwards the view, the foreign key and column `snap.c` (with its data) were gone.
- The prompt said only "Drops everything in schema public, the recorded migrations, then deploys ...".

**63:**
- An extension installed into `public` by a superuser got no mention in the prompt.
- After YES the output was `Error: must be owner of extension pgcrypto`, exit 1, with the attempt recorded as `rebuild failed`.
- The transaction rolled back, but the message didn't say so.

**Root cause:**
- The wipe issues one `DROP ... IF EXISTS ... CASCADE` per object in the managed schema.
- Its header says the cascade into other schemas is deliberate ("objects elsewhere that depend on it go too, as with DROP SCHEMA ... CASCADE").
- Its post-check only looks for things that depend on the schema itself.
- ADR-0005, ticket 19, spec story 80 and the confirmation all describe the wipe as the managed schema only. So the code's intent contradicts what the user is told.
- Nothing checks before YES what the deploy role cannot drop (63).

## Brief (ready-for-human)

**Category:** bug

**Summary:** `rebuild` must not drop or alter objects outside the managed and history schemas without saying so before YES. It must not fail after YES on objects it could have known it can't drop.

**Current behavior:**
- The wipe cascades into other schemas. Views, foreign keys and composite-typed columns (with their data) that depend on managed objects are dropped silently, even though the confirmation scopes the wipe to the managed schema.
- Objects in the managed schema that the deploy role can't drop (for example an extension owned by a superuser) are found only after YES, with a bare PostgreSQL error and no "nothing changed".

**Desired behavior:**
- Before asking YES, `rebuild` finds:
  - objects outside the managed and history schemas that depend on objects in the managed schema (`pg_depend`);
  - objects in the managed schema the deploy role can't drop (not owned by it or a role it belongs to).
- Objects it can't drop make it refuse before YES, naming each object, its owner, that nothing changed, and what to do (drop it, change its owner, or ask its owner).
- Dependents in other schemas are handled per the decision below.
- If a raw drop error still escapes after YES, the error says the rebuild was rolled back and the target is unchanged.

**Key interfaces:**
- `rebuild`'s guarded `check()` (runs before the YES question) and the wipe (`WipeFailedError` already names admin-made grants; extend the same style).
- The rebuild confirmation text.

**Acceptance criteria:**
- [ ] Pseudo-terminal test: a disposable target with a view, an FK and a composite-typed column in another schema depending on a managed table. `rebuild` either refuses before YES naming all three (option 1), or lists them in the confirmation (option 2). After it, nothing in the other schema has been dropped unless the user confirmed a list naming it.
- [ ] A superuser-owned extension in the managed schema makes `rebuild` refuse before YES, naming the extension and its owner. The target is unchanged and no failed rebuild attempt is recorded.
- [ ] A rebuild with no such objects behaves exactly as today.

**Out of scope:**
- What the `disposable` confirmation shows (68).
- Default privileges affecting the replay (27).

**Why not delegated:** it changes what a destructive guarded command is allowed to do, against the wipe's documented intent. Someone has to choose the policy.

**Decision needed:**
1. **(Recommended)** Refuse before YES when objects outside the managed and history schemas depend on managed objects, naming each one, and tell the user to drop them first or move the dependency. This matches how rebuild already refuses admin-made grants.
2. List those dependents in the confirmation box ("also drops: view reporting.customer_names, ...") and keep the cascade.
3. Keep the cascade, but correct the confirmation text and the docs to say objects elsewhere that depend on the managed schema go too.

Whichever is chosen, the pre-YES refusal for objects the deploy role can't drop (63) applies.

### Decided, 2026-10-21

The maintainer chose **option 2: list the dependents in the confirmation and keep the cascade.** The pre-YES refusal for objects the deploy role can't drop (63) applies as the brief above says. This supersedes the brief above.

## Brief (ready-for-agent)

**Category:** bug

**Summary:** Before asking YES, `rebuild` lists every object outside the managed and history schemas that its wipe will drop or alter, and refuses up front when the managed schema holds something the deploy role can't drop.

**Current behavior:**
- The wipe (`deploy/wipe.ts`) drops each managed object with `CASCADE`, so views, foreign keys and composite-typed columns (with their data) in other schemas that depend on managed objects go too. The confirmation (`commands/rebuild.ts`, `check`) says only "Drops everything in schema public, the recorded migrations ...".
- An object in the managed schema the deploy role can't drop (e.g. an extension a superuser installed) is found only after YES: `Error: must be owner of extension pgcrypto`, exit 1, with no word that the target is unchanged.

**Desired behavior:**
- In `rebuild`'s guarded `check()` (before YES), read `pg_depend` for objects outside the managed and history schemas that depend, directly or transitively, on objects in the managed schema.
- When there are any, the confirmation adds an "Also drops, outside schema <managed>:" block listing each one by kind and qualified name, e.g. `view reporting.customer_names`, `foreign key archive_customer_fk on reporting.orders_archive`, `column reporting.snap.c (with its data)`. Columns say "with its data". When there are none, the confirmation is exactly as today.
- The cascade stays: after YES those listed objects are dropped, and nothing else outside the managed and history schemas is.
- If the set of dependents differs between the question and the run (something was added or removed while the prompt waited), `rebuild` refuses with the existing target-changed refusal (`TargetChangedError`) and changes nothing.
- Objects in the managed schema the deploy role can't drop (not owned by it or a role it is a member of, as the ownership pre-flight in `deploy/ownership.ts` judges it) make `rebuild` refuse before YES, naming each object and its owner, saying nothing changed, and saying what to do (drop it, change its owner to the deploy role, or ask its owner). No attempt is recorded.
- If a drop error still escapes after YES, the error says the rebuild rolled back and the target is unchanged.
- ADR-0005, spec story 80 and the README's `rebuild` entry say that dependents in other schemas are dropped and listed in the confirmation first. The wipe's header comment says the same.

**Key interfaces:**
- `commands/rebuild.ts`: the guarded `check()` and its `details` (the confirmation box), and whatever `runGuarded` compares to detect a changed target.
- `deploy/wipe.ts`: the wipe and its post-check.
- `deploy/ownership.ts`: reuse its ownership judgement for the can't-drop refusal.

**Acceptance criteria:**
- [ ] Pseudo-terminal test: a disposable target at migration 1 with `public.customers`, and in schema `reporting` a view on it, a foreign key to it and a column of its row type holding data. The confirmation lists all three, the column marked "with its data". After YES the three are gone, and an unrelated table in `reporting` is untouched.
- [ ] Pseudo-terminal test: adding a dependent while the prompt waits makes `rebuild` refuse as target-changed after YES, with nothing dropped.
- [ ] A superuser-owned extension in the managed schema makes `rebuild` refuse before YES, naming the extension and its owner; the target is unchanged and no rebuild attempt is recorded.
- [ ] A rebuild with no dependents and nothing undroppable shows the same confirmation as today and behaves as today.
- [ ] ADR-0005, spec story 80, the README and the wipe's header are updated.

**Out of scope:**
- Refusing because of dependents (option 1, decided against).
- What the `disposable` confirmation shows (68).
