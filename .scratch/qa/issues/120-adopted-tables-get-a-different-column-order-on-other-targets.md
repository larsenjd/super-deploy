# 120: Tables adopted with domain-, composite- or function-default columns get a different column order on every other target

**Status:** wontfix
**Category:** bug
**Severity:** medium
**Duplicate of:** 101
**Area:** adopt
**Round:** 2

## What I did
Existing database, built as the superuser and then handed to the deploy role:

```sql
-- database qa2_adopt_shop
create schema shop;
set search_path = shop;
create domain email as text check (value ~ '^[^@]+@[^@]+$');
create domain positive_money as numeric(12,2) check (value >= 0);
create type address as (street text, city text, zip text);
create table customers (
  id bigint generated always as identity primary key,
  email email not null,
  name text not null,
  shipping address,
  created_at timestamptz not null default now(),
  constraint customers_email_key unique (email));
create function new_order_ref() returns text language sql volatile as $$ select 'ORD-' || substr(md5(random()::text), 1, 8) $$;
create table orders (
  id bigint generated always as identity primary key,
  ref text not null default new_order_ref(),
  customer_id bigint not null references customers(id),
  status text not null default 'new',
  total positive_money not null default 0,
  placed_at timestamptz not null default now());
-- (then ALTER ... OWNER TO the deploy role, GRANT CREATE ON DATABASE)
```

Project: `init`, `managedSchema: "shop"`, target `qa: { adapter: postgresTarget({ env: "QA_DATABASE_URL" }) }`.

```sh
pnpm exec super-deploy init --adopt qa
pnpm exec super-deploy deploy --target dev
```

Then compared column order on both (`information_schema.columns` ordered by `ordinal_position`).

## Expected
`dev` (and any target built from `00001-adopt`, including rehearsal databases) has the same columns in the same order as the adopted target. The generated `data-model/desired-schema/tables.sql` lists them in the target's order:

```sql
CREATE TABLE "shop"."customers" ("id" ..., "email" shop.email NOT NULL, "name" text NOT NULL, "shipping" shop.address, "created_at" ... );
```

## Actual
`00001-adopt/schema-change.sql` creates the tables without those columns and adds them afterwards with `ALTER TABLE ... ADD COLUMN`, so they end up last:

| table | adopted target `qa` | `dev`, built from 00001-adopt |
|---|---|---|
| customers | id,email,name,shipping,created_at | id,name,created_at,email,shipping |
| orders | id,ref,customer_id,status,total,placed_at | id,customer_id,status,placed_at,total,ref |
| products | id,sku,title,price,tax_rate,price_with_tax | id,sku,title,tax_rate,price,price_with_tax |

The same happens to a stored generated column of a domain type (`crm."Companies".slug`, moved after `order` and `tags`). `status` reports no drift on either target, so nothing tells the user.

## Notes
- Any `select *`, `INSERT ... VALUES` without a column list or `COPY` without a column list behaves differently on `dev` and in rehearsals than on the adopted QA/production database.
- The columns that move are those whose type (domain, composite) or default (a managed-schema function) is created in the same migration. Guess: the differ creates the table before the type/function and appends the dependent columns; it could create the types and functions first.
- The README's `mark` section says its comparison ignores column order; nothing says deployments or adoption may reorder columns.

### Triage, 2026-10-21

Closed as a duplicate of 101: same cause, and its adoption angle is folded into 101's brief.

**Verification:** CONFIRMED from the reporter's `shop` database (`qa2t_adopt_shop`). The adopted `tables.sql` keeps the target's column order. Adoption's fold from round-1 issue 20 does that. pg-delta then generates `00001-adopt/schema-change.sql` from that desired schema, and it creates `customers` without `email` and `shipping` and adds them later with `ALTER TABLE ... ADD COLUMN`. The same goes for `orders.ref`, `orders.total`, `products.price` and `products.price_with_tax`. So every target built from migration 1 has a different column order from the adopted one. The catalog comparison ignores column order by design, so no rehearsal, drift check or `mark` reports it.
