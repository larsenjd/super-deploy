## What I did
On a real target `qa` (at the newest migration), someone added an index by hand as the deploy role:
```sql
create index hand_idx on orders (note);
```
```sh
pnpm exec super-deploy status --target qa
pnpm exec super-deploy deploy --target qa
grep -n -i drift README.md
```

## Expected
The README has a section on drift: what it is (anything in the managed schema the recorded migrations don't create, or
differs), that `deploy` refuses a drifted target, and the ways out: undo the change by hand, or put it in the desired schema,
finalize a migration and `mark` it on that target. The error says what to do next.

## Actual
```
Error: Target qa has drifted from its recorded migrations: index public.hand_idx (only on the target). Deployments refuse until it matches them again (status --target qa lists the differences)
```
No next step. The README mentions drift only in passing (lines 271, 403, 699: lockTimeout applies to "its drift check", grants
"are not drift", `deploy-draft` targets aren't checked).

Only once a pending migration exists does the message point at `mark`:
```
... If its changes are those of the next pending migration applied by hand, mark --target qa records that migration as deployed
```
which worked well (I added `hand_idx` to the desired schema, finalized it, `mark --target qa`). But a user has to know to
write that migration first.

## Notes
`status` exits 1 on drift, as `--help` says.

## Agent Brief

**Category:** enhancement
**Summary:** The README explains drift and the ways back from it, and the drift refusal points there whether or not migrations are pending.

**Current behavior:**
A drifted target makes `deploy` refuse and `status` exit 1. With no pending migration, the message ends "Deployments refuse until it matches them again", with no next step. The README never explains drift.

**Desired behavior:**
- A README section "Drift", reachable from "When a deploy fails", says:
  - What drift is: any difference between the target's managed schema and a replica built from the migrations it recorded. Checked by `deploy` before it changes anything and shown by `status`, which exits 1 on it.
  - What is not compared: grants, default privileges, policies and row-level security (ADR-0006), ownership (checked separately by the pre-flight), and column order.
  - When drift isn't checked (a deployed draft; a history mismatch; the target locked), as `status` shows.
  - The ways back:
    - undo the hand-made change on the target;
    - or keep it: add it to the desired schema, `draft` and `finalize` a migration, then `mark --target X` records that migration on the drifted target without running it (other targets deploy it normally);
    - on a disposable target, `rebuild`.
- `DriftError`'s message, after "Deployments refuse until it matches them again", always points to the README's "Drift" section. With migrations pending, it keeps the `mark` hint. With none, it says to undo the change, or capture it in a new migration and `mark` it.
- The section's commands and wording match `--help` and the code.

**Key interfaces:**
- `DriftError`'s message (its `code`, `target` and `objects` unchanged).
- The template README.

**Acceptance criteria:**
- [ ] API seam: `deploy` on a drifted target with no pending migration throws a `DriftError` whose message mentions both undoing the change and capturing it in a migration with `mark`, and the README's "Drift" section.
- [ ] With a pending migration, the message still has round 1's `mark` hint (existing test passes).
- [ ] `status`'s error still doesn't tell the user to run `status` (48's criterion).
- [ ] The README section exists and is linked from "When a deploy fails". Following its "keep it" path on 149's drift (column, index, default, table by hand) ends with `mark` succeeding and `status` clean.

**Out of scope:**
- How drift lines are formatted (153 covers multi-line definitions).
- Detecting that drift is exactly the next pending migration (round 1, 48).
- `status` saying when no drift was found (113).
