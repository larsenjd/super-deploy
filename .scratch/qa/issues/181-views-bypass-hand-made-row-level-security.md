# 181: Views in the desired schema bypass hand-made row-level security; the README doesn't warn

**Status:** resolved
**Category:** enhancement
**Severity:** medium
**Area:** privs
**Round:** 2

## What I did
Setup as in 180 (managed schema `app` owned by deploy role `qa2_privs_deploy`,
README's default-privileges recipe for `qa2_privs_reader` (select) and
`qa2_privs_writer` (select/insert/update/delete)). Desired schema:

```sql
create table customers (id bigint generated always as identity primary key, email text not null);
create table orders (
  id bigint generated always as identity primary key,
  customer_id bigint not null,
  owner_name text not null,
  total numeric(10,2) not null,
  constraint orders_customer_fk foreign key (customer_id) references customers (id)
);
create view customer_orders as
  select c.email, o.id as order_id, o.total
  from customers c join orders o on o.customer_id = c.id;
```

`draft`, `finalize`, `deploy --target qa`. Then, by hand on the target as the
deploy role, the README's "policies set up outside super-deploy":

```sql
insert into app.customers(email) values ('a@x');
insert into app.orders(customer_id, owner_name, total) values (1, 'nobody', 99);
create policy orders_owner on app.orders using (owner_name = current_user and total >= 0);
alter table app.orders enable row level security;
```

As `qa2_privs_reader`:

```
select id, owner_name, total from app.orders;   -> SELECT 0   (policy applies)
select * from app.customer_orders;              -> [{"email":"a@x","order_id":"3","total":"99.00"}, ...]
```

## Expected
Either the README warns that a view runs with its owner's (the deploy role's)
rights, so it ignores row-level security on the tables it reads unless it has
`security_invoker`, or something flags views over RLS tables.

## Actual
Every row is visible through the view. The deploy role owns both the view and the
table, and RLS doesn't apply to a table's owner, so a view without
`security_invoker` silently exposes everything the policy hides.

## Notes
- README "What the desired schema declares" refuses `SECURITY DEFINER` because "the
  routine would run with the deploy role's rights for every role allowed to call
  it", but a plain view has the same effect and is the default.
- `with (security_invoker = true)` is supported by the desired schema, so the fix is
  a sentence in "Permissions" (next to "Two things to know about grants and policies
  made by hand"): use `security_invoker` on views over tables you put policies on.
- Materialized views are similar (and have no `security_invoker`): they're
  populated as their owner, so their rows ignore the caller's policies. Functions
  are fine: they run as the caller.

### Triage, 2026-10-21

**Verification:** CONFIRMED. On target `qa` (managed schema `app`, README's default-privileges recipe), a hand-made policy `owner_name = current_user` with RLS enabled on `app.orders`: the reader role got `SELECT 0` from `app.orders` and both rows from the view `app.customer_orders`.

**Root cause:** PostgreSQL's behaviour, not super-deploy's. A view without `security_invoker` reads its tables as the view's owner, the deploy role, and RLS doesn't apply to a table's owner unless the table has `FORCE ROW LEVEL SECURITY`. A materialized view is built and refreshed as its owner too, so it holds every row; policies can't be put on it.

**Intended?** ADR-0006 puts policies outside super-deploy, and the desired schema already supports `security_invoker`. Nothing is wrong in the code; the README's "Permissions" section (`packages/template/README.md:441-452`) just never says that policies need views written this way. This is a docs brief.

## Agent Brief

**Category:** enhancement
**Summary:** The README tells users that views over tables with hand-made policies need `security_invoker = true`, and that materialized views ignore those policies.

**Current behavior:**
"Permissions" says policies are set up by hand and lists two things to know about hand-made grants and policies (recreated objects lose them; column changes under a policy fail at deploy). It doesn't say that a plain view, owned by the deploy role, shows every row of a table whose policy hides them. `SECURITY DEFINER` is refused for this exact reason, so readers assume views are safe.

**Desired behavior:**
In "What each target needs set up outside super-deploy", next to the two existing points, a third:
- Every object belongs to the deploy role, and row-level security doesn't apply to a table's owner. A view reads its tables as its owner, so it shows every row unless it is created `with (security_invoker = true)`, which makes it read them as the caller. Declare views over tables that get policies that way (the desired schema supports the option).
- A materialized view is built and refreshed as the deploy role, so it holds every row whatever the policies on its tables; don't build one over rows a policy must hide.
- Optionally one line in "Supported" or "Rules for writing it" pointing to it.

**Key interfaces:**
- The template README's "Permissions" section only. The spec's target-setup paragraph ("Target setup that stays outside super-deploy") gets the same sentence.
