### Triage, 2026-10-20

**Verification:** CONFIRMED, together with merged issues 45 and 47.
- A NOT NULL failure on line 4 of a pre-migration script and a duplicate key on line 2 were both reported without a line. `--debug` shows no DETAIL either.
- With a read lock held on `customers` in another session, a deploy failed after 6 s with `.../schema-change.sql: PostgreSQL refused it: canceling statement due to lock timeout`.
- A deploy failing on real data printed only the `PostgreSQL refused it` line, with no "rolled back" and no next step. `recovery`'s own output doesn't say what to do next either.

Root cause: replay (`rehearsal/replay.ts`) sends each file as one simple-protocol batch, so runtime errors carry no position. `SqlFileFailedError` keeps only the message and drops `detail` and `hint`, and the same path serves every SQL error, whatever its SQLSTATE. Nothing on the deploy path says the transaction rolled back. The README parts of 45 (lockTimeout/statementTimeout) and 47 (the Recovery workflow) belong to issues 03 and 15.

## Agent Brief

**Category:** enhancement
**Summary:** When a deploy-time SQL file fails, the error gives the statement's line, PostgreSQL's DETAIL and HINT, whether the deploy rolled back, and a next step that fits the kind of failure.

**Current behavior:**
A failing pre-migration script, schema change or post-migration script, in a rehearsal or a deploy, is reported as `<file>: PostgreSQL refused it: <message>`. There is no line or statement, PostgreSQL's DETAIL (e.g. `Key (slug)=(a) already exists.`) and HINT are dropped, and nothing says the target is unchanged. A lock or statement timeout reads as if the SQL were wrong and doesn't name the setting that controls it. A data failure doesn't point to `recovery`, the only way forward for a finalized migration.

**Desired behavior:**
- **Line:** the error names the failing statement's file and line (`pre-migration.sql:4`), as the static rule checks already do. Achieve this by running each file's statements one at a time inside the same transaction, using the existing SQL splitter, rather than as one batch. All-or-nothing behaviour is unchanged.
- **DETAIL and HINT:** PostgreSQL's DETAIL and HINT, when present, are appended to the message.
- **Rolled back (deploy only):** the error says the deployment was rolled back and the target is unchanged at its last recorded migration (e.g. `rolled back: target script is still at migration 00003-add-email`).
- **Next step, by SQLSTATE:**
  - Lock timeout (`55P03`) or statement timeout (`57014`): say which timeout fired, name the target setting (`lockTimeout`, default 5s; `statementTimeout`, default none) and suggest retrying once whatever held the lock has finished. No Recovery suggestion.
  - Data errors (SQLSTATE classes `22` and `23`) during a deploy of a finalized migration: point to `super-deploy recovery --migration N`, with seed data to reproduce the problem rows in the rehearsal.
  - Anything else: no extra next step.
- **`recovery` output:** after creating a Recovery draft, `recovery` says what to do next in one line: fix the scripts, add seed data that reproduces the failure, rehearse, finalize, deploy.

**Key interfaces:**
- `SqlFileFailedError`: gains the statement line, `detail`, `hint`, the SQLSTATE, and (on deploy) the last recorded migration. Its one-line message includes them.
- The replay unit runner shared by rehearsals and deploys: per-statement execution within the existing transaction.
- The `recovery` command's CLI output.

**Acceptance criteria:**
- [ ] A pre-migration script whose fourth line violates NOT NULL fails a rehearsal with an error naming `pre-migration.sql:4` and including PostgreSQL's DETAIL (API seam).
- [ ] A post-migration unique violation on deploy includes `Key (...)=(...) already exists.`, says the deploy rolled back and names the migration the target is still at, and suggests `recovery --migration N`.
- [ ] A deploy failing on lock timeout (hold ACCESS SHARE through `testSession`, with `lockTimeout: "200ms"`) names `lockTimeout`, suggests retrying, and doesn't suggest a Recovery.
- [ ] A statement timeout names `statementTimeout`.
- [ ] Existing deploy, rehearsal and Recovery tests still pass: per-statement execution doesn't change outcomes or transaction boundaries.
- [ ] `recovery`'s CLI output includes the next-step line.

**Out of scope:**
- Naming the blocking session (`pg_blocking_pids`) on a lock timeout; nice to have, not required.
- README sections on timeouts (issue 03) and the Recovery workflow (issue 15).
