# Transactional hazards for single-transaction deploys (PostgreSQL 18)

Scope: every pending migration (generated DDL plus pre/post scripts) runs inside one `BEGIN ... COMMIT`. A libpg_query (branch `18-latest`) AST walker enforces an allowlist. This file catalogues what breaks, what escapes the transaction, and what is non-deterministic in that setting.

Rule legend: **BAN** = reject at parse time. **COND** = allow only under the stated condition (some conditions need a catalog lookup, not just the AST). **ALLOW** = fine, maybe lint/warn.

AST names are PG18 `parsenodes.h`/`primnodes.h` node and field names, which libpg_query's JSON/protobuf output mirrors (e.g. `{"IndexStmt":{"concurrent":true}}`). Enum values appear as strings (`"AT_DetachPartition"`).

Citations use short keys `[K]` (resolved in **References**) plus the section name. Where the docs say nothing, the PG18 source file (REL_18_STABLE) is cited.

---

## 0. Key takeaways

1. **No `CONCURRENTLY`-style operations at all.** Every online/low-lock variant (CIC, REINDEX CONCURRENTLY, DROP INDEX CONCURRENTLY, DETACH CONCURRENTLY) is rejected inside a transaction block. A one-transaction tool therefore cannot do zero-downtime index builds on existing large tables. Either support a separate non-transactional phase or accept the locks.
2. **The "NOT VALID then VALIDATE" pattern buys nothing inside one transaction.** The `ACCESS EXCLUSIVE` lock from `ADD CONSTRAINT ... NOT VALID` is held until COMMIT anyway. This also applies to PG18's new NOT NULL `NOT VALID`. Every lock taken by any migration is held until the final COMMIT, so lock *duration* is the length of the whole deploy.
3. **Enum `ADD VALUE` values can't be used until commit**, unless the enum type was created in the same *top-level* transaction. That exception disappears if the tool wraps migrations in SAVEPOINTs (source: `pg_enum.c`).
4. **Things that escape rollback:** `nextval`/`setval`, session advisory locks, session `SET`/`set_config(...,false)`, dblink/postgres_fdw remote writes, `COPY ... TO file/PROGRAM`, `COPY FROM PROGRAM` side effects, `lo_export`, signal/admin functions, replication slot creation, `LOAD`, prepared statements, and WITH HOLD cursors/temp tables/LISTEN after commit.
5. **Transaction control inside the script is catastrophic.** A `COMMIT`/`ROLLBACK`/`END`/`ABORT` in a script ends the deploy transaction, and everything after it runs in autocommit. `BEGIN` only produces a WARNING. `CALL` of a procedure that commits fails with `invalid transaction termination`.
6. **Deferred constraints move failures to COMMIT.** Pending deferred trigger events also make later `ALTER TABLE`/`TRUNCATE`/`DROP TABLE`/`CREATE INDEX` on the same table fail with `cannot ALTER TABLE "t" because it has pending trigger events`.
7. **Physical column order differs between a fresh rehearsal database and a long-lived target** (ADD COLUMN appends, dropped columns keep their attnum). Every column-order-dependent construct is therefore a rehearsal/target divergence risk.

## 1. Statements that cannot run inside a transaction block (PG18)

Mechanism: `PreventInTransactionBlock()` (`xact.c`). It raises an error in three cases. In an explicit block the error is `"%s cannot run inside a transaction block"`. Inside a SAVEPOINT it is `"... cannot run inside a subtransaction"`. Inside any function, procedure or DO block (`EXECUTE` included) it is `"... cannot be executed from a function"` (SQLSTATE 25001). A multi-statement simple-Query message is also an implicit transaction block, so this applies there too. [S-xact]

The list below is exhaustive for PG18 SQL. It was taken from every `PreventInTransactionBlock` call site in REL_18_STABLE: `utility.c`, `dbcommands.c`, `discard.c`, `indexcmds.c`, `subscriptioncmds.c`, `vacuum.c`, `cluster.c`, plus `walsender.c` for replication-protocol commands. ## 2. Effects that escape the transaction (not rolled back, or that outlive it)

## 4. Transaction control inside scripts and routines

| # | Construct | Behaviour inside the deploy transaction | Citation | AST detection | Rule |
|---|---|---|---|---|---|
| 4.1 | `BEGIN` / `START TRANSACTION` in a script | "Issuing BEGIN when already inside a transaction block will provoke a warning message. | 4.3 | `ROLLBACK` / `ABORT` in a script | Rolls back *all* prior migrations, then continues in autocommit | [D-rollback] | `TRANS_STMT_ROLLBACK` | BAN (hard) |

## 5. Lock / long-transaction hazards from holding everything in one transaction

Core fact: locks are never released before COMMIT. Each lock's hold time is from acquisition until the end of the *entire* deploy, and waiting `ACCESS EXCLUSIVE` requests queue ahead of later readers. "So long as no deadlock situation is detected, a transaction seeking either a table-level or row-level lock will wait indefinitely" [D-explicitlocking] §13.3.

| # | Hazard | Detail | Citation | AST detection | Rule |
|---|---|---|---|---|---|
| 5.1 | ACCESS EXCLUSIVE statements on pre-existing tables | `DROP TABLE`, `TRUNCATE`, `REINDEX`, `CLUSTER`, `VACUUM FULL`, `REFRESH MATERIALIZED VIEW` (non-concurrent), `LOCK TABLE` (default mode), and "many forms of ALTER INDEX and ALTER TABLE" (the ALTER TABLE default: "An ACCESS EXCLUSIVE lock is acquired unless explicitly noted") | [D-explicitlocking] §13.3.1; [D-altertable] §Description | `DropStmt`, `TruncateStmt`, `ReindexStmt`, `RefreshMatViewStmt.concurrent=false`, `LockStmt.mode`, `AlterTableStmt` | COND: allowed. The tool sets `lock_timeout` (5.7), orders heavy-lock statements as late as possible, and reports lock footprint per deploy. |
| 5.2 | Lighter locks that still block writers for the whole deploy | `CREATE INDEX` (SHARE: blocks writes, and CONCURRENTLY is impossible here). `ADD FOREIGN KEY` and `CREATE TRIGGER` (SHARE ROW EXCLUSIVE on **both** the table and the referenced table). `ATTACH PARTITION` (SHARE UPDATE EXCLUSIVE on parent plus ACCESS EXCLUSIVE on the partition and the default partition). `DETACH PARTITION` (SHARE on FK-referencing tables). | [D-createindex] §Description; [D-altertable] §Description; [D-explicitlocking] §13.3.1 | `IndexStmt.concurrent=false`; `Constraint.contype=CONSTR_FOREIGN`; `CreateTrigStmt`; `AT_AttachPartition`/`AT_DetachPartition` | COND (as 5.1). | 5.3 | Table rewrites (ACCESS EXCLUSIVE plus full copy of table and indexes) | ADD COLUMN with **volatile** DEFAULT (e.g. `clock_timestamp()`, `random()`, `gen_random_uuid()`, `uuidv7()`, `nextval`), a **stored** generated column, an **identity** column, or a constrained-domain type. `ALTER COLUMN TYPE` (unless binary-coercible / unconstrained domain and USING doesn't change data). `SET EXPRESSION` on a stored generated column. `SET ACCESS METHOD`. `SET TABLESPACE` (copies files). `SET LOGGED/UNLOGGED` (rewrite per `tablecmds.c`; the docs don't say so explicitly). `CLUSTER`, `VACUUM FULL`. | 5.12 | `max_locks_per_transaction` exhaustion | The shared lock table has space for `max_locks_per_transaction` objects "per server process or prepared transaction" (default 64; restart to change). | 5.13 | Hot standby replay conflicts | ACCESS EXCLUSIVE locks are WAL-logged and replayed on standbys, which cancels or blocks standby queries (`max_standby_streaming_delay`). ## 7. Column-order dependence

Root cause: `ALTER TABLE ADD COLUMN` always appends. Dropped columns keep their attnum (hidden). PostgreSQL cannot reorder columns without a rebuild. A database built fresh from the declarative schema (rehearsal) can therefore have a different physical order than a long-lived target built by incremental migrations. Every construct below can behave differently, or error, between the two.

| # | Construct | Why order-dependent | Citation | AST detection | Rule |
|---|---|---|---|---|---|
| 7.1 | `INSERT INTO t VALUES (...)` / `INSERT INTO t SELECT ...` without a column list | "the default is all the columns of the table in their declared order ... associated ... left-to-right" | [D-insert] §Parameters column_name | `InsertStmt.cols` empty | BAN (require a column list) |
| 7.2 | `INSERT INTO t2 SELECT * FROM t1` (table-rebuild idiom; `OVERRIDING USER VALUE` variant) | Both sides positional | [D-insert] §OVERRIDING | `InsertStmt` + `ColumnRef` with `A_Star` | BAN |
| 7.3 | `MERGE ... WHEN NOT MATCHED THEN INSERT VALUES (...)` without columns | Positional insert | [D-merge] | `MergeWhenClause.targetList` empty with `values` | BAN |
| 7.4 | `SELECT *` / `t.*` in views and materialized views | "*" is expanded at creation: "columns added later to the table will not be part of the view". `CREATE OR REPLACE VIEW` must keep "the same column names in the same order" (may only append). | [D-createview] §Description, §Examples | `ViewStmt.query` / `CreateTableAsStmt` (objtype MATVIEW) containing `ColumnRef{fields:[...,A_Star]}` | BAN |

## 9. Suggested allowlist skeleton (top-level statement nodes)

- **ALLOW, with per-node checks above:** `CreateStmt`, `AlterTableStmt` (subtype filter), `IndexStmt` (`concurrent=false`), `DropStmt` (`concurrent=false`), `RenameStmt`, `AlterObjectSchemaStmt`, `CreateEnumStmt`, `AlterEnumStmt` (3.1), `CreateDomainStmt`, `AlterDomainStmt`, `CompositeTypeStmt`, `CreateRangeStmt`, `ViewStmt` (no `*`), `CreateTableAsStmt` (matview, no `*`), `RefreshMatViewStmt`, `CreateSeqStmt`, `AlterSeqStmt`, `CreateFunctionStmt` (language allowlist; body scan), `AlterFunctionStmt`, `CreateTrigStmt`, `CreatePolicyStmt`/`AlterPolicyStmt`, `CreateStatsStmt`, `CommentStmt`, `GrantStmt`, `AlterOwnerStmt`, `CreateSchemaStmt`, `CreateExtensionStmt` (allowlist + VERSION), `AlterExtensionStmt`, `InsertStmt`/`UpdateStmt`/`DeleteStmt`/`MergeStmt`/`SelectStmt` (scripts only; §6/§7 lints; function-call denylist), `VariableSetStmt` (`is_local=true` + GUC allowlist), `ConstraintsSetStmt`, `LockStmt`, `VacuumStmt` with `is_vacuumcmd=false` (ANALYZE).
- **COND:** `CallStmt`, `DoStmt` (body analysis), `NotifyStmt`, `TruncateStmt`, `CopyStmt` (STDIN only, explicit columns).
- **BAN:** everything in §1, `TransactionStmt` (all kinds), `ListenStmt`/`UnlistenStmt`, `DeclareCursorStmt`/`FetchStmt`/`ClosePortalStmt`, `PrepareStmt`/`ExecuteStmt`/`DeallocateStmt`, `LoadStmt`, `CheckPointStmt`, `DiscardStmt`, `ReindexStmt`, `ClusterStmt`, `AlterSystemStmt`, database/tablespace/subscription statements, `CreateEventTrigStmt` (or COND), role statements (policy), `VariableShowStmt` (harmless; allow if desired), `ExplainStmt` with `ANALYZE` (executes the statement).
- **Function-call denylist (any `FuncCall`, schema-qualified or not):** `setval` (COND), `pg_advisory_lock*`/`pg_try_advisory_lock*`/`pg_advisory_unlock*`, `dblink*`, `lo_import`, `lo_export`, `lo_*` writes, `pg_terminate_backend`, `pg_cancel_backend`, `pg_reload_conf`, `pg_rotate_logfile`, `pg_switch_wal`, `pg_create_restore_point`, `pg_promote`, `pg_wal_replay_*`, `pg_backup_*`, `pg_stat_reset*`, `pg_*replication_slot*`, `pg_logical_emit_message`, `pg_replication_origin_*`, `pg_sleep*`, `set_config` (unless the 3rd arg is literal `true` and the GUC is allowlisted), `pg_read_file`/`pg_read_binary_file`/`pg_ls_*` (information disclosure), `pg_export_snapshot`.

## Open questions

1. **Non-transactional phase?** Do we want an explicit, separately-committed phase (before or after the main transaction) for `CREATE INDEX CONCURRENTLY`, `DROP INDEX CONCURRENTLY`, `REINDEX CONCURRENTLY`, `DETACH ... CONCURRENTLY`, and `ALTER TYPE ... ADD VALUE` whose values are used later? Or do these simply require a separate deploy?
2. **Savepoints per migration?** Useful for error attribution, but they lose the enum same-transaction exception (3.2), add subtransaction overhead (5.11), and need reserved names. Decide before finalizing 3.1/3.2 rules.
3. **Catalog-aware checks.** Several rules need target-database facts: partitioned vs not, table size, deferred constraints present, foreign table targets, whether a procedure's body commits. Will the checker connect to rehearsal/target, or be AST-only and conservative (ban)?
4. **Opaque code.** Dynamic `EXECUTE` in DO blocks/functions, extension install scripts, existing event triggers, and functions *called* by scripts can all do banned things the AST walker cannot see. Should we accept runtime enforcement (rehearsal run plus a restricted deploy role lacking `pg_execute_server_program`, `pg_write_server_files`, `pg_signal_backend`, superuser) as the backstop?
5. **Function denylist evasion.** Name-based `FuncCall` matching misses operators, casts, defaults (serial → `nextval`), triggers firing on DML, and functions wrapping denylisted calls. Is a "deploy role without the privileges" the primary control, with the parser as a lint?
6. **Timeout and retry policy.** What exact `SET LOCAL` values (`lock_timeout`, `statement_timeout`, `idle_in_transaction_session_timeout`, `transaction_timeout`) and whole-deploy retry count on `55P03 lock_not_available` / `40P01 deadlock_detected`? Given that `idle_in_transaction_session_timeout`/`transaction_timeout` *terminate the session*, how should the tool treat a connection loss during COMMIT (outcome unknown; it must re-check state via a migrations ledger row written in the same transaction)?
7. **Unverified-by-docs behaviours to test empirically on PG18:** prepared statements (`PREPARE`) persisting after rollback; replication-slot creation persisting after rollback; dblink autocommit semantics; `SET LOGGED/UNLOGGED` rewrite; PG18 NOT NULL constraint naming parity between fresh and pg_upgrade'd clusters.
8. **libpg_query parse assumptions.** Confirm that libpg_query parses with `standard_conforming_strings=on` (affects backslash-escaped literals if the target sets it off), and that PL/pgSQL body parsing (`pg_query_parse_plpgsql`) is available in our binding for 4.6/4.7/7.13.
9. **Column order policy.** Should the differ ever attempt a table rebuild to fix order drift, or declare column order out of scope and ban all order-dependent constructs (§7) instead?
